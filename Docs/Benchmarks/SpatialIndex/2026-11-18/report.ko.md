## 3. 비교군과 이식에서 정한 것

| 군 | 구현 | 정한 것·원본과 달라진 점 |
|---|---|---|
| A1 | AoS `{Box<double>, filter, id}` 전수 검색(scalar) | 삽입은 끝에 추가, 갱신은 덮어쓰기, 삭제는 swap-remove. 박스는 닫힌 구간 double 비교, 구·프러스텀·ray는 Core `Overlap`·`Raycast` |
| A2 | float SoA(min·max 6배열, `ToFloatOutward` 바깥쪽 반올림) + SIP3 SIMD 4개 묶음 | D와 같은 정밀도: 박스 계열(박스·존재·개수)은 float, 구·프러스텀·ray·최근접은 D처럼 별도 double AABB 배열에 Core 술어(SIMD 없음). 필터는 4개 묶음의 필터 bit를 먼저 구해 통과 lane만 판정 |
| A2s | A2와 같은 데이터, scalar 판정 | SIMD 효과를 분리하려고 더한 변형이다(계획에 없음) |
| B | UnityOctree bbc4735의 `BoundsOctree`·`BoundsOctreeNode` C++ 이식 | 노드별 개별 할당, 노드별 객체 목록, 노드마다 따로 할당한 자식 경계 배열, 임계 8, 재귀 순회, 자식 0–7 고정 순서, 21회 확장 한도, 삭제마다 1단계 축소를 그대로 둠. 설정: 초기 131,072 cm(D 초기 루트와 같음), minNodeSize 128 cm, looseness 2(동일 설정 비교). 달라진 점: float → double(center·extents 표현은 유지), 필터 mask 추가, GC 대신 공통 할당기와 즉시 해제, C# `List` 규칙(첫 용량 4, 2배 성장, 앞에서 찾아 당기는 `Remove`, 필드 전체 비교)을 따르는 목록, 로그 → 계수, 결과는 공통 버퍼, 구·최근접·개수 순회 추가. 경계를 주는 삭제가 실패하면(원본 동작) 경계 없는 삭제로 지우고 셌다 |
| C16·C256 | TOctree2(UE 5.8.4) 설계 사실에 기반한 독립 구현(Unreal의 성능이 아니다) | 8 byte 노드, 자식 8개 인접 블록과 블록 번호 재사용 스택, 노드별 요소 배열, looseness 1/16(자식 반폭 = 부모/2·17/16, 자식 중심 거리 = 부모 반폭 − 자식 반폭), 가장 가까운 자식 하나만 검사하는 배치, 잎 초과 시 분할·전체 재삽입, 삭제 시 swap-remove와 `SetElementId` 콜백, 루트까지 수를 줄여 `MinInclusiveElementsPerNode`(7) 미만인 가장 위 노드로 모음, 재귀 순회, `MaxNodeDepth` 12, 잎 용량 16(광원 옥트리)·256(프리미티브 옥트리). 외부 ID 저장소(식별 값 → {노드, 색인}) 갱신과 콜백이 삭제·이동 측정 구간 안이다. 루트는 고정이며 데이터 영역을 덮는 128·2^k cm 반폭, 128 cm 격자 중심으로 정했다(사례별 값은 `counters-*.json`의 `rootExtent`). 달라진 점: 원본 4-lane double SIMD 판정을 같은 식의 scalar double로 계산(Register4f는 float뿐이고 플랫폼 경계 밖 intrinsic을 쓰지 않음), 필터 추가. 구·프러스텀·ray는 전용 질의가 없어 노드 경계 predicate 순회, 최근접은 predicate가 현재 최단 거리로 가지치기 |
| D | 엔진 `LooseOctree`(6.2절 초기 제안값: 최소 셀 128 cm, 초기 루트 level 10, 최대 24, looseness 2, 분할 16, 병합 6, 청크 16) | 질의마다 읽기 범위를 열지 않고 질의 묶음마다 연다. 최근접의 정밀 판정은 `TryGet`으로 레코드 AABB를 읽어 Raycast한다. 프레임마다 `RunMaintenance(Operations(256))` |

**공통 조건.** 모든 군이 같은 double AABB 입력, 같은 입력 순서, 같은 할당기, 같은 필터(프록시마다 식별 값에서 유도한 4종 중 1 bit, 질의 mask는 3종 — 약 75% 통과, 공간 판정 전에 적용)를 쓴다. 결과는 미리 예약한 버퍼에 식별 값을 쓰고 개수와 합계를 기록한다. 좌표는 1/64 cm 격자로 양자화했다. 그래서 center·extents 표현(B·C)과 min·max 표현(A·D)이 같은 AABB를 나타내고, 정확성 대조에 반올림 차이가 생기지 않는다. 이 양자화 때문에 이번 입력에서는 D·A2의 float 박스 판정도 초과 후보가 0건이었다(초과 후보가 생기는 원점에서 먼 좌표는 LO02 시험 몫이다).

**Unity `Bounds` 경계 규칙 확인(15절 미확인 항목).** UnityCsReference master(commit cf583fbe, 2026-11-05)를 읽었다(코드 복사 없음).

- `Intersects`: 관리 코드, 축마다 `min <= other.max && max >= other.min`(닫힌 구간). **확인.**
- `min`·`max`: `center ∓ extents`로 계산. **확인.**
- `Contains(Vector3)`: native `IsInside`, `IntersectRay`: native `IntersectRayAABB`, `GeometryUtility.TestPlanesAABB`: native `TestPlanesAABB`(Math.bindings.cs·Graphics.bindings.cs의 선언만 공개). 소스가 없어 **가정**으로 두었다: Contains는 닫힌 구간, IntersectRay는 slab 진입 거리(원점이 안이면 Hit), TestPlanesAABB는 "어느 평면에서도 완전히 바깥이 아님". 이식은 각각 닫힌 비교, Core `Raycast`, Core `Overlap(ConvexVolume, Box)`로 계산한다.

**외부 코드 등록(결정 9).** `ThirdParty.json`은 원본 파일의 SHA-256과 원본 디렉터리를 요구하고(정책 `third-party`가 파일 집합·해시를 대조), 다시 쓴 이식 코드는 원본 파일이 아니므로 그 형식에 그대로 넣을 수 없다. 그래서 `Engine/Source/ThirdParty/UnityOctree/`에 `kind: data` 라이브러리로 등록하고 원본 디렉터리에는 commit archive에서 그대로 꺼낸 `LICENCE`만 두었다(archive SHA-256 `01efa5cb…ee8ad`, LICENCE SHA-256 `933f2507…1345`, BSD-2-Clause, `binaryNoticeRequired: true`). 이식 파일 두 개(`UnityOctreePort.h`·`.cpp`)는 머리에 BSD 2-Clause 원문과 기준 commit을 두고, manifest `notes`가 이식 위치·달라진 점·엔진 바이너리 비포함을 적는다. 벤치 실행 파일에만 링크되므로 `embeddedIn`은 없다. ## 4. 입력과 측정 방법

**분포(9.2절)**: 균일(한 변 200 m·(N/1000)^(1/3)), 지형(수평 400 m·(N/1000)^(1/2), 높이 0–20 m), 군집(32개), 넓고 희소(한 변 100 km), 크기 편차(반폭 10 cm–100 m 로그 균일), 셀 경계 집중(128 cm·2^k 경계 ±1 cm), 분리 가능한 과밀(128 cm 셀당 약 8개, 반폭 2–8 cm), 겹치는 과밀(중심 1 m 정육면체, 반폭 2–3 m — 모든 AABB가 서로 겹침). 정의 코드는 `BenchInput.cpp`.

**규모**: 8분포 × 10³·10⁴·10⁵(3회 반복), 대표 4분포(균일·군집·크기 편차·겹치는 과밀) × 10⁶(2회 반복). 10⁶은 1회 실행이 길어 대표 분포만 쟀다. 9.2절 이동 비율 0·1·10·100%는 프레임 부하에 적용했다.

**질의**: 형태 7종(박스, 구, 프러스텀(반각 45도 6평면), ray, 최근접 ray, 존재(박스), 개수(박스)) × 결과 규모 3종(없음: 영역 밖 먼 곳·멀어지는 방향, 적음: 프록시 중심에 전형 반폭 2배, 많음: 영역 반폭의 절반 크기 박스·영역 대각선 길이 ray).

**묶음 크기 K와 반복 수(9.5절)**:

| 규모 | 질의 수 / K | 변경 연산 수 / K | 프레임 수 | 정확성 대조(분류별) |
|---|---|---|---|---|
| 10³ | 512 / 32 | 1,000 / 50 | 30 | 32 |
| 10⁴ | 256 / 16 | 8,192 / 64 | 12 | 16 |
| 10⁵ | 64 / 8 | 16,384 / 64 | 4 | 8 |
| 10⁶ | 16 / 2 | 16,384 / 64 | 2 | 4 |
| 겹치는 과밀 10⁵ / 10⁶ | 8 / 2, 4 / 2 | 위와 같음 | 2 | 2 / 1 |

구축은 256개 묶음, 전체 삭제는 256개 묶음, B의 경계 없는 삭제는 32개 묶음(최대 512회)이다. 분위수는 묶음 표본의 최근접 순위다. 보고 값은 프로세스 반복별 중앙값의 반복 간 중앙값이다(최소값·관측 최대값은 원시 JSON에 있다).

**절차(한 사례)**: 구축 → 정확성 대조(A1을 같은 프로세스에 따로 만들어 비교, 타이밍 밖) → 질의 전부(구축 직후) → 변경 연산별(삭제, 다시 삽입, B만 경계 없는 삭제, 작은 이동 ±10 cm, 경계 통과 ±500 cm, 순간 이동, 크기 0.5–2배) → 트리 상태(10% 순간 이동 3회 → D만 "유지보수 대기 중" 질의 → `MaintainAll` → "유지보수 완료" 질의) → 정확성 재대조 → 프레임 부하 → 전체 삭제. 비교군은 프로세스마다 하나이고 반복마다 순서를 회전했으며 각 측정은 첫 묶음을 재지 않는 워밍업으로 시작한다.

**프레임 부하(9.3절 대표 부하)**: 프레임 = 이동 비율 r의 걷기 이동(±50 cm, 높이 ±10 cm) 갱신 + 광원 L개 구 질의(중심은 무작위 프록시, 반경 3–30 m 로그 균일) + 그림자 caster 프러스텀 4개(영역 최대 변의 1/4 깊이) + 유지보수 `Operations(256)`. r = 0·1·10·100%(L = 64), r = 10%에서 L = 16·256(10⁵ 이하).

**계수 분리**: A·B·C의 계수 코드는 `Counting=false` 템플릿 인스턴스에서 컴파일되지 않는다. D는 `QueryStats*`를 nullptr로 넘긴다(엔진 코드의 실행 시 분기는 남는다). 계수는 별도 프로세스(`--counters`)에서 시간 없이 쟀다. 공통 할당기의 요청 크기 계수(덧셈 몇 번)는 타이밍 경로에도 있다.

**별도 시나리오**(10³–10⁵ 프로세스 끝): 루트 확장·축소(2만 개를 원점에서 바깥으로 지수 거리(최대 약 163 km)로 넣고 역순으로 뺌), 분할·병합 집중(분리 가능 과밀 10⁴ 위에서 24개를 한 곳에 넣었다 빼는 주기 2,000회, 주기마다 유지보수 16).

**looseness의 경향**(잡음보다 큰 변화만): 작은 looseness(1–5/4)는 균일·군집·겹치는 과밀의 질의와 프레임을 크게 줄이고(10⁶ 균일 r 10% 프레임: 기준 392.7 ms, 65/64 80.6 ms, 1 76.2 ms), 크기 편차에서 크게 나쁘게 한다(큰 프록시가 위 노드에 쌓임 — 6.7절의 큰 객체 문제). 결정 필요 8(큰 객체 전용 목록)과 함께 판단할 항목이다.

## 7. 성능이 나빠지는 조건

- **D, 경계 갱신 뒤 구조 저하**: `TryUpdateBounds`의 재삽입 경로를 거친 뒤 내부 노드 직접 저장이 늘고 작은 질의 비용이 10–25배가 되며 `RunMaintenance(All)`로 회복되지 않는다(5.3절). 같은 이동을 `TryRemove`+`TryAdd`로 하면 생기지 않는다. 원인 확인과 수정은 OT6 전에 필요하다(이번 범위에서 엔진 코드는 고치지 않았다).
- **D, 결과가 많은 구·프러스텀·ray**: 후보마다 레코드 double AABB를 무작위 접근해 겹치는 과밀에서 순차 전수 검색보다 3–6배 느리다(5.1절). 6.8절의 대안(float + 넓힘)을 9.4절 항목으로 다시 잴 필요가 있다.
- **D, looseness 2의 넓은 겹침**: 작은 질의도 노드를 100–200개 판정한다. C(1/16)는 5–15개다.
- **D, 겹치는 과밀 + 변경마다 전체 유지보수**: 10⁶에서 한 사례가 8분을 넘었다.
- **B, 큰 노드 목록**: 겹치는 과밀(노드 하나에 전부)과 10⁶(고정 크기 루트의 loose 띠 객체 53,602–119,671개가 직접 저장)에서 삭제·이동이 O(목록)이다(10⁶ 삭제 256–723 µs). 그래서 그 조건의 전체 삭제·트리 상태·큰 이동 프레임은 재지 않았다.
- **B, 경계를 주는 삭제 실패**: 루트 확장 뒤(넓고 희소·지형) 경로가 달라져 실패하는 경우가 있었다(계수 모드에서 10³ 넓고 희소 3회, 10⁵ 지형 13회). 원본은 실패만 돌려주므로 호출자가 경계 없는 삭제(10⁵에서 약 1 ms)로 대신해야 한다.
- **C, 고정 루트**: 데이터에 맞춰 루트를 정해야 하고, 루트 밖 요소는 루트에 쌓인다(이번 입력은 루트 안). 겹치는 과밀에서는 내부 노드에 요소가 무제한 쌓인다(최대 깊이 12).
- **A(전수)**: 비용이 N에 비례한다. SIMD는 박스 계열만 돕고, 광원 질의(구)에는 효과가 없다.

## 9. 스펙과 다른 점(스펙 반영 요청)

1. **결정 9의 등록 방식**: `ThirdParty.json`에 이식 코드 자체를 등록할 수 없어(원본 파일 SHA-256 대조 정책) `kind: data` 라이브러리로 LICENCE 원문만 원본 디렉터리에 두고 이식 파일 위치는 `notes`에 적었다(3절). 결정 9 문구를 이 방식으로 고칠 필요가 있다.
2. **15절 Unity `Bounds` 미확인 항목**: Intersects·min·max는 확인, Contains·IntersectRay·TestPlanesAABB는 native라 가정으로 남았다(3절).
3. **9.2절 규모**: 10⁶은 대표 4분포만 쟀다. 9.5절 반복 수는 10³–10⁵ 3회, 10⁶ 2회, 변형 1회다.
4. **9.3절 프레임 부하 정의**: 광원 64개(16·256 변형)·반경 3–30 m, caster 프러스텀 4개, 걷기 이동 ±50 cm, 유지보수 256으로 정했다(4절). 9.6절 "대표 부하"의 정의로 반영할 것을 제안한다.
5. **9.1절 A2**: 구·프러스텀·ray는 D와 같은 정밀도라 double·SIMD 없음이다. SIMD 효과 분리용 A2s를 더했다.
6. **9.1절 C**: 원본의 double SIMD 판정을 scalar double로 계산했다("SIMD 박스 판정은 넣는다"와 다름, 3절).
7. **9.5절 계수 분리**: D는 `QueryStats*` 실행 시 분기가 타이밍 경로에 남는다(컴파일 시점 제거가 아님).
8. **9.6절 판정**: 제자리 갱신 미충족, 저장 변형 모두 미충족, 노드 묶음 미실행(6절). 제자리 갱신 판정은 재삽입 경로 결함(7절) 수정 뒤 다시 해야 한다.
9. **6.4–6.6절 관련 발견**: 경계 갱신의 재삽입 경로가 `TryAdd`보다 나쁜 구조를 남기고 유지보수가 회복하지 못한다(5.3절). 6.4절 "경계 갱신의 재삽입 경로는 분할 평가를 하지 않고 대기만 표시" 설계와 유지보수 재평가·재배치의 효과를 다시 검토해야 한다.
10. **6.10절 진단 로그**: 겹치는 과밀에서 `parentWarnCount` 경고가 노드마다 한 번 표준 오류로 나온다(측정 경로에 포함). 실행 스크립트는 그 줄을 화면 출력에서만 거른다.
