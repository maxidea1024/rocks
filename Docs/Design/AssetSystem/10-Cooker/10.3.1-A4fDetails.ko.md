#### 10.3.1 A4f 구현 세부(2026-11-25 — 착수 때 정함, 교차 검증 1차 반영)

**나눔**: 넷으로 나누고 차례로 구현한다.
- **A4f1** 필드 플래그 `TextMapMergeByKey`, 새 모듈 `TargetProfiles`(TargetProfile 옮기기·셰이더 칸·구조 검증·`Mac`·호스트 프로필).
- **A4f2** 매니페스트 v2(backend 표·artifact 표·`AppendCookedArtifactPath`·판정 순서·`CheckCookedManifestMerge`의 artifact 표 병합), 로더 `Backends`·`Artifacts`·`FindArtifact`·`CheckCookedArtifactFile`.
- **A4f3** 비에셋 산출물 단계(`CookArtifactStage`·표·요청·sink), 게시·정리·부분 쿠킹 재사용, `cookDevelopmentShaders`, 미등록 `UnsupportedCapability`.
- **A4f4** `asset-cook --engine`, 쿠킹 루트 잠금, 엔진 전용 실행의 `asset.cooked_root` 기본값(11.8절). 완료 조건에 렌더 세션(rocks-6b) 알림을 넣는다(10.3절 "구현 시점").
- 후속: 10.3절 5항의 패키징 규칙(매니페스트가 가리키는 파일만 복사)은 패키징 도구가 생길 때 한다.

**A4f1 결정**:
1. **Map 병합 필드 플래그**(1항의 "리플렉션 필드 지정자" — 기존 지정자가 없어 새로 둔다):
   - `FieldFlags::TextMapMergeByKey`(새 비트 256)와 지정자 `ROCKS_PROPERTY(TextMapMergeByKey)`다. Map 필드에만 쓴다(그 밖은 MetaCompiler `RMC2202` — AssetBundles와 같은 필드 종류 진단).
   - 의미: 그 필드의 JSON import 기본 병합이 키별이다(`options.mapMerge`가 Replace여도). 옵션 MergeByKey는 지금처럼 모든 Map을 덮는다. 플래그를 끄는 옵션은 두지 않는다 — 플래그 단 Map은 어느 ImportJson 경로에서도 키별이다(Config 런타임 변경 import가 일부러 Replace로 부르는 경로 — ConfigRuntimeChanges.cpp 359 — 에서도. 그 경로에 플래그 단 Map을 쓰는 Config 타입이 생기면 그 타입의 뜻으로 키별이 맞다).
   - 플래그는 바깥 필드로 전파하지 않는다(`PropagateFieldFlags`의 inherited에 넣지 않는다 — 자기 Map만, 안쪽 struct의 Map은 자기 플래그를 본다).
   - 닿는 곳(`TextExportTransient` 경로와 같다): TypeSchema.h `FieldFlags`, ObjectRuntime TypeRegistryRegister.cpp `KnownFieldFlags`(빠뜨리면 등록 InvalidArgument), MetaCompiler `Specifiers.cs`(이름 목록·파싱)·`SchemaModel.cs`(비트)·`SchemaValidator.cs`(RMC2202 — Map이 아니면 거부)·`ModuleDescriptor.cs`(descriptor 쓰기·받는 이름·읽기 — 빠뜨리면 다른 모듈이 import할 때 플래그를 잃는다), ReflectionText `TextJsonImport.cpp`(merge = 옵션 MergeByKey 또는 플래그), 문서 ReflectionFoundations 6.4절 플래그 표·ReflectionExtensions 10.4절 import 의미와 Map 행.
   - TargetProfile 읽기는 기본 옵션(Replace)으로 바꾸고 `textureLodGroups`에 플래그를 단다. `shaderFormats`는 플래그 없이 Replace다(1항). 12.14절의 "한계: 옵션이 import 전체에 걸린다"는 이것으로 풀린다.
   - UE 대응: UE는 배열 하나의 키 병합을 ini에서 선언한다 — `BaseDeviceProfiles.ini` 3–4행 `[DeviceProfile]` `*TextureLODGroups=Group`(ConfigCacheIni ArrayOfStructKeys, ConfigCacheIni.cpp 911·966 — 같은 Group 항목은 덮고 새 항목은 더한다). 필드마다 병합 의미를 고르는 같은 구조를 Rocks는 리플렉션 지정자로 둔다.
   - 버린 대안: `shaderFormats`를 struct 배열(`[{backend, formats}]`)로 두기 — 배열은 늘 통째 교체라 플래그가 필요 없고 "목록에 없는 backend 키" 검증도 사라지지만, 렌더 세션과 합의한 칸 모양(SSD10 `graphicsBackends` + `shaderFormats` Map)을 바꾼다. 합의 비용이 더 커서 플래그 안을 택한다.
2. **TargetProfiles 모듈**(1항 모듈 분리):
   - 위치: `Engine/Source/Developer/TargetProfiles`.
   - 의존: Core·ObjectRuntime·ReflectionText·AssetRuntime(매니페스트 상한 상수), 그리고 Texture(A5j의 `textureLodGroups`가 Texture enum을 쓴다)·HostConfig(4번)를 더한다(1항 목록에 더한다).
   - 옮기는 것:
     - `TargetProfile`·`TextureLodGroup`·`TextureLodMinMagFilter`·`TextureLodMipFilter`·`CookBulkCodec`, `FindTextureLodGroup`.
     - `ReadTargetProfile`(새 문맥 `TargetProfileContext{allocator, files, registry, access, types, engineConfigDirectory, projectConfigDirectory(비면 없음)}`).
     - `TargetProfileFailure`·`TargetProfileField`·`TargetProfileFile`(None·EngineProfile·ProjectProfile).
     - JSON 층 읽기 도우미(크기 상한·JSON 문법·대입 진단·층 — 지금 AssetCooker `ApplyJsonFile`)를 공개 도우미 `ApplyConfigJsonFile`로 옮기고 AssetCooker `ReadCookSettings`가 다시 쓴다(두 모듈에 같은 도우미를 두지 않는다).
   - 실패 진단: `CookConfigField`·`CookConfigFile`은 AssetCooker에 남는다(CookSettings 칸 — AlwaysCook·NeverCook·PrimaryAsset·CookSettings 파일 — 이 섞여 있다). `TargetProfileField`·`TargetProfileFile`은 같은 이름의 `CookConfigField`·`CookConfigFile` 값과 1:1로 대응하고, AssetCooker가 `CookConfigFailure`로 변환해 담는다(대응은 static_assert 표로 묶는다). `AssetCookCommandlet` `AppendConfigField`에 새 칸(GraphicsBackends·ShaderFormats) 문구를 더한다.
   - 리플렉션 안정 id는 AssetCooker.rocksids.json의 항목을 TargetProfiles.rocksids.json으로 **옮긴다**(같은 Guid — 새로 만들지 않는다).
   - AssetCooker는 TargetProfiles에 public 의존하고 `HashTargetProfile`·CookSettings를 둔다. A5j1에서 더한 AssetCooker의 직접 Texture 의존은 TargetProfiles public 의존으로 대체한다.
   - 비용: `shader-compile`·SSD16 공급자도 TargetProfiles를 거쳐 Texture 런타임 모듈을 링크한다(엔진 실행 파일은 이미 가진다 — 비용은 셰이더 도구 쪽뿐). `TargetProfileContext`가 Registry·TypeRegistry를 요구하므로 셰이더 도구는 프로필을 읽으려고 ObjectRegistry 하나를 만든다(ReflectionText import 때문 — 피할 수 없다).
   - rocksids 이동은 한 커밋에서 한다(두 파일에 같은 Guid가 동시에 있지 않게). 같은 Guid라 TypeId와 `HashTargetProfile`의 필드 기록이 그대로이고, 프로필 SHA는 새 칸만큼만 바뀐다.
3. **셰이더 칸**: `graphicsBackend`를 지우고(하위호환 없음, 안정 id는 retired로 남긴다) `graphicsBackends`·`shaderFormats`를 둔다. 리플렉션 Map 값은 컨테이너를 담지 못하므로 `shaderFormats`는 `OrderedMap<String, ShaderFormatList{formats: Array<String>}>`다 — JSON은 `{"D3D12": {"formats": ["D3D12_SM6"]}}`(1항의 `Map<String, Array<String>>`과 뜻은 같고 한 층 감싼다, A4f 끝 알림에 넣는다). 1항 구조 검증의 위반은 새 칸 `TargetProfileField::GraphicsBackends`(index = 번호)·`ShaderFormats`(index = backend 번호, 형식 id 위반은 그 backend 번호)다.
   - 판정 순서(위반이 겹치면 앞의 것이 나온다 — 2026-11-25 A4f1 리뷰): (1) 셰이더 없는 프로파일(backend 목록 빔)은 형식 Map도 빔 — 아니면 `ShaderFormats` 0, (2) backend 수 상한 — `GraphicsBackends` index = 상한 8, (3) backend마다 번호 순으로 어휘 → 앞 번호와 중복 — `GraphicsBackends` index = 번호, (4) 목록에 없는 형식 Map 키 — `ShaderFormats` index = **Map 순서 번호**, (5) backend마다 번호 순으로 형식 목록 있음·비지 않음·형식 수 상한 → 형식마다 id 문법 → 앞 형식(앞 backend 전부와 같은 backend의 앞 형식)과 중복 — `ShaderFormats` index = backend 번호.
4. **호스트 프로필** `ReadHostTargetProfile(context, platform, out, diagnostics, failure)`: platform은 호출자가 넘긴 HostSettings 플랫폼 이름 재정의다(HostSettings.h 57 — 비면 HostConfig `HostPlatformName()`, Windows·Mac·Android). 그 이름으로 `ReadTargetProfile`을 부른다. 그래서 의존에 HostConfig를 더한다(가벼운 Core 모듈). Linux 호스트(BS6 보류)는 엔진 프로필 파일이 없어 엔진 파일 없음 진단(`InvalidSetting`·NotFound)이다.
5. 엔진 파일 `Mac.json`(1항 값 — LOD 그룹 27행은 Windows와 같고, norm16 true), Windows·Android의 셰이더 칸(1항 값).

**A4f1 시험**:
- 플래그: MetaCompiler 수용·Map 아닌 필드 `RMC2202`, 키별 병합·플래그 없는 Map의 Replace·옵션 MergeByKey 전체 적용.
- TargetProfiles 단독(AssetCooker 없이): 프로필 병합·구조 검증 위반마다(어휘·중복·형식 목록 없음·키 남음·형식 id 문법·전역 중복·상한 8·16)·Replace(프로젝트가 한 backend만 적으면 Map 전체 교체)·셰이더 없는 프로필(형식 Map도 빔), 호스트 프로필, 엔진 파일 셋(Windows·Android·Mac).
- AssetCooker: SHA-256이 새 칸을 포함, `CookConfigFailure` 변환(대응 표 전부), `ReadCookSettings`가 공개 도우미로 읽기, 명령 문구(GraphicsBackends·ShaderFormats).
- 호스트 프로필: HostSettings 재정의 이름을 따름, 빈 재정의는 HostPlatformName().

**A4f2 결정**(2026-11-25 — 착수 때 정함):
1. **모델**(AssetRuntime `CookedManifest.h`):
   - `enum class CookArtifactKind : uint8 { ShaderLibrary = 1 }`(0은 쓰지 않는다 — 손상 판정).
   - `CookedManifestBackend{name, formats(Array<String>)}`.
   - `CookedManifestArtifact{kind, name, formatId, bytes, sha256, cookKey}`.
   - `CookedManifest`에 `backends`·`artifacts` 칸(entries처럼 공개 칸)과 읽기 함수 `Backends()`·`Artifacts()`(Span)·`FindArtifact(kind, name, formatId)`(정렬 불변식에 기댄 이진 탐색, 없으면 null)를 더한다.
   - 정렬 규칙은 공개 함수 `CookedArtifactLess`(kind 값 → 이름 byte 순 → formatId byte 순) 하나다. 검증·`FindArtifact`·쿠커 병합이 같은 함수를 쓴다.
   - 이름 상수: `CookedArtifactEngineName`(`Engine`), `CookedArtifactProjectName`(`Project`), `CookedManifestMaxArtifacts`(4096), `CookedArtifactMaxBytes`(4 GiB).
2. **어휘·문법은 한 곳에 둔다**:
   - `IsKnownGraphicsBackend`·`IsValidShaderFormatId`·`ShaderFormatIdMaxBytes`를 TargetProfiles에서 AssetRuntime `CookedManifest.h`로 옮긴다. TargetProfiles는 그 함수를 쓴다.
   - 매니페스트 검증과 프로필 검증이 같은 함수를 쓰므로, 통과한 프로필은 늘 쓸 수 있는 매니페스트를 만든다(상한 상수와 같은 이유).
3. **진단 칸**:
   - `CookedManifestField` 끝에 4항의 칸 열한 개와 `ArtifactCookKey`를 더한다. `ArtifactCookKey`는 4항 목록에 없던 칸이다. reader의 잘림 칸으로 필요하다 — 앞 문자열이 길면 뒤의 고정 칸이 잘릴 수 있다.
   - detail 값:
     - `Backend`·`ShaderFormat`·`FormatCount`: backend 번호.
     - `BackendCount`·`ArtifactCount`: `CookedManifestNoEntry`.
     - `Artifact*`: artifact 번호.
     - 런타임 대조(`CheckCookedArtifactFile`): `CookedManifestNoEntry`, asset은 null.
   - reader의 잘림 칸:

     | 표 | 읽던 칸 | 진단 칸 |
     |---|---|---|
     | backend | 이름 | `Backend` |
     | backend | 형식 개수 | `FormatCount` |
     | backend | 형식 문자열 | `ShaderFormat` |
     | artifact | kind | `ArtifactKind` |
     | artifact | 이름 | `ArtifactName` |
     | artifact | formatId | `ArtifactFormat` |
     | artifact | bytes | `ArtifactBytes` |
     | artifact | sha256 | `ArtifactSha256` |
     | artifact | cookKey | `ArtifactCookKey` |

   - 문자열 칸의 길이 상한·UTF-8 위반도 같은 칸이다(`Backend`·`ShaderFormat`·`ArtifactName`·`ArtifactFormat` — 2026-11-25 교차 검증 A).

4. **reader 구조 상한**(남은 byte로 묶는다 — 작은 파일이 큰 할당을 요구하지 못하게, v1과 같은 방식):
   - backendCount: 8 초과이거나 남은 byte / 12 초과면 `BackendCount`.
   - backend마다 formatCount: 16 초과이거나 남은 byte / 8 초과면 `FormatCount`.
   - artifactCount: 4096 초과이거나 남은 byte / 89 초과면 `ArtifactCount`.
   - entryCount의 남은 byte 검사는 그대로다. backend 표 byte까지 남은 byte에 들어 있지만, 상한 검사는 보수적일 뿐 맞는 입력을 거부하지 않는다.
5. **칸 규칙**(`ValidateCookedManifest` — 4항 순서):
   - backend 표:
     - backend 수 8 초과: `BackendCount`.
     - backend 번호 순으로: 어휘 밖·앞 번호와 같은 이름은 `Backend`, 형식 0개·16 초과는 `FormatCount`, 형식 id 문법·전역 중복은 `ShaderFormat`.
   - artifact 표:
     - 수 4096 초과: `ArtifactCount`.
     - artifact 번호 순으로: kind → 이름(`Engine`·`Project`) → formatId가 backend 표에 있음 → bytes(1 이상 4 GiB 이하) → 앞 항목보다 `CookedArtifactLess`로 큼(`ArtifactOrder`).
6. **경로** `AppendCookedArtifactPath(out, const CookedManifestArtifact&)`:
   - `Shaders/<이름>-<formatId>-<sha256 앞 16 hex 소문자>.rshl`을 만든다.
   - kind·이름·formatId 칸 규칙을 다시 본다(위반은 InvalidArgument). 경로 조각이 되는 문자열이라 검증하지 않은 항목(A4f3 단계 sink 입력)에서도 경로가 쿠킹 루트 밖을 가리키지 못한다.
7. **대조** `CheckCookedArtifactFile(artifact, file, failure)`:
   - 길이가 다르면 `ArtifactBytes`, SHA-256이 다르면 `ArtifactSha256`. 둘 다 `CorruptPackage` / InvalidArgument다.
   - 길이를 먼저 본다(`CheckCookedPackageFile`과 같은 순서).
8. **쿠커**:
   - `CookPublishConfig`에 `backends`(Span)를 더한다. `CookProject`는 TargetProfiles의 새 함수 `MakeCookedManifestBackends(allocator, profile, out)`로 채운다(`graphicsBackends` 순서, backend마다 `shaderFormats` 순서).
   - `Finish`가 만드는 매니페스트에 backend 표를 복사한다.
   - artifact 표는 이번 쿠킹 항목(A4f3 전에는 없다)과, 부분 쿠킹이면 merge 항목 중 같은 (kind, 이름, formatId)가 이번 쿠킹에 없는 것을 합쳐 `CookedArtifactLess`로 정렬한다.
   - 전체 쿠킹은 이전 artifact를 넘기지 않는다. `Shaders/` 정리는 A4f3이다.
   - 한계: 부분 쿠킹이 이어받은 artifact의 파일 존재·크기·SHA-256은 A4f2에서 대조하지 않는다(A4f3 6항의 파일 대조가 맡는다 — 교차 검증 B).
   - A4f2와 A4f3 사이의 쿠킹 결과는 backend 표만 있고 artifact 표는 비어 있다. 미빌드 중간 단계라 런타임 영향은 없다.
9. **런타임 노출**: `EngineAssetsSubsystem::Manifest()`(초기화 뒤 Deinitialize까지 유효한 const 참조)를 더한다. 셰이더 쪽(SSD15)이 표를 읽을 곳이다. `AssetLoaderConfig`는 이미 매니페스트 포인터를 받는다.
10. **v1**: reader를 두지 않는다. formatVersion 1 파일은 `UnsupportedVersion`이다. 저장소에 실수로 들어온 시험 산출물 `rocks-engine-assets-admission-00-31200/`(BS8e 커밋, v1)은 읽는 곳이 없다. 지우는 것은 그 커밋 주인 몫이라 그대로 두고 사용자에게 알린다(교차 검증 E).

**A4f2 시험**(14.1.109):
- 왕복·결정성과 시험 인코더 배치 일치: backend 셋·형식 여럿·artifact 넷, 셰이더 없는 매니페스트.
- 칸 규칙 위반 표에 backend·artifact 행을 더한다(검증·writer·reader 같은 진단). 셰이더 없는 매니페스트(backend 0개)의 artifact는 `ArtifactFormat`이다(교차 검증 D).
- 구조 변조: 개수 칸 셋(상한 + 1·남은 byte 초과), 모든 칸의 잘림 위치(표 범위 대조), v1 `UnsupportedVersion`.
- 판정 순서 표에 더하는 행:
  - backend 위반 + 항목 위반 → backend.
  - 항목 위반 + artifact 위반 → 항목.
  - reader 구조(artifact 개수 칸) + 칸 규칙(backend 어휘) → 구조.
- 경계: 어휘 다섯 backend 전부·형식 16·모든 (이름, 형식) artifact 조합·bytes 1과 4 GiB를 받는다. backend 8·artifact 4096은 어휘·이름이 모자라 맞는 매니페스트로 닿지 않는다(개수 상한은 구조 시험이 본다).
- 할당 실패 전 지점.
- `FindArtifact`: 있음·없음, 앞·사이·뒤.
- `AppendCookedArtifactPath`: 값, 칸 위반, 할당 실패.
- `CheckCookedArtifactFile`: 길이·SHA, 판정 순서.
- 쿠커: backend 표가 프로필 순서, 부분 쿠킹의 artifact 병합(이번 항목 우선·이전 항목 유지).
- `MakeCookedManifestBackends`.
- 엔진 에셋 `Manifest()`.

**A4f3 결정**(2026-11-25 — 착수 때 정함):
1. **CookSettings** `cookDevelopmentShaders`(bool, 기본 false — 10.3절 2항): 리플렉션 칸이라 CookSettings SHA-256(`WriteReflected`)에 그대로 들어간다. 안정 id는 MetaCompiler `ids add`로 더한다. 단계의 cookKey도 이 값을 담아야 한다(셰이더 쪽 정의 — 재사용 판정은 cookSettings SHA를 보지 않는다, 아래 3번). 규칙: 앞으로 셰이더 결과를 바꾸는 CookSettings 칸은 모두 단계 cookKey에 넣는다(2026-11-25 교차 검증 1).
2. **interface**(AssetCooker 새 헤더 `CookArtifacts.h`):
   - 요청 `CookArtifactRequest`: allocator, files, profile, settings, cookedRoot, stagingDirectory(`<루트>/.staging`), nuggets(null이면 너겟 없이), engineOnly, verifyNuggets, reusable(재사용 후보 — 3번).
   - 출력 `CookArtifactOutput`: name, formatId, cookKey, stagingFile(sink가 준 경로).
   - sink `CookArtifactSink`의 함수 다섯:
     - `NewStagingPath(out)`: 이번 실행에서 유일한 staging 경로(`<루트>/.staging/artifact-<번호>.tmp`)를 준다. 단계가 이름을 스스로 정하면 패키지 임시 파일·다른 단계와 겹칠 수 있다(교차 검증 6). 남은 파일은 다음 `Begin`이 지운다.
     - `Produce(output)`: 새로 만든 artifact.
     - `Reuse(artifact)`: 재사용 후보 하나를 그대로 쓴다.
     - `Report(CookDiagnostic)`: job 실패·경고. 오류가 하나라도 있으면 게시하지 않는다.
     - `ReportStat(name, value)`: 보고서 절.
   - 단계 `CookArtifactStage`: `Kind()`, `Identity()`(NuggetProcessorId — 보고서에 적는다), `Run(request, sink)`.
   - 표 `CookArtifactStageTable`:
     - 종류마다 칸 하나다.
     - `Register(stage)`: 같은 종류 두 번은 AlreadyExists, 모르는 종류는 InvalidArgument.
     - `Unregister(stage)`: 등록한 그 객체가 아니면 NotFound.
     - `Find(kind)`.
     - 등록·해제는 모듈 시작·종료 hook에서만 한다(ModuleLoader가 한 스레드에서 부른다). 쿠킹은 읽기만 한다 — 잠금은 두지 않는다.
     - 사용 중 계수: `CookProject`가 단계 `Run` 동안 올린다(RAII). 계수가 0이 아니면 `Register`·`Unregister`는 Busy다(쿠킹 도중 해제는 계약 위반 — 핫 리로드가 생기면 바로 드러난다, 교차 검증 5).
     - 프로세스 표는 `CookArtifactStages()`다(AssetCooker 모듈 소유). 시험은 자기 표를 만들어 쓴다.
   - `CookProjectRequest::stages`(null이면 빈 표와 같다).
3. **흐름**(`CookProject` — `CookPackages` 뒤, `Finish` 전):
   1. 재사용 후보:
      - 조건: 이전 매니페스트가 있고 verifyNuggets가 아니며, 머리의 profileId·profileSettings·cookerVersion이 같다(`PlanCookReuse`와 같은 조건).
      - 후보: 같은 종류 artifact 중 `Shaders/` 파일의 크기·SHA-256이 매니페스트와 같은 것. 파일이 없거나 다르면 후보가 아니다(단계가 다시 만든다).
   2. 프로필 `graphicsBackends`가 비면 단계를 부르지 않는다(등록되어 있어도 — 셰이더 없는 프로필).
   3. 비지 않았는데 `ShaderLibrary` 단계가 없으면 오류 진단을 남긴다: code None, error `UnsupportedCapability`, asset null. 게시하지 않는다. 명령 출력은 원인 오류 이름이다(`asset-cook: UnsupportedCapability: <루트>: error` — 10.2절 진단 출력 규칙). `UnsupportedSetting`은 "설정은 맞지만 구현하지 않은 값"이라 "이 실행에 단계가 없음"과 뜻이 달라 쓰지 않는다(교차 검증 2). 셰이더 쪽의 "이 호스트가 만들 수 없는 형식"도 같은 모양(code None + `UnsupportedCapability`)으로 낸다.
   4. 단계는 에셋 오류가 있어도 돈다(보고서가 오류를 한 번에 모은다 — 에셋 쿠킹이 대상 하나의 오류로 멈추지 않는 것과 같다).
   5. sink가 단계 계약을 확인한다. 위반은 단계 코드 결함이라(사용자 규칙 위반이 아니다) sink 함수의 InvalidArgument이고, `Run`이 그대로 돌려주면 `CookProject`가 멈춘다(보고서 없음 — 10.2절 "함수 오류는 결함·자원"):
      - `Produce`: 이름·형식 문법(`AppendCookedArtifactPath`와 같은 규칙), 형식이 프로필 backend 표에 있음, engineOnly면 `Engine`만, 이번 실행에서 같은 키 두 번 금지, stagingFile이 `NewStagingPath`가 준 경로이고 아직 쓰지 않음, 파일 크기 1 이상 `CookedArtifactMaxBytes` 이하(게시기가 계산한 값).
      - `Reuse`: 후보 안의 항목.
      - 원인 기록: 실패한 sink 호출·단계 정체성·formatId를 `CookProjectResult::stageFailure`에 담고, 명령 실패 줄에 적는다(`asset-cook: InvalidArgument: <루트>: stage <processor Guid> Produce(D3D12_SM6): the cook failed` — 교차 검증 3).
   6. `Run`의 다른 오류(IO·할당)도 `CookProject`가 멈춘다.
4. **게시**(`CookPublisher`):
   - `Begin`이 `Shaders/`도 만든다.
   - `PutArtifact(kind, output)`:
     1. staging 파일을 흘려 읽어 크기·SHA-256을 직접 계산한다(10.3절 3항). 0 byte이거나 `CookedArtifactMaxBytes` 초과면 InvalidArgument다(계약 위반 — sink 위반과 같은 경로로 `stageFailure`에 적는다).
     2. `AppendCookedArtifactPath`로 이름을 지어 `Move(no-replace)`한다.
     3. 같은 이름이 있으면 크기·SHA-256을 대조한다. 같으면 staging 파일을 지우고, 다르면 `CorruptEntry` 경고(asset null) 뒤 `Replace`한다.
     4. `Shaders/`를 동기화 목록에 넣는다.
   - `ReuseArtifact(artifact)`: 항목을 그대로 복사한다.
   - `Finish`:
     - artifact를 `CookedArtifactLess`로 정렬한다. 같은 키가 두 번이면 계약 위반이다 — sink가 먼저 막는다.
     - 부분 쿠킹 병합은 A4f2 그대로다(이번 항목이 이긴다).
     - 전체 쿠킹은 게시 뒤 새 매니페스트가 가리키지 않는 `Shaders/` 파일을 지운다(못 지우면 경고 — 패키지와 같다). 부분 쿠킹은 지우지 않는다.
   - `BytesWritten`에 새로 쓴 artifact byte를 더한다.
   - 한계:
     - `Produce`가 게시 전에 `Shaders/`로 옮기므로, 게시하지 않은 실행(오류)의 파일은 고아로 남는다. 패키지 `Put`과 같은 성질이고, 다음 전체 쿠킹이 지운다(교차 검증 7).
     - 재사용 후보 파일이 후보 계산 뒤 `Run` 전에 지워지면, `ReuseArtifact`가 복사한 항목이 없는 파일을 가리킨다. 존재를 다시 확인하지 않는다. 쿠킹 루트 잠금 아래라 외부 삭제뿐이고, 런타임 `CheckCookedArtifactFile`이 잡는다.
5. **보고서**: `CookReport`에 두 칸을 더한다.
   - `artifacts`: 행마다 kind·name·format·bytes·sha256 hex·reused.
   - `stageStats`: 행마다 stage 정체성(processor Guid 문자열)·name·value.
6. **명령**: `asset-cook`이 `CookArtifactStages()`를 넘긴다.
   - 셰이더 쪽 단계가 등록되기 전에는 셰이더 있는 프로필(Windows·Android·Mac)의 쿠킹이 `UnsupportedCapability`로 게시되지 않는다(10.3절 3항 의도).
   - 명령 시험은 가짜 단계를 프로세스 표에 RAII로 등록·해제해 돈다(다른 시험으로 새지 않게).

**A4f3 시험**(14.1.111):
- 표:
  - 등록·찾기·중복 AlreadyExists·모르는 종류·해제 NotFound.
  - 프로세스 표.
- 흐름(가짜 단계 — 형식마다 파일 하나):
  - 게시: 크기·SHA를 직접 계산(단계가 다른 값을 말할 칸이 없다), 매니페스트 artifact 표, `FindArtifact`·`CheckCookedArtifactFile` 통과.

- 보고서 두 칸.
- 할당 실패.
- 명령: 가짜 단계로 게시, 미등록 오류 문구(`UnsupportedCapability`), 계약 위반 실패 줄의 단계 정체성.
