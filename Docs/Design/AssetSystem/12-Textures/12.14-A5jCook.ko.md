### 12.14 A5j 구현 명세 — 텍스처 쿠킹(2026-11-24 — 교차 검증 1차 반영)

이 절은 12.7절 A5j(TargetProfile 텍스처 칸·텍스처 쿠킹 처리기·`TexturePlatformData`·에셋 원본 묶음)의 구현 방법을 정한다.
- 처리기 틀은 10.2절 결정 6이다(`CookProcessor` — 대표 에셋 타입의 가장 가까운 등록 처리기).
- 너겟 키 구성은 9절 텍스처 표(이 절에 맞춰 개정), Record 규칙은 9.1절(결정 2·3·15)이다.
- 빌드는 A5i(12.13절), 스트리밍 메타는 12.5.1절, LOD 그룹은 12.4.5절이다.
- 둘로 나눈다. **A5j1**은 프로파일 텍스처 칸, 처리기, 플랫폼 데이터, 너겟, 호스트 연결이다. **A5j2**는 에셋 원본 묶음(`SourceTextures`·`Source2DTexture`)이다.

#### A5j1

**TargetProfile 텍스처 칸**(A4f1에서 TargetProfiles 모듈 `TargetProfiles/TargetProfile.h`로 옮겼다 — 10.3.1절):
- `textureLodGroups`(`OrderedMap<TextureGroup, TextureLodGroup>`): UE `FTextureLODGroup`. struct `TextureLodGroup`(ROCKS_STRUCT)의 칸과 기본값은 UE 멤버 기본값(TextureLODSettings.h 28–141)이다.
  - 구현 칸: `minLodSize` 1, `maxLodSize` 4096, `lodBias` 0, `mipGenSettings` SimpleAverage, `maxAniso` 0(전역 값), `highPriorityLoad` false, `mipLoadOptions` AllMips, `cookPlatformTilingDisabled` false.
  - 필터 칸: `minMagFilter`(enum `TextureLodMinMagFilter` Point·Linear·Aniso — 기본 Aniso)·`mipFilter`(enum `TextureLodMipFilter` Point·Linear — 기본 Point). UE는 FName 문자열이다. Rocks는 같은 값의 enum으로 두고, JSON에 모르는 이름이 오면 대입 진단(InvalidValue)이다. UE는 모르는 값을 aniso로 본다(TextureLODSettings.cpp 110–137) — 오타를 조용히 받지 않으려고 다르게 정한다.
  - 계약 칸(저장·전달만 — 런타임 스트리밍 단계가 쓴다): `numStreamedMips`(-1 = 전부 — BaseDeviceProfiles Shadowmap 행이 3을 쓴다, UE StreamingManagerTexture.cpp 201), `maxLodSizeLow`·`maxLodSizeMedium`·`maxLodSizeHigh`·`maxLodSizeEpic`(-1 — UE 5.8 품질 등급별 상한, `!GIsEditor`에서만 쓴다, TextureLODSettings.cpp 97–105). 쿠킹 결과에는 쓰지 않는다.
  - 표에 없는 그룹은 기본값 struct다(UE도 정의하지 않은 그룹은 멤버 기본값이다).
  - 샘플러 필터는 두 값의 조합이다(12.4.5절 표 — point → Point, linear·point → Bilinear, linear·linear → Trilinear, aniso·point → AnisotropicPoint, aniso·linear → AnisotropicLinear, UE SetupGroup과 같다). Filter를 따로 적는 칸은 없다(12.4.5절 표의 Filter 행을 이것으로 고친다).
  - UE `MaxLODMipCount`는 UPROPERTY가 아니라 CeilLog2(MaxLODSize)로 계산하는 값이라 칸으로 두지 않는다(TextureLODSettings.cpp 108 — 12.4.5절 표를 고친다).
- `textureNorm16Supported`(bool, 기본 true): 대상이 R16·RG16·RGBA16 Unorm 텍스처를 표본할 수 있는지다.
  - false면 그 출력을 같은 채널 수의 16F로 바꾼다. A5i 빌드 설정에 `norm16Supported`를 더해 출력 종류를 정할 때 바꾼다. 대체 출력은 Unorm 규칙대로 [0, 1]로 자르고 NaN → 0을 적용한 뒤 RNE로 16F를 만든다(재표본 넘침이 Unorm에서 생길 수 없는 값으로 남지 않게 — 12.2절 3번의 8비트 → 16F 대체도 같은 규칙으로 고친다). 정밀도는 약 11비트다.
  - 엔진 Android는 false다. OpenGL ES 3.2 core에 norm16이 없다(EXT_texture_norm16 — UE도 Android GLES에서 PF_G16을 R16F로 대체한다, OpenGLDevice.cpp 1039–1041). Windows는 true다. Mac 프로파일은 A4f가 더하고 true다.
  - UE와 다른 점: UE Vulkan은 R16_UNORM 지원을 런타임에 보고 고른다(VulkanDevice.cpp 874–881). Rocks는 쿠킹 때 프로파일 하나로 정하므로 지원 기기에서도 16F다.
- 프로파일 JSON 병합: `textureLodGroups`에 필드 플래그 `TextMapMergeByKey`를 단다(A4f1 — 10.3.1절). 프로젝트 파일은 그룹 하나의 칸 하나만 덮을 수 있다(struct 값 멤버 병합 — TextJson.h). A5j1의 import 전체 MergeByKey는 A4f1에서 이 플래그로 바꿨다(`shaderFormats`는 Replace).
- 검증(`InvalidSetting`):
  - 그룹의 `minLodSize` > `maxLodSize`(12.4.5절 결정 — UE는 Clamp 순서로 Min이 이기지만 설정 실수로 본다), 음수 크기.
  - 그룹 `mipLoadOptions` OnlyFirstMip(계약 — 텍스처 칸은 `CheckTextureSettings`가 거르지만 그룹 값은 텍스처가 Default일 때 쓰이므로 프로파일에서 거른다).
  - 그룹 `mipGenSettings`가 FromTextureGroup이거나 SimpleAverage·NoMipmaps·Unfiltered 밖(계약).
  - 음수 `maxAniso`(0 = 전역 값 — UE도 음수를 쓰지 않는다).
  - 실패 칸은 `CookConfigField::TextureLodGroup`이고 index는 `TextureGroup` 값이다.
- 엔진 파일(`Engine/Config/TargetProfiles/Windows.json`·`Android.json`)은 UE 5.8 `BaseDeviceProfiles.ini` `[GlobalDefaults DeviceProfile]`의 TextureLODGroups 27행(190–216)과 같은 값을 적는다(Windows·Android 둘 다 이것을 물려받는다).
  - 예: World·NormalMap·Character 계열은 MaxLODSize 16384·aniso·point. Effects는 linear. UI는 NoMipmaps. Shadowmap은 NumStreamedMips 3. Bokeh는 MaxLODSize 256·linear·linear. Pixels2D는 point. 8BitData·16BitData는 point·NoMipmaps(크기 생략 — 기본값).

**A5i 보강**(TextureTools — 이 단계가 쓴다):
- `TextureBuildSettings`를 리플렉션 struct로 옮긴다(Texture 모듈 `Texture/TextureBuildSettings.h` — 옵션 struct와 같은 이유로 에셋 세션이 등록하는 모듈, ROCKS_STRUCT). 너겟 키가 `WriteReflected`로 쓴다(9.1절 결정 2 — 처리기가 설정을 손으로 쓰지 않는다). `norm16Supported` 칸을 더한다.
- `TextureBuildWarnings(settings) → 경고 목록`: 빌드 경고(`SrgbIgnored`·`PreserveBorderWithWrap`)를 설정만으로 계산하는 순수 함수다. `BuildTexture`도 이것을 쓴다. 너겟 적중이어도 같은 경고가 나온다.
- `TextureBuildVersion`(uint32 공개 상수): 빌드 규칙(12.5·12.13절)이 바뀌면 올린다. 너겟 키에 들어간다(처리기 버전 Guid와 따로 — 빌드 코드와 쿠킹 배치가 따로 바뀐다).

**처리기 `TextureCookProcessor`**(TextureTools — `TypeIdOf<Texture>()`에 등록, Texture 파생 다섯 클래스에 쓰인다):
1. **정체성**: 처리기 Guid·버전 Guid(출력 배치 — 값·meta 형식·플랫폼 데이터 채우기 — 가 바뀌면 버전 Guid를 바꾼다 — 쿠킹 재사용 키). 너겟 키 머리는 따로 둔 `TextureNuggetProcessorId`를 쓴다(플랫폼 데이터 배치만 바뀌면 너겟 값을 그대로 쓰도록 — 너겟 값의 뜻이 바뀔 때만 그 버전을 올린다, 2026-11-25 A5k 리뷰).
2. **설정 판정**: `CheckTextureSettings`(12.8절 — 계약 `UnsupportedSetting`·숨김 `InvalidSetting`)가 이슈를 내면 첫 이슈의 코드로 실패한다(detail = 이슈 수 — 경로는 보고서 후속).
3. **유효 설정**:
   - 그룹 = `profile.textureLodGroups[texture.lodGroup]`(없으면 기본값)이다.
   - `ResolveTextureBuildSettings(texture, 차원, 그룹 값)`(A5i)에 `norm16Supported = profile.textureNorm16Supported`를 더한다.
   - 차원은 객체 타입이다: Texture2D·TextureCube·Texture2DArray·TextureCubeArray·VolumeTexture.
4. **원본 byte**: `context.bulkSource->ReadBulk(texture.source.bulk)`이다(파일 bulk 저장소가 CRC·해제·SHA-256을 확인한다). 원본이 비면 `InvalidSource`다.
5. **너겟 키**(bucket `texture`):
   - `WriteNuggetKeyHeader` 뒤 차례로 쓴다:
     - TypeId.
     - `TextureBuildVersion`.
     - 원본 정체성: bulk SHA-256·rawBytes·형식·크기·slice·mip·layer 수.
     - `WriteReflected(TextureBuildSettings)`(그룹의 빌드 칸 — 최소·최대 크기·편향·mipGen — 이 이미 들어 있다).
     - 압축 기록 칸(`compressionNoAlpha`·`compressionForceAlpha`·`compressionNone`·`compressionCacheId` — 결과를 바꾸지 않지만 9절 표대로 넣는다).
   - 너겟 값에 들어가지 않는 입력은 넣지 않는다(R-0의 불필요한 입력 — 적중률만 떨어뜨린다). 대상: 샘플러(filter·Border 색·maxAniso), 스트리밍(neverStream·mipLoadOptions·availability·lodGroup — R·비스트리밍은 적중 뒤 계산), 그룹의 비빌드 칸, 프로파일 id·bulk codec·정렬(패키지 단계 값).
   - 키에 쓰는 `TextureBuildSettings`는 사본을 정규화한다(2026-11-25 리뷰 반영):
     - 주소 셋은 Wrap으로 고정한다. A5i mip 결과는 주소에 의존하지 않고(12.5절 — 길이 1인 축은 Wrap·Clamp가 같은 texel, PreserveBorder 조회는 원본 크기로 정한다, 재표본은 늘 clamp), 주소를 쓰는 PreserveBorderWithWrap 경고는 너겟 밖에서 계산한다(10번).
     - `norm16Supported`는 출력이 실제로 바뀔 때(표 출력이 Unorm16 — `TextureBuildOutput`이 true·false에서 다를 때)만 실제 값을 쓰고, 그 밖은 true로 고정한다. 8비트·float 텍스처는 Windows·Android가 같은 너겟을 쓴다.
   - Build 의존이 없으므로 SCC는 구성원 하나다(`NuggetSccKey` — Record는 SCC key, 9.1절 결정 3). Put은 `PutScc`, Get은 `GetSccMember`다.
   - 9절 텍스처 키 표를 이것으로 개정한다(행 "주소·샘플러"는 주소만, "대상 플랫폼"은 norm16 표지만, "대상 픽셀 형식"은 `TextureBuildSettings`가 정하므로 빌드 버전으로 대신한다).
6. **너겟 값**(9.1절 결정 15 SCC 규약 — meta는 구성원 목록이라 쓰지 않는다): ValueId = `NuggetSccValueId(0, part)`다.
   - part 0 = 머리 { 형식 버전 1, PixelFormat 번호, srgb, swizzle 넷, numSlices, mip 수, mip마다 sizeX·sizeY·sizeZ·byte 수 }(little-endian 고정 배치).
   - part 1..N = mip 0..N − 1(쿠킹 편향 뒤 남은 mip, 상위부터)이다.
   - 적중이면 머리와 값으로 결과를 다시 만든다. 다음이면 미적중으로 다룬다(9.1절 — 틀린 적중 0건):
     - 머리가 해석되지 않음.
     - 값 수·byte 수가 머리와 다름.
     - mip 크기 사슬이 max(1, n >> 1)로 이어지지 않음.
     - 형식·srgb·swizzle이 이번 유효 설정의 출력 규칙(`TextureBuildOutput(settings)` — 순수 함수, A5i가 더한다)과 다름.
     - 사슬 끝이 맞지 않음: NoMipmaps면 mip이 정확히 하나, 아니면 마지막 mip이 1×1(Volume은 1×1×1)이다(빌드는 쿠킹 편향으로 위 mip만 버린다 — 일관되게 잘린 사슬을 거른다).
   - 미적중으로 다룬 적중 Record는 `NuggetCache::Reject`로 치운다(9절 A3c1 — Memory 항목·세션 고정·backend 항목). 치우지 않으면 backend 해시가 정상인 그 Record가 남아 이후 Put이 늘 Conflict가 되고 매번 다시 빌드한다. Reject 실패는 `required`일 때만 오류다.
   - 한계: mip 0 크기·mip 수를 유효 설정에서 계산해 대조하지는 않는다(빌드의 pow2 → 최대 크기 → 편향 계산을 순수 함수로 떼면 더할 수 있다 — 후속).
   - `verifyNuggets`면 적중이어도 빌드해 머리·값 byte를 대조하고, 다르면 `NuggetMismatch`이며 Put하지 않는다(10.2절 결정 12). 미적중이면 verify할 것이 없어 빌드·Put한다.
   - 미적중이면 빌드하고 Put한다(Put 실패는 쿠킹 실패가 아니다 — `required`면 오류, Conflict는 캐시 진단).
     - Put은 쿠킹 패키지를 쓴 뒤 mip byte를 값으로 옮겨 한다(복사 없음).
     - Conflict는 경고 `NuggetConflict`(새 진단 코드 — 4.6절 표)다. 이번 결과를 쓰고 기존 항목은 둔다.
     - `required`인 캐시의 Get·Put `failed`는 쿠킹 실패다(진단 코드 None, 오류는 캐시가 준 원인 오류 — 없으면 새 `ErrorCode::IoError`).
     - 적중이면 원본 bulk를 읽지 않는다(키는 원본 ref의 SHA-256·크기로 만든다). 빈 원본 검사도 ref로 한다.
   - UE와 다른 점: UE DDC는 편향 전 mip 사슬 전체를 두고 직렬화 때 편향만큼 위 mip을 자른다(TextureDerivedData.cpp 2958–2974 — SerializeForKey에 LODBias가 없다). Rocks는 빌드에서 잘라 편향·최소·최대 크기가 키에 들어가므로 편향만 바꿔도 다시 빌드한다. 전체 사슬을 너겟에 두고 쿠킹에서 자르는 안은 적중률 개선 후속이다.
   - 한계: mip byte의 SHA-256을 bulk ref 만들 때·writer 재검증·너겟 Put RawHash에서 세 번 계산한다. 앞의 값을 넘기는 경로는 후속 성능 개선이다.
7. **`TexturePlatformData`**(12.1·12.5.1절):
   - `dimension`, `pixelFormat`(PixelFormat 번호 — 12.8절 저장 계약), `srgb`, `swizzle*`를 채운다.
   - `sizeX`·`sizeY`·`sizeZ`(쿠킹 상위 mip — Volume 깊이, 그 밖 1), `numMips`(N), `numSlices`(Volume 1, 그 밖 slice 수)를 채운다.
   - `mips[i]`: 크기, `byteSize`. 스트리밍 mip은 `bulk`(mip 하나가 bulk 하나)를 쓰고, 상주 꼬리 mip은 `tailOffset`(꼬리 덩어리 안 오프셋)을 쓴다.
   - `tailBulk`(상주 꼬리 mip을 큰 mip부터 이은 bulk 하나), `residentTailMips`(R)를 채운다.
   - R은 12.5.1절 2번이다. 비압축이라 블록 규칙이 없고 형식 mip tail 수는 0이다. 상수 `TextureMinResidentMipCount` = 7은 TextureTools 공개 상수다.
   - 비스트리밍(R = N)은 12.5.1절 3번 조건이다: `neverStream`, UI 그룹, N = 1, NoMipmaps(유효 설정), Cube·CubeArray, X 또는 Y — Volume은 Z도 — 가 2의 거듭제곱이 아님(UE Texture.cpp 1873–1877, 12.5.1절 3번을 고친다), `mipLoadOptions` OnlyFirstMip(계약 — 2번·프로파일 검증에서 이미 거부), `availability` CPU.
   - `availability` CPU: UE는 GPU 쪽 placeholder mip 하나와 CPU 사본을 둔다(12.13절). A5j1은 mip 0을 상주 꼬리에 두고 비스트리밍으로 쓴다. placeholder 배치는 렌더러 CPU 텍스처 지원(화면 마일스톤 뒤)과 함께 정한다(계약 — 렌더 세션 알림에 적는다).
8. **샘플러 `TextureSamplerSettings`**:
   - `filter`는 텍스처 `filter`다. Default면 그룹 MinMagFilter·MipFilter 조합이고, Nearest → Point, Bilinear → Bilinear, Trilinear → Trilinear다.
   - `maxAniso`는 그룹 값이다.
   - 주소: Texture2D addressX·Y(W Wrap — UE Texture.h 2033 기본), 2DArray X·Y·Z, Volume addressMode 세 축, Cube·CubeArray Clamp 셋이다(UE TextureCubeArray.cpp 171–176, Texture2DArrayResource.cpp 21–23, VolumeTexture.h 92–94와 같다).
   - `borderColor`: Texture2D·2DArray·Volume의 값, Cube 계열 TransparentBlack이다.
   - UE와 다른 점: UE는 런타임에 활성 장치 프로파일에서 필터·MaxAniso를 정한다(StreamableTextureResource.cpp 133–136). 장치 프로파일(Android_Low 등)마다 다를 수 있고 바꿔도 재쿠킹이 없다. Rocks는 쿠킹 프로파일에서 굳힌다(쿠킹 결과 재사용 키는 프로파일 SHA-256으로 바뀐다 — 너겟은 재사용된다).
9. **쿠킹 패키지와 에디터 객체 불변**:
   - 처리기는 쿠킹 Registry에 연 에디터 객체의 `platformData`를 채우고 `WritePackage`한 뒤, **성공·실패 모두** `platformData`를 기본값으로 되돌린다(범위 가드 — 쿠킹 시작 때 이미 열려 있던 패키지(CookRun `before_`)는 닫지 않으므로 사용자 객체에 쿠킹 값이 남으면 다음 에디터 저장이 쿠킹 BulkDataRef를 쓰게 된다). 되돌리기는 할당하지 않는다(빈 Array로 교체).
   - bulk 원본은 연쇄 원본이다: 새 bulk(mip·꼬리 — 빌드 결과·적중 값 byte를 빌린다)가 먼저, 그 밖 ref는 에디터 bulk 저장소(`context.bulkSource`)다(같은 패키지의 다른 export가 EditorOnly가 아닌 bulk를 가질 수 있다). 두 원본의 bulkId가 겹치지 않게 새 bulk id는 uint32 최댓값부터 내려간다(에디터 저장소의 저장하지 않은 bulk는 최상위 비트 id를 1부터 올려 쓰므로 겹치지 않는다 — 열려 있던 패키지가 편집 중이어도 된다). 새 bulk는 저장 byte가 없어(`ReadStoredBulk` NotFound) writer가 raw를 부호화한다.
   - `WritePackage(kind Cooked, …)`이고 bulk codec·정렬은 프로파일 값(기본 처리기와 같다)이다.
10. **경고**: 빌드 경고(`TextureBuildWarnings` — 적중·미적중이 같다)를 `CookContext`의 새 칸 `warnings`(`Array<CookDiagnostic>*`, null이면 버린다)에 둔다.
    - 쿠킹 실행은 이것을 실행 진단에 `warning = true`로 옮긴다. `CookRunResult::HasErrors`는 경고가 아닌 진단만 센다. CookProject의 게시 판정은 이미 경고를 빼고 센다(CookProject.h 100–108). 보고서·명령 출력은 경고 줄로 낸다.
    - 경고 push의 할당 실패는 OutOfMemory다(10.2절 할당 실패 규칙).
    - 한계: 쿠킹 결과 재사용(처리기를 부르지 않는 대상)은 경고를 다시 내지 않는다. 증분 쿠킹 보고서에는 그 대상의 경고가 없다(UE 증분 쿠킹도 다시 쿠킹하지 않은 패키지의 경고를 내지 않는다).

**호스트 연결**(A5h의 임포터·hook과 같은 방식):
- `commandlet_host::AssetCommandContext`에 `AssetCookProcessorSetup cookProcessors{registerProcessors(state, CookProcessorTable&)}`를 더한다.
- `asset-cook` 명령은 표를 만든 뒤 이것을 부른다.
- 제품 호스트(Commandlet)는 TextureTools `RegisterTextureCookProcessors(state = TextureCookProcessor*)`를 건다.
- TextureTools는 AssetCooker·AssetNugget에 의존하고, AssetCooker는 Texture 모듈(LOD 그룹 enum)에 의존한다.

**버린 대안**:
- 텍스처 객체 통째 `WriteReflected`: ObjectRef(compositeTexture)가 키에 쓸 수 없는 종류다. 빌드 입력을 모은 리플렉션 struct(`TextureBuildSettings`)를 쓴다.
- 키를 손으로 쓰고 칸 수를 static_assert로 묶기: C++에서 struct 칸 수를 셀 수단이 없고 9.1절 결정 2와 어긋난다.
- 샘플러·스트리밍 입력을 키에 넣기: 그룹 aniso 하나만 바꿔도 그 그룹의 모든 텍스처를 다시 빌드한다. 값에 들어가지 않는 입력이다.
- meta에 텍스처 머리 두기: SCC Record의 meta는 구성원 목록이다(9.1절 결정 15).
- 그룹 표를 배열로 두기: 배열은 통째 교체라 프로젝트가 그룹 하나를 바꾸려면 27행을 모두 다시 적어야 한다.
- 16비트 Unorm을 Android에서 거부: 16비트 원본 텍스처 쿠킹이 Android에서 실패한다. 16F 대체는 정밀도만 낮다.
- 쿠킹 사본 객체에 쓰기: 객체 그래프 복제 비용과 참조 재배선이 든다. 범위 가드로 되돌리는 편이 단순하고 실패 경로까지 시험으로 묶을 수 있다.

**시험(A5j1)**:
- 프로파일: 텍스처 칸 기본값, MergeByKey(그룹 하나의 칸 하나만 덮음·새 그룹 넣기), 검증(Min > Max·음수·그룹 OnlyFirstMip·그룹 계약 mipGen·모르는 그룹 이름·모르는 필터 이름), 엔진 Windows·Android 파일의 27행(Shadowmap NumStreamedMips 3)과 Android norm16 false, 출력 설정 SHA-256이 텍스처 칸을 포함함.
- 처리기:
  - 차원 다섯의 쿠킹 패키지(EditorOnly 원본 없음·platformData 칸·bulk 수와 SHA-256이 mip byte와 같음).
  - 다른 bulk를 가진 export가 섞인 패키지(연쇄 bulk 원본).
  - R 표(12.5.1절 6번 — 1×1·4×4·8×8·256×256·2048×2048·2048×64), 비스트리밍 조건마다 R = N·스트리밍 bulk 없음(Volume Z가 2의 거듭제곱이 아닌 경우 포함).
  - 샘플러 표(Texture2D W Wrap), norm16 대체(R16·RG16·RGBA16, 넘침값 자르기), 계약 설정 실패, 빈 원본 `InvalidSource`.
  - 쿠킹 뒤 에디터 객체 불변: 성공·처리기 실패·미리 열린 패키지·두 프로파일 연속 쿠킹.
- 너겟:
  - 미적중 → Put → 같은 키 적중(빌드 호출 없음·같은 byte), SCC ValueId·meta(`FindNuggetSccMember`).
  - 머리 손상·값 수 불일치·크기 사슬·형식 규칙 불일치는 미적중.
  - verify 일치·불일치(`NuggetMismatch`·Put 없음), 미적중 상태의 verify.
  - 같은 키 다른 값 Put의 Conflict 진단.
  - 변이 시험: `TextureBuildSettings` 칸·원본 정체성·압축 기록 칸·빌드 버전마다 키가 바뀌고, 샘플러·스트리밍·경로·이름·프로파일 id는 바뀌지 않음.
- 경고: 적중과 미적중의 경고가 같음, 쿠킹 진단 경고(`SrgbIgnored`)는 publish를 막지 않고 보고서에 나옴, 재사용 대상은 경고 없음.
- 명령: `asset-cook --profile=Windows`의 텍스처 쿠킹(제품 호스트 연결), 할당 실패.

#### A5j2(2026-11-25 — 교차 검증 1차 반영)

**에셋 원본 묶음**(12.3절 — `asset-new Texture2DArray … SourceTextures=…` 등):
- Texture2DArray·TextureCubeArray의 `sourceTextures`(Texture2D·TextureCube 목록)와 VolumeTexture의 `source2DTexture`·`source2DTileSizeX/Y`가 원본을 정한다.
- UE는 편집 때 묶음을 자기 `Source`로 복사한다. Rocks도 UE처럼 **편집 때 복사**한다.
  - UE 코드: `UTexture2DArray::UpdateSourceFromSourceTextures`·`PostEditChangeProperty`(Texture2DArray.cpp 354–520·606–654), `UTextureCubeArray`의 같은 함수(TextureCubeArray.cpp 608–836·930–984), `UVolumeTexture::UpdateSourceFromSourceTexture`·`SetDefaultSource2DTileSize`(VolumeTexture.cpp 163–240·575–592·594–618).
  - 쿠킹은 자기 원본만 읽는다. 쿠킹 입력에 다른 에셋이 없으므로 Build 의존이 필요 없다(12.7절 문구는 개정함).
- 둘로 나눈다. **A5j2a**는 같은 크기·형식·sRGB의 묶음을 그대로 잇는 경로다(이 절). **A5j2b**는 UE의 변환 경로다(아래 "계약" — 후속).

**hook**(AssetRuntime `AssetTypeHooks` — 12.12절 정규화 hook과 같은 표):
- 새 종류 `rebuildSource`(`AssetSourceRebuildHook(context, assignedFields, sink)`)다. 정규화 hook은 자기 객체만 보지만 묶음은 다른 패키지의 bulk를 읽고 자기 패키지에 bulk를 더해야 해서 따로 둔다.
- `AssetSourceRebuildSink`(AssetRuntime 추상 — EditorPackageSet이 구현):
  - `ReadBulk(object, ref) -> Span`: object가 속한 패키지(outermost)의 bulk raw byte다(열린 패키지의 파일 bulk 저장소 — CRC·해제·SHA-256 확인). span은 sink가 살아 있는 동안 유효하다.
  - `AddBulk(raw) -> BulkDataRef`: hook 대상 패키지의 저장 전 bulk로 더한다(FilePackageBulkStore::AddUnsaved). 이전 원본 bulk는 참조가 없어져 저장에서 빠진다.
  - `Fail(code, error, detail)`: 진단을 남기고 그 오류로 실패한다(Set은 패키지를 dirty로 두고 저장하지 않는다 — 정규화 실패와 같다, New는 아래).
  - `Warn(code, detail)`: 경고(EditorWarning `SourceRebuildWarning`)를 남긴다.
  - `HasImportRecord()`: 대상에 ImportRecord가 있는지다.
  - `Cause()`(Edit·New·Propagate)·`ChangedSource()`(Propagate일 때 재임포트한 원소): 전파는 필드 이름을 흉내 내지 않는다 — 다른 EditorOnly 필드(예: `compositeTexture`)로만 원소를 참조하는 에셋에 묶음 필드 이름을 넘기면 빈 목록이 원본을 지운다. 그래서 Propagate의 hook은 자기 묶음 필드가 ChangedSource를 가리킬 때만 지금 값 그대로 다시 복사한다(Volume 타일을 다시 정하지 않는다 — UE도 `UpdateSourceFromSourceTexture()`만 부른다).
- hook이 쓴 칸(원본·`srgb`·처음 만들기 설정)은 override 집합에 기록하지 않는다(정규화 hook과 같다 — 클래스 기본값과 다를 때만 차이 저장된다, UE의 CDO 기준 delta와 같다).
- 서비스가 부르는 곳:
  - `asset-set`(Set): 대입·되돌리기를 게시한 뒤, 정규화 hook 앞에서 부른다.
  - `asset-new`(New): 패키지를 만든 뒤 첫 저장 앞에서 원본 재구성 → 정규화 순으로 부른다(지금은 New가 정규화를 부르지 않는다 — 같이 고친다. UE 팩토리도 만든 뒤 `ValidateSettingsAfterImportOrEdit`를 부른다). New의 hook·정규화 실패는 만든 패키지를 저장하지 않고 집합에서 닫는다(파일이 생기지 않고 같은 경로의 다음 New가 막히지 않는다).
  - 임포트는 부르지 않는다(원본 파일이 원본을 정한다 — 임포트 결과의 묶음 칸은 빈다).
  - 재임포트 전파(UE `UReimportTextureFactory`, EditorFactories.cpp 4194–4245): Texture2D·TextureCube를 재임포트하면 그것을 EditorOnly로 참조하는 에셋(색인 역방향 — 삭제의 참조자 찾기와 같은 훑기)을 열어 rebuildSource를 Propagate 까닭·바뀐 원소로 부른다(assignedFields는 빈다 — 아래 sink 설명). UE는 메모리에 올라온 객체만 갱신한다 — Rocks는 색인 전체다(UE의 상위집합, 결정적).
    - hook이 원본을 실제로 다시 쓴 에셋(sink `MarkRebuilt`)만 정규화하고 원소 뒤에 저장한다. 묶음과 무관한 참조자(`compositeTexture` 등)는 열기만 하고 바꾸지도 저장하지도 않는다(2026-11-25 코드 리뷰 반영).
    - 저장 전에 판정한다: hook 실패, 다시 쓴 대상이 저장할 수 없음(읽기 전용 NewerVersion·미해결 import MissingDependency — Save와 같은 진단), 일 전부터 열려 있고 저장하지 않은 편집이 있음(Busy — 그 편집까지 저장하게 되므로)이면 재임포트가 실패하고 아무것도 저장하지 않는다(묶음이 원소와 어긋나지 않게).
    - 전파는 처음 만들기 설정을 바꾸지 않고(UE `UpdateSourceFromSourceTextures(false)`), ImportRecord가 있는 묶음 에셋(교환 임포트가 묶음 칸을 옮긴 경우)은 실패시키지 않고 둔다.
    - 일 전부터 열려 있던 깨끗한 대상을 다시 쓴 뒤 실패하면 그 패키지를 dirty로 둔다(메모리 값이 디스크와 다르다).
    - 한계: 저장 단계의 IO 실패(원소 저장 → 묶음 일부 저장 → 실패)는 되돌리지 않는다(다른 기존 출력의 저장 실패와 같다). 클래스 기본값 레코드 없음(ClassDefaultsUnavailable) 같은 저장 판정도 사전 판정에 없다.
- hook은 assignedFields에 자기 필드가 없으면 아무것도 하지 않는다(Texture2DArray·TextureCubeArray: `sourceTextures`, VolumeTexture: `source2DTexture`·`source2DTileSizeX`·`source2DTileSizeY`). 이름은 대소문자를 무시해 비교한다(`EqualsIgnoringAsciiCase` — assignedFields는 텍스트 경로의 첫 마디이고 대소문자를 보존한다, 정규화 hook과 같다).
  - 되돌리기(`--reset=sourceTextures`)도 assignedFields에 들어간다. 목록이 기본값(빈 목록)으로 돌아가면 아래 1번(빈 원본)이다.
  - 같은 값을 다시 대입해도 assignedFields에 들어가고 Set은 늘 저장까지 가므로, 같은 목록을 다시 대입하면 다시 복사한다(수동 재복사).
- 임포트한 배열 보호(UE `bSourceGeneratedFromSourceTexturesArray` — Texture2DArray.cpp 216·546, TextureCubeArray.cpp 476·866, 파일로 임포트한 배열에서는 편집기가 SourceTextures를 숨긴다): ImportRecord가 있는 에셋에 `sourceTextures`·`source2DTexture`를 대입하면 `InvalidSetting`이다(다음 재임포트가 원본을 다시 덮어쓰므로). 묶음이 비어 있으면(되돌리기로 빈 목록·원본 2D none, Volume 타일만 대입) 묶음이 원본을 정하지 않으므로 아무것도 하지 않는다 — 임포트한 원본을 지우지 않는다(UE는 편집기가 그 칸을 숨겨 이 경우가 생기지 않는다).

**2DArray·CubeArray 규칙(A5j2a):**
1. 목록이 비면 원본을 기본값(빈 원본)으로 되돌린다(UE `InvalidateTextureSource`). 쿠킹은 `InvalidSource`가 된다.
2. 원소마다:
   - null 원소: `InvalidSetting`(detail = 원소 번호)이다. UE는 null이 있으면 복사하지 않고 둔다(편집기 배열 칸을 채우는 중간 상태). 명령행 대입은 목록 전체를 한 번에 주므로 오류로 알린다.
   - 원본이 없는 원소(bulk 빔·형식 Invalid): `InvalidSource`(detail = 번호)다(UE는 경고하고 null로 바꾼다).
   - 크기·형식·sRGB 여부가 첫 원소와 다르면 `InvalidSetting`(detail = 번호)이다. UE의 변환은 A5j2b 계약이다.
     - 원소의 sRGB 여부 = `srgb` on이고 `useLegacyGamma` off이며 8비트 정수 형식(G8·GA8·RGBA8)일 때다(UE `GetGammaSpace(0) == sRGB`, Texture.cpp 3189–3213 — 16비트·float는 Linear, legacy gamma는 Pow22라 sRGB가 아니다).
   - 원소의 `numLayers` ≠ 1(다층 원본 — 계약)이나 `numMips` ≠ 1(원본 mip — 계약)은 `UnsupportedSetting`(detail = 번호)이다. bulk 길이는 mip 0과 정확히 같아야 한다(아니면 `InvalidSource`).
   - CubeArray 원소는 slice 6이어야 한다(Rocks는 위도·경도 Cube 원본이 없다 — 12.3절). 2DArray 원소는 slice 1이다(Texture2D).
   - 원소 수 상한은 임포트와 같다(2DArray 256, CubeArray 42 — 12.12절). 넘으면 `InvalidSetting`(detail = 상한).
   - 결과 원본 byte(X × Y × slice × texel byte)는 디코더 한도 `ImageDecodeLimits::maxPixelBytes`(4 GiB — 12.9절) 이하다. 넘거나 곱이 넘치면 `InvalidSetting`·`CapacityExceeded`(detail = 0)다(할당 전에 판정 — UE Volume의 넘침 검사 VolumeTexture.cpp 181–184와 같은 목적).
3. 새 원본: 형식 = 첫 원소 형식, 크기 = 첫 원소 크기, slice = 원소 수(CubeArray는 × 6), mip 1, layer 1. bulk = 원소마다 mip 0 byte(그 원소의 모든 slice)를 원소 순으로 이은 것이다(UE `Source.Init(SizeX, SizeY, ArraySize * NumSlices, 1, Format)` 뒤 원소별 memcpy).
4. 배열 `srgb` = 첫 원소의 sRGB 여부(위 정의)다(UE `SRGB = bSRGB` — legacy gamma는 복사하지 않는다, UE와 같다).
5. 처음 만들기(UE `bCreatingNewTexture`): 대입 전에 자기 원본이 비어 있었으면(새 에셋·빈 원본) 첫 원소에서 설정을 가져온다 — `compressionSettings`, `mipGenSettings` = NoMipmaps, `powerOfTwoMode` = None, `lodGroup`, `neverStream` = true. 이 칸들이 같은 명령에서 대입되었으면 대입 값을 둔다(사용자 지정 우선).
   - 근거: UE 팩토리(Texture2DArrayFactory.cpp 60–70, TextureCubeArrayFactory.cpp 60)는 목록을 다 넣은 뒤 기본 인자 `bCreatingNewTexture = true`(Texture2DArray.h 66, TextureCubeArray.h 52)로 부른다 — asset-new + 목록 전체와 같다.
   - UE와 다른 점: 편집 경로(Texture2DArray.cpp 627–631)는 목록이 하나면 원본이 있던 배열도 처음 만들기로 본다. Rocks는 "원본이 비어 있었음"만 본다(원본이 있는 배열의 사용자 설정을 덮지 않는다).
6. 쿠킹 데이터(`platformData`)는 건드리지 않는다(에디터에서는 늘 기본값 — A5j1 9번).

**Volume 규칙(A5j2a — UE와 같다, 3번 경고는 Rocks 추가):**
1. 대입에 `source2DTexture`가 있고 타일 칸이 대입되지 않았으면 기본 타일 크기를 정한다(UE `SetDefaultSource2DTileSize` — VolumeTexture.cpp 575–592): N = 원본 X × Y, t = max(1, round(N^(1/3))), s = max(1, round(sqrt(⌊X / t⌋ × ⌊Y / t⌋))), 타일 = (⌊X / s⌋, ⌊Y / s⌋). 원본이 없으면 타일 0.
   - 반올림은 정수로 정확히 한다(t는 (2t − 1)³ ≤ 8N < (2t + 1)³, s는 P = ⌊X / t⌋ × ⌊Y / t⌋일 때 (2s − 1)² ≤ 4P < (2s + 1)²). s는 곱이 작아 UE float와 늘 같다. t는 UE `powf` 오차 안의 경계에서 1 차이가 날 수 있다(8N은 짝수라 정확한 동률은 없다 — 빌드 때 UE 결과와 대조한다).
2. 원본 2D가 있고 타일이 모두 양수이고 Z = min((X / 타일X) × (Y / 타일Y), 512) > 0이면 새 원본 = 형식 그대로, 크기 타일X × 타일Y, slice Z다. 타일은 왼쪽 → 오른쪽, 위 → 아래이고 나머지 행·열은 버린다(UE와 같다 — 파일 임포트 `--volume-tile`은 나뉘어야 하지만 묶음은 UE를 따른다). 512는 UE `MAX_VOLUME_TEXTURE_DEPTH`다(이름 있는 상수).
3. 그 밖(원본 없음·타일 0 이하·Z 0)이면 원본을 빈 원본으로 되돌린다(UE와 같다 — VolumeTexture.cpp 225–233, 오류가 아니다). 경고 `SourceCleared`(새 경고 코드 — 4.6절 표)를 하나 낸다(Rocks 추가 — 비프로그래머가 원본이 사라진 것을 알게 한다, 배열 쪽은 오류로 알리므로 정책을 맞춘다).
   - 원본 2D의 `numLayers`·`numMips` ≠ 1은 `UnsupportedSetting`이고 결과 byte 한도는 배열과 같다. 원본 2D 크기가 디코더 한도(16384)를 넘으면 기본 타일 계산 전에 `InvalidSetting`·`CapacityExceeded`다.
4. 원본 2D가 Texture2D가 아니면 대입이 막는다(필드 타입 `ObjectRef<Texture2D>`).
5. asset-new로 원본 2D 없이 만든 VolumeTexture는 1×1×1 RGBA8 (0, 0, 0, 255) 원본을 둔다(UE `UVolumeTextureFactory` — VolumeTextureFactory.cpp 63–68, UE BGRA8을 Rocks 정규 형식 RGBA8로).

**진단**: `InvalidSetting`·`InvalidSource`·`UnsupportedSetting`(detail = 원소 번호 또는 상한), 경고 `SourceCleared`. 이 hook의 실패는 명령 실패다(아무것도 저장하지 않는다).

**A5j2b — UE 변환 경로(2026-11-25 — 착수 때 정함, UE 5.8 `UTexture2DArray::UpdateSourceFromSourceTextures`·`UTextureCubeArray` 같은 함수·`FImageCoreUtils::GetCommonSourceFormat`·`FImageCore::CopyImage`·`ResizeImageAllocDest`):**

1. **공통 형식**: UE는 원소를 차례로 접는다 — `Format = GetCommonSourceFormat(Format, 원소 형식)`, 감마(sRGB 여부)가 다른 원소를 만나면 그때부터 RGBA32F·선형이다(`bSRGB = false`). Rocks도 같은 순서로 접는다(감마 검사 먼저, 그다음 형식 — 이 그래프는 최소 공통 조상이라 순서와 무관하지만 UE와 같게 둔다).
   - UE 그래프(변환이 손실 없다고 보는 간선): G8 → BGRA8 → RGBA16, G8 → G16 → RGBA16, RGBA16 → RGBA32F, R16F → RGBA16F → RGBA32F, R16F → R32F → RGBA32F, BGRE8 → RGBA32F. 결과는 두 형식의 가장 낮은 공통 조상이다.
   - Rocks 원본 형식(12.1절)으로 옮긴다: BGRA8 자리는 RGBA8이고, UE에 없는 GA8·GA16은 G8·G16과 RGBA 사이에 둔다 — G8 → GA8 → RGBA8, G8 → G16 → GA16 → RGBA16, GA8 → GA16, RGBA8 → RGBA16. 정수 무리와 float 무리가 만나면 RGBA32F다(UE `IsHDR` 갈래와 같다). Rocks에는 BGRE8 원본이 없다.
   - 표(같은 형식은 그대로, 순서는 상관없다): G8 + X(정수) = X. GA8 + G16 = GA16, GA8 + GA16 = GA16, GA8 + RGBA8 = RGBA8, GA8 + RGBA16 = RGBA16. G16 + GA16 = GA16, G16 + RGBA8 = RGBA16, G16 + RGBA16 = RGBA16. GA16 + RGBA8 = RGBA16, GA16 + RGBA16 = RGBA16. RGBA8 + RGBA16 = RGBA16. R16F + RGBA16F = RGBA16F, R16F + R32F = R32F. 그 밖의 float 쌍과 정수·float 쌍은 RGBA32F다.
   - 표는 감마가 같을 때만 쓰인다. 16비트·float 원본은 늘 선형이므로(UE `GetGammaSpace`), sRGB 8비트 원소와 16비트·float 원소가 만나면 접기 단계에서 이미 RGBA32F 선형이다 — "G16 + RGBA8 = RGBA16"은 RGBA8이 선형일 때만이다.
   - 배열의 SRGB는 접은 결과다(감마가 갈리면 off). sRGB는 지금처럼 8비트 원본 + srgb on + legacy gamma 아님이다(A5j2a).
   - 원소의 감마는 셋이다: sRGB, Pow22(8비트 + srgb on + legacy gamma — UE `EGammaSpace::Pow22`), 선형. 접기는 "sRGB인가"만 본다(UE `== sRGB`) — Pow22 원소는 선형 원소와 갈린 것으로 보지 않는다. 그래서 Pow22 원소는 형식이 같으면 byte 그대로 복사되고, 형식이 달라 변환할 때는 Pow22로 푼다(UE `GetMipImage`의 GammaSpace — `FromPow22Color`).
   - UE에는 GA 형식이 없다(회색 + 알파 원본은 UE에서 BGRA8). UE golden에서는 GA8을 BGRA8(L, L, L, A)로 대응시켜 만든다.
2. **변환**(UE `CopyImage`): 형식·감마가 같으면 byte 그대로다. 다르면:
   - 직접 경로(배열 경로에서 실제로 쓰는 넓히는 변환 — UE `CopyImage`의 같은 감마 직접 경로, ImageCore.cpp 793–828·862–873): 같은 감마의 8비트 → 8비트(G8 → GA8은 (L, 255), G8 → RGBA8은 (L, L, L, 255), GA8 → RGBA8은 (L, L, L, A)) byte 복제, 선형 8비트 → 16비트는 v·257(채널 배치는 같은 복제), 16비트 → 16비트(G16 → GA16은 (v, 65535), G16·GA16 → RGBA16 복제). 두 단계 변환의 sRGB 표 왕복에 기대지 않는다.
   - 그 밖은 두 단계다 — 원본(형식·감마)을 RGBA32F 선형으로 풀고, 대상(형식·감마)으로 부호화한다(UE `CopyImage` RGBA32F → 대상 규칙). 풀기는 UE `CopyImage` 원본 → RGBA32F다: 회색 원본(G8·GA8·G16·GA16)은 (v, v, v, a), **R16F·R32F는 (v, 0, 0, 1)**(ImageCore.cpp 763·783), 8비트 알파는 A/255 선형.
   - A5i 수정: A5i `DecodeSource`는 R16F·R32F를 (v, v, v, 1)로 풀어 UE와 달랐다(12.13절 "회색 원본은 r = g = b"에 R16F·R32F를 넣은 결함 — 2026-11-25 A5j2b 교차 검증에서 찾았다). 회색 복제를 G8·GA8·G16·GA16에만 두고 R16F·R32F는 (v, 0, 0, 1)로 고친다. 형식·감마(sRGB·Pow22·선형)·크기만 받는 핵심 함수 `DecodeTexels`로 나누고, 빌드의 `DecodeSource`와 이 변환이 함께 쓴다(한 곳에서 고친다). R16F·R32F 원본에서 RG·RGBA 출력을 내는 빌드의 G·B가 바뀐다(1채널 출력은 그대로 — A5i 시험 기대값은 바뀌지 않는다).
   - G8: R 채널만 쓴다(UE "gray가 아니라 R" — R16F·R32F에서 온 값이 그대로 간다). sRGB면 `LinearToSrgb8`(UE `ToFColorSRGB`), 아니면 `QuantizeUnorm8`(UE `QuantizeRound`).
   - RGBA8: 네 채널이다. sRGB면 RGB는 `LinearToSrgb8`, A는 선형 `QuantizeUnorm8`(UE `ConvertFLinearColorsToFColorSRGB`), 아니면 넷 다 `QuantizeUnorm8`.
   - GA8(Rocks 추가): R과 A다(G8·RGBA8 규칙을 따른다 — R은 sRGB면 sRGB, A는 선형).
   - G16·GA16·RGBA16: `QuantizeUnorm16`(UE `QuantizeUNormFloatTo16`)이다. G16은 R, GA16은 R과 A다.
   - R16F·RGBA16F: `Float16::FromFloat`(UE `FFloat16::Set` — RTNE, 넘치면 ±Inf)다. R16F는 R이다. A5i 출력의 `QuantizeHalf`(유한 범위 포화)와 다르다.
   - R32F: R, RGBA32F: 그대로다.
3. **크기**(2DArray만): 배열 크기는 원소의 최대 X·최대 Y다. 크기가 다른 원소는 형식 변환 뒤 재표본한다(UE 순서 — 변환 → `ResizeTo`).
   - 재표본(UE `ResizeImageAllocDest` → `ResizeImage`): UE는 채널 수가 같으면 RGBA32F로 바꾸지 않고 원래 데이터형 그대로 stb_image_resize2에 넘긴다(ImageCore.cpp 2148–2200, `GetFormatSTBIR` 1838–1898 — G8은 1채널, sRGB면 `UINT8_SRGB`(알파 선형), 16비트 `UINT16`, 16F `HALF`, 32F `FLOAT`, 미리 곱하지 않는다). stbir는 안에서 그 형식을 float로 풀고(sRGB는 표, 8·16비트는 /최대), 표본하고, 다시 부호화한다.
   - Rocks는 같은 뜻을 이렇게 낸다: 그 형식·감마를 `DecodeTexels`로 풀고, A5i `Resample`(UE 기본 필터 AdaptiveSharp — 확대 Catmull-Rom, 축소 Mitchell, 같은 길이 축은 점 표본)로 바꾸고, 같은 형식·감마로 부호화한다. 부호화 대응: uint8 선형은 `x·255 + 0.5`를 clamp한 뒤 버림(stbir — `QuantizeUnorm8`과 같다), sRGB는 stb `fp32_to_srgb8_tab4` 표(UE `ToFColorSRGB`도 같은 표 — `LinearToSrgb8`이 이 표다), uint16은 같은 반올림(`QuantizeUnorm16`), half는 RTNE(`Float16::FromFloat`), float는 그대로. 채널은 서로 독립이라 1채널 형식을 4채널 작업 픽셀로 돌려도 R 값은 같다.
   - 한계: stbir는 float 가중치·비용 휴리스틱으로 정한 패스 순서·역수 곱을 쓰고, A5i `Resample`은 double 가중치다. 그래서 UE golden은 재표본한 원소에 ±1 LSB(결정적 허용)를 두고, 재표본하지 않은 변환은 byte 일치로 나눈다.
   - 가로세로 비율이 달라도 거부하지 않는다(UE는 Log만 남긴다 — Rocks는 진단을 남기지 않는다).
   - CubeArray는 크기가 다르면 지금처럼 `InvalidSetting`이다(UE도 거부 — CheckArrayTexturesCompatibility).
   - 형식이 같고 크기만 다른 원소는 배열 감마로 재해석해 재표본한다. Pow22 원소도 선형으로 보고 재표본해, 같은 크기 Pow22 원소의 byte 그대로와 뜻을 맞춘다. UE는 이 경우 `ResizeTo(…, Pow22)`가 `check(DestImage.GetGammaSpace() != Pow22)`(ImageCore.cpp 2158)에 걸려 정한 동작이 없다 — UE와 다른 점(12.7절, 2026-11-25 코드 리뷰).
4. **그대로 두는 판정**: 원소 numLayers·numMips ≠ 1은 `UnsupportedSetting`, 원본 없음 `InvalidSource`, 결과 4 GiB 초과 `InvalidSetting`/CapacityExceeded, Cube 원소의 slice ≠ 6은 `InvalidSetting`(UE의 longlat 한 장 CubeArray 원소는 Rocks에 longlat 원본이 없어 받지 않는다 — 12.3절).
5. **구현**:
   - TextureTools 새 공개 헤더 `TextureSourceConvert.h`에 `CommonTextureSourceFormat(a, b)`와 `ConvertTextureSource(allocator, 원본 형식·sRGB·크기·slice 수·byte, 대상 형식·sRGB·크기, out)`를 둔다(시험이 표를 직접 대조한다).
   - A5i의 `DecodeSource`·`Resample`·`Level`과 양자화 함수를 내부 헤더 `TextureBuildInternal.h`로 꺼내 함께 쓴다(두 번 구현하지 않는다).
   - 작업 메모리는 A5i `WithinWorkingBytes`와 같은 상한이다(넘으면 `InvalidSetting`/CapacityExceeded).
   - `TextureSourceRebuild`의 원소 판정에서 형식·sRGB 불일치(Array·CubeArray)와 크기 불일치(Array) 거부를 지우고 이 경로를 탄다.
   - 출력이 바뀌므로 묶음 결과에 영향이 있는 버전은 없다(원본 재구성은 에디터 패키지에 저장되고, 쿠킹 키는 원본 bulk SHA로 이미 바뀐다).
6. **12.7절 UE와 다른 점**에서 "A5j2a는 형식·크기가 다르면 거부" 줄을 지운다.

**시험(A5j2b)**:
- 공통 형식 표: 10 × 10 모든 쌍(교환 대칭 포함)이 위 표와 같다.
- 접기: 순서대로 접은 결과, 감마가 갈리면 RGBA32F·SRGB off, G16 선형 + RGBA8 sRGB → RGBA32F, Pow22 원소(같은 형식이면 byte 그대로, 다른 형식이면 Pow22로 풀기).
- 직접 경로: G8 sRGB → RGBA8 sRGB 256값 전부 복제, 선형 8 → 16비트 v·257, G16 → GA16.
- 풀기: R16F + RGBA16F → RGBA16F의 (v, 0, 0, 1), R32F → RGBA32F의 G·B = 0.
- 공개 함수 계약과 재표본 출력에만 해당하는 좁히는 변환(배열 경로에는 없다 — 공통 형식은 늘 조상): G8 ← RGBA32F(R만), half(Inf·RTNE). 값마다 기대 byte를 단언한다.
- 재표본 원소의 sRGB·알파 선형 부호화.
- 2DArray: 형식이 다른 원소(G8 + RGBA8 → RGBA8), 감마가 갈린 원소(→ RGBA32F 선형), 크기가 다른 원소(최대 X·Y, 재표본 값은 A5i `Resample`과 같은 식).
- CubeArray: 형식이 달라도 받고, 크기가 다르면 지금처럼 거부한다.
- 할당 실패 전 지점.
- UE 대조 golden(같은 원소 셋을 UE에서 묶은 결과 byte)은 빌드 때 더한다(화면 마일스톤 뒤).

**버린 대안**:
- 쿠킹 때 묶음 읽기(Build 의존): UE와 다르고, 쿠킹 키에 다른 에셋 원본이 들어가 SCC가 커진다.
- 정규화 hook에서 복사: 정규화 hook은 다른 패키지 bulk를 읽거나 자기 패키지에 bulk를 더할 수 없다(문맥이 객체 하나다).
- UE처럼 맞지 않는 마지막 원소를 조용히 빼기: 명령행에서는 사용자가 결과를 보지 못한다(비프로그래머 대상 — 오류로 알린다).

**시험(A5j2a)**:
- 2DArray·CubeArray: 원소 2·3개 복사(크기·형식·slice·bulk byte = 원소 byte 순서), 처음 만들기 설정 복사와 대입 칸 우선, 원본이 있던 배열은 설정을 바꾸지 않음, 빈 목록 → 빈 원본, null·원본 없음·크기·형식·sRGB·slice 다름 → 진단과 번호, 상한, 같은 목록 다시 대입 → 바뀐 원소 원본으로 다시 복사, 저장 뒤 다시 열어 원본 bulk가 남고 이전 bulk가 빠짐.
- sRGB 판정: legacy gamma 원소·G16 + SRGB on 원소는 sRGB가 아님(배열 srgb off·8비트 sRGB 원소와 섞으면 불일치).
- Volume: 기본 타일(정사각 4×4 타일 16장 아틀라스·비정사각·정수 나눗셈 경계 10×27·1×1·원본 없음), 명시 타일, 나머지 버림, 512 상한, 타일 0·음수 → 빈 원본 + `SourceCleared` 경고, 타일 순서 byte, asset-new 1×1 원본.
- 경계: 크기 한도·곱 넘침, numLayers ≠ 1, `--reset=sourceTextures`, 대문자 필드 이름(`SourceTextures=`), ImportRecord가 있는 배열에 대입 거부.
- 서비스: asset-new가 원본 재구성·정규화를 부름·실패하면 패키지 없음, asset-import는 부르지 않음, 원소 재임포트가 묶음 에셋을 다시 복사·저장(묶음 hook 실패면 재임포트 실패·둘 다 저장 안 함), 쿠킹이 복사한 원본으로 쿠킹됨(Build 의존 없음).

#### A5j3 보강 — 스트리밍 덩어리 4 KiB 정렬(2026-11-25 — 렌더 세션 rocks-6b 요구)

12.15절 3번 알림의 답으로 렌더 세션이 4 KiB를 렌더 쪽 요구로 굳혔다(RenderBase 6.5절 — 비버퍼·DirectStorage식 읽기 단위).
- 규칙: 텍스처 쿠킹 패키지의 bulk 정렬은 max(프로필 `bulkAlignment`(0이면 `PackageDefaultCookedBulkAlignment` 4096), `TextureStreamingBulkAlignment` 4096)이다. 스트리밍 mip bulk와 `tailBulk`의 시작 오프셋이 늘 4096 배수가 된다.
- 프로필 검증으로 막지 않는다. 다른 에셋은 프로필의 더 작은 정렬을 그대로 쓴다(렌더 세션 결정).
- 구현:
  - AssetCooker `CookProcessor`에 보호된 쓰기 함수 `WriteCookedPackage(context, minimumBulkAlignment)`를 둔다. 기본 `Cook`은 최소값 0으로 부른다.
  - `TextureCookProcessor`는 `TextureStreamingBulkAlignment`로 부른다.
  - 출력 byte가 바뀌므로(프로필 정렬이 4096보다 작을 때) 처리기 정체성 버전을 올린다(`TextureCookProcessorId` 2 → 3 — cookKey가 바뀌어 이전 쿠킹 결과를 재사용하지 않는다). 너겟(플랫폼 데이터 값)은 정렬과 무관해 `TextureNuggetProcessorId`는 그대로다.
- 시험: 프로필 `bulkAlignment` 16으로 쿠킹해도 텍스처 패키지의 bulk 시작 오프셋이 모두 4096 배수다(`TextureCook_Streaming`).
