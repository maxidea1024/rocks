### 12.17 텍스처 압축 단계 구현 세부(TC — 2026-11-26 착수 때 정함, 교차 검증 반영 개정 1, TC1 원본 대조 개정 2)

12.16절 형식 표를 구현하는 단계다. 착수는 사용자 결정(2026-11-26 — 화면 마일스톤 SM7·SM8에서 쿠킹 비압축 텍스처가 화면에 나온 뒤, 렌더 SM9와 병행)이다. 기준은 UE 5.8 Oodle 없는 경로다: BC1–5 `TextureFormatDXT`(NVTT 2.0.8 — Quality_Production), BC6H·BC7 `TextureFormatIntelISPCTexComp`(ISPC Texture Compressor), ASTC `TextureFormatASTC`(ARM astc-encoder). 형식 선택은 `GetDefaultTextureFormatName`(Texture.cpp 4201–4489), 채널 복제는 TextureDerivedData.cpp 876–883, 알파 판정은 TextureCompressorModule.cpp 2998–3080·TextureCompressorModule.h 388–400, 압축 입력 변환은 TextureFormatDXT.cpp 506이다.

개정 1(2026-11-26, 교차 검증 필수 15·권장 8 반영): 압축 입력을 형식 선택 뒤 RGBA8로 고정(F1), 가장자리 채움을 NVTT 주기 반복으로(F2), BC3 색의 알파 가중치(F3), BC4·BC5·BC3 알파를 NVTT `compressDXT5A`로(F4), cluster fit 선택을 닫힌식 대리 오차로(F5), 끝점 순서·같은 끝점 규칙(F6), 기준 디코더(F7), 품질 기준을 NVTT 원본 golden으로(F8 — UE 클론의 NVTT 2.0.8 원본, MIT), 결정성 규칙(F9), Android 4의 배수(F10)·Normalmap 대체(F11)·Displacementmap SRGB(F12)를 UE대로 12.16절 정정, 너겟 키에 형식·인코더 버전(F13), 단계 사이 동작(F14), 샘플링 검증 전제(F15 — 렌더 요청).

개정 2(2026-11-27, TC1 착수 때 NVTT 2.0.8 원본과 UE 빌드 설정을 직접 대조): TD1·TD2·TD7·TD9를 원본대로 고친다. 고친 이유는 12.17.4에 모았다.

#### 12.17.1 결정

- **TD1 BC1–BC5는 자체 구현 — NVTT 2.0.8 Production 경로를 옮긴다**(사용자 승인 2026-11-26: 자체 구현. 교차 검증 F8·F9: UE 클론 `Engine/Source/ThirdParty/nvTextureTools/nvTextureTools-2.0.8/src`에 원본이 있다 — MIT). 알고리즘·순서를 NVTT 스칼라(비 AVX2) 경로와 같게 옮기고, 같은 원본을 시험 probe로 빌드해 golden을 만든다(TD9). 외부 라이브러리로 링크하지 않는 이유: NVTT 2는 nvcore·nvimage·nvmath 전체를 끌고 오며 필요한 것은 블록 압축 경로 몇 파일이다. 기준 경로는 squish SSE 경로다. UE 라이브러리는 VS2015 프로젝트로 빌드되고 `__SSE2__`를 정의한다(`src/project/vc14/squish/squish.vcxproj` 240). Epic 수정은 FMA를 끄고 역수 근사 대신 나눗셈을 써서(squish/config.h 52–58 `SQUISH_USE_DIV 1`) SSE2 DLL과 AVX2 DLL의 출력이 같게 했다(같은 파일 60–72의 MD5 대조 — 텍스처 몇 장의 경험적 확인이다). 한계: golden은 UE가 배포한 `nvtt_64.dll`이 아니라 같은 원본을 같은 설정으로 clang 빌드한 probe다. UE 클론에는 Win64 DLL이 없다(GitDependencies가 받는다). AVX2 DLL은 squish만 `/arch:AVX2`로 빌드하고(squish.vcxproj 274·281·290 — nvtt.vcxproj에는 없다), 그때 MSVC가 스칼라 식을 FMA로 합쳤다면 공분산·투영 동률에서 갈릴 수 있다. 배포 DLL 두 개와의 직접 대조는 TC5에서 한다(DLL을 받아 같은 그림을 nvtt API로 압축하고, AVX2 DLL squish 함수에 `vfmadd`가 있는지 본다). Rocks는 그 SSE 경로의 lane 연산 순서를 스칼라 float로 옮긴다(12.17.4 1). squish의 비 SIMD 경로(weightedclusterfit.cpp 678–899)는 연산 순서가 달라 기준이 아니다.
- **TD2 인코더 알고리즘**(NVTT CompressDXT.cpp·QuickCompressDXT.cpp·squish 대응):
  - BC1 색: 중복 색을 가중치 1씩 묶은 집합(squish `ColourSet(rgba, 0, true)` minimal set — CompressDXT.cpp 224, colourset.cpp 35–)으로 시작한다. flags가 0이라 투명 texel 처리는 없고 같음 판정은 RGB만 본다. 단색 블록(알파 무시 — ColorBlock.cpp 114–128)은 최적 단색 표(SingleColorLookup `OMatch5`·`OMatch6` — 12.17.4 1)다. 그 밖은 `WeightedClusterFit`이다. 주축은 공분산의 power iteration 8회다. 시작 벡터는 노름이 가장 큰 행이고, 정규화는 세 성분의 max(절댓값 아님)로 나눈다(maths.cpp 64–77·84–107 SIMD판). max가 0이면 주축이 NaN이 되고 투영값 정렬이 texel 순서를 그대로 둔다. 결정적이므로 UE대로 둔다. 투영값은 안정 삽입 정렬이다(동률은 texel 순서). 4색 순서 분할(n개 집합이면 C(n+3, 3) — n = 16이면 969)·3색(C(n+2, 2) — 153)마다 닫힌식 대리 오차(양자화 격자 k/31·k/63, 이상적인 1/3 보간 — weightedclusterfit.cpp 441–676 SIMD판)를 구하고, 엄격한 `<`로 먼저 찾은 쪽을 남긴다. 3색 대 4색 비교도 같은 대리 오차다(4색은 3색 최선보다 엄격히 작을 때만 바꾼다 — colourfit.cpp 48–63). 정련은 NVTT처럼 하지 않는다. 3색 모드는 index 3(투명 검정)을 쓰지 않는다(UE `bSupportDXT1a = false`, TextureFormatDXT.cpp 155). 채널 가중치 1:1:1(231).
  - BC3: 색은 4색 모드만이고 texel 가중치는 (a + 1)/256이다(squish `kWeightColourByAlpha` — CompressDXT.cpp 353, colourset.cpp 63·96). 집합은 묶지 않은 16점이다(`ColourSet(rgba, kWeightColourByAlpha)` — minimal set 인자가 기본값 false라 같은 색도 따로 센다, colourset.cpp 103–124). 단색 색 블록도 단색 표를 쓴다(347–350). 알파는 아래 DXT5A다.
  - BC4·BC5(채널마다)·BC3 알파: NVTT `QuickCompress::compressDXT5A`(CompressDXT.cpp 343·421·458, QuickCompressDXT.cpp 537–578) — min·max를 정수 (max − min)/34만큼 안으로 당긴 뒤 최소제곱 반복 최대 8회. 인덱스 선택·오차는 NVTT 내부 팔레트(바닥 나눗셈 `(6a + b)/7` — BlockDXT.cpp 353–364)로 잰다. 블록 안 값이 모두 같으면 처음 끝점이 alpha0 = alpha1이어서 6값 모드 블록이 나온다(팔레트 0·1이 그 값이라 index 0). 최소제곱이 alpha0 = alpha1을 내면 index를 0으로 쓴 뒤 곧바로 인덱스를 다시 고르므로(computeAlphaIndices — 6값 팔레트), 그 블록이 채택되면 index 6·7(0·255)이 나올 수 있다. 그 밖은 8값 모드다(UE와 같다). NVTT `compressBC4`는 A 채널을 압축한다. UE가 BC4를 쓰는 설정은 Alpha뿐이고 ReplicateRed(A = R) 뒤이므로 R을 압축하는 것과 같다. Rocks는 R을 압축한다. BC5는 R·G를 따로 한다(`splatX`·`splatY`).
  - **끝점 순서(F6)**: 4색·8값은 e0 > e1(uint16 / uint8)로 쓴다. 양자화 뒤 끝점이 같으면 index를 모두 0으로 쓴다(squish colourblock.cpp 116–130). 3색은 e0 ≤ e1로 쓰고, 맞바꿀 때 index 0·1도 맞바꾼다. 같으면 그대로 둔다. 단색 표 블록은 index를 모두 2로 쓰고, col0 < col1이면 끝점을 맞바꾸고 index를 모두 3으로 쓴다. 같으면 index 2 그대로다(OptimalCompressDXT.cpp 189–204 — 이때 디코더는 3색 모드로 읽지만 index 2가 같은 색이다). 8값 알파의 같은 끝점은 최소제곱 단계에서 index를 0으로 쓰지만 다음 인덱스 계산이 덮어쓴다(QuickCompressDXT.cpp 368–374·560 — 위 BC4·BC5 항목).
- **TD3 압축 입력(F1)**: BC4는 R을 압축한다. NVTT·UE는 A를 압축하므로(CompressDXT.cpp 421) 둘이 같은 조건은 ReplicateRed(A = R)가 적용되고 sRGB가 꺼진 경우다(TextureDerivedData.cpp 880–882, TextureCompressorModule.cpp 3143). TC2는 BC4를 이 조건(Alpha 설정 — TD6)에서만 고른다. 형식 선택(12.17.2)을 12.13절 출력 단계(8번) 앞에 둔다. 고른 형식이 BC1–BC5·BC7이면 출력 단계는 원본 정밀도와 무관하게 RGBA8을 만든다(sRGB 텍스처는 색을 sRGB 부호화, 알파는 선형 — UE `CopyTo(BGRA8, GetDestGammaSpace())`, TextureFormatDXT.cpp 506). BC6H 입력은 RGBA16F다. 오차는 그 부호화 공간에서 잰다(UE와 같다). BC4 입력은 복제 뒤 R(TD6), BC5는 R·G다.
- **TD4 블록 가장자리(F2)**: 블록보다 작은 mip(하위 mip — 상위 mip은 TD8 규칙상 4의 배수)은 NVTT `ColorBlock` 주기 반복으로 채운다: 폭(높이) 1은 0,0,0,0, 2는 0,1,0,1, 3은 0,1,2,0(nvimage/ColorBlock.cpp 58–82 remainder 표). 채움 texel도 맞춤 가중치에 들어간다(NVTT와 같다). 블록 수는 ceil(w/4) × ceil(h/4)이다. UE 예외: UE `CompressImageUsingNVTT`(TextureFormatDXT.cpp 320–388)는 배치마다 높이를 `RowsPerBatch × 4`로 고정하므로, 높이가 4의 배수가 아니고 배치 조건이 맞으면(예: 1024 × 510, 64 × 1022 mip) 마지막 배치가 버퍼 밖 행을 읽어 마지막 블록 행이 remainder 반복이 아닌 값으로 채워진다(slice가 여럿이면 다음 slice의 행). Rocks는 NVTT 전체 그림 의미(remainder 반복)를 따르고, 그 경우만 UE와 byte가 다르다.
- **TD5 알파 판정**(UE `DetermineAlphaChannelTransparency` cpp 2998–3080, `GetTextureExpectsAlphaInPixelFormat` h 388–400): ForceNoAlpha면 불투명, 아니고 ForceAlpha면 투명, 아니면 원본 mip 0(모든 블록·slice)의 선형 최소 알파 ≤ 254.5/255면 투명(8비트 A ≠ 255와 같다). 원본에 알파 채널이 없으면 불투명이다. ReplicateRed 설정은 빨강 최솟값을 본다. UE는 ChromaKey·Bokeh LOD 그룹을 투명으로 강제하고 AdjustMin/MaxAlpha 등 보정을 판정 전에 적용한다 — 보정·ChromaKey는 Rocks에 아직 없으므로(12.4.1 계약) 그 단계를 구현할 때 이 판정에 넣는다. Bokeh 그룹은 TD8 비압축 조건이라 형식에 영향이 없다.
- **TD6 채널 복제 UE 대응 확정**(12.4.3 표 개정 — 그 표는 UE 5.6 공개 문서만으로 정했다): Grayscale·Alpha는 ReplicateRed(RGBA = R), Displacementmap·DistanceFieldFont는 ReplicateAlpha(RGBA = A — TextureCompressorModule.cpp 3151–3164)다. 지금 Displacementmap·DistanceFieldFont의 "빨강"은 UE와 다르다 — TC2에서 알파로 바꾼다. 원본에 알파가 없으면 결과는 1이다(UE 그대로 — UE에 경고가 없으므로 Rocks도 경고하지 않는다, R3).
- **TD7 기준 디코더(F7, 개정 2)**: 시험·PSNR은 golden 원본과 같은 식인 NVTT `BlockDXT` 디코더로 잰다(BlockDXT.cpp 36–140·343–380). 색: 565 확장 `(q << 3) | (q >> 2)`(6비트는 `(q << 2) | (q >> 4)`), col0 > col1이면 4색 (2a + b)/3·(a + 2b)/3, 아니면 3색 (a + b)/2와 투명 검정이다. 알파·BC4·BC5: alpha0 > alpha1이면 8값 ((7 − k)·a0 + k·a1)/7(k = 1…6, 바닥), 아니면 6값 ((5 − k)·a0 + k·a1)/5와 0·255다. D3D 명세는 보간 반올림을 정하지 않고 오차를 허용하므로(정확한 식이 없다) golden 원본의 식을 기준으로 둔다. 인코더의 index 선택은 이 디코더 값이 아니라 위 TD2의 NVTT 내부 계산을 따른다(색은 대리 오차, 알파는 같은 바닥 팔레트).
- **TD8 비압축 대체·마무리(F10·F11·F12·R2)**: UE `GetDefaultTextureFormatName` 순서를 그대로 쓴다(12.17.2). 4의 배수 규칙(상위 mip 한 변이 4 미만이거나 4의 배수 아님 → 비압축)은 Android(ASTC 재대응 전)에도 적용한다(Texture.cpp 4253–4263, AndroidTargetPlatformControls.cpp 509 — 12.16.2 "정렬" 문단을 정정한다). Normalmap 대체는 UE대로 `BGRA8Unorm`이다(4396–4434 — XGXR8은 DXT5n일 때만, 12.16.1 정정). SRGB를 막는 설정은 Alpha·Normalmap·Masks·HDR류뿐이고(772–777) G8 + SRGB → `BGRA8UnormSrgb`는 Displacementmap·DistanceFieldFont에도 적용한다(4444–4446 — 12.4.3·12.13 `TextureCompressionIgnoresSrgb`·12.16.1을 같이 맞춘다). G16 원본 + SRGB는 선형 `R16Unorm` 그대로다(TextureFormatUncompressed.cpp 230–232). 32F → 16F 대체(4450–4475)는 샘플링 검증 앞이다. 4채널 8비트 비압축 출력은 `BGRA8Unorm`(sRGB면 `BGRA8UnormSrgb`)이고 byte 순서는 B, G, R, A다.
- **TD9 결정성과 품질 기준(F8·F9)**:
  - 결정성: 블록 인코딩은 블록 하나의 순수 함수다. 블록 안 부동소수점은 12.13절 계산 정밀도 규칙(FMA 금지·연산 순서 고정·fast-math 금지)을 따르고, 정렬은 안정 정렬이다. 블록 범위 병렬은 제자리에 쓰므로 스레드 수와 무관하다. 이후 SIMD 최적화는 byte가 같아야 하고, 아니면 인코더 버전(TD10)을 올린다.
  - 품질(개정 2): UE 클론의 NVTT 2.0.8 원본을 SSE 경로(`__SSE2__`, AVX2 끔, FMA 끔 — UE 비 AVX2 DLL과 같은 설정)로 probe에 빌드해 시험 그림 셋의 압축 byte를 golden으로 기록한다(12.17.4 3). 전제: 부동소수 제어는 기본값이다(FTZ·DAZ 꺼짐, 가장 가까운 값으로 반올림 — 12.13절 계산 정밀도 규칙). TD1 한계(배포 DLL 직접 대조는 TC5)와 TD4 UE 예외를 함께 본다. 판정은 모든 블록의 byte 동일이다. 다르면 시험이 다른 블록 수와 첫 블록 위치를 보고하고 실패한다(PSNR 허용 범위로 넘기지 않는다 — 같은 연산 순서이므로 차이는 이식 오류다). 기준 디코더(TD7) PSNR은 측정 보고용이다(TC5). golden 생성 도구와 절차는 저장소에 둔다(Tools — probe 원본은 UE 클론 경로를 인자로 받는다, NVTT 원본을 저장소에 복사하지 않는다).
- **TD10 너겟 키·버전(F13)**: 고른 PixelFormat, 인코더 id(`RocksBc` 등)와 형식별 인코더 버전(UE `GetEncoderName`·`GetVersion` 대응)을 너겟 키에 넣는다. 형식은 프로필(backend 검증·32F 필터·압축 볼륨 지원·TC4 형식 계열)에 따라 달라지므로 12.14절 "프로필은 키에 넣지 않고 대상 형식은 빌드 버전으로 대신"을 이 둘로 바꾼다. TC2에서 출력 byte가 바뀌므로 `TextureBuildVersion`도 한 번 올린다. 이후 인코더만 바뀌면 그 형식 버전만 올린다.
- **TD11 단계 사이 동작(F14)**: TC2 뒤 TC3 전에는 BC7 설정이 `BGRA8Unorm(Srgb)` 대체 + 경고 `EncoderUnavailable`(detail = 원래 형식), HDR_Compressed는 12.16.1 대체 `RGBA16Float`(경고 같음)다. TC4 전 Android 프로필은 12.16.2 재대응 없이 TD8 비압축이다(BC를 Android에 내지 않는다 — 형식 계열 칸이 없으면 비압축). 12.4.3 끝의 "프로파일이 압축을 요구하면 UnsupportedSetting"은 TC2에서 지운다(압축을 하므로).
- **TD12 모든 backend 샘플링 검증(F15·R5)**: 고른 형식(대체 포함)은 프로필 `graphicsBackends`마다 샘플링 보장이어야 하고, 못 하면 다음 대체로, 마지막 대체는 backend별 보장 비압축(`RGBA8Unorm` 계열)이다. 경고 `PlatformFormatFallback`(detail = 원래 형식, 진단 related에 backend·텍스처 id). 판정 표는 렌더 세션이 GraphicsTypes 공개 표로 넣었다(2026-11-27 d4f5e56d8 — `GraphicsTypes/CookSampling.h`, 설계 Docs/Design/PixelFormat 7.1절). 키는 (Backend, GraphicsPlatform — Windows·Mac·Android)이고, 쿠킹 대상 조합은 D3D12·D3D11·Vulkan(Windows), Vulkan·OpenGL(Android), Metal(Mac)이다. 쓰는 법: `CookSamplingGuarantee(backends, platform, format)`으로 보장 caps를 얻어 `HasPixelFormatCaps(…, CookSamplingCaps)`로 판정하고, 마지막 대체는 `CookSamplingFallback(backends, platform, format[, required])`이다. 프로필 id는 `ParseGraphicsPlatformName`, backend 이름은 `ParseBackendName`으로 바꾼다. 쿠커는 GraphicsTypes만 링크한다. Vulkan BC는 이제 선택 기능이 아니다. 장치 생성이 표의 "엔진 요구" 칸(예: Windows Vulkan은 BC·16비트 unorm·32F 필터, Android Vulkan은 ASTC LDR·ETC2)과 대조하고, 칸이 하나라도 없으면 장치를 받지 않는다(UE와 같다). TC2가 이 표로 검증을 켠다(12.17.2 8번).
- **TD13 외부 인코더(TC3·TC4 — 착수 때 세부, R8)**: BC6H·BC7은 ISPC Texture Compressor(MIT) 원본을 ThirdParty로 들여와 빌드한다(커널 컴파일용 ISPC 컴파일러는 LLVM처럼 toolchains에 받는 도구다 — 미리 만든 ispc_texcomp 라이브러리는 쓰지 않는다, 12.17.6). ASTC는 ARM astc-encoder(Apache-2.0 — C++ 예외를 쓰지 않는 빌드 설정 확인). 품질 설정은 UE 그 모듈을 따른다. BC6H·BC7은 고정 basic 프로필이고(TextureFormatIntelISPCTexComp.cpp 895–915 — CompressionQuality를 보지 않는다), CompressionQuality ↔ astcenc preset은 ASTC만이다(TC3 리뷰 정정 2026-11-27).

#### 12.17.2 형식 선택(TC2 — UE `GetDefaultTextureFormatName` 순서의 코드화)

입력: 유효 CompressionSettings·SRGB(TD8로 막힌 설정은 끔)·ForceAlpha·ForceNoAlpha·CompressionNone·LOD 그룹·차원, TD5 알파, 원본 형식(회색·16비트·float), 상위 mip 크기, 프로필(backend 목록·norm16·32F 필터·압축 볼륨·형식 계열). 순서:
1. 계약 밖 설정(LQ 등)은 지금처럼 `InvalidSetting`(12.8절).
2. 비압축 강제(CompressionNone, LOD 그룹 ColorLookupTable·Bokeh·IESLightProfile, 압축 볼륨 미지원 대상의 Volume)면 비압축 형식.
3. 12.16.1 표의 형식(AutoDXT = TD5 알파로 BC1·BC3, sRGB 짝 BC1·BC3·BC7).
4. BC이고 상위 mip 한 변이 4 미만이거나 4의 배수가 아니면 비압축(TD8 — 모든 플랫폼).
5. UE 마무리: G8 + SRGB → `BGRA8UnormSrgb`, 32F → 16F(필터·플랫폼).
6. TD11 단계 사이 대체(인코더 없음).
7. Android면 12.16.2 재대응(TC4 — 12.17.8 6, 형식 계열은 플랫폼으로 정한다).
8. TD12 샘플링 검증(표가 있을 때).

swizzle 칸(TexturePlatformData)은 12.16.4 (가)대로 sampler type 계약 데이터이고, UE처럼 형식이 아니라 CompressionSettings로 정한다(MaterialExpressionUtils.cpp 32–48 — R1): Grayscale·Alpha·DistanceFieldFont `rrrr`, Displacementmap `r001`, Normalmap `rg01`(BC5·대체 BGRA8 모두 — 셰이더가 Z 복원), 그 밖 항등. 12.13절이 회색 sRGB를 데이터에 복제한 뒤 항등으로 두는 지금 동작은 TC2에서 이 규칙으로 바꾼다(12.16.4 (가) — 데이터는 BGRA8 그대로, swizzle 칸만).

#### 12.17.4 TC1 구현 세부(2026-11-27)

1. **연산 순서(TD1·TD9)**: squish SSE 경로의 `Vec4` 연산(simd_sse.h)을 lane마다 float 한 번씩의 스칼라 연산으로 옮긴다. IEEE 단정밀도 연산은 SSE와 스칼라가 같은 값을 내므로, 연산의 종류와 순서만 같으면 byte가 같다. 옮길 때 지키는 의미는 다음과 같다.
   - `MultiplyAdd(a, b, c)` = a·b 뒤 + c(두 번 반올림 — FMA 끔), `NegativeMultiplySubtract(a, b, c)` = c − a·b, `Reciprocal(v)` = 1/v 나눗셈(`SQUISH_USE_DIV`).
   - `Max(x, y)` = x > y ? x : y, `Min(x, y)` = x < y ? x : y(`_mm_max_ps`·`_mm_min_ps` — NaN이면 둘째 값).
   - `Truncate(v)` = int32 절사 뒤 float(`_mm_cvttps_epi32` — NaN·범위 밖은 INT32_MIN). AVX2 DLL은 floor를 쓰지만 0 이상 값에서는 같고 NaN 후보는 어느 쪽이든 이기지 못한다.
   - `CompareAnyLessThan` = 네 lane 중 하나라도 `<`. 오차는 세 lane 합을 모든 lane에 펴므로 첫 lane 비교와 같다.
   - 점 lane: (R, G, B, 1)/255 × 가중치(W lane = 가중치). 공분산·주축 시작·투영은 squish `Vec3` 스칼라 식 그대로다(`/=` float는 역수 곱 — maths.h 107–113, `Dot`은 x·x + y·y + z·z 왼쪽부터).
   - NVTT 알파 최소제곱의 `uint(min(max(a, 0), 255))`는 NaN이면 0이다(nv::max·nv::min은 `<` 비교로 NaN을 그대로 넘기고, x64의 float → uint 변환은 64비트 절사의 하위 32비트라 NaN이 0이 된다). Rocks는 이 결과를 명시 코드로 쓴다(C++ 미정의 동작에 기대지 않는다).
   - 단색 표는 상수 표(`Private/TextureBlockTables.h` — NVTT `OMatch5`·`OMatch6`과 같은 값)로 둔다. 컴파일 때 만들기에는 반복이 너무 많다(256 × 64 × 64). 시험이 `PrepareOptTable`(SingleColorLookup.h 주석 — float 오차 + 0.03·|max − min|, 엄격 `<`)로 다시 만들어 golden의 NVTT 표와 같은지, 인코더의 단색 끝점이 그 값인지 본다. 보간은 주석 본문의 `maxe + Mul8Bit(mine − maxe, 0x55)`가 아니라 같은 주석에 정의만 된 `Lerp13`(= (2·max + min)/3, 정수)이다. 주석 본문 식으로는 5비트 표 70항목이 다르고, Lerp13으로는 두 표 모두 같다(2026-11-27 golden 대조). NVTT 표는 Lerp13으로 만든 것이다.
2. **공개 API**(TextureTools `Public/TextureTools/TextureBlockEncode.h`):
   - `enum class TextureBlockFormat : uint8 { Bc1, Bc3, Bc4, Bc5 }` — TC2가 PixelFormat(sRGB 짝 포함)을 이 값으로 바꾼다. sRGB는 인코딩에 영향이 없다(UE도 감마는 입력 byte로만 들어간다).
   - `TextureBlockBytes(format)`(8·16·8·16), `TextureBlockOutputBytes(format, sizeX, sizeY, numSlices)` → `Result<uint64>`. 크기 0은 InvalidArgument, 곱이 넘치면 CapacityExceeded다. 블록 수는 slice마다 ceil(sizeX/4) × ceil(sizeY/4)이다.
   - `TextureBlockImage { Span<const uint8> rgba; uint32 sizeX, sizeY, numSlices = 1; usize rowPitch = 0; usize slicePitch = 0; }` — 입력은 RGBA8(R, G, B, A byte 순서)이다. pitch 0은 빽빽함(sizeX·4, rowPitch·sizeY)이다.
   - `EncodeTextureBlocks(format, image, Span<uint8> out)` → `Result<void>`. 출력은 slice 순, 블록 행 순, 블록 열 순이다. 할당은 없다(블록마다 스택 64 byte). 오류: 크기 0·rowPitch가 행보다 작음·slicePitch가 slice가 닿는 byte(rowPitch × (sizeY − 1) + 행 byte)보다 작음·입력 byte 부족·out 크기가 `TextureBlockOutputBytes`와 다름은 InvalidArgument, 출력 크기나 pitch로 계산한 입력 범위가 uint64를 넘으면 CapacityExceeded다. 실패하면 out 내용은 정하지 않는다.
   - `EncodeTextureBlock(format, const uint8 (&texels)[64], uint8* out)` — 4×4 RGBA texel 한 블록(행 우선)이다. 가장자리 채움(TD4)은 `EncodeTextureBlocks`가 하고 이 함수는 받은 16 texel을 그대로 쓴다.
   - `DecodeTextureBlock(format, const uint8* block, uint8 (&texels)[64])` — TD7 기준 디코더다. BC1·BC3은 RGBA, BC4는 (R, 0, 0, 255), BC5는 (R, G, 0, 255)를 쓴다.
   - `RocksBcEncoderVersion`(1) — TD10의 인코더 버전이다(키 연결은 TC2).
3. **golden 도구**(`Tools/NvttGolden`):
   - `NvttGoldenProbe.cpp`가 UE 클론의 NVTT 원본(squish colourset·colourfit·weightedclusterfit·colourblock·maths, nvimage ColorBlock·BlockDXT·Image, nvtt OptimalCompressDXT·QuickCompressDXT)을 한 번역 단위로 묶어 빌드한다. 압축은 `SlowCompressor`와 같은 순서로 블록마다 부른다(BC4는 A = R로 만든 블록, BC5는 `splatX`·`splatY`). 가장자리 블록은 NVTT `ColorBlock::init`(remainder 표)을 그대로 쓴다.
   - `make_golden.py <UE 클론 경로>`가 LLVM 툴체인 clang으로 probe를 빌드해 실행하고 `Engine/Source/Developer/TextureTools/Tests/Fixtures/NvttGolden/NvttBlockGolden.bin`을 쓴다. NVTT 원본은 저장소에 들어오지 않는다.
   - 시험 그림은 probe와 시험이 같은 생성기 헤더(`TextureTools/Tests/BlockGoldenImages.h` — Rocks·표준 헤더 없이 정수식만)를 include해 만든다. golden 파일에 그림별 입력 해시를 넣어 생성기가 바뀌면 시험이 먼저 실패한다. 그림: 선형 그라디언트, 방사형, 값 노이즈(부드러운 자연 그림 대용), 백색 노이즈, 색 경계(체커), 알파 경계(알파 계단 + 색 그라디언트), 노멀(구면 RG), 두 색, 한 texel만 다른 블록, 회색조, 단색 — 각 32×32. 가장자리: (w, h) ∈ {1, 2, 3, 5, 6, 7, 9}²의 일부 조합. 무작위: 128×128 블록 단위 분포 셋(균일, 좁은 범위, 두 무리). 드문 경로(리뷰 반영): 256×256 넷 — 값 차이 0–2(565 같은 끝점), 블록마다 2–4색 + 섞인 알파, 0·255 근처 알파(6값 붕괴·index 6/7), 한 texel의 한 채널만 1 다름(거의 퇴화한 공분산). 이 넷은 golden에 출력 해시만 둔다.
   - 파일 형식(버전 2): 머리(magic `RNVG`, 버전, 항목 수), 단색 표(OMatch5·OMatch6 각 512 byte), 항목마다(이름, 형식, 크기, 입력 FNV-1a 64, NVTT 디코드 FNV-1a 64 — 블록마다 64 byte를 출력 순서로 이어서, 출력 FNV-1a 64, 출력 byte 수와 byte — 해시 전용 항목은 0). 리틀 엔디언이다. 해시는 어긋남 검출용이라 FNV로 충분하다(probe에 SHA-256을 넣지 않는다).
   - 사진 조각은 넣지 않는다(probe에 이미지 디코더를 들이지 않는다 — 값 노이즈와 무작위 분포가 대신한다). TC5 측정에서 TestContent 실제 텍스처로 PSNR을 잰다.
4. **시험**(EngineTests `TextureTools/Tests/TextureBlockEncodeTests.cpp`):
   - golden: 모든 항목·형식의 byte 동일(다르면 다른 블록 수·첫 위치 보고 — 해시 전용 항목은 출력 해시), 기준 디코더 결과의 해시가 NVTT 디코드와 같음, 단색 표가 NVTT 표와 같음. 경로 커버리지: BC1 3색 승리(col0 < col1)·BC3 4색 같은 끝점(index 0)·알파 최소제곱 채택(처음 inset 끝점과 다름) 블록이 각각 하나 이상이고, BC3 색 블록마다 col0 ≥ col1·같은 끝점이면 index 0 또는 단색 index 2다. 6값 모드 index 6/7 블록 수는 보고한다.
   - 규칙: 단색 블록 끝점(표 값·index 2/3 규칙), 4색 같은 끝점이면 index 0, 3색 맞바꿈, 6값 알파(값이 모두 같을 때), BC4 = BC3 알파 블록(같은 채널 값이면 같은 8 byte), BC5 = R·G 각각 BC4.
   - 가장자리: 1–9 크기에서 remainder 채움과 블록 수, pitch·slice 입력(빽빽함과 같은 결과).
   - 결정성: 같은 입력 두 번, 다른 출력 버퍼에서 같은 byte. 주축 성분 부호가 섞이는 블록(음의 상관 — golden `negative-correlation`)도 golden과 같다. 주축 max가 0이 되는 NaN 경로는 단색이 아닌 블록에서는 정확한 산술로는 생기지 않는다(시작 행 i에 대해 (Mᵏeᵢ)ᵢ = ‖M^{k/2}eᵢ‖² > 0 — M은 양의 준정부호). 반올림이 끼면 이론상 깨질 수 있어 코드는 UE 의미(NaN이면 순서 그대로) 그대로 둔다.
   - 인자 오류: 크기 0, 입력 부족, pitch 부족, out 크기 다름, 출력 크기 넘침.

#### 12.17.5 TC2 구현 세부(2026-11-27 — UE `GetDefaultTextureFormatName` 원본 대조)

UE 원본(Texture.cpp 4201–4489, TextureDerivedData.cpp 867–894, TextureCompressorModule.cpp 2998–3080·3986–4040·4695–4708, TextureFormatDXT.cpp 506)을 다시 읽고 정한 것이다. 12.4.3절 출력 표와 12.16.1절 표에서 UE와 다른 칸은 이 절이 우선한다(아래 6번에서 그 절들을 고친다).

1. **단계 나눔**: TC2a 형식 선택 순수 함수와 시험 → TC2b 빌드 연결(채널 복제·알파 판정·인코딩·빌드 설정 칸·`TextureBuildVersion` 3) → TC2c 쿠킹 연결(프로필 대상·너겟 키·적중 검증·경고·TestContent 재쿠킹·렌더 알림). 단계마다 리뷰어 하나다.
2. **형식 선택(TC2a — `TextureTools/TextureFormatSelect.h`)**: `SelectTextureFormat(request, target, alphaTransparent)` → `TextureFormatChoice`. 입력은 다음과 같다.
   - request: CompressionSettings, 텍스처 srgb, 원본 형식, 차원, LOD 그룹, compressionNone·compressionNoAlpha·compressionForceAlpha, 샘플러 필터가 Point인지, 쿠킹된 상위 mip 크기.
   - target: GraphicsPlatform, backend 비트 집합(0이면 TD12 검증을 끈다 — 프로필 없는 빌드·시험), norm16 지원.
   - 결과: PixelFormat, 출력 sRGB, swizzle, 인코딩(비압축·Bc1·Bc3·Bc4·Bc5), 채널 복제(없음·Red·Alpha), 경고(최대 둘: EncoderUnavailable·PlatformFormatFallback — detail = 원래 형식 번호).
   - `TextureFormatDependsOnAlpha(request, target)`는 알파 둘에 대한 결과가 다른지다(AutoDXT일 때만 참). 빌드는 이때만 알파를 잰다. (TC3에서 `TextureFormatNeedsAlpha`로 바뀜 — BC7 프로필도 본다, 12.17.6 9.)
   - 순서(UE 그대로):
     1. sRGB 막음: Alpha·Normalmap·Masks·HDR류(HDR·HDR_F32·HDR_Compressed·HalfFloat·SingleFloat — UE `IsHDR`)와 ColorLookupTable 그룹이면 srgb를 끈다(Texture.cpp 759–777). float 원본의 float 출력도 sRGB가 아니다(12.13 그대로).
     2. 비압축 강제: compressionNone, EditorIcon, LOD 그룹 ColorLookupTable·Bokeh·IESLightProfile, 압축 볼륨을 못 하는 대상의 Volume(데스크톱은 된다), 상위 mip 한 변이 4 미만이거나 4의 배수가 아님(Z는 보지 않는다). Availability CPU인 Texture2D도 비압축이다(Resolve가 compressionNone을 켠다). UE는 GPU 자리표시를 BC1로 쿠킹하고 CPU 사본을 따로 두지만(Texture.cpp 4481–4484), Rocks는 플랫폼 데이터가 CPU 사본이라 읽을 수 있어야 한다 — UE와 다른 점(리뷰 반영 2026-11-27).
     3. 이름 표: HDR → RGBA16F, HDR_F32 → RGBA32F, Normalmap → BC5, VectorDisplacementmap → BGRA8, Grayscale·Displacementmap → 원본 G16이면 G16, 아니면 G8, Alpha → BC4, DistanceFieldFont → G8, HDR_Compressed → BC6H, BC7 → BC7, HalfFloat → R16F, SingleFloat → R32F, Default·Masks → compressionNoAlpha면 BC1, 아니면 AutoDXT(알파로 BC1·BC3, ForceNoAlpha가 ForceAlpha보다 먼저 — `GetTextureExpectsAlphaInPixelFormat`). LQ는 받지 않는다(12.8절).
     4. 압축 이름인데 비압축 강제이거나 이름이 없으면(EditorIcon): HDR_Compressed 또는 float 원본이면 RGBA16F, 원본 G16 + Grayscale·Displacementmap이면 G16, 원본 G8 + 같은 둘이면 G8, 그 밖은 BGRA8이다(Normalmap 포함 — DXT5n을 두지 않으므로 XGXR8 경로가 없다).
     5. 마무리: G8 + sRGB → BGRA8 sRGB(UE GrayscaleSRGB 꺼짐). R32F·RGBA32F는 필터가 Point가 아니고 대상이 32F 선형 필터를 보장하지 않으면 R16F·RGBA16F다. 대상 판정은 쿠킹 보장 표(`CookSamplingGuarantee`의 Filterable)이고, 검증을 끈 대상(backend 0)은 플랫폼 기본이다(Windows·Mac 됨, Android 안 됨 — UE `bSupportFilteredFloat32Textures`, AndroidTargetPlatformControls.cpp 500). G16은 norm16을 못 하면 R16F다(12.14절 그대로 — 결과의 `norm16Remapped`가 참이고 빌드가 0…1로 자른다. 사용자가 고른 HalfFloat의 R16F는 자르지 않는다).
     6. 플랫폼: Android는 TC4 전까지 BC를 내지 않는다. 압축 이름은 4번 비압축 대체로 바꾸고 경고하지 않는다(TD11). TC4부터는 12.17.8 6의 ASTC·EAC 재대응이다.
     7. 단계 사이 대체(TD11 — TC3에서 없어짐, 12.17.6 6·9): BC7 → BGRA8(sRGB 짝), BC6H → RGBA16F, 경고 EncoderUnavailable(detail = 원래 형식). BC6H 대체만 알파를 1로 쓴다(`opaqueAlpha` — BC6H에는 알파가 없다). HDR_Compressed의 다른 RGBA16F(비압축 강제)는 UE처럼 원본 알파를 지킨다(TextureFormatUncompressed.cpp 293).
     8. 샘플링 검증(TD12): 필요한 능력은 Point 필터면 Sampled, 아니면 Sampled | Filterable이다. 보장이 모자라면 `CookSamplingFallback`(그 능력)으로 바꾸고 경고 PlatformFormatFallback(detail = 바꾸기 전 형식)이다. 대체가 Unknown이면 InvalidSetting 실패다(쿠킹 대상 조합만 든 프로필에서는 생기지 않는다).
   - PixelFormat 대응: G8 → R8Unorm, G16 → R16Unorm, BGRA8 → BGRA8Unorm(sRGB면 BGRA8UnormSrgb), RGBA16F → RGBA16Float, RGBA32F → RGBA32Float, R16F → R16Float, R32F → R32Float, BC1·BC3·BC7 → `…Unorm`(sRGB면 `…UnormSrgb`), BC4 → BC4Unorm, BC5 → BC5Unorm, BC6H → BC6HUfloat. sRGB 출력은 그 짝을 고른 경우만이다(R16·float·BC4·BC5·BC6H는 sRGB가 아니고, 막힌 설정이 아닌데 sRGB를 잃으면 SrgbIgnored 경고 — 12.13 규칙 유지).
   - swizzle(12.17.2 — sampler type 계약): Grayscale·Alpha·DistanceFieldFont `rrrr`, Displacementmap `r001`, Normalmap `rg01`, 그 밖 항등. 형식과 무관하게 CompressionSettings로만 정한다(BGRA8 대체도 같다).
   - 채널 복제(TD6): Grayscale·Alpha는 Red(RGBA = R), Displacementmap·DistanceFieldFont는 Alpha(RGBA = A)다.
3. **빌드 연결(TC2b)**:
   - `TextureBuildSettings`에 칸을 더한다: compressionNone·compressionNoAlpha·compressionForceAlpha(쿠킹 facts에서 옮김), lodGroup, samplerPointFilter, cookPlatform(GraphicsPlatform 값), cookBackends(Backend 비트 집합 — 0이면 검증 끔). 리플렉션 칸이라 너겟 키에 그대로 들어간다(TD10의 "프로필에 따라 다른 형식"이 키에 들어간다).
   - `TextureBuildTopMipSize(settings)`: BuildTexture와 같은 크기 계산(PowerOfTwoMode·Resize·최대 크기·쿠킹 편향 뒤 상위 mip)을 픽셀 없이 한다. 형식 선택의 4의 배수 판정이 쓴다(UE `GetBuiltTextureSize`).
   - BuildTexture 순서: … NormalizeNormals → 채널 복제(모든 mip, 선형 float — UE 4695–4708) → 알파 판정(`TextureFormatDependsOnAlpha`일 때만 — TC3부터 `TextureFormatNeedsAlpha` — 디코딩한 원본의 모든 slice·깊이, PowerOfTwoMode·크기 조정 전의 최소 알파 ≤ 254.5/255, UE 주 경로의 원본 층 ColorMin·ColorMax 판정(TextureDerivedData.cpp 886–894 → DetermineAlphaChannelTransparency)과 같은 대상이다. 그래서 불투명 원본의 반투명 채움 색은 알파로 보지 않는다(리뷰 반영 2026-11-27 — 처음에는 mip 0으로 쟀다)) → 형식 선택 → 출력 부호화.
   - 출력 부호화: 비압축은 형식의 byte 순서다(BGRA8은 B, G, R, A이고 sRGB면 색은 sRGB, 알파는 선형이다). R8·R16은 R 채널이다(복제 뒤라 Displacementmap은 원본 A다). BC는 RGBA8(같은 부호화)을 만들고 `EncodeTextureBlocks`로 압축한다. Volume 깊이와 slice는 블록 slice로 넘긴다.
   - `TextureBuildOutput(settings, alphaTransparent)`가 빌드 결과와 같은 형식을 낸다(적중 검증용). `TextureBuildResult`에 `alphaTransparent`를 더한다. 형식 경고는 빌드 경고에 더한다(TextureBuildMaxWarnings 4).
   - `TextureBuildVersion`을 3으로 올린다(출력 byte가 바뀐다).
4. **쿠킹 연결(TC2c)**:
   - 프로필 → 대상: `ParseGraphicsPlatformName(profile.id)`, `graphicsBackends`마다 `ParseBackendName`. 모르는 이름은 프로필 검증이 이미 거른다(그래도 실패하면 InvalidSetting).
   - 너겟 키: 리플렉션 설정 뒤에 두 후보 형식(알파 없음·있음)마다 형식 번호와 인코더 버전(BC면 `RocksBcEncoderVersion`, 비압축이면 0)을 쓴다. 대상 칸(cookPlatform·cookBackends·norm16Supported·samplerPointFilter)은 형식으로만 결과에 닿으므로 키 사본에서 고정하고 후보 형식이 대신한다. 출력이 같은 프로필은 너겟을 같이 쓴다(전의 norm16 정규화도 이 규칙에 들어간다). lodGroup도 형식 선택이 보는 ColorLookupTable·Bokeh·IESLightProfile이 아니면 고정한다. 그룹 값(mip 설정·편향 등)은 이미 다른 칸에 풀려 있다. BC6H·BC7 인코더(TC3)가 들어오면 그 버전이 같은 자리에 들어간다.
   - 적중 검증: 머리의 형식이 두 후보 중 하나와 같아야 한다. 같은 후보의 알파로 형식 경고를 다시 계산한다(적중·미적중 경고가 같다). 쿠킹 경고(`CookDiagnostic`)는 형식 경고의 detail(대체 전 PixelFormat 번호)을 `setting` 칸에 둔다.
   - 쿠킹 데이터 판정: `TexturePlatformData::Validate`는 블록 압축 색(BC·ASTC·ETC2)도 받는다(전에는 비압축 색만 받았다).
   - TestContent(Sandbox) 재쿠킹과 렌더 세션 알림(BC·BGRA8·swizzle 변경, 업로드 pitch는 블록 행 — PixelFormat 블록 크기).
5. **시험**:
   - TC2a: CompressionSettings 15종 × 알파 둘 × sRGB 둘 × 원본 종류(G8·G16·BGRA8·RGBA16·RGBA16F·RGBA32F) × 플랫폼(Windows·Android) 표. 비압축 강제 조건마다(compressionNone·EditorIcon·그룹 셋·크기 3·5·2·6 등), 32F 필터 대체(Point·Bilinear × 보장 유무), norm16 대체, TD11 경고, TD12 대체(D3D11·Vulkan·OpenGL Android 조합 — 렌더 표의 실제 값), swizzle·복제 칸.
   - TC2b: 복제 결과 byte(Grayscale RGBA = R, Displacementmap R8 = 원본 A), 알파 판정 경계(254·255, 16비트 65406·65407, float), AutoDXT BC1·BC3 선택, BGRA8 byte 순서와 sRGB, BC 출력이 `EncodeTextureBlocks` 결과와 같음, Volume·Array slice, 상위 mip 크기 함수 = 빌드 결과 크기(PowerOfTwoMode·Resize·최대 크기·편향 조합).
   - TC2c: 키가 backend 집합·플랫폼·인코더 버전에 따라 달라짐, 적중 검증 두 후보·경고 재계산, verify, TestContent 재쿠킹 결과.
6. **같이 고치는 문서**:
   - 12.4.3절 출력 표: 이 절 2번이 대신한다. 끝의 "프로파일이 압축을 요구하면 UnsupportedSetting"은 지운다.
   - 12.13절 `TextureCompressionIgnoresSrgb`: UE `bPreventSRGB` 목록(Alpha·Normalmap·Masks·HDR류)으로 바꾼다. Displacementmap·VectorDisplacementmap·DistanceFieldFont는 sRGB를 지킨다.
   - 12.16.1절 표: Default·Masks·Normalmap의 비압축 대체는 BGRA8(회색 원본도 — Grayscale·Displacementmap만 G8·G16), RGBA16 원본의 비압축 대체도 BGRA8(UE와 같다 — 16비트 정밀도를 지키지 않는다). Rocks에 RG8·RGBA16Unorm 출력은 없어진다.

#### 12.17.6 TC3 구현 세부(2026-11-27 — BC6H·BC7)

사용자 결정(2026-11-27): ISPC Texture Compressor를 들여와 결정적으로 빌드한다. UE는 `--target=sse2,sse4,avx,avx2 --opt=fast-math`로 빌드한 DLL을 써서 BC6H·BC7 byte가 호스트 CPU마다 다를 수 있다. Rocks는 아키텍처당 타깃 하나이고 fast-math·FMA를 끈다(빌드 시스템 — [BuildTargets 3.12절](../../BuildTargets/03-Design/03.12-IspcSources.ko.md) BD45–BD50). 그래서 UE와는 byte가 아니라 품질(PSNR)로 대조한다.

1. **단계**: TC3a 빌드 시스템 ISPC 지원(BuildTargets BS12) → TC3b ThirdParty 반입·인코더 API·빌드·쿠킹 연결 → TC3c 검증 도구(아키텍처 간 결정성·UE DLL PSNR 대조). 단계마다 리뷰어 하나다.
2. **원본(TC3b)**: ThirdParty `IspcTextureCompressor`다. 기준은 UE 클론의 `Engine/Source/ThirdParty/Intel/ISPCTexComp/ISPCTextureCompressor-14d998c`이고, ThirdParty.json의 출처는 upstream(GameTechDev/ISPCTextureCompressor — 2023-09부터 관리 중단)의 같은 커밋 archive(sha256)다. 구현 때 UE 사본과 upstream을 diff해 Epic 수정을 확인하고, 있으면 `Rocks.patch`로 기록한다. 들이는 파일은 `kernel.ispc`, `ispc_texcomp.h`, `ispc_texcomp.cpp`(BC6H·BC7 진입점과 프로필 — ASTC 진입점은 빼거나 컴파일하지 않는다, ASTC는 TC4 astcenc), `license.txt`(MIT)다. 고정 ISPC(1.32.x)에서 컴파일되지 않는 곳은 최소 수정을 `Rocks.patch`로 둔다(upstream 이슈에 보고된 1.14+ 수정 — 중복 typedef 등).
3. **커널 연산 확인과 결정성 범위**(TC3 리뷰 반영): `kernel.ispc`는 나눗셈 `1.0f/x`와 `sqrt`를 쓴다(`rcp`·`rsqrt` 호출은 주석 26–37). 초월 함수나 gang 폭(`programCount`)에 달린 코드는 없고, `foreach`가 블록마다 독립이다(lane 사이 reduce·shuffle이 없다). fast-math가 없으면 정확한 IEEE 연산이고, `--opt=disable-fma`로 곱셈·덧셈 합치기를 막는다.
   - x86 안(sse2·sse4·avx2): `maxps`·`vmaxps`, `cvttps2dq`의 의미가 같아 byte가 같다고 본다(TC3c 확인).
   - x86 ↔ Arm64: IEEE 연산만으로는 같지 않을 수 있다. NEON min/max는 NaN을 퍼뜨리고(FMAX·FMIN) x86은 둘째 피연산자를 돌려준다. NaN·범위 밖 float → int 변환도 x86은 INT_MIN, ARM은 포화 또는 0이다. 부호 있는 0의 처리도 다를 수 있다. 커널은 eps(942–946)와 `+0.001f`(1604)로 이런 값을 막아 실제로 갈릴 일은 드물지만, 퇴화 블록 시험(단색, 두 값, HDR 0·65504, NaN·±Inf·−0 입력 — 정리 뒤 값)으로 확인한다. 다르면 원인을 찾아 커널 앞 정리나 `Rocks.patch`로 고친다(인코더 버전을 아키텍처별로 나누지 않는다).
   - 부동소수 제어: 커널은 부르는 쪽의 FTZ·DAZ 상태를 따른다. wrapper가 호출 앞뒤로 MXCSR·FPCR을 기본(FTZ·DAZ 끔, 가장 가까운 값 반올림)으로 저장·복원한다(ISPC `reset-ftz-daz`는 쓰지 않는다).
   - CPU 확인: x64 단일 타깃 sse4는 SSE4.1·4.2가 있어야 한다. wrapper가 처음 쓸 때 CPUID를 보고 없으면 Unsupported로 실패한다(잘못된 명령으로 죽지 않는다).
4. **UE 처리 그대로(TextureFormatIntelISPCTexComp.cpp 860–925·775–820, ImageCore.cpp 1559–1577)**:
   - BC7: 입력은 BGRA8(sRGB 텍스처는 색 sRGB — `GetDestGammaSpace`)을 R·B를 바꿔 RGBA로 넘긴다. 프로필은 알파가 있으면 `GetProfile_alpha_basic`, 없으면 `GetProfile_basic`이다. 알파는 TD5 판정(원본 최소 알파 ≤ 254.5/255, ForceNoAlpha·ForceAlpha 우선)이다. 그래서 BC7도 알파를 잰다(형식은 같고 프로필만 바뀐다 — 원본 해시가 키에 있으므로 키는 그대로 맞다). 12.17.5의 `TextureFormatDependsOnAlpha`는 `TextureFormatNeedsAlpha`(형식이나 인코더 프로필이 알파에 달렸는지 — AutoDXT·BC7)로 넓힌다. UE는 원본 색 정보가 없으면 basic으로 떨어지지만 Rocks는 늘 재므로 결과는 같다. 쓰지 않게 되는 `TextureFormatChoice::opaqueAlpha`는 지운다.
   - BC6H: RGBA16F 선형 입력의 R·G·B를 `GetClampedNonNegativeAndFinite`(NaN·음수 → 0, +Inf → 65504)로 고치고 알파를 1로 둔 뒤 `GetProfile_bc6h_basic`으로 압축한다. 결과는 `BC6HUfloat`다.
   - 가장자리: 블록 배수가 아닌 모든 mip(4 미만뿐 아니라 12 → 6, 20 → 10 → 5 같은 중간 mip도)에서 마지막 열·행을 복제해 채운다(`PadImageToBlockSize` — BC1–5의 NVTT 주기 반복(TD4)과 다르다). TD4의 remainder 표는 BC1–5에만 해당한다.
   - float32 → half 변환은 가장 가까운 짝수로 반올림한다(RTNE — UE `FFloat16::Set`).
5. **API(TextureBlockEncode.h)**: `TextureBlockFormat`에 `Bc6h`·`Bc7`을 더한다. `TextureBlockSourceTexelBytes(format)`는 BC6H 8(RGBA16F), 그 밖 4(RGBA8)다. `TextureBlockOptions { bool alphaProfile; }`가 BC7 프로필을 고른다. 진입점은 `EncodeTextureBlocks(format, image, options, out)`이다. 블록 하나 함수 `EncodeTextureBlock`도 BC6H·BC7을 받는다(블록 하나 surface — 시험용).
   - 입력 준비는 할당 없이 스택 strip 버퍼로 한다. ISPC는 쓰기 가능한 입력을 받고(`rgba_surface.ptr`), R·B 교환·BC6H 정리·가장자리 복제가 입력을 바꾸기 때문이다. strip은 4행 × K블록(K = 64 — BC6H 8 KiB)이고, 복사하면서 교환·정리·복제를 한 뒤 `CompressBlocksBC6H`·`CompressBlocksBC7`을 부른다. 블록이 독립이므로 strip으로 나눠도 byte가 같다(시험: 그림 전체 surface 한 번 = strip 결과). 그림 전체를 surface 하나로 넘기지 않는다(큰 HDR 그림에서 int32 stride·offset이 넘친다).
   - `DecodeTextureBlock`은 BC6H·BC7 기준 디코더를 더한다(시험·PSNR용 — D3D 명세의 정수식, TC3b에서 명세 문구로 확인해 적는다).
   - 인코더 버전 `IspcBcEncoderVersion`(1 — TC3c `Rocks.patch`로 2)과 ISPC 신원 문자열(`ROCKS_ISPC_IDENTITY` — 버전·타깃·인자, BuildTargets BD50)이 TD10 키에 들어간다(BC1–5의 `RocksBcEncoderVersion`과 따로). ISPC 판이나 인자가 바뀌면 키가 바뀐다.
6. **쿠킹 연결**: 데스크톱의 TD11 대체를 지운다. BC7은 `BC7Unorm(Srgb)`, HDR_Compressed는 `BC6HUfloat`이고, `EncoderUnavailable`은 더 나오지 않는다(Android는 TC4까지 비압축 대체 그대로). BC6H 대체 알파 1 규칙(`opaqueAlpha`)은 BC6H 자체가 알파가 없으므로 지운다(5번). 비압축 강제의 RGBA16F는 원본 알파를 지킨다(TC2 리뷰 반영 그대로). 형식 선택 결과가 바뀌므로 후보 형식이 키에 들어가 너겟이 다시 만들어진다(`TextureBuildVersion`은 그대로).
7. **검증(TC3c)**:
   - 결정성: 검증 도구(`Tools/IspcDeterminism`)가 같은 커널을 sse2·sse4·avx2 단일 타깃 object로 따로 빌드해(fast-math·FMA 끔) 시험 그림 셋(BlockGoldenImages 생성기 + HDR 그림)의 출력이 byte로 같음을 확인하고 결과를 기록한다. Arm64는 Mac에서 같은 도구로 확인한다(사용자 Mac 확인 항목).
   - UE 품질 대조: 도구가 UE 클론 `Engine/Binaries/ThirdParty/Intel/ISPCTexComp/Win64-Release/ispc_texcomp.dll`을 불러 같은 입력(같게 정리한 half·교환한 RGBA8)과 같은 프로필로 압축하고, 기준 디코더 결과로 PSNR을 비교한다. BC7은 RGBA8 byte 공간 PSNR이다. BC6H는 half → float 선형 값을 `log2(1 + x)`로 바꾼 공간의 PSNR이다(HDR 오차 지표 — 넓은 범위에서 밝은 값이 지배하지 않게). 판정은 묶음 전체 PSNR이 Rocks ≥ UE − 0.05 dB, 그림마다 Rocks ≥ UE − 0.3 dB다(작은 그림은 모드 선택 차이로 흔들린다). 표에 측정 CPU(UE DLL이 dispatch한 ISA)를 같이 적는다. fast-math 근사 차이라 byte는 다르다.
   - 회귀: EngineTests가 Rocks 출력의 해시 golden(시험 그림 셋 + 퇴화 블록 셋)과 규칙(가장자리 복제 — 4의 배수가 아닌 중간 mip 포함, BC6H 입력 정리, 프로필 선택, strip = 전체, FTZ·DAZ가 켜진 호출자에서도 같은 byte)을 본다.
   - Epic 수정: UE 사본의 패치는 ASTC 하나다(`patches/0001`). `kernel.ispc`는 이미 `ISPC_UINT_IS_DEFINED`로 typedef를 막고 있어 중복 typedef 수정은 필요 없을 것이다(고정 ISPC로 컴파일해 확인).
8. **한계**: SIMD 폭이 x64 4(sse4)라 UE avx2 DLL보다 느릴 수 있다. TC5에서 재고 필요하면 블록 병렬(스레드)로 메운다. x64 avx2 단일 타깃 결과가 sse4와 같으면 TC5에서 avx2로 올리는 것도 검토한다(결정성이 유지될 때만).

   - **시험**: BC6H·BC7 왕복 PSNR 하한(시험 그림 셋), strip 경계 무관(넓은 그림 결과 = 블록마다 4 × 4 그림으로 따로 인코딩한 결과), 가장자리 복제(4의 배수가 아닌 크기 = 손으로 복제한 그림), BC6H 정리(NaN·음수·−0·+Inf 입력 = 정리한 입력), 프로필 선택(알파 그림에서 alpha 프로필과 basic 프로필 결과가 다르고 각각 결정적), FTZ·DAZ가 켜진 호출자에서도 같은 byte, 해시 golden, 디코더 모드별 알려진 블록, 형식 선택·빌드·쿠킹 표 갱신.
   - **리뷰 반영**(2026-11-27): 기준 디코더 시험에 BC7 mode 1(2 subset·공유 p-bit·anchor)·mode 4(rotation·index 선택)와 BC6H mode 12(1 subset 변환 — 음수 차이·wrap)의 손으로 만든 블록을 더했다. 쿠킹 시험(`TextureCook_IspcFormats`)이 BC7 적중(같은 byte)·ForceAlpha 키 변화·HDR_Compressed → BC6HUfloat를 본다. BC7 적중은 알파 판정을 되살리지 못한다(두 후보 형식이 같다) — 그 값은 경고에만 쓰고 BC7 경고는 알파와 무관하다. `IspcBcEncoderVersion`은 커널 원본(upstream 갱신·`Rocks.patch`)이 바뀌어도 올린다(커널 내용은 키에 없다). 품질 측정(시험 그림 셋, 2026-11-27 x64): BC7 RGB 18–61 dB(노이즈 18 dB, 그 밖 37 dB 이상 — 모든 그림에서 BC1 이상), BC7 알파 프로필 RGBA 15.7–63 dB(모든 그림에서 BC3 이상), BC6H log2 공간 19–85 dB. 해시 golden은 x64 값만 단언한다(Arm64는 Mac 확인 때 기록).
10. **TC3c 구현 세부**(2026-11-27 — 구현 전 기록, 7번을 구체화):
   - **결정성 도구** `Tools/IspcDeterminism`(Rocks 빌드 밖 probe — 고정 인자가 아닌 타깃이 필요하다): `run.py`가 고정 ISPC로 `kernel.ispc`를 타깃마다(`sse2-i32x4`·`sse4-i32x4`·`avx1-i32x8`·`avx2-i32x8`) 따로 컴파일하고(나머지 인자는 Rocks 빌드와 같다 — `-O2 --opt=disable-fma --math-lib=default`), 같은 probe 원본(`IspcDeterminismProbe.cpp` + 저장소의 `ispc_texcomp.cpp`)과 링크해 타깃마다 실행 파일을 만든다. probe는 시험 그림 셋(`BlockGoldenImages.h` — 32 × 32·128 × 128)과 시험의 HDR 변환(v² × 배율, Rocks `FloatToHalf`와 같은 RTNE 식)으로 BC7(RGB·알파 프로필)·BC6H 출력을 만들어 FNV-1a 64를 시험(`TextureBlockBptc_OutputHashGolden`)과 같은 순서로 잇는다. 판정: 모든 타깃의 해시가 같고, sse4 해시가 Rocks 해시 golden과 같다(probe가 Rocks 빌드와 같은 입력·인자임을 확인). Arm64(neon)는 Mac에서 같은 도구로 본다.
   - **UE 품질 대조** `Programs/TextureCodecCompare`(Rocks 빌드 Program — Rocks 인코더·기준 디코더를 그대로 쓴다): `--ue-dll <ispc_texcomp.dll 절대 경로>`(UE 클론 `Engine/Binaries/ThirdParty/Intel/ISPCTexComp/Win64-Release/ispc_texcomp.dll`)를 `platform::DynamicLibrary`로 열어 같은 입력·같은 프로필(`GetProfile_basic`·`GetProfile_alpha_basic`·`GetProfile_bc6h_basic`)로 압축하고, 두 결과를 같은 기준 디코더로 풀어 PSNR을 잰다(BC7 RGB는 RGB, 알파 프로필은 RGBA, BC6H는 log2(1 + x) 공간). 표는 그림마다 Rocks·UE·차이와 묶음 전체(오차 제곱 합으로 계산)다. 판정은 7번(묶음 Rocks ≥ UE − 0.05 dB, 그림마다 Rocks ≥ UE − 0.3 dB)이고 어기면 종료 코드 1이다. 측정 CPU의 SIMD 능력(UE DLL이 고른 ISA — avx2 여부)을 함께 출력한다. Windows 전용이다(UE 클론에 Mac dylib도 있지만 TC3c는 Windows에서 잰다).
   - 결과는 이 절에 기록한다(측정일, CPU, 표 요약).
   - **결과(2026-11-27, Windows x64 — CPU sse4.2·avx·avx2, UE DLL은 avx2 경로)**:
     - 첫 대조에서 negative-correlation(블록마다 R +t, G −t, B 고정)의 BC7이 Rocks 37.7 dB, UE 49.9 dB였다(알파 프로필 −0.75 dB). 원인을 가르려고 같은 커널을 우리 ISPC로 인자만 바꿔 DLL로 빌드했다. 정확 연산(Rocks 인자)은 Rocks와 byte가 같았고, fast-math만 켜거나 FMA만 켜면 49.9 dB, UE식(avx2 + fast-math)은 UE DLL 결과를 재현했다. 원인: `compute_axis`의 거듭제곱 반복이 고정 시작 벡터 {1,1,1,1}에서 시작한다. 주축 (1, −1, 0)이 이 벡터와 정확히 직교하면 정확한 IEEE 연산에서는 직교가 유지되어 작은 축으로 수렴한다(UE는 fast-math·FMA 반올림으로 우연히 벗어난다).
     - **`Rocks.patch`**(3번의 "Rocks.patch로 고친다"): 첫 결과의 Rayleigh 몫이 trace/channels의 절반(`axis_restart_ratio` 0.5)보다 작으면(주 고유값은 늘 trace/channels 이상이므로 주축이 아님이 증명된다) 대각이 가장 큰 공분산 열에서 다시 시작한다. 절반을 쓰는 이유: 등방 공분산(단색 블록 — 대각에 eps만)은 경계 trace/channels에 정확히 닿으므로(리뷰 모사: 4채널은 양변이 같다) 반올림 1 ulp가 단색 블록 전체를 재시작시키면 안 된다. 어떤 `compute_axis` 호출에서도 재시작하지 않은 블록은 upstream byte 그대로다(`get_pca_bound` — 분할 후보 순위 — 도 같은 판정을 거치므로 재시작이 분할 선택을 바꿀 수 있다). 시작 벡터를 아예 그 열로 바꾸는 안은 단색 블록(99 → 59 dB)·one-different(61.5 → 57.7 dB)를 나쁘게 해 버렸다(공분산이 eps뿐인 블록은 {1,1,1,1} 축이 낫다). `IspcBcEncoderVersion` 2. 커널 원본이 CRLF라 ThirdParty 패치 검증(`ThirdPartyPatch.Reverse`)을 일관된 CRLF 원본까지 넓혔다(LF patch를 CR을 뗀 줄과 대조, 복원은 CRLF — 섞인 줄 끝·떠도는 CR·CRLF 추가 파일은 거부).
     - 결정성: sse2·sse4·avx1·avx2 출력이 byte로 같다. 측정 그림 해시는 Rocks 빌드 해시 golden과 같고(`a66a3317215b715d`), 모든 그림(드문 경로 256 × 256 포함)·퇴화 HDR 입력(0·65504·비정규·두 값)의 전체 해시도 네 타깃이 같다(`97f30af257bb9494`). 패치 전 커널도 네 타깃이 같았다.
     - UE 대조(패치 뒤, 드문 경로 256 × 256 넷 포함): 묶음 BC7·BC7 알파·BC6H 모두 −0.000 dB. 그림마다 rare-one-channel-one(한 texel의 한 채널만 1 다름)만 BC7 −6.6 dB·알파 −1.8 dB·BC6H −0.25 dB다. 이것은 fast-math 차이다(패치 전 정확 연산 커널과 FMA만 켠 빌드는 Rocks와 같은 63.6 dB, fast-math만 켜면 70.1 dB). 평균 제곱 오차로는 BC7 0.028 대 0.006, 알파 0.14 대 0.09(8비트 단위²)로 몇 texel이 1 단계 어긋나는 차이다. 그래서 그림마다 판정에 거의 무손실 여유를 더했다: LDR은 −0.3 dB 이내이거나 평균 제곱 오차가 UE보다 0.1 이하로 크면 통과(BC6H는 dB만). 묶음 판정은 그대로다. 묶음 가중치는 값 수라 128²·256² 그림이 대부분이므로, 병적 그림은 그림마다 판정이 지킨다. 그 밖 그림의 가장 큰 부족은 gray BC6H −0.101 dB다 — PASS.
     - 남은 확인: Arm64(neon) 결정성과 해시는 Mac에서 같은 도구로 본다(사용자 Mac 확인 항목 — run.py가 호스트 아키텍처로 neon-i32x4·neon-i32x8을 비교하고 golden 값을 출력한다). 패치가 더한 연산(분할 후보마다 ssymv 한 번·비교)의 속도 영향은 TC5에서 잰다.

#### 12.17.7 블록 디코더 위치(2026-11-27 — 렌더 세션 rocks-2e 요청)

기준 디코더(BC1–BC5 TD7, BC7·BC6H 12.17.6 9)는 CPU에서 쿠킹 플랫폼 데이터를 푸는 기능이다. TextureTools(Developer — 에디터 데이터에 기댄다)에만 있으면 Game 타깃(Sandbox CPU 대조 기준)이 링크하지 못해 사본을 두게 된다. 그래서 디코더를 런타임 `Texture` 모듈로 옮기고, 인코더(NVTT 이식·ISPC 감싸기)는 TextureTools에 남긴다(ISPC 커널을 Game 타깃에 끌어들이지 않는다).

- 공개 헤더 `Texture/TextureBlockDecode.h`: `TextureBlockFormat`(Bc1·Bc3·Bc4·Bc5·Bc6h·Bc7), 블록 상수(`TextureBlockSize`·`TextureBlockTexels`·`TextureBlockTexelBytes`·`TextureBlockRgbaBytes`·`TextureBlockHalfTexelBytes`), `TextureBlockBytes`, `TextureBlockOutputBytes`, `DecodeTextureBlock`(RGBA8 — BC1–BC5·BC7), `DecodeTextureBlockHalf`(BC6H Ufloat → RGBA16F half bit), `TextureBlockAlphaPalette`(BC3 알파·BC4·BC5의 8값·6값 팔레트 — NVTT 바닥 나눗셈, 인코더의 index 선택이 같은 함수를 쓴다). Core에만 기댄다(에디터 데이터 없음). 할당하지 않는다.
- TextureTools `TextureBlockEncode.h`는 이 헤더를 include하고 인코딩 API(`EncodeTextureBlocks`·`EncodeTextureBlock`·`TextureBlockOptions`·`TextureBlockSourceTexelBytes`·인코더 버전·`IspcBcEncoderIdentity`)만 둔다. 이름과 동작은 바뀌지 않는다(옮김만).
- 표 생성기(`Tools/BptcTables/make_tables.py`)의 출력은 `Engine/Source/Runtime/Texture/Private/TextureBlockBptcTables.h`다. 디코더 알려진 블록 시험은 Texture 시험(`TextureBlockDecodeTests.cpp`)으로 옮긴다.
- 옮긴 뒤 렌더 세션이 Sandbox TexelCodec의 BC1–BC5 사본을 지운다(알림).
- BC3 색 블록은 끝점 순서와 무관하게 늘 4색으로 푼다(2026-11-27 렌더 세션 지적 — D3D 명세·하드웨어·DirectXTex D3DXDecodeBC3. NVTT BlockDXT5는 BC1 규칙으로 풀지만, 이 디코더는 GPU 결과와 대조하는 CPU 기준이므로 명세를 따른다). Rocks BC3 인코더는 c0 ≥ c1만 쓰므로(같은 끝점이면 index 0뿐) 지금 Rocks 출력의 디코드는 바뀌지 않는다. 다른 출처의 BC3 byte만 달라진다.

#### 12.17.8 TC4 구현 세부(2026-11-27 — ASTC·EAC R11, 구현 전 기록, 설계 교차 검증 반영 개정 1)

Android 쿠킹이 ASTC와 EAC R11을 낸다(12.16.2). 기준은 UE 5.8 `TextureFormatASTC`(TextureFormatASTC.cpp)·`astc_thunk.cpp`·Android 재대응이다. UE 클론에는 astcenc thunk 바이너리가 없어 UE 출력과 직접 대조하지 못한다(아래 한계).

개정 1(설계 교차 검증 높음 6·중간 8·낮음 5 반영): HDR 대체를 UE대로 ASTC RGB로(H1), `compressionQuality` 계약 해제와 전달 경로(H2), astcenc 전역 가변 상태와 libm 의존을 `Rocks.patch`로 제거(H3·H4), EAC 탐색의 가지치기·처리량 측정(H5)과 base 구간 정정(H6), EAC 입력 16 bit(M1), EAC byte·texel 순서(M2), 명세 인용(M3), HQ·RGBA 무알파 A = 1(M4), EAC 11 bit 디코드 API와 시험(M5), UE 판 서술(M6), API 서명·할당·pitch(M7), 형식에 달린 swizzle 예외(M8), 가장자리 문구·EAC 채움 가중치 0(L1), 가상 텍스처 기록(L2), sse2 preset 정의(L3), 형식 계열 판정(L4), 고정 기본값·오류 코드 표(L5).

1. **ASTC 원본**: ThirdParty `AstcEncoder` = ARM astc-encoder **5.1.0**(Apache-2.0). UE 5.8 Android 기본이 thunk 판 501(`BaseAndroidEngine.ini` 37 `ASTCVersion=501`)이고, UE 폴더 `astcenc/5.0.1`은 CMake 판이 5.1.0이지만 태그와 조금 다르다(RDO 연동 `ASTCENC_FLG_USE_LZ_RDO`, decompress lerp 정리, `unorm16_to_sf16`, `hadd_s(vint4)` 없음, preset 배열 7칸에 초기값 6개). 그래서 "거의 같은 판"이다. 출처는 GitHub 태그 archive(커밋 `4a86301166014904afa8143a20f3b1223f7f392a`, sha256 `2e60fc2917e0796bd62429242accdf71c784f99f21fcae6c69159c11332fba40`)다. 들이는 파일은 `Source/astcenc*.h`·`astcenc_*.cpp`(라이브러리 — `astcenccli_*`·`astcenc_diagnostic_trace.cpp`·`wuffs`·시험 제외)와 `LICENSE.txt`다. RDO는 쓰지 않는다.
2. **결정적 빌드**:
   - SIMD 경로: upstream 불변성 빌드(기본 — `ASTCENC_NO_INVARIANCE`를 정의하지 않는다)는 ISA 사이 bit 동일을 목표로 한다(Docs/Building.md "Non-invariant builds"; NEON `hadd_s`는 x86과 같은 덧셈 순서, 근사 `rcp`·`rsqrt` 없음). x64는 `ASTCENC_SSE=20`·`ASTCENC_X86_GATHERS=0`·`ASTCENC_NEON=0`(upstream `x86_64-sse2` preset — Rocks 빌드는 ISA 인자를 금지하므로 x64 기준은 SSE2다, PhysicsJoltAdapter SIMD 정의 줄과 같다), Arm64는 `ASTCENC_NEON=1`·`ASTCENC_SSE=0`, 공통으로 `ASTCENC_AVX=0`·`ASTCENC_F16C=0`·`ASTCENC_POPCNT=0`·`ASTCENC_SVE=0`이다(manifest `defines`·`platformDefines`). SSE2·NEON은 각 아키텍처의 기준이라 CPU 검사가 없다. 곱셈·덧셈 합치기는 Rocks 프로필(`-ffp-contract=off`)이 막는다. SSE2 `round`의 magic-number 방식은 가장 가까운 짝수 반올림을 전제하므로 `RunWithDeterministicFloatingPoint` 안에서 압축한다. NaN·범위 밖 float → int 변환은 ISA마다 다르지만 LDR 입력(유한 [0, 1])에서는 닿지 않는다.
   - libm(H4): upstream은 `sinf`·`cosf`(각 표 64 × 32 — `prepare_angular_tables`)와 `logf`(블록 texel 수의 log10 — `astcenc_config_init`)를 C runtime으로 계산한다. `Rocks.patch`가 둘을 상수 표(`astcenc_rocks_angular_tables.h`·`astcenc_rocks_log10_table.h` — `Tools/AstcEncoderTables/generate.py`가 mpmath로 만든, upstream float 식의 올바르게 반올림한 값)로 바꾼다. Windows UCRT `sinf`는 4096칸 중 한 칸에서 올바른 반올림과 1 ulp 다르다(확인함) — 그래서 Rocks 출력은 upstream Windows 빌드와 드문 블록에서 다를 수 있다. 나머지 수학은 `sqrt`·`floor`(정확)와 astcenc 자체 다항식(`atan2`·`pow`·`log2`)이다.
   - 전역 가변 상태(H3): `astcenc_config_init`의 `static` preset 포인터(블록 크기가 다른 동시 호출이 서로의 선택을 읽는다)와 `context_alloc`마다 다시 쓰는 sin·cos 표(동시 컨텍스트 사이 data race)를 `Rocks.patch`가 없앤다. 구현 때 셋째를 찾았다: `compress_block`의 함수 안 `static const float errorval_overshoot = 1 / tune_mse_overshoot`는 프로세스의 첫 컨텍스트 값으로 한 번만 초기화되므로, 블록 크기가 다른(따라서 `tune_mse_overshoot`가 다른 — 4×4 2.5·12×12 3.5) 뒤 컨텍스트가 첫 값을 쓰고 출력이 "프로세스가 먼저 무엇을 압축했나"에 달렸다(해시 golden이 단독 실행과 다른 ASTC 시험 뒤 실행에서 달랐다 — 단독 시험대로 재현, 힙·스택 초기화·ASan과 무관, obj 기호의 thread-safe static 가드로 확정). `Rocks.patch`가 static을 뗀다. upstream과 UE thunk는 이 동작 그대로라 UE 출력도 처리 순서에 달린다. 그 뒤 manifest `globalState`는 거짓이다.
   - 해시 golden 하나가 x64·Arm64 모두에 맞아야 한다(Mac 확인 전까지는 x64만 단언하고 Arm64 값은 Mac에서 확인한다). 그때까지 `AstcEncoderIdentity()`에 SIMD 경로(`x64-sse2`·`arm64-neon`)를 넣어 아키텍처 사이 너겟 공유를 막는다 — 같음을 확인하면 빼고 `AstcEncoderVersion`을 올린다(구현 리뷰 반영). 남은 ISA 차이는 NaN·±0·범위 밖 float → int(SSE `minps`·`cvttps`와 NEON `vminnm`·`vcvtq`)뿐이고, 닿을 수 있는 NaN 경로 하나(`compute_angular_offsets`의 각 합이 둘 다 정확히 0이면 `atan2` 0/0)는 `Rocks.patch`가 각 0으로 막는다. 컨텍스트 스레드 수는 1이다(병렬화는 TC5에서 잰다).
3. **UE 설정 그대로**(TextureFormatASTC.cpp 271–345·400–520·astc_thunk.cpp 69–158). 고정 기본값은 UE ini 기본을 상수로 둔다(`DefaultASTCQualityBySize` 3·`DefaultASTCQualityBySizeHQ` 4·`DefaultASTCQualityBySpeed` 2 — 이름 있는 상수, 설정 칸은 두지 않는다):
   - profile: sRGB 출력이면 `ASTCENC_PRF_LDR_SRGB`, 아니면 `ASTCENC_PRF_LDR`.
   - quality: `DefaultASTCQualityBySpeed` 2 → `ASTCENC_PRE_MEDIUM`(60). 블록은 2D이고 slice는 이미지 z로 넘긴다(astc_thunk.cpp 111·123 — UE와 같다. 블록 z = 1이라 slice는 서로 독립이다).
   - 입력·swizzle(Rocks 입력은 RGBA8 — UE BGRA 입력 swizzle을 RGBA로 옮긴다): `Rgb`(ASTC RGB, 그리고 알파가 없는 RGBA·RGBA HQ — UE는 `bHasAlpha`가 거짓이면 어느 RGBA 형식이든 A = 1, TextureFormatASTC.cpp 466–483) A = 1, `Rgba` 그대로, `NormalLa`: R = G = B = X(입력 R), A = Y(입력 G), `ASTCENC_FLG_MAP_NORMAL`, `tune_db_limit` = max(preset 값, 60), 오차 가중치 R 1·G 0·B 0·A 1. 그 밖 오차 가중치는 astcenc 기본(1)이다.
   - 가장자리: 블록 배수가 아닌 크기를 그대로 넘긴다. astcenc는 블록 texel 좌표를 그림 안으로 clamp해 마지막 행·열을 복제한다(astcenc_image.cpp 213–222 — UE와 같다). 출력은 slice마다 ceil(w/bx) × ceil(h/by) × 16 byte다.
   - 감싸기는 텍스처 호출 하나에 컨텍스트 하나를 만들고 slice마다 `astcenc_compress_image`·`astcenc_compress_reset`을 부른다. 설정(`astcenc_config_init` — preset 보간)과 컨텍스트 할당(`astcenc_context_alloc` — CPU 부동소수 검사, 호출자가 반올림 방향을 바꿨으면 `BAD_CPU_FLOAT`)도 결정적 부동소수 환경 안에서 한다(구현 때 시험으로 찾음). astcenc 입력은 행 사이 여백이 없어야 하므로(astcenc_image.cpp 224) pitch가 있는 입력은 빽빽한 사본을 만든다. 그래서 ASTC 경로는 할당한다(컨텍스트·사본 — 할당 실패는 OutOfMemory, astcenc 내부 `new`는 null 검사가 없어 예외 없는 빌드에서 할당 실패가 종료다).
   - 오류 코드 표: `ASTCENC_ERR_OUT_OF_MEM`(출력 버퍼 부족 — 감싸기가 크기를 맞추므로 내부 오류) → InvalidArgument, `ASTCENC_ERR_BAD_CPU_FLOAT` → Unsupported, 그 밖 설정 오류(`BAD_PARAM`·`BAD_BLOCK_SIZE`·`BAD_PROFILE`·`BAD_QUALITY`·`BAD_FLAGS`·`BAD_SWIZZLE`·`BAD_CONTEXT`) → InvalidArgument.
4. **EAC R11 인코더**(자체 구현 — BC4 → EAC R11, Alpha 설정):
   - 형식(OpenGL ES 3.0.6 부록 C.1.5, Khronos Data Format 1.3 22.5절): 블록 8 byte = 64 bit big-endian 정수다. 최상위부터 base 8 bit(bit 63–56), multiplier 4 bit(55–52), 표 4 bit(51–48), index 16개 × 3 bit(47–0)다. index 순서는 열 우선이다(a = (0,0), b = (0,1), c = (0,2), d = (0,3), e = (1,0) … p = (3,3) — Table C.2·C.9, BC4의 행 우선과 반대). 수정값 표는 ETC2 알파 표(Table C.10) 16 × 8이다.
   - 디코드(unorm, 식 C.4·C.5): multiplier m ≥ 1이면 `clamp(base·8 + 4 + modifier·m·8, 0, 2047)`, m = 0이면 `clamp(base·8 + 4 + modifier, 0, 2047)`이다(modifier·multiplier·8 항이 modifier가 된다 — 실효 multiplier 1/8). 11 bit 값의 16 bit 확장은 `(x << 5) | (x >> 6)`이다.
   - 입력(M1): 선형 R을 16 bit unorm으로 받는다(`TextureBlockSourceTexelBytes(EacR11)` = 2 — R16 little-endian, 빌드가 float 레벨에서 `QuantizeUnorm16`으로 만든다). UE는 RGBA32F를 넣는다(TextureFormatETC2.cpp 77–190·418–431). 8 bit를 거치면 3 bit를 잃으므로 쓰지 않는다. 인코더 목표값은 v11 = (v16 · 2047 + 32767) / 65535(정수 나눗셈 — 가장 가까운 11 bit)다.
   - 탐색(H5·H6): 결정적 정확 최적이다. 목적은 블록 texel의 (목표 − 디코드)² 합이 가장 작은 (표 t, multiplier m, base b)이고, 동률은 (오차, t, m, b) 사전순으로 작은 것이다(방문 순서와 무관한 유일한 답). index는 texel마다 오차가 가장 작은 것, 동률은 작은 index다. base 구간은 s = 8m(m ≥ 1)·s = 1(m = 0), 표의 가장 작은·큰 수정값 mn·mx, 블록 최솟값·최댓값 vmin·vmax로 b ∈ [lo, hi] ∩ [0, 255]이고 lo = floor((vmin − 4 − mx·s) / 8), hi = ceil((vmax − 4 − mn·s) / 8)이다. 다만 8·lo + 4 + mx·s ≤ 0(팔레트 위끝이 0으로 잘림)이면 lo = 0이다. 근거: b > hi면 모든 texel이 팔레트 아래끝보다 8 이상 아래라 b − 1이 오차가 같거나 작고 b가 작아 이긴다. b < lo면 모든 texel이 위끝보다 8 이상 위라 b + 1이 오차가 정확히 줄어든다. 위끝이 0으로 잘린 b끼리만 오차가 같고, 그때는 가장 작은 b(0)가 이긴다. 시험이 256 전체 탐색과 같음을 확인한다. 가지치기는 부분합이 현재 최선 이상이면 그 후보를 버리는 것(부분합 = 최선이고 사전순 키가 크면 버림)과, texel 순서를 vmin·vmax 쪽부터 보는 것이다. 첫 후보는 m = 범위에 맞는 값부터 보아 최선을 일찍 줄인다(결과는 사전순 규칙이 정하므로 순서와 무관하다).
   - 가장자리(L1): 블록보다 작은 가장자리는 BC4처럼 NVTT 주기 반복으로 채우되, 채운 texel은 오차에 넣지 않는다(UE etc2comp가 경계 밖 texel을 오차에서 빼는 것과 같다 — EtcBlock4x4.cpp 277). 채운 texel의 index도 같은 최근접 규칙으로 고른다.
   - 후보 줄이기(구현 때 더함 — 답은 같다): 같은 목표값은 하나로 모아 texel 수를 가중치로 둔다. (표, multiplier)마다 현재 최선 오차 E*에서 r = floor(√E*)(정수 이분 탐색)를 구하고, 목표값마다 "그 texel 오차 ≤ r²"인 base 집합을 구간으로 정확히 만든다(잘리지 않은 팔레트 값은 |v − x| ≤ r, 0으로 잘린 값은 v ≤ r일 때, 2047로 잘린 값은 2047 − v ≤ r일 때). 그 교집합만 평가한다 — texel 하나의 오차는 블록 오차 이하이므로 최선이 될 수 있는 base는 모두 남는다. 집합은 256 bit이고 word 단위로 채운다.
   - 처리량(2026-11-27 측정, x64 Release clang -O2 단일 스레드, 블록 4000개): 단색 5.5 × 10⁴, 좁은 범위(600) 2.8 × 10⁴, 경사(16값) 1.0 × 10⁴, 전체 범위 잡음 3.1 × 10³, 넷 섞음 8.6 × 10³ blocks/s(후보 줄이기 전 2.6 × 10³). 잡음이 많은 블록은 2 × 10⁴ 기준에 못 미치므로 TC5 첫 항목으로 블록 병렬(텍스처 안 strip)이나 탐색 제한(그리고 그 품질 차이)을 정한다(Android 쿠킹 시간에 바로 걸린다 — 잡음 4096² Alpha는 mip 포함 약 1.4M 블록, 단일 스레드 약 7분). 인코더 이름 `RocksEac`·버전 `RocksEacEncoderVersion`(1).
5. **API**(M5·M7):
   - Texture `TextureBlockDecode.h`: `TextureBlockFormat`에 `EacR11`과 `Astc4x4`·`Astc6x6`·`Astc8x8`·`Astc10x10`·`Astc12x12`를 더한다. `TextureBlockWidth`·`TextureBlockHeight`(형식의 블록 texel 크기 — BC·EAC 4, ASTC 각 크기)를 두고 `TextureBlockOutputBytes`는 그 크기로 센다. `TextureBlockSize`(4)·`TextureBlockTexels`·`TextureBlockRgbaBytes`는 BC·EAC 4 × 4 블록의 상수로 남는다(주석에 ASTC 제외를 적는다). `DecodeTextureBlock`은 4 × 4 형식만 받는다: EAC R11은 (round(x · 255 / 2047), 0, 0, 255)이고, ASTC·BC6H는 받지 않는다(0으로 채운다 — 지금 BC6H와 같은 규칙, 주석에 적는다). `DecodeEacR11Block(block, uint16 (&values)[16])`이 11 bit 값을 행 우선(y × 4 + x)으로 낸다(시험·품질 비교용). ASTC CPU 디코드는 Texture에 두지 않는다(astcenc가 필요하다 — 렌더 CPU 대조에 필요해지면 decompressor 전용 빌드를 Texture에 둔다).
   - TextureTools `TextureBlockEncode.h`: `TextureBlockOptions`에 `astcMode`(`Rgb`·`Rgba`·`NormalLa`)와 `srgb`(ASTC profile)를 더한다. `EncodeTextureBlocks`가 ASTC·EAC를 받는다(ASTC 입력 RGBA8, EAC 입력 R16 — 텍스처 하나 전체를 slice 수만큼). 머리 주석의 "할당하지 않는다"는 BC·EAC로 좁히고 ASTC 할당을 적는다. `EncodeTextureBlock`(블록 하나)은 BC1–BC5·EAC R11만 받는다(EAC 입력은 R16 16개 — 별도 함수 `EncodeEacR11Block(const uint16 (&values)[16], uint16 validMask, uint8* out)`, validMask는 오차에 넣는 texel — bit y × 4 + x). `DecodeAstcBlocks`(astcenc decompress — 시험·품질 측정용)를 TextureTools에 둔다. 신원: `AstcEncoderVersion`(1)과 `AstcEncoderIdentity()`("astcenc 5.1.0 medium invariant rocks-patch 1").
6. **형식 선택**(12.17.2 7번 — Android 재대응):
   - TD8의 "Android는 TC4 전 비압축"을 지우고, 2–6번 뒤 Android면 12.16.2 재대응 표로 바꾼다. 형식 계열은 플랫폼으로 정한다(L4 — Android는 ASTC 하나, 프로필 칸은 두지 않는다. TD10·TD11·12.17.3의 "형식 계열 칸"은 이 판정을 말한다). 4의 배수 규칙(2–4번)은 그대로 먼저 적용한다(UE).
   - 재대응: AutoDXT·BC1 → ASTC(품질 크기, 알파면 `Rgba` 아니면 `Rgb`), BC3 → ASTC(품질 크기, 알파 따라), BC7 → ASTC HQ(HQ 품질 크기, 알파 따라), BC5 → ASTC 6×6 `NormalLa`(노멀은 품질을 보지 않는다), BC4 → `EACR11Unorm`, BC6H(HDR_Compressed) → ASTC RGB LDR(H1 — UE `cook.FallbackForASTCHDRProfile` 기본 0: ASTC HDR이 없으면 ASTC_RGB, TargetPlatformSettingsBase.cpp 7–14·132–145, AndroidTargetPlatformControls.cpp 590–600. 입력은 선형 RGBA8로 [0, 1]에 자른 값, 블록 크기는 일반 품질 규칙).
   - 블록 크기(12.16.2 표): `TextureBuildSettings.compressionQuality`(새 칸, 아래)가 Default면 일반 6×6·HQ 4×4, 그 밖은 Lowest 12×12·Low 10×10·Medium 8×8·High 6×6·Highest 4×4다(HQ도 명시 품질은 같은 표).
   - 알파: AutoDXT·BC1·BC3·BC7 재대응은 알파 판정이 인코더 입력(A = 1 여부)을 바꾸므로 `TextureFormatNeedsAlpha`가 참이다(형식은 같고 `astcMode`가 다르다 — 비교에 `astcMode`를 더한다). BC1(compressionNoAlpha)은 유효 알파가 거짓이라 늘 `Rgb`다.
   - sRGB: 짝 형식(`ASTC…UnormSrgb`)이 있으면 그것이다(EAC R11·노멀·HDR 대체는 선형 — sRGB 막음).
   - 볼륨은 비압축(12.16.2 유지 — UE의 ETC2 대체와 다르다).
   - swizzle 칸(M8): 12.17.2·12.17.5의 "CompressionSettings로만 정한다"에 형식에 달린 예외 하나를 둔다. 노멀 LA는 X = R, Y = A이므로 `(r, a, 0, 1)`이다(셰이더가 Z 복원 — 렌더 세션 알림). Alpha 설정의 EAC R11은 `rrrr` 그대로다.
   - 가상 텍스처(L2): UE는 VT면 ASTC 4×4(TextureFormatASTC.cpp 294)이고 Android VT는 ETC2다(AndroidTargetPlatformControls.cpp 290–323). 지금 VT는 계약 거부라(TextureSettingsCheck 65) 영향이 없다. 계약을 풀 때 이 둘을 따른다.
   - `TextureFormatEncoding`에 `Astc`·`EacR11`, `TextureFormatChoice.astcMode`를 더한다. `TextureFormatRequest`에 `compressionQuality`를 더한다.
7. **compressionQuality 계약 해제(H2)**: `CompressionQuality`(UE `ETextureCompressionQuality` 6종)를 12.8절 계약 필드에서 뺀다(`TextureSettingsCheck`가 Default 아님을 거부하던 것). `TextureBuildSettings.compressionQuality`(Resolve가 텍스처 값을 옮긴다)와 `TextureFormatRequest.compressionQuality`를 더하고 12.4절 표·12.8절 계약 목록을 고친다. 데스크톱 BC에는 영향이 없다(UE도 ASTC·Oodle만 본다 — Oodle은 Rocks에 없다). 너겟 키 사본에서는 Default로 고정한다(블록 크기는 후보 형식이 담는다 — 데스크톱은 품질이 키를 바꾸지 않는다). `TextureBuildVersion`은 4로 올린다(빌드 설정 칸이 늘어 반영 직렬화가 바뀐다).
8. **너겟 키**: 후보 형식마다 ASTC면 `AstcEncoderVersion`·`AstcEncoderIdentity()`, EAC면 `RocksEacEncoderVersion`을 쓴다(12.17.6 9와 같은 방식). `astcMode`는 설정과 후보 알파에서 정해지므로 따로 쓰지 않는다.
9. **시험**:
   - ASTC: 블록 크기마다 왕복 PSNR 하한(astcenc decompress — 값 잡음 32 × 32 x64 측정 4×4 41.05·6×6 36.36·8×8 32.39·10×10 30.53·12×12 28.55 dB, 하한은 2 dB 낮춘 값), RGB 모드가 입력 알파를 무시함, 노멀 LA의 채널 배치(디코드한 R = G = B = X, A = Y), sRGB profile, 블록 배수가 아닌 크기, slice 여럿 = slice마다 따로 인코딩한 결과, pitch 입력 = 빽빽한 입력 결과, 해시 golden(x64 `7f9510dbe3f421cd` — ASTC·EAC 함께, 단독 실행·다른 시험 뒤 실행이 같은 값, Arm64는 같은 값이어야 한다, Mac 확인), FTZ·DAZ 호출자, 블록 크기가 다른 두 스레드 동시 인코딩의 결정성(H3), 출력 크기 오류.
   - EAC R11: 명세 예(base 103·표 13·index 3·multiplier 2 → 668, multiplier 0 → 818), byte·texel 순서(손으로 만든 블록), 무작위 블록에서 256 base 전체 탐색과 같은 결과(H6), 단색·두 값·0·2047 경계, 동률 규칙, 채운 texel 가중치 0, 묶음 단위 오차가 BC4(같은 16 bit 원본을 11 bit로 비교)보다 크지 않음(블록 단위 불변식이 아니다 — 측정 366400 대 427045), 처리량 측정(기록만 — 위 4번).
   - 형식 선택: Android × 설정 × 품질 다섯 + Default × 알파 × sRGB 표, HQ 4×4, 노멀이 품질을 무시함, HQ·RGBA 무알파 → `Rgb`, Android 볼륨 비압축, HDR_Compressed → ASTC RGB 선형, 4의 배수 규칙이 먼저.
   - 쿠킹: Android 프로필 → `ASTC6x6UnormSrgb` 등, 적중, Android에서 `compressionQuality`가 키를 바꾸고 데스크톱에서는 안 바꿈, `compressionQuality` 계약 해제(설정 판정).
10. **렌더 알림**: Android 쿠킹이 ASTC(4×4–12×12, sRGB 짝)·EAC R11을 낸다. 업로드(블록 크기 pitch)·NormalLA swizzle(`r, a, 0, 1`)·CPU 대조(ASTC 디코드 부재, EAC는 `DecodeTextureBlock`)를 렌더 세션에 알린다.
11. **한계**: UE astcenc thunk 바이너리가 클론에 없어 UE 출력과 대조하지 못한다(판이 거의 같고 설정이 같지만 Rocks.patch 표 한 칸·UE 포크 차이로 byte가 다를 수 있다 — 품질로만 본다). EAC 인코더는 UE etc2comp와 byte가 다르다(정확 최적이므로 같은 입력에서 오차가 같거나 작다).

#### 12.17.9 TC5 구현 세부(2026-11-28 — 병렬 압축·속도·품질 측정, 구현 전 기록, 설계 교차 검증 반영 개정 1)

TC4까지 모든 인코더는 텍스처 하나를 호출 스레드 하나로 압축한다. EAC R11 잡음 블록이 3.1 × 10³ blocks/s라 큰 Alpha 텍스처가 분 단위다(12.17.8 4). UE는 형식 모듈 안에서 나눈다: DXT는 2048블록 단위 행 묶음을 각각 sub-image로(TextureFormatDXT.cpp 285·320–404), ISPC는 slice마다 블록 행 하나가 작업 하나(TextureFormatIntelISPCTexComp.cpp 271–329·771), ASTC는 컨텍스트 하나에 TaskCount 작업(TextureFormatASTC.cpp 557–606, astc_thunk.cpp 151·166–175), ETC2는 8 job(TextureFormatETC2.cpp 112). TextureCompressorModule은 mip 생성·노멀 정규화·색 보정 등 준비 단계를 병렬로 하고(612–923·2975·3642), 압축은 mip 0과 아래 mip 묶음을 동시에 돌린다(3485–3594). TC5는 블록 병렬과 준비 단계 병렬을 넣고 그 위에서 속도·품질을 잰다.

개정 1(설계 교차 검증 높음 2·중간 5·낮음 6 반영): 압축 전용 scheduler(H1), BC1–BC5·빌드 준비 단계도 결정적 FP 환경 안(H2), ASTC는 컨텍스트 하나 + thread_count(M1), 형식별 최소 batch와 시험용 batch 크기(M2), scratch 동시 안전 계약·사본은 호출 스레드에서 한 번(M3), CookProjectRequest까지 연결(M4), 준비 단계 병렬(M5), UE 서술 정정(L1), nvtt 서술 정정(L2), 헤더 주석·scratch 검사 시점·중첩 한계·출력 위치 계산(L3–L6).

1. **단계**: TC5a 블록 병렬(인코더 API·결정적 FP·쿠킹 연결·결정성 시험) → TC5b 준비 단계 병렬과 측정(단계별 시간, 형식별 blocks/s, 최소 batch 확정, EAC 탐색 제한 판단) → TC5c 대조 기록(ISPC patch 속도 영향, BC1–BC5 기준). 단계마다 리뷰어 하나다.
2. **병렬 단위(TC5a)**: 블록이 서로 독립이고(BC1–BC5·EAC는 블록마다 순수 함수이고 채움도 블록 기준, BC6H·BC7 ISPC 커널은 블록 행 안 strip이 독립, astcenc는 블록 z = 1이고 블록 fetch가 넘겨받은 그림 크기로 clamp하며 그림 전체를 보는 `compute_averages`는 `a_scale_radius` = 0이라 돌지 않는다 — astcenc_image.cpp 213–222·297–301, astcenc_entry.cpp 584·874–905) 전역 가변 상태가 없으므로(12.17.8 2) 순서 없이 압축해도 byte가 같다. 모든 batch는 `RunWithDeterministicFloatingPoint` 안에서 돈다(FP 제어는 스레드마다다 — worker의 FP 설정이 결과를 바꾸지 않게).
   - BC1–BC5·EAC: 일 단위는 (slice, 블록 행)이고 batch가 맡은 행을 압축한다. 출력 위치는 순차 cursor가 아니라 ((slice · blocksY + row) · blocksX + bx) · blockBytes로 계산한다. BC1–BC5는 직렬 경로도 결정적 FP 환경 안으로 옮긴다(지금은 호출자 환경 — 기본 환경이면 golden은 그대로다).
   - BC6H·BC7: 일 단위는 (slice, 블록 행)이고 batch마다 스택 strip 버퍼로 지금 strip 루프를 돈다(UE와 같은 단위). SSE4.2 검사는 호출 스레드에서 한 번 한다.
   - ASTC: UE처럼 호출 하나에 컨텍스트 하나를 만들고 `thread_count` = 참여자 수 P(helper 수 + 1 — 같은 scheduler의 worker 안이거나 scheduler가 없으면 1)로 할당한다. `ParallelFor(count = P, minBatchSize = 1)`의 batch 번호를 `thread_index`로 `astcenc_compress_image`를 부른다(astcenc가 16블록 단위로 동적으로 나눈다 — astcenc_entry.cpp 852). 한 participant가 batch 둘을 맡아도(helper 회수) 앞 batch가 모든 블록을 가져가 뒤 batch는 할 일 없이 끝난다. 그림은 `dim_z` = slice 수와 slice 포인터 배열(scratch로 할당)로 넘기고(UE astc_thunk.cpp 120–124), 호출마다 `astcenc_compress_reset`을 명시적으로 부른다(thread_count > 1이면 자동 reset이 없다 — astcenc_entry.cpp 1063. reset·free는 카운터 대입·해제라 결정적 FP 환경 밖이어도 된다). astcenc는 블록 수·출력 offset을 `int`로 세므로(astcenc_entry.cpp 819·936) 호출 하나의 블록 수를 2^27 − 1 이하로 slice 묶음을 나누고, slice 하나가 그 상한을 넘으면 직렬·병렬 모두 CapacityExceeded다(구현 리뷰 반영 — 큰 배열·볼륨에서 넘쳐 버퍼 밖에 쓰던 것). participant 수는 블록 수 / 16(astcenc 분배 단위)으로 자르고 1이면 직렬이다(작은 mip에 worker 수만큼 작업 버퍼를 잡지 않게). 구현 때 찾은 upstream 결함: U8·항등 swizzle·2D 블록에서 쓰는 빠른 읽기 `load_image_block_fast_ldr`가 `zpos`를 무시하고 늘 `img.data[0]`을 읽어, `dim_z` > 1 그림의 모든 slice가 slice 0으로 압축됐다(병렬과 직렬 대조가 RGBA ASTC에서만 갈려 찾음 — thread_count는 무관, dim_z만 결과를 바꿨다). `Rocks.patch`가 `img.data[zpos]`로 고친다. UE는 BGRA 입력이라 swizzle이 항등이 아니어서 일반 경로(`load_image_block`)를 타 걸리지 않는다. 직렬은 slice마다 `zpos` = 0이라 byte가 같으므로 `AstcEncoderIdentity`의 `rocks-patch 1`과 너겟 키는 그대로다(신원 문자열은 patch 내용과 1:1이 아니다 — 출력이 바뀔 때만 올린다). 컨텍스트 생성·reset도 결정적 FP 환경 안이다. 행 여백 입력의 빽빽한 사본은 ParallelFor 전에 호출 스레드에서 한 번 만든다.
   - 최소 batch: 형식마다 블록 비용이 100배 넘게 달라 형식별 이름 있는 상수로 둔다(초기값 — BC1–BC5 2048블록(UE DXT), BC6H·BC7·EAC 블록 행 하나, ASTC는 블록 단위 동적이라 해당 없음. TC5b에서 측정해 확정한다).
3. **API(TC5a)**: `TextureBlockOptions`에 `WorkerScheduler* scheduler`(없으면 호출 스레드 혼자)와 `uint32 minBatchBlocks`(0이면 형식 기본 — 시험이 작은 그림으로 batch 경계를 보게 낮춘다, 결과는 값과 무관)를 더한다. scheduler가 있으면 `scratch`가 필요하다(ParallelFor의 helper 작업 할당·ASTC slice 포인터와 사본 — 동시 Allocate·Deallocate가 안전한 allocator, `SystemAllocator`는 잠금 기반이라 맞다). scheduler가 null이 아닌데 scratch가 없으면 그림 크기와 무관하게 InvalidArgument다(작은 그림에서만 통과하는 오류를 막는다). 결과 byte는 scheduler 유무·worker 수·`minBatchBlocks`와 무관하다(계약). 헤더 주석을 고친다: "BC·EAC는 할당하지 않는다"는 직렬일 때로 좁히고 병렬의 helper 할당을 적는다, 옵션 머리 "BC1–BC5·EAC는 보지 않는다"는 scheduler·minBatchBlocks를 본다로 고친다.
4. **쿠킹 연결(TC5a)**: `TextureBuildExecution{ WorkerScheduler* scheduler; Allocator* scratch; }`를 `BuildTexture`의 새 인자로 둔다(설정이 아니라 결과가 같으므로 너겟 키에 넣지 않는다). `CookProjectRequest`(CookProject.h) → `CookRunRequest` → `CookContext`에 같은 두 칸을 더하고, `TextureCookProcessor`가 `BuildTexture`에 넘기며, `Encode`가 `TextureBlockOptions`에 옮긴다. `asset-cook` 명령은 압축 전용 scheduler(`CookWorkScheduler`)를 쿠킹 잠금을 잡은 뒤에 따로 만든다: worker 수 = min(논리 프로세서 − 1, 64)(셰이더 컴파일 관리자와 같은 규칙 — ShaderCompileManager.cpp 306–309). 검색용 ScanScheduler(worker 3 — CommandletScanWorkers)는 쓰지 않는다. scratch는 명령의 allocator다(Launch 프로세스 기본 allocator — 여러 스레드 동시 호출 안전, 구현 리뷰 정정: 전에는 SystemAllocator라 적었다).
5. **결정성 시험(TC5a)**: 모든 형식(BC1·BC3·BC4·BC5·BC6H·BC7·EAC R11·ASTC 다섯 크기 × RGB·RGBA·노멀 LA·sRGB)에서 직렬과 scheduler worker 1·2·4·8의 byte가 같음 — `minBatchBlocks`를 작게 해 batch가 여럿이고, 블록 높이 배수가 아닌 그림 높이, 마지막 batch가 1행, batch가 slice를 넘는 경우를 넣는다. 행 여백 입력 + scheduler, scheduler 시작 전·종료 뒤(직렬 대체), 같은 scheduler worker 안에서 부름(직렬 대체), scheduler 있고 scratch 없음 InvalidArgument. BC1·BC3·BC4·BC5 FTZ·DAZ·0 쪽 반올림 호출자 시험(직렬·병렬). 해시 golden(BC·ISPC·ASTC·EAC)은 그대로다. 쿠킹: scheduler 유무로 너겟 byte·키가 같음, `verifyNuggets` 통과.
6. **준비 단계 병렬과 측정(TC5b)**:
   - 단계별 시간을 먼저 잰다(원본 decode·resample·mip 생성·노멀 정규화·float → 인코더 입력 변환·인코딩, Release x64, 1024² 이상 그림 — 256²은 BC 4096블록이라 batch 하나다).
   - UE처럼 준비 단계를 행 병렬로 한다: `Encode`의 변환 루프, `Resample`·`NextMip`·`NormalizeNormals`(행마다 순수 함수 — 같은 `TextureBuildExecution`, 결정적 FP 환경 안. `BuildTexture` 전체의 float·double 연산도 결정적 환경 안으로 옮긴다). mip 사이 병렬(UE식 mip 0과 아래 mip 묶음 동시, 또는 (mip, 행)을 펼친 ParallelFor 하나)은 측정을 보고 정한다.
   - 형식마다 직렬·worker 수별 blocks/s와 최소 batch 후보별 시간을 기록하고 최소 batch 상수를 확정한다.
   - EAC: 잡음 4096² Alpha(mip 포함 약 1.4M 블록)가 개발 기기 전체 코어(압축 scheduler)로 1분 안이면 탐색은 그대로 둔다. 넘으면 탐색 제한과 그 오차 차이를 잰 뒤 정한다(정확 최적을 버리면 `RocksEacEncoderVersion`을 올린다).
   - **측정 결과(2026-11-28, x64 Release, 논리 프로세서 20 — 압축 scheduler worker 19 + 호출 스레드, `TextureCodecCompare --speed --judge-eac`)**:
     - 인코더(1024² 값 잡음, blocks/s 직렬 → 병렬): BC1 60 305 → 466 582(7.7배), BC3 68 011 → 523 448(7.7배), BC4 4.38M → 31.4M(7.2배), BC5 2.25M → 14.2M(6.3배), BC6H 170 579 → 1.52M(8.9배), BC7 31 786 → 419 218(13.2배), EAC R11 6 179 → 76 805(12.4배), ASTC 4×4 15 179 → 212 358(14.0배), 6×6 5 407 → 68 409(12.7배), 8×8 2 643 → 36 133(13.7배), 12×12 1 096 → 15 475(14.1배).
     - BC1 최소 batch 후보(병렬 초): 128블록 0.136, 512 0.134, 2048 0.140, 8192 0.238, 32768 0.814 — 기본 2048을 확정한다(작은 값과 같은 수준, 8192부터 batch 수가 모자라 느려진다).
     - BuildTexture(2048² 값 잡음, mip 사슬, 초 직렬 → 병렬): 준비만(비압축 BGRA8) 0.087 → 0.087, Windows BC1 8.15 → 0.91, Windows BC7 10.44 → 1.06, Android ASTC 6×6 31.07 → 2.33, Android EAC R11 73.19 → 6.13.
     - EAC 판단: 잡음 4096² Alpha(Android, mip 사슬) 병렬 34.3초 — 1분 안이므로 정확 최적 탐색을 그대로 둔다(`RocksEacEncoderVersion` 1).
   - **결정(측정 반영)**: 준비 단계(decode·재표본·mip 생성·변환) 병렬은 보류한다 — 2048²에서 0.087초로 가장 빠른 병렬 경우(BC1 0.91초)의 10% 안이고 나머지 형식에서는 2–4%다. 대신 결정성 빈틈을 막는다: `BuildTexture` 전체를 결정적 FP 환경 안에서 실행한다(호출자의 FTZ·DAZ·반올림이 sRGB 변환·재표본·mip 생성을 바꾸지 않게 — 시험 TextureBuild_FloatingPointEnvironment). 준비 단계가 병목이 되는 프로필(아주 큰 비압축 출력 등)이 나오면 그때 행 병렬을 넣는다.
7. **대조 기록(TC5c)**:
   - ISPC `Rocks.patch`(주축 재시작)의 속도 영향: 측정 그림에서 patch 있음·없음 blocks/s와 재시작 블록 비율.
   - BC1–BC5 기준: UE 클론 `Engine/Binaries/ThirdParty/nvTextureTools`에는 Linux `libnvtt.so`(x86_64)만 있고 Win64 DLL은 없다. UE Windows는 기본·AVX2 두 DLL을 배포하므로(nvTextureTools.Build.cs 36–37) UE BC1–BC5 byte도 호스트 CPU에 따라 다를 수 있다. TC1 golden은 같은 NVTT 2.0.8 원본을 같은 경로로 빌드한 probe 출력이다(12.17.4 3). WSL이 있으면 `libnvtt.so`로 golden 그림을 압축해 TC1 golden과 byte를 대조하고, 없으면 한계로 둔다.
   - **결과(2026-11-28)**:
     - ISPC patch 속도(1024² 값 잡음, Release, 같은 조건에서 patch 있음·없음을 번갈아 두 번씩 — 기계를 다른 세션이 같이 써 회차 사이 흔들림이 크다, blocks/s 평균): BC7 직렬 40 712 대 46 769(0.87배), 병렬 431 294 대 485 768(0.89배), BC6H 직렬 164 669 대 172 428(0.95배), 병렬 1.52M 대 1.84M(0.83배). 재시작이 power iteration을 한 번 더 도는 비용으로 5–17% 느리다(흔들림을 감안한 범위). BC6H도 같은 `compute_axis`를 써 영향을 받는다. 품질 이득(음의 상관 그림 BC7 37.7 → UE 수준 — 12.17.6 10)이 이 비용보다 커서 patch를 그대로 둔다. 재시작 블록 비율은 커널에 계수를 넣어야 재므로 재지 않았다.
     - BC1–BC5 `libnvtt.so` 대조: 이 기계의 WSL Ubuntu가 디스크 이미지(ext4.vhdx)를 찾지 못해 시작되지 않는다. 대조하지 못했고 한계로 남긴다(TC1 golden은 같은 NVTT 원본 빌드와 byte 동일 — 12.17.4 3).
8. **한계**: 텍스처 사이 병렬과 쿠커 패키지 병렬은 TC5 밖이다. 나중에 패키지 병렬을 같은 scheduler에 올리면 worker 안 호출이 조용히 직렬이 되므로(ParallelFor 규칙) 별도 scheduler나 기다리는 동안 돕는 기능이 필요하다. Mac Arm64 결정성·해시 확인은 사용자 몫으로 남는다.
