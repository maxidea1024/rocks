### 12.17 텍스처 압축 단계 구현 세부(TC — 2026-11-26 착수 때 정함, 교차 검증 반영 개정 1, TC1 원본 대조 개정 2)

12.16절 형식 표를 구현하는 단계다. 착수는 사용자 결정(2026-11-26 — 화면 마일스톤 SM7·SM8에서 쿠킹 비압축 텍스처가 화면에 나온 뒤, 렌더 SM9와 병행)이다. 기준은 UE 5.8 Oodle 없는 경로다: BC1–5 `TextureFormatDXT`(NVTT 2.0.8 — Quality_Production), BC6H·BC7 `TextureFormatIntelISPCTexComp`(ISPC Texture Compressor), ASTC `TextureFormatASTC`(ARM astc-encoder). 형식 선택은 `GetDefaultTextureFormatName`(Texture.cpp 4201–4489), 채널 복제는 TextureDerivedData.cpp 876–883, 알파 판정은 TextureCompressorModule.cpp 2998–3080·TextureCompressorModule.h 388–400, 압축 입력 변환은 TextureFormatDXT.cpp 506이다.

개정 1(2026-11-26, 교차 검증 필수 15·권장 8 반영): 압축 입력을 형식 선택 뒤 RGBA8로 고정(F1), 가장자리 채움을 NVTT 주기 반복으로(F2), BC3 색의 알파 가중치(F3), BC4·BC5·BC3 알파를 NVTT `compressDXT5A`로(F4), cluster fit 선택을 닫힌식 대리 오차로(F5), 끝점 순서·같은 끝점 규칙(F6), 기준 디코더(F7), 품질 기준을 NVTT 원본 golden으로(F8 — UE 클론의 NVTT 2.0.8 원본, MIT), 결정성 규칙(F9), Android 4의 배수(F10)·Normalmap 대체(F11)·Displacementmap SRGB(F12)를 UE대로 12.16절 정정, 너겟 키에 형식·인코더 버전(F13), 단계 사이 동작(F14), 샘플링 검증 전제(F15 — 렌더 요청).

개정 2(2026-11-27, TC1 착수 때 NVTT 2.0.8 원본과 UE 빌드 설정을 직접 대조): TD1·TD2·TD7·TD9를 원본대로 고친다. 고친 이유는 12.17.4에 모았다.

#### 12.17.1 결정

- **TD1 BC1–BC5는 자체 구현 — NVTT 2.0.8 Production 경로를 옮긴다**(사용자 승인 2026-11-26: 자체 구현. 교차 검증 F8·F9: UE 클론 `Engine/Source/ThirdParty/nvTextureTools/nvTextureTools-2.0.8/src`에 원본이 있다 — MIT). 알고리즘·순서를 NVTT 스칼라(비 AVX2) 경로와 같게 옮기고, 같은 원본을 시험 probe로 빌드해 golden을 만든다(TD9). 외부 라이브러리로 링크하지 않는 이유: NVTT 2는 nvcore·nvimage·nvmath 전체를 끌고 오며 필요한 것은 블록 압축 경로 몇 파일이다. 기준 경로는 squish SSE 경로다. UE 라이브러리는 VS2015 프로젝트로 빌드되고 `__SSE2__`를 정의한다(`src/project/vc14/squish/squish.vcxproj` 240). Epic 수정은 FMA를 끄고 역수 근사 대신 나눗셈을 써서(squish/config.h 52–58 `SQUISH_USE_DIV 1`) SSE2 DLL과 AVX2 DLL의 출력이 같게 했다(같은 파일 60–72의 MD5 대조 — 텍스처 몇 장의 경험적 확인이다). 한계: golden은 UE가 배포한 `nvtt_64.dll`이 아니라 같은 원본을 같은 설정으로 clang 빌드한 probe다. UE 클론에는 Win64 DLL이 없다(GitDependencies가 받는다). AVX2 DLL은 squish만 `/arch:AVX2`로 빌드하고(squish.vcxproj 274·281·290 — nvtt.vcxproj에는 없다), 그때 MSVC가 스칼라 식을 FMA로 합쳤다면 공분산·투영 동률에서 갈릴 수 있다. 배포 DLL 두 개와의 직접 대조는 TC5에서 한다(DLL을 받아 같은 그림을 nvtt API로 압축하고, AVX2 DLL squish 함수에 `vfmadd`가 있는지 본다). Rocks는 그 SSE 경로의 lane 연산 순서를 스칼라 float로 옮긴다(12.17.4 1). squish의 비 SIMD 경로(weightedclusterfit.cpp 678–899)는 연산 순서가 달라 기준이 아니다.
- **TD2 인코더 알고리즘**(NVTT CompressDXT.cpp·QuickCompressDXT.cpp·squish 대응):
  - BC1 색: 중복 색을 가중치 1씩 묶은 집합(squish `ColourSet(rgba, 0, true)` minimal set — CompressDXT.cpp 224, colourset.cpp 35–)으로 시작한다. flags가 0이라 투명 texel 처리는 없고 같음 판정은 RGB만 본다. 단색 블록(알파 무시 — ColorBlock.cpp 114–128)은 최적 단색 표(SingleColorLookup `OMatch5`·`OMatch6` — 12.17.4 1)다. 그 밖은 `WeightedClusterFit`이다. 주축은 공분산의 power iteration 8회다. 시작 벡터는 노름이 가장 큰 행이고, 정규화는 세 성분의 max(절댓값 아님)로 나눈다(maths.cpp 64–77·84–107 SIMD판). max가 0이면 주축이 NaN이 되고 투영값 정렬이 texel 순서를 그대로 둔다. 결정적이므로 UE대로 둔다. 투영값은 안정 삽입 정렬이다(동률은 texel 순서). 4색 순서 분할(n개 집합이면 C(n+3, 3) — n = 16이면 969)·3색(C(n+2, 2) — 153)마다 닫힌식 대리 오차(양자화 격자 k/31·k/63, 이상적인 1/3 보간 — weightedclusterfit.cpp 441–676 SIMD판)를 구하고, 엄격한 `<`로 먼저 찾은 쪽을 남긴다. 3색 대 4색 비교도 같은 대리 오차다(4색은 3색 최선보다 엄격히 작을 때만 바꾼다 — colourfit.cpp 48–63). 정련은 NVTT처럼 하지 않는다. 3색 모드는 index 3(투명 검정)을 쓰지 않는다(UE `bSupportDXT1a = false`, TextureFormatDXT.cpp 155). 채널 가중치 1:1:1(231).
  - BC3: 색은 4색 모드만이고 texel 가중치는 (a + 1)/256이다(squish `kWeightColourByAlpha` — CompressDXT.cpp 353, colourset.cpp 63·96). 집합은 묶지 않은 16점이다(`ColourSet(rgba, kWeightColourByAlpha)` — minimal set 인자가 기본값 false라 같은 색도 따로 센다, colourset.cpp 103–124). 단색 색 블록도 단색 표를 쓴다(347–350). 알파는 아래 DXT5A다.
  - BC4·BC5(채널마다)·BC3 알파: NVTT `QuickCompress::compressDXT5A`(CompressDXT.cpp 343·421·458, QuickCompressDXT.cpp 537–578) — min·max를 정수 (max − min)/34만큼 안으로 당긴 뒤 최소제곱 반복 최대 8회. 인덱스 선택·오차는 NVTT 내부 팔레트(바닥 나눗셈 `(6a + b)/7` — BlockDXT.cpp 353–364)로 잰다. 블록 안 값이 모두 같으면 처음 끝점이 alpha0 = alpha1이어서 6값 모드 블록이 나온다(팔레트 0·1이 그 값이라 index 0). 최소제곱이 alpha0 = alpha1을 내면 index를 0으로 쓴 뒤 곧바로 인덱스를 다시 고르므로(computeAlphaIndices — 6값 팔레트), 그 블록이 채택되면 index 6·7(0·255)이 나올 수 있다. 그 밖은 8값 모드다(UE와 같다). NVTT `compressBC4`는 A 채널을 압축한다. UE가 BC4를 쓰는 설정은 Alpha뿐이고 ReplicateRed(A = R) 뒤이므로 R을 압축하는 것과 같다. Rocks는 R을 압축한다. BC5는 R·G를 따로 한다(`splatX`·`splatY`).
  - **끝점 순서(F6)**: 4색·8값은 e0 > e1(uint16 / uint8)로 쓴다. 양자화 뒤 끝점이 같으면 index를 모두 0으로 쓴다(squish colourblock.cpp 116–130). 3색은 e0 ≤ e1로 쓰고, 맞바꿀 때 index 0·1도 맞바꾼다. 같으면 그대로 둔다. 단색 표 블록은 index를 모두 2로 쓰고, col0 < col1이면 끝점을 맞바꾸고 index를 모두 3으로 쓴다. 같으면 index 2 그대로다(OptimalCompressDXT.cpp 189–204 — 이때 디코더는 3색 모드로 읽지만 index 2가 같은 색이다). 8값 알파의 같은 끝점은 최소제곱 단계에서 index를 0으로 쓰지만 다음 인덱스 계산이 덮어쓴다(QuickCompressDXT.cpp 368–374·560 — 위 BC4·BC5 항목).
- **TD3 압축 입력(F1)**: BC4는 R을 압축한다. NVTT·UE는 A를 압축하므로(CompressDXT.cpp 421) 둘이 같은 조건은 ReplicateRed(A = R)가 적용되고 sRGB가 꺼진 경우다(TextureDerivedData.cpp 880–882, TextureCompressorModule.cpp 3143). TC2는 BC4를 이 조건(Alpha 설정 — TD6)에서만 고른다. 형식 선택(12.17.2)을 12.13절 출력 단계(8번) 앞에 둔다. 고른 형식이 BC1–BC5·BC7이면 출력 단계는 원본 정밀도와 무관하게 RGBA8을 만든다(sRGB 텍스처는 색을 sRGB 부호화, 알파는 선형 — UE `CopyTo(BGRA8, GetDestGammaSpace())`, TextureFormatDXT.cpp 506). BC6H 입력은 RGBA16F다. 오차는 그 부호화 공간에서 잰다(UE와 같다). BC4 입력은 복제 뒤 R(TD6), BC5는 R·G다.
- **TD4 블록 가장자리(F2)**: 블록보다 작은 mip(하위 mip — 상위 mip은 TD8 규칙상 4의 배수)은 NVTT `ColorBlock` 주기 반복으로 채운다: 폭(높이) 1은 0,0,0,0, 2는 0,1,0,1, 3은 0,1,2,0(nvimage/ColorBlock.cpp 58–82 remainder 표). 채움 texel도 맞춤 가중치에 들어간다(NVTT와 같다). 블록 수는 ceil(w/4) × ceil(h/4)이다. UE 예외: UE `CompressImageUsingNVTT`(TextureFormatDXT.cpp 320–388)는 배치마다 높이를 `RowsPerBatch × 4`로 고정하므로, 높이가 4의 배수가 아니고 배치 조건이 맞으면(예: 1024 × 510, 64 × 1022 mip) 마지막 배치가 버퍼 밖 행을 읽어 마지막 블록 행이 remainder 반복이 아닌 값으로 채워진다(slice가 여럿이면 다음 slice의 행). Rocks는 NVTT 전체 그림 의미(remainder 반복)를 따르고, 그 경우만 UE와 byte가 다르다.
- **TD5 알파 판정**(UE `DetermineAlphaChannelTransparency` cpp 2998–3080, `GetTextureExpectsAlphaInPixelFormat` h 388–400): ForceNoAlpha면 불투명, 아니고 ForceAlpha면 투명, 아니면 원본 mip 0(모든 블록·slice)의 선형 최소 알파 ≤ 254.5/255면 투명(8비트 A ≠ 255와 같다). 원본에 알파 채널이 없으면 불투명이다. ReplicateRed 설정은 빨강 최솟값을 본다. UE는 ChromaKey·Bokeh LOD 그룹을 투명으로 강제하고 AdjustMin/MaxAlpha 등 보정을 판정 전에 적용한다 — 보정·ChromaKey는 Rocks에 아직 없으므로(12.4.1 계약) 그 단계를 구현할 때 이 판정에 넣는다. Bokeh 그룹은 TD8 비압축 조건이라 형식에 영향이 없다.
- **TD6 채널 복제 UE 대응 확정**(12.4.3 표 개정 — 그 표는 UE 5.6 공개 문서만으로 정했다): Grayscale·Alpha는 ReplicateRed(RGBA = R), Displacementmap·DistanceFieldFont는 ReplicateAlpha(RGBA = A — TextureCompressorModule.cpp 3151–3164)다. 지금 Displacementmap·DistanceFieldFont의 "빨강"은 UE와 다르다 — TC2에서 알파로 바꾼다. 원본에 알파가 없으면 결과는 1이다(UE 그대로 — UE에 경고가 없으므로 Rocks도 경고하지 않는다, R3).
- **TD7 기준 디코더(F7, 개정 2)**: 시험·PSNR은 golden 원본과 같은 식인 NVTT `BlockDXT` 디코더로 잰다(BlockDXT.cpp 36–140·343–380). 색: 565 확장 `(q << 3) | (q >> 2)`(6비트는 `(q << 2) | (q >> 4)`), col0 > col1이면 4색 (2a + b)/3·(a + 2b)/3, 아니면 3색 (a + b)/2와 투명 검정이다. 알파·BC4·BC5: alpha0 > alpha1이면 8값 ((7 − k)·a0 + k·a1)/7(k = 1…6, 바닥), 아니면 6값 ((5 − k)·a0 + k·a1)/5와 0·255다. D3D 명세는 보간 반올림을 정하지 않고 오차를 허용하므로(정확한 식이 없다) golden 원본의 식을 기준으로 둔다. 인코더의 index 선택은 이 디코더 값이 아니라 위 TD2의 NVTT 내부 계산을 따른다(색은 대리 오차, 알파는 같은 바닥 팔레트).
- **TD8 비압축 대체·마무리(F10·F11·F12·R2)**: UE `GetDefaultTextureFormatName` 순서를 그대로 쓴다(12.17.2). 4의 배수 규칙(상위 mip 한 변이 4 미만이거나 4의 배수 아님 → 비압축)은 Android(ASTC 재대응 전)에도 적용한다(Texture.cpp 4253–4263, AndroidTargetPlatformControls.cpp 509 — 12.16.2 "정렬" 문단을 정정한다). Normalmap 대체는 UE대로 `BGRA8Unorm`이다(4396–4434 — XGXR8은 DXT5n일 때만, 12.16.1 정정). SRGB를 막는 설정은 Alpha·Normalmap·Masks·HDR류뿐이고(772–777) G8 + SRGB → `BGRA8UnormSrgb`는 Displacementmap·DistanceFieldFont에도 적용한다(4444–4446 — 12.4.3·12.13 `TextureCompressionIgnoresSrgb`·12.16.1을 같이 맞춘다). G16 원본 + SRGB는 선형 `R16Unorm` 그대로다(TextureFormatUncompressed.cpp 230–232). 32F → 16F 대체(4450–4475)는 샘플링 검증 앞이다. 4채널 8비트 비압축 출력은 `BGRA8Unorm`(sRGB면 `BGRA8UnormSrgb`)이고 byte 순서는 B, G, R, A다.
- **TD9 결정성과 품질 기준(F8·F9)**:
  - 결정성: 블록 인코딩은 블록 하나의 순수 함수다. 블록 안 부동소수점은 12.13절 계산 정밀도 규칙(FMA 금지·연산 순서 고정·fast-math 금지)을 따르고, 정렬은 안정 정렬이다. 블록 범위 병렬은 제자리에 쓰므로 스레드 수와 무관하다. 이후 SIMD 최적화는 byte가 같아야 하고, 아니면 인코더 버전(TD10)을 올린다.
  - 품질(개정 2): UE 클론의 NVTT 2.0.8 원본을 SSE 경로(`__SSE2__`, AVX2 끔, FMA 끔 — UE 비 AVX2 DLL과 같은 설정)로 probe에 빌드해 시험 그림 셋의 압축 byte를 golden으로 기록한다(12.17.4 3). 전제: 부동소수 제어는 기본값이다(FTZ·DAZ 꺼짐, 가장 가까운 값으로 반올림 — 12.13절 계산 정밀도 규칙). TD1 한계(배포 DLL 직접 대조는 TC5)와 TD4 UE 예외를 함께 본다. 판정은 모든 블록의 byte 동일이다. 다르면 시험이 다른 블록 수와 첫 블록 위치를 보고하고 실패한다(PSNR 허용 범위로 넘기지 않는다 — 같은 연산 순서이므로 차이는 이식 오류다). 기준 디코더(TD7) PSNR은 측정 보고용이다(TC5). golden 생성 도구와 절차는 저장소에 둔다(Tools — probe 원본은 UE 클론 경로를 인자로 받는다, NVTT 원본을 저장소에 복사하지 않는다).
- **TD10 너겟 키·버전(F13)**: 고른 PixelFormat, 인코더 id(`RocksBc` 등)와 형식별 인코더 버전(UE `GetEncoderName`·`GetVersion` 대응)을 너겟 키에 넣는다. 형식은 프로필(backend 검증·32F 필터·압축 볼륨 지원·TC4 형식 계열)에 따라 달라지므로 12.14절 "프로필은 키에 넣지 않고 대상 형식은 빌드 버전으로 대신"을 이 둘로 바꾼다. TC2에서 출력 byte가 바뀌므로 `TextureBuildVersion`도 한 번 올린다. 이후 인코더만 바뀌면 그 형식 버전만 올린다.
- **TD11 단계 사이 동작(F14)**: TC2 뒤 TC3 전에는 BC7 설정이 `BGRA8Unorm(Srgb)` 대체 + 경고 `EncoderUnavailable`(detail = 원래 형식), HDR_Compressed는 12.16.1 대체 `RGBA16Float`(경고 같음)다. TC4 전 Android 프로필은 12.16.2 재대응 없이 TD8 비압축이다(BC를 Android에 내지 않는다 — 형식 계열 칸이 없으면 비압축). 12.4.3 끝의 "프로파일이 압축을 요구하면 UnsupportedSetting"은 TC2에서 지운다(압축을 하므로).
- **TD12 모든 backend 샘플링 검증(F15·R5)**: 고른 형식(대체 포함)은 프로필 `graphicsBackends`마다 샘플링 보장이어야 하고, 못 하면 다음 대체로, 마지막 대체는 backend별 보장 비압축(`RGBA8Unorm` 계열)이다. 경고 `PlatformFormatFallback`(detail = 원래 형식, 진단 related에 backend·텍스처 id). 판정 표는 렌더 세션이 GraphicsTypes 공개 표로 넣었다(2026-11-27 d4f5e56d8 — `GraphicsTypes/CookSampling.h`, 설계 Docs/Design/PixelFormat 7.1절). 키는 (Backend, GraphicsPlatform — Windows·Mac·Android)이고, 쿠킹 대상 조합은 D3D12·D3D11·Vulkan(Windows), Vulkan·OpenGL(Android), Metal(Mac)이다. 쓰는 법: `CookSamplingGuarantee(backends, platform, format)`으로 보장 caps를 얻어 `HasPixelFormatCaps(…, CookSamplingCaps)`로 판정하고, 마지막 대체는 `CookSamplingFallback(backends, platform, format[, required])`이다. 프로필 id는 `ParseGraphicsPlatformName`, backend 이름은 `ParseBackendName`으로 바꾼다. 쿠커는 GraphicsTypes만 링크한다. Vulkan BC는 이제 선택 기능이 아니다. 장치 생성이 표의 "엔진 요구" 칸(예: Windows Vulkan은 BC·16비트 unorm·32F 필터, Android Vulkan은 ASTC LDR·ETC2)과 대조하고, 칸이 하나라도 없으면 장치를 받지 않는다(UE와 같다). TC2가 이 표로 검증을 켠다(12.17.2 8번).
- **TD13 외부 인코더(TC3·TC4 — 착수 때 세부, R8)**: BC6H·BC7은 ISPC Texture Compressor(MIT) 원본을 ThirdParty로 들여와 빌드한다(커널 컴파일용 ISPC 컴파일러는 LLVM처럼 `out/toolchains`에 받는 도구다 — 미리 만든 ispc_texcomp 라이브러리는 쓰지 않는다). ASTC는 ARM astc-encoder(Apache-2.0 — C++ 예외를 쓰지 않는 빌드 설정 확인). 품질 설정은 UE 그 모듈의 기본(ISPC BC7 프로필·astcenc preset ↔ CompressionQuality)을 따른다.

#### 12.17.2 형식 선택(TC2 — UE `GetDefaultTextureFormatName` 순서의 코드화)

입력: 유효 CompressionSettings·SRGB(TD8로 막힌 설정은 끔)·ForceAlpha·ForceNoAlpha·CompressionNone·LOD 그룹·차원, TD5 알파, 원본 형식(회색·16비트·float), 상위 mip 크기, 프로필(backend 목록·norm16·32F 필터·압축 볼륨·형식 계열). 순서:
1. 계약 밖 설정(LQ 등)은 지금처럼 `InvalidSetting`(12.8절).
2. 비압축 강제(CompressionNone, LOD 그룹 ColorLookupTable·Bokeh·IESLightProfile, 압축 볼륨 미지원 대상의 Volume)면 비압축 형식.
3. 12.16.1 표의 형식(AutoDXT = TD5 알파로 BC1·BC3, sRGB 짝 BC1·BC3·BC7).
4. BC이고 상위 mip 한 변이 4 미만이거나 4의 배수가 아니면 비압축(TD8 — 모든 플랫폼).
5. UE 마무리: G8 + SRGB → `BGRA8UnormSrgb`, 32F → 16F(필터·플랫폼).
6. TD11 단계 사이 대체(인코더 없음).
7. 형식 계열 ASTC(TC4)면 12.16.2 재대응.
8. TD12 샘플링 검증(표가 있을 때).

swizzle 칸(TexturePlatformData)은 12.16.4 (가)대로 sampler type 계약 데이터이고, UE처럼 형식이 아니라 CompressionSettings로 정한다(MaterialExpressionUtils.cpp 32–48 — R1): Grayscale·Alpha·DistanceFieldFont `rrrr`, Displacementmap `r001`, Normalmap `rg01`(BC5·대체 BGRA8 모두 — 셰이더가 Z 복원), 그 밖 항등. 12.13절이 회색 sRGB를 데이터에 복제한 뒤 항등으로 두는 지금 동작은 TC2에서 이 규칙으로 바꾼다(12.16.4 (가) — 데이터는 BGRA8 그대로, swizzle 칸만).

#### 12.17.4 TC1 구현 세부(2026-11-27)

1. **연산 순서(TD1·TD9)**: squish SSE 경로의 `Vec4` 연산(simd_sse.h)을 lane마다 float 한 번씩의 스칼라 연산으로 옮긴다. IEEE 단정밀도 연산은 SSE와 스칼라가 같은 값을 내므로, 연산의 종류와 순서만 같으면 byte가 같다. 옮길 때 지키는 의미는 다음과 같다.
   - `MultiplyAdd(a, b, c)` = a·b 뒤 + c(두 번 반올림 — FMA 끔), `NegativeMultiplySubtract(a, b, c)` = c − a·b, `Reciprocal(v)` = 1/v 나눗셈(`SQUISH_USE_DIV`).
   - `Max(x, y)` = x > y ? x : y, `Min(x, y)` = x < y ? x : y(`_mm_max_ps`·`_mm_min_ps` — NaN이면 둘째 값).
   - `Truncate(v)` = int32 절사 뒤 float(`_mm_cvttps_epi32` — NaN·범위 밖은 INT32_MIN). AVX2 DLL은 floor를 쓰지만 0 이상 값에서는 같고 NaN 후보는 어느 쪽이든 이기지 못한다.
   - `CompareAnyLessThan` = 네 lane 중 하나라도 `<`. 오차는 세 lane 합을 모든 lane에 펴므로 첫 lane 비교와 같다.
   - 점 lane: (R, G, B, 1)/255 × 가중치(W lane = 가중치). 공분산·주축 시작·투영은 squish `Vec3` 스칼라 식 그대로다(`/=` float는 역수 곱 — maths.h 107–113, `Dot`은 x·x + y·y + z·z 왼쪽부터).
   - NVTT 알파 최소제곱의 `uint(min(max(a, 0), 255))`는 NaN이면 0이다(nv::max·nv::min은 `<` 비교로 NaN을 그대로 넘기고, x64의 float → uint 변환은 64비트 절사의 하위 32비트라 NaN이 0이 된다). Rocks는 이 결과를 명시 코드로 쓴다(C++ 미정의 동작에 기대지 않는다).
   - 단색 표는 상수 표(`Private/TextureBlockTables.h` — NVTT `OMatch5`·`OMatch6`과 같은 값)로 둔다. 컴파일 때 만들기에는 반복이 너무 많다(256 × 64 × 64). 시험이 `PrepareOptTable`(SingleColorLookup.h 주석 — float 오차 + 0.03·|max − min|, 엄격 `<`)로 다시 만들어 golden의 NVTT 표와 같은지, 인코더의 단색 끝점이 그 값인지 본다. 보간은 주석 본문의 `maxe + Mul8Bit(mine − maxe, 0x55)`가 아니라 같은 주석에 정의만 된 `Lerp13`(= (2·max + min)/3, 정수)이다. 주석 본문 식으로는 5비트 표 70항목이 다르고, Lerp13으로는 두 표 모두 같다(2026-11-27 golden 대조). NVTT 표는 Lerp13으로 만든 것이다.
2. **공개 API**(TextureTools `Public/TextureTools/TextureBlockEncode.h`):
   - `enum class TextureBlockFormat : uint8 { Bc1, Bc3, Bc4, Bc5 }` — TC2가 PixelFormat(sRGB 짝 포함)을 이 값으로 바꾼다. sRGB는 인코딩에 영향이 없다(UE도 감마는 입력 byte로만 들어간다).
   - `TextureBlockBytes(format)`(8·16·8·16), `TextureBlockOutputBytes(format, sizeX, sizeY, numSlices)` → `Result<uint64>`. 크기 0은 InvalidArgument, 곱이 넘치면 CapacityExceeded다. 블록 수는 slice마다 ceil(sizeX/4) × ceil(sizeY/4)이다.
   - `TextureBlockImage { Span<const uint8> rgba; uint32 sizeX, sizeY, numSlices = 1; usize rowPitch = 0; usize slicePitch = 0; }` — 입력은 RGBA8(R, G, B, A byte 순서)이다. pitch 0은 빽빽함(sizeX·4, rowPitch·sizeY)이다.
   - `EncodeTextureBlocks(format, image, Span<uint8> out)` → `Result<void>`. 출력은 slice 순, 블록 행 순, 블록 열 순이다. 할당은 없다(블록마다 스택 64 byte). 오류: 크기 0·rowPitch가 행보다 작음·slicePitch가 slice가 닿는 byte(rowPitch × (sizeY − 1) + 행 byte)보다 작음·입력 byte 부족·out 크기가 `TextureBlockOutputBytes`와 다름은 InvalidArgument, 출력 크기나 pitch로 계산한 입력 범위가 uint64를 넘으면 CapacityExceeded다. 실패하면 out 내용은 정하지 않는다.
   - `EncodeTextureBlock(format, const uint8 (&texels)[64], uint8* out)` — 4×4 RGBA texel 한 블록(행 우선)이다. 가장자리 채움(TD4)은 `EncodeTextureBlocks`가 하고 이 함수는 받은 16 texel을 그대로 쓴다.
   - `DecodeTextureBlock(format, const uint8* block, uint8 (&texels)[64])` — TD7 기준 디코더다. BC1·BC3은 RGBA, BC4는 (R, 0, 0, 255), BC5는 (R, G, 0, 255)를 쓴다.
   - `RocksBcEncoderVersion`(1) — TD10의 인코더 버전이다(키 연결은 TC2).
3. **golden 도구**(`Tools/NvttGolden`):
   - `NvttGoldenProbe.cpp`가 UE 클론의 NVTT 원본(squish colourset·colourfit·weightedclusterfit·colourblock·maths, nvimage ColorBlock·BlockDXT·Image, nvtt OptimalCompressDXT·QuickCompressDXT)을 한 번역 단위로 묶어 빌드한다. 압축은 `SlowCompressor`와 같은 순서로 블록마다 부른다(BC4는 A = R로 만든 블록, BC5는 `splatX`·`splatY`). 가장자리 블록은 NVTT `ColorBlock::init`(remainder 표)을 그대로 쓴다.
   - `make_golden.py <UE 클론 경로>`가 LLVM 툴체인 clang으로 probe를 빌드해 실행하고 `Engine/Source/Developer/TextureTools/Tests/Fixtures/NvttGolden/NvttBlockGolden.bin`을 쓴다. NVTT 원본은 저장소에 들어오지 않는다.
   - 시험 그림은 probe와 시험이 같은 생성기 헤더(`TextureTools/Tests/BlockGoldenImages.h` — Rocks·표준 헤더 없이 정수식만)를 include해 만든다. golden 파일에 그림별 입력 해시를 넣어 생성기가 바뀌면 시험이 먼저 실패한다. 그림: 선형 그라디언트, 방사형, 값 노이즈(부드러운 자연 그림 대용), 백색 노이즈, 색 경계(체커), 알파 경계(알파 계단 + 색 그라디언트), 노멀(구면 RG), 두 색, 한 texel만 다른 블록, 회색조, 단색 — 각 32×32. 가장자리: (w, h) ∈ {1, 2, 3, 5, 6, 7, 9}²의 일부 조합. 무작위: 128×128 블록 단위 분포 셋(균일, 좁은 범위, 두 무리). 드문 경로(리뷰 반영): 256×256 넷 — 값 차이 0–2(565 같은 끝점), 블록마다 2–4색 + 섞인 알파, 0·255 근처 알파(6값 붕괴·index 6/7), 한 texel의 한 채널만 1 다름(거의 퇴화한 공분산). 이 넷은 golden에 출력 해시만 둔다.
   - 파일 형식(버전 2): 머리(magic `RNVG`, 버전, 항목 수), 단색 표(OMatch5·OMatch6 각 512 byte), 항목마다(이름, 형식, 크기, 입력 FNV-1a 64, NVTT 디코드 FNV-1a 64 — 블록마다 64 byte를 출력 순서로 이어서, 출력 FNV-1a 64, 출력 byte 수와 byte — 해시 전용 항목은 0). 리틀 엔디언이다. 해시는 어긋남 검출용이라 FNV로 충분하다(probe에 SHA-256을 넣지 않는다).
   - 사진 조각은 넣지 않는다(probe에 이미지 디코더를 들이지 않는다 — 값 노이즈와 무작위 분포가 대신한다). TC5 측정에서 TestContent 실제 텍스처로 PSNR을 잰다.
4. **시험**(EngineTests `TextureTools/Tests/TextureBlockEncodeTests.cpp`):
   - golden: 모든 항목·형식의 byte 동일(다르면 다른 블록 수·첫 위치 보고 — 해시 전용 항목은 출력 해시), 기준 디코더 결과의 해시가 NVTT 디코드와 같음, 단색 표가 NVTT 표와 같음. 경로 커버리지: BC1 3색 승리(col0 < col1)·BC3 4색 같은 끝점(index 0)·알파 최소제곱 채택(처음 inset 끝점과 다름) 블록이 각각 하나 이상이고, BC3 색 블록마다 col0 ≥ col1·같은 끝점이면 index 0 또는 단색 index 2다. 6값 모드 index 6/7 블록 수는 보고한다.
   - 규칙: 단색 블록 끝점(표 값·index 2/3 규칙), 4색 같은 끝점이면 index 0, 3색 맞바꿈, 6값 알파(값이 모두 같을 때), BC4 = BC3 알파 블록(같은 채널 값이면 같은 8 byte), BC5 = R·G 각각 BC4.
   - 가장자리: 1–9 크기에서 remainder 채움과 블록 수, pitch·slice 입력(빽빽함과 같은 결과).
   - 결정성: 같은 입력 두 번, 다른 출력 버퍼에서 같은 byte. 주축 성분 부호가 섞이는 블록(음의 상관 — golden `negative-correlation`)도 golden과 같다. 주축 max가 0이 되는 NaN 경로는 단색이 아닌 블록에서는 정확한 산술로는 생기지 않는다(시작 행 i에 대해 (Mᵏeᵢ)ᵢ = ‖M^{k/2}eᵢ‖² > 0 — M은 양의 준정부호). 반올림이 끼면 이론상 깨질 수 있어 코드는 UE 의미(NaN이면 순서 그대로) 그대로 둔다.
   - 인자 오류: 크기 0, 입력 부족, pitch 부족, out 크기 다름, 출력 크기 넘침.
