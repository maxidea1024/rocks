### 12.15 A5k 구현 명세 — 텍스처 시나리오·PostLoad 판정·렌더 세션 알림(2026-11-25)

이 절은 12.7절 A5k를 정한다. A5k는 새 기능이 아니라 A5 전체를 한 흐름으로 묶어 확인하고, 다른 세션에 넘길 계약을 정리하는 단계다.

#### 1. 텍스처 시나리오(14절 1·2·10·11·21·24번의 텍스처 경로)

시험 `TextureScenario_ImportEditCookLoad`(TextureTools `Tests/TextureScenarioTests.cpp`)가 제품 부품을 그대로 이어 돈다. 쓰는 부품은 AssetService와 TextureTools 임포터·타입 hook, AssetCooker CookProject와 TextureCookProcessor, AssetRuntime 패키지 로드다.

1. **임포트**: PNG 둘(16×16 RGBA8)을 `/Game/T/Wall`·`/Game/T/Wall2`로 임포트한다. 패키지를 닫았다 다시 열어 같은 AssetId이고 원본 bulk가 PNG 픽셀과 같은지 본다(시나리오 1).
2. **묶음**: `asset-new Texture2DArray /Game/T/Arr sourceTextures=/Game/T/Wall,/Game/T/Wall2`로 묶음 배열을 만든다. 원본은 slice 2이고, 처음 만들기 설정(NoMipmaps·NeverStream)이 들어간다(12.14절 A5j2).
3. **설정 편집**: `asset-set /Game/T/Wall compressionSettings=Masks lodBias=1`을 한다. 정규화가 SRGB를 off로 저장한다(12.12절).
4. **원본 삭제**: Wall의 PNG 파일을 지우고 에디터 패키지만으로 쿠킹한다(시나리오 2).
5. **쿠킹**: `CookProject`(프로파일 Windows — 엔진 LOD 그룹 표 없이 기본 그룹, `alwaysCook /Game/`)에 TextureCookProcessor를 등록해 쿠킹한다. 게시와 매니페스트 3항목을 본다.
6. **로드 대조**: 매니페스트 항목의 쿠킹 패키지를 로드해 다음을 확인한다.
   - Wall: RGBA8Unorm, sRGB off, mip 4개(16에서 편향 1 — 8·4·2·1), 비스트리밍 R = 4(N < 7), mip 0 byte = 원본의 2×2 상자 평균(UE 식 — 12.5절, 시험이 같은 float 식으로 계산).
   - Arr: RGBA8UnormSrgb, slice 2, mip 1개, R = 1.
   - EditorOnly 원본·묶음 칸이 쿠킹 객체에 없다(시나리오 11).
7. **재현성**: 같은 입력으로 다시 쿠킹하면 모두 재사용되고(cooked 0) 매니페스트 byte가 같다(시나리오 13의 텍스처 경로).

시험은 메모리 파일 시스템과 임시 프로젝트 루트를 쓴다(AssetDatabase 시험 지원과 같다).

#### 2. 클래스별 PostLoad dispatch 판정(11절 16번)

판정: **텍스처는 클래스 PostLoad를 쓰지 않는다. dispatch는 후속으로 둔다.**

근거:
- 쿠킹 텍스처는 로드한 값 그대로 완결이다. 쿠킹 데이터(`platformData`)는 쿠킹 때 계산이 끝났고, 런타임이 다시 계산할 파생 상태가 없다(R·샘플러·mip 배치 — 12.5.1절, 렌더는 메타를 그대로 쓴다).
- UE `UTexture::PostLoad`가 하는 일은 Rocks의 다른 곳에 있다.
  - 에디터의 원본 판정·플랫폼 데이터 캐시 시작(`BeginCachePlatformData`)은 Rocks에서는 쿠킹 처리기가 한다.
  - 리소스 만들기(`UpdateResource`)는 렌더 세션이 맡는 업로드 경로가 한다(쿠킹 패키지 공개를 받아 GPU 리소스를 만든다 — TextureStreaming).
  - 에디터 객체의 `platformData`는 늘 기본값이다(12.14절 A5j1 9번).
- 그래서 지금 handler(`AssetPostLoadHandler`)는 EngineAssets가 주는 대로(없으면 공개와 함께 끝남) 둔다. 클래스 hook 등록·dispatch(RuntimeClassMetadata)는 처음 필요한 타입(예: 메시 LOD 파생값, 머티리얼 셰이더 맵 연결)이 정한다. 11절 16번의 "A5가 정한다"는 이 판정으로 바꾼다.
- 렌더 업로드를 PostLoad에 둘 수도 있지만 버린다. 업로드는 렌더 스레드·스트리밍 예산이 정하고, 로더 PostLoad는 Game 스레드의 동기 단계라서 섞으면 로더 예산(`maxPostLoads`)이 GPU 일에 묶인다. 렌더 세션 설계(TextureStreaming 4절)도 공개 뒤 요청으로 업로드한다.

#### 3. 렌더 세션 알림(쿠킹 데이터 형태)

A5k가 끝나면 렌더 세션(화면·업로드·스트리밍 담당 — 렌더 세션 조율 메모)에 다음을 알린다.
- **TexturePlatformData 칸**: 12.8절 목록. mip마다 크기·byte 수(패딩 제외), 스트리밍 mip은 bulk 하나씩(덩어리 hash = 그 BulkDataRef SHA-256), 상주 꼬리는 `tailBulk` 하나에 큰 mip부터 잇고 `tailOffset`으로 찾는다. 꼬리 안 mip 시작은 16 byte 정렬이고 사이는 0이다(RenderBase 6.5절 계약 — A5k에서 구현을 맞췄다, 12.5.1절 1번). 비스트리밍은 R = N이다(별도 표시 없음 — 12.5.1절).
- **bulk 정렬**: 쿠킹 패키지 bulk 정렬은 프로파일 `bulkAlignment`(0이면 4096)다. RenderBase 6.5절의 "스트리밍 덩어리 4 KiB 정렬"은 기본값이 지킨다. 프로파일이 4096보다 작게 정할 수 있으므로(8–65536), 렌더 쪽이 4 KiB를 요구로 굳히려면 알려 달라고 한다(그때 텍스처 쿠킹이 max(프로파일, 4096)을 쓰거나 프로파일 검증으로 막는다).
- **PixelFormat 번호 저장 계약**: `pixelFormat`은 GraphicsTypes `PixelFormat` enum의 숫자이고 쿠킹 데이터의 저장 형식이다. 기존 번호를 바꾸거나 다시 쓰지 않는다. 부득이 뜻을 바꾸면 TexturePlatformData 타입 버전을 올려 다시 쿠킹되게 한다. PixelFormat 문서(렌더 세션 소유)에 같은 계약을 적어 달라고 요청한다(12.8절).
- **지금 쿠킹이 내는 형식**: 비압축만 낸다 — R8·RG8·RGBA8(sRGB 변형 포함 — sRGB R8·RG8은 RGBA8 sRGB로 넓힌다), R16·RG16·RGBA16 Unorm(norm16 미지원 프로파일은 16F), R16F·RG16F·RGBA16F, R32F·RGBA32F. swizzle 넷은 셰이더 표본 뒤 적용한다(12.4.3절). 압축(BC·ASTC)은 압축 단계에서 더한다.
- **샘플러**: `sampler`(필터·maxAniso·주소 셋·Border 색)는 쿠킹 프로파일에서 굳힌 값이다. UE처럼 장치 프로파일마다 런타임에 바꾸지 않는다(12.14절 8번 — 다르게 하려면 렌더 세션 요구로).
- **CPU 가용성(계약)**: `availability` CPU 텍스처는 지금 mip 0 하나를 상주 꼬리에 두고 비스트리밍으로 쓴다. UE의 GPU placeholder + CPU 사본 배치는 렌더러 CPU 텍스처 지원과 함께 정한다(렌더 세션 결정 — 12.14절 A5j1 7번).
- **PostLoad 없음**: 텍스처는 클래스 PostLoad를 쓰지 않는다(2절). 업로드 시작은 쿠킹 패키지 공개(로드 요청 결과)다.
- **런타임 bias·시네마틱 mip**: 12.5.1절 4·5번 그대로다(TextureStreaming 4.3절 문구 개정 요청은 이미 했다).

알림은 cross-session 메시지로 보내고, 보낸 날짜와 대상 세션을 이 절 끝에 적는다.
