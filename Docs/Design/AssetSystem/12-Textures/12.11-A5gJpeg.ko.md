### 12.11 A5g 구현 명세 — JPEG(2026-11-24, 개정 1 — 교차 검증 1차 반영, 착수 전)

12.2절 표의 JPEG 행과 12.10절 TIFF의 JPEG·옛 JPEG 압축을 libjpeg-turbo로 받는다(12.7절 A5g). 결과·진단·한도·외부 라이브러리 공통 규칙은 12.9·12.10절과 같다.

**ThirdParty 모듈 `LibJpegTurbo`**(Engine/Source/ThirdParty/LibJpegTurbo — libjpeg-turbo 3.2.1, 2026-10-27 최신 안정판, 버전·SHA-256 고정. UE 5.8은 3.0.0 — 보안 수정이 쌓인 최신판을 쓴다, 하위호환 고려 없음. 라이선스 IJG·BSD-3-Clause·zlib — `LICENSE.md`·`README.ijg`):
- 반입: libjpeg API 라이브러리 전체(복호·부호화 — CMake `JPEG_SOURCES`와 같은 목록, 정밀도별 wrapper `src/wrapper/*-8·12·16.c`를 번역 단위로 — 12·16비트를 디코딩 전에 거부해도 `jdmaster.c`·`jcinit.c` 등이 `j12*`·`j16*` 함수를 참조하므로 링크에 필요하다, 산술 부호 복호·부호화 `jaricom.c`·`jdarith.c`·`jcarith.c` — libjpeg-turbo 기본과 같다). 부호화를 넣는 이유: libtiff의 JPEG 코덱(`tif_jpeg.c`)이 부호화 함수를 참조하고, 텍스처 내보내기(ImageCodec 인코더 — 후속)가 같은 라이브러리를 쓴다. TurboJPEG API(`turbojpeg.c` — 이미지 파일 I/O·내장 libspng를 끌고 온다)·도구·SIMD는 넣지 않는다(`WITH_SIMD` 미정의 — NASM 없는 C 경로, 12.2절).
- 손으로 쓰는 설정(원본 디렉터리 `src/`에 추가 파일 — modifications `upstreamSha256: null`, 12.10절 선례): `jconfig.h`(JPEG_LIB_VERSION 62 — libjpeg-turbo 기본, `C_ARITH_CODING_SUPPORTED`·`D_ARITH_CODING_SUPPORTED`·`MEM_SRCDST_SUPPORTED`, `WITH_SIMD` 없음), `jconfigint.h`(템플릿 `jconfigint.h.in`을 그대로 옮기고 값만 채운다 — `BUILD`·`HIDDEN`·`INLINE`·`THREAD_LOCAL`·`PACKAGE_NAME`·`VERSION`·`SIZEOF_SIZE_T`(SIZE_MAX로 판정 — 12.10절 리뷰와 같다)·`HAVE_BUILTIN_CTZL`·`HAVE_INTRIN_H`·`FALLTHROUGH`, 그리고 `BITS_IN_JSAMPLE`별로 산술 부호·`WITH_SIMD`를 다시 정하는 정밀도 블록 — 빠지면 12·16비트 wrapper가 다른 설정으로 컴파일된다), `jversion.h`(JPEG_LIB_VERSION 62 판).
- 메모리: `jmemnobs.c`(CRT malloc)를 빼고 Rocks 메모리 관리 파일 `jmemrocks.c`(추가 파일)가 `jpeg_get_small`·`jpeg_free_small`·`jpeg_get_large`·`jpeg_free_large`·`jpeg_mem_available`·`jpeg_mem_init`·`jpeg_mem_term`·`jpeg_open_backing_store`를 정의한다. 할당은 tif_rocks.c와 같은 스레드별 묶음(`RocksJpegBindAllocator` — 블록 머리에 할당 표를 적어 해제는 묶음과 무관)이다. libjpeg의 `client_data`는 쓰지 않는다(libtiff `tif_ojpeg.c`가 그 칸을 자기 용도로 쓴다). `jpeg_mem_available`은 jmemnobs처럼 `max_bytes_needed`를 돌려주고(크기는 `AllocateImage` 한도가 이미 막는다 — 16384²에서 progressive 계수 버퍼 최대 약 1.6 GB), 실제 할당 실패는 묶음의 실패 표지로 OutOfMemory가 된다(남은 몫을 돌려주면 jmemmgr가 backing store를 요구해 `JERR_NO_BACKING_STORE` → `InvalidSource`로 잘못 분류된다). backing store는 열지 않는다.
- 오류 경계: libjpeg는 오류를 `error_exit` → `longjmp`로 알린다. `longjmp`가 C++ 프레임을 건너지 않게 Rocks C 파일 `rocksjpeg.c`·`rocksjpeg.h`(추가 파일)가 `setjmp`를 C 안에 가둔 두 함수를 둔다: `RocksJpegReadInfo(data, size, info, error)`(`jpeg_read_header(…, TRUE)`까지 — tables-only 스트림은 오류, 크기·성분 수·색 공간·정밀도·lossless 여부·progressive 여부)와 `RocksJpegDecode(data, size, grayscale, pixels, rowBytes, error)`(`jpeg_start_decompress` → `jpeg_read_scanlines` → `jpeg_finish_decompress`). `emit_message`의 경고(level −1 — 손상 데이터 복구)는 곧바로 실패로 끝내고(아래), `output_message`는 출력하지 않는다(실행 중 printf 금지). libjpeg 상태(`jpeg_decompress_struct`·오류 관리자·progress 관리자)는 `setjmp`를 부르는 함수의 지역 변수가 아니라 호출자가 가진 상태 구조체에 두고, `setjmp`를 부르는 함수는 그 포인터로만 다룬다(TurboJPEG handle과 같은 방식). C17 7.13.2.1은 `setjmp` 뒤 바뀐 비-`volatile` 자동 변수의 값을 `longjmp` 뒤 불확정으로 둔다 — 지역 `cinfo`로 두었더니 Release(ThinLTO)가 `RocksJpegReadInfo`의 오류 경로를 도달 불가로 지워, `longjmp`가 정상 경로로 다시 들어가 create→오류→`longjmp`를 끝없이 반복하며 메모리 풀이 새었다(2026-11-25, 수십 GB). `volatile` 구조체는 libjpeg API에 넘길 때 한정자를 버려야 해서 버렸다. `setjmp` 뒤 바뀌는 그 밖의 지역 변수는 오류 경로에서 읽지 않는다. 오류 경로는 C 안에서 `jpeg_destroy_decompress`를 부른 뒤 돌아온다. progressive scan 수는 progress monitor로 `JpegMaxScans`(1000 — TurboJPEG `TJPARAM_SCANLIMIT`·djpeg `-maxscans`와 같은 방식)까지만 받는다(넘으면 `InvalidSource` + `CapacityExceeded` — 수천 scan짜리 작은 파일이 CPU를 오래 쓰는 알려진 문제, UE는 상한이 없다 — Rocks가 더 엄격하다).
- 경고 0(첫 빌드 2026-11-25): libjpeg 메서드 서명이 요구하지만 구현이 읽지 않는 인자에 `(void)`를 넣는다(Rocks.patch — 22개 파일, `-Wunused-parameter`; 진단 억제 지시문은 금지라 원본을 고친다). `rocksjpeg.c`는 `JPEG_INTERNALS`로 `jpeglib.h`가 이미 include하는 `jpegint.h`를 다시 include하지 않는다.
- libtiff: `tiffconf.h`에 `JPEG_SUPPORT`·`OJPEG_SUPPORT`를 켜고 `tif_jpeg.c`·`tif_ojpeg.c`를 번역 단위에 더한다(LibTiff 모듈이 LibJpegTurbo 헤더를 include — LibTiff.Build.cs, 12비트 JPEG TIFF의 dual mode는 켜지 않는다 — 12비트 TIFF는 12.10절 받는 비트 수 밖). ImageCodec 링크 순서는 LibTiff → LibJpegTurbo → Zlib. **TIFF 디코딩은 tif_rocks·jmemrocks 두 묶음을 함께 건다**(`tif_jpeg.c`·`tif_ojpeg.c`의 libjpeg 할당이 jmemrocks로 간다 — 할당 실패 표지는 같은 `ExternalAllocationScope`).

**JPEG 파일 규칙**(UE ImageWrapper `JpegImageWrapper.cpp` — TurboJPEG):
- 받는 것: JFIF·Adobe·EXIF 컨테이너, baseline·확장(8비트)·progressive·산술 부호, 8비트 정밀도, 정밀도 8 이하 lossless(SOF3·SOF7·SOF11·SOF15 — UE TurboJPEG 8비트 API(`tj3Decompress8`)도 푼다, 크기 조정만 막는다 — turbojpeg.c 2250. 정밀도 2–7은 값을 늘리지 않고 저장 값 그대로 G8·RGBA8에 둔다 — UE와 같다, 무손실 원본 보존), 비표준 sampling factor(UE `tjDecompressHeader3`는 `TJSAMP_UNKNOWN`으로 실패 — turbojpeg.c 2049, Rocks는 libjpeg API로 받는 상위집합). 성분 1 → G8, 성분 3(YCbCr — JFIF·Adobe transform 1, 또는 RGB — Adobe transform 0) → RGBA8(알파 255, libjpeg가 RGB로 바꾼다). 색 해석은 Unknown(12.10절 — 임포터가 SRGB 기본을 정한다).
- 판정 순서: `RocksJpegReadInfo` 뒤 디코딩 전에 정한다(12.10절 공통 규칙 2) — 정밀도 12·16(`data_precision` — lossless 9–16 포함, UE도 8비트 API라 실패)은 `UnsupportedSourceFormat`, CMYK·YCCK(성분 4 — UE도 거부, JpegImageWrapper.cpp 342–344)와 그 밖의 성분 수·색 공간은 `UnsupportedSourceFormat`. 크기는 `AllocateImage` 한도로.
- 디코딩 설정: IDCT `JDCT_ISLOW`(12.2절 결정 — UE는 `TJFLAG_FASTDCT`(`JDCT_IFAST`)로 풀어 픽셀이 1–2 정도 다를 수 있다. UE는 JPEG byte를 원본으로 보관하고 빌드 때 다시 풀 수 있지만 Rocks는 임포트 때 푼 픽셀을 영구 원본으로 저장하므로 정확한 IDCT를 쓴다 — UE와 다르다), fancy upsampling·block smoothing은 libjpeg 기본값(TurboJPEG 기본과 같다 — UE와 같다).
- 손상: libjpeg 경고(level −1 — 예: 이른 파일 끝을 회색으로 채움, 마커 앞 남는 byte)는 `InvalidSource`다. UE TurboJPEG도 경고가 있으면 −1을 돌려줘 임포트가 실패한다 — 머리 단계 `tj3DecompressHeader`(turbojpeg.c 2024, UE `tjDecompressHeader3` 2044 → 2024)와 복호 `tj3Decompress8`(turbojpeg-mp.c 293), JpegImageWrapper.cpp 336–338·452–455. Rocks는 첫 경고에서 멈춘다(머리 단계 경고까지 UE와 같은 결과이고 덜 일한다). 오류(`error_exit`)도 `InvalidSource`, 할당 실패는 묶음의 실패 표지로 OutOfMemory다(12.10절 공통 규칙 2).
- EXIF 회전은 적용하지 않는다(12.2절 — UE와 같다).

**TIFF JPEG**(12.10절 개정 — A5f의 "JPEG·옛 JPEG `UnsupportedSourceFormat`"을 바꾼다): Compression 7(JPEG)·6(옛 JPEG)을 libtiff 코덱으로 푼다(UE는 Mac·Linux에서만 받는다 — Windows libtiff는 JPEG 코덱을 끈다, 12.10절. Rocks는 모든 플랫폼 상위집합). 범위: `TiffDecoder.cpp`의 Compression 6·7 거부 분기와 `TiffDecode_RejectionsAndDamage`의 JPEG·OJPEG 기대값(`UnsupportedSourceFormat`)을 걷어낸다. Photometric YCbCr + JPEG는 12.10절 RGBA 경로(libtiff가 JPEGCOLORMODE RGB로 푼다), RGB·회색 + JPEG는 직접 경로다. libtiff JPEG 코덱의 경고는 다른 libtiff 경고처럼 버린다(UE와 같다 — libtiff 경로는 TurboJPEG가 아니다).

**버린 대안**: TurboJPEG API(UE가 쓰는 API — 그러나 `turbojpeg.c`가 이미지 파일 I/O·libspng를 끌고 오고 할당·오류 처리를 감싸 버린다. libjpeg API + C 경계 파일로 같은 디코딩을 한다), 복호만 반입(libtiff JPEG 코덱과 후속 내보내기가 부호화를 참조한다), `JDCT_IFAST`(UE와 같은 픽셀 — 그러나 영구 원본의 정확도가 낮다, 위), 경고 무시(UE와 다르고 손상을 조용히 받는다).

**시험(A5g)**: libjpeg 부호화 API로 시험 안에서 만든 JPEG — 회색·YCbCr 4:4:4·4:2:0·RGB(Adobe transform 0)·progressive·산술 부호·리셋 마커(DRI) → 같은 그림의 baseline 결과와 픽셀 대조(디코딩 경로가 같은 픽셀), 정밀도 8 lossless(`jpeg_enable_lossless` — 원본 픽셀과 정확히 같다)·정밀도 5 lossless(값을 늘리지 않음), 비표준 sampling factor(받음), 12비트·12비트 lossless·CMYK·YCCK·성분 2개 `UnsupportedSourceFormat`, tables-only 스트림 `InvalidSource`, 머리 단계 경고(JFIF 판 번호 이상·SOF 앞 남는 byte) `InvalidSource`, scan 상한(`JpegMaxScans` + 1 scan → `CapacityExceeded`), 절단 전수(경고 포함 — `InvalidSource`), 마커 앞 남는 byte `InvalidSource`, 한도 `CapacityExceeded`, NFail(OutOfMemory 또는 같은 결과로 성공), 스레드 둘의 할당 횟수 = 단독, TIFF JPEG(RGB·YCbCr 4:2:0·JPEGTables 태그·할당 실패 NFail — 두 묶음 확인)·옛 JPEG(libtiff 원본의 `ojpeg_*.tiff` — 외부 참조 파일, 빌드 때). 외부 참조 파일: libjpeg-turbo `testimages`(testorig.jpg·testimgp.jpg·testimgari.jpg·testorig12.jpg 등)를 `ImageCodec/Tests/Fixtures/`에 두고 UE 결과와 대조한다(빌드 때 — IDCT 차이는 허용 오차로 확인).
