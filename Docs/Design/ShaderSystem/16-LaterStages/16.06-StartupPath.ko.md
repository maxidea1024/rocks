### 16.6 셰이더 준비 시작 경로 단축(개정 69, 2026-11-28)

사용자 지시(2026-11-28): "언리얼에서도 제일 짜증나는게 쉐이더 컴파일 시간 … 이부분은 시간단축이 매우 중요함". 16.4절에서 워커 시작 비용(도구 확인 SHA-256)을 줄인 뒤 남은 시간을 단계별로 재고, 줄일 곳을 정한다.

**측정(Sandbox D3D12 개발 경로, Debug, job 118, 기계 부하 약 80%).**
- 관리자 단계 시간: 이 절에서 넣은 `ShaderCompileProgress` 단계 칸으로 잰다.
- 워커 시간 축: `worker.log` 줄 앞의 단조 시계 ms와 공급자 Info 줄의 시작 시각을 맞춰 본다.

| 단계 | 차가운 시작(캐시 없음) | 따뜻한 시작(118개 모두 적중) |
|---|---|---|
| prepare(정의·전처리·키, job마다 호출 스레드에서 차례로) | 547–565 ms | 550–568 ms |
| lookup(너겟 일괄 조회) | 6 ms | 251–457 ms |
| compile(워커) | 1,238–2,077 ms | 0 |
| publish(너겟 일괄 쓰기) | 651–756 ms | 0 |
| 라이브러리 만들기 전체 | 2,571–3,357 ms | 809–1,034 ms |

- 워커 쪽: 빌드 시작 뒤 약 0.43 s에 뜬다(그 전은 prepare). 도구 적재 약 0.11 s, job 각 10–20 ms이고, 마지막 job은 빌드 시작 뒤 약 0.7–0.8 s에 끝난다.
- 원인 둘:
  - prepare는 job 118개를 한 스레드에서 차례로 전처리한다(Debug에서 job당 약 4.7 ms).
  - 공급자의 너겟 스케줄러가 기본 설정(`WorkerSchedulerConfig::workerCount = 1`)으로 시작된다. 너겟 일괄 요청은 항목마다 작업 하나를 제출하므로(AssetNugget `NuggetRequest`), 스레드 하나가 조회 118건·쓰기 118건을 차례로 처리한다.

**결정.**
- **SSD93 단계 시간 진단.**
  - `ShaderCompileProgress`에 단계별 누적 벽시계 시간(`prepareNanoseconds`·`lookupNanoseconds`·`compileNanoseconds`·`publishNanoseconds`)을 둔다.
  - Development 공급자의 첫 만들기 Info 줄에 시작 시각(단조 ms)과 단계 시간을 남긴다.
  - 워커 `worker.log`는 줄마다 단조 시계 ms를 앞에 붙인다. 같은 기기에서는 관리자 로그와 시간 축이 맞는다.
- **SSD94 준비 병렬.**
  - 관리자에 `scheduler`가 있으면 job 준비를 `ParallelFor`로 나눈다(UE도 전처리를 작업 그래프에서 병렬로 한다).
  - 병렬 구간에서는 결과(전처리 원문·키·실패 진단)만 job 칸에 쓴다.
  - 실패 계수와 진행 sink 호출(`Count`·`Report`)은 호출 스레드가 루프 뒤 job 순서대로 한다. 그래서 sink는 지금처럼 한 스레드에서만 불리고, 진단 순서도 결정적이다.
  - system 도구 조회(`QueryTools`, 채널 하나를 쓴다)는 병렬 구간 앞에서 한 번 한다. 실패하면 그 형식의 job이 `ToolError`다.
  - 취소는 job마다 확인한다. 준비하지 못한 job은 지금처럼 `CancelRemaining`이 취소로 끝낸다.
  - 병렬 구간의 함수(정의 조립·`PreprocessShader`·`BuildShaderJobKey`)는 재진입 가능하고, 소스 트리 `Load`는 여러 스레드에서 불러도 된다(ShaderSourceTree.h). 할당자는 이미 여러 스레드의 동시 할당을 받아야 한다(`ShaderCompileManagerConfig::allocator`).
  - `scheduler`가 없거나(동기 모드) 시작되지 않았으면 `ParallelFor`가 호출 스레드 혼자 실행한다. 결과는 같다.
- **SSD95 공급자 스케줄러 크기.** Development 공급자의 스케줄러는 `LogicalProcessorCount() − 1` 스레드로 시작한다(최소 1, 상한 `MaxProviderSchedulerWorkers` = 16).
  - 너겟 조회·쓰기가 병렬이 되고, SSD94의 helper도 이 스케줄러에서 돈다.
  - 상한은 코어 수가 아주 많은 기계에서 쓰레드를 지나치게 만들지 않으려는 것이다. 엔진 GC 스케줄러의 자동 크기(`LogicalProcessorCount() − 1`, 상한)와 같은 모양이다.
  - 워커 프로세스(compile 단계)가 도는 동안 이 스레드들은 기다리기만 하므로 CPU를 다투지 않는다.
- **SSD96 게시 분리(후속).**
  - 캐시가 필수가 아닐 때는 너겟 쓰기를 빌드 끝에서 기다리지 않고, 다음 `Compile`이나 `Shutdown` 앞에서 기다리게 할 수 있다(UE는 DDC 쓰기를 비동기로 한다).
  - 쓰기 실패와 충돌을 그때 Log로 남기는 규칙이 필요하다(조용한 실패 금지). SSD95 적용 뒤 publish 시간을 다시 재고 정한다.
- **SSD97 입력 해시 키(후속 검토).**
  - 지금 job 키는 전처리 원문의 해시를 쓴다. 그래서 따뜻한 시작도 전처리를 모두 한다.
  - UE는 셰이더 파일 해시(`GetShaderFileHash`, include 전체를 조건과 상관없이 모은 해시)와 정의로 키를 만들어, 적중하면 전처리하지 않는다.
  - 키 정의(P5, 12.2절)를 바꾸는 일이므로 SSD94·SSD95 뒤 측정으로 필요성을 정한다.

**완료 기준.**
- 같은 측정에서 prepare·lookup·publish가 각각 줄어든다. 결과(라이브러리 byte, 너겟 키·값)는 바뀌지 않는다.
- 준비 실패 진단 순서가 job 순서와 같다.
- 바뀐 범위의 시험(`ShaderCompile*`·`ShaderWorker*`)이 통과한다.

**결과(구현 2026-11-28, 같은 측정 — 이번 측정의 기계 부하는 약 49%로 앞선 측정의 약 80%보다 낮다).**

| 단계 | 차가운 시작: 앞 → 뒤 | 따뜻한 시작: 앞 → 뒤 |
|---|---|---|
| prepare | 547–565 → 127–133 ms | 550–568 → 125–133 ms |
| lookup | 6 → 2 ms | 251–457 → 6–33 ms |
| compile | 1,238–2,077 → 685–711 ms | 0 |
| publish | 651–756 → 124–137 ms | 0 |
| 라이브러리 만들기 전체 | 2,571–3,357 → 953–980 ms | 809–1,034 → 138–172 ms |

- 시험: `ShaderCompileManager_PreparesInParallelLikeSerial`이 새로 생겼다. 실패 job 둘(없는 원문 `PreprocessError`, 빈 진입점 `InvalidJob`)을 섞어, scheduler 없이와 scheduler 스레드 넷으로 결과·진단·키·계수가 같은지 본다. `UsesWarmNuggetCache`(scheduler 스레드 둘)는 병렬 준비에서도 차가운·따뜻한 키가 같다. 컴파일 관리자 시험 9개가 통과했다.
- 다음 후보: 따뜻한 시작의 남은 prepare(약 0.13 s)는 SSD97(입력 해시 키)이 없앨 수 있다. 차가운 시작의 compile(약 0.7 s)은 워커 띄우기·도구 적재 시간과 Debug 워커의 job 처리 시간이다.
