# 셰이더 시스템 설계 — 16.5 머티리얼 셰이더 묶음·형식 플랫폼 분류

[16장](README.ko.md) · [목차](../README.ko.md)

### 16.5 머티리얼 셰이더 묶음·형식 플랫폼 분류(개정 65, 2026-11-28)

머티리얼 MS3 쿠킹 설계(MaterialSystem 12.8절, 16절 MSR17·MSR18·MSR19·MRD18)가 셰이더 시스템에 요구한 것을 정한다. 머티리얼 묶음이 지금 필요로 하는 것만 하고, 일반 프로젝트 라이브러리(프로젝트·플러그인 셰이더 타입)는 그대로 후속이다(SSD91). 결정은 권장안으로 확정했고 애매한 곳은 UE 5.8을 따랐다(SSD85–SSD92).

**UE 5.8 방식.**

| 항목 | UE 5.8 | 근거 |

**결정.**

- **SSD85 묶음 id와 라이브러리 배정(MSR17 (c)).**
  - 묶음 id = 셰이더 집합 id(SHA-256, MaterialSystem 8.6절) 앞 8 byte를 little-endian u64로 읽은 값이고, 0이면 1이다(0은 엔진 셰이더 묶음). ShaderCore `MaterialShaderBundleId(shaderSetId)`다. 쿠커와 런타임 MaterialRuntime이 같은 함수를 쓴다.
  - 라이브러리 배정은 `ShaderLibraryKindOf(bundleId, owner)`다: 묶음 id가 0이 아니면 `Project`, 0이면 소속(SSD3)으로 정한다. 머티리얼 pass 셰이더 타입은 엔진 모듈(`RendererShaders`)의 `Engine` 소속이지만 묶음 id로 `Project` 라이브러리에 간다(UE도 머티리얼 셰이더 맵은 Global이 아닌 라이브러리에 간다).
  - `Engine` 라이브러리 항목의 묶음 id는 늘 0이다. `BuildShaderLibrary`는 어기면 `InvalidArgument`, `ShaderLibraryView::Open`은 `CorruptPackage`다(SSD90).
- **SSD86 머티리얼 거르기 서명(MSR19 — MSR15의 실제 서명).**
  - `ShaderMaterialShouldCompileFunction = bool (*)(Span<const uint8> materialTraits, VertexInputTypeId, uint32 permutationId, const ShaderFormatFacts&) noexcept`이고 `ShaderTypeDesc::materialShouldCompile`에 둔다(null이면 늘 참). `materialTraits`는 `MaterialShaderTraits` 정규 바이트(MaterialSchema `WriteMaterialShaderTraits`, MaterialSystem 12.8절 MS3c)다. ShaderCore는 MaterialSchema를 모르고 바이트를 그대로 넘긴다.
  - 타입마다 거르기는 하나다(12.2절): `ShaderTypeMaterialShader` 타입은 `materialShouldCompile`만, 그 밖의 타입은 `shouldCompile`만 쓴다. 등록부는 어긋난 칸을 `InvalidArgument`로 거부한다.
  - 해석은 pass 셰이더 타입(`RendererShaders`, Renderer 3.2절)이 MaterialSchema 읽기로 한다(UE와 같은 분담). `RendererShaders`는 Renderer RS0에서 생기므로 그 전에는 해석기가 없다: 엔진에 머티리얼 셰이더 타입이 없고, 머티리얼 쪽 보고는 "traits 거르기 없음"(MaterialSystem 12.8절 MS3e)이다. 시험은 자기 해석 함수를 단 시험 타입을 쓴다.
  - 거르기에 오는 바이트는 늘 읽힌다: 묶음 원천(SSD87)이 넘기기 전에 읽기로 검사하고, 읽지 못하면 그 머티리얼 쿠킹 오류다. 해석기가 그래도 읽지 못하면(계약 위반) Log Error를 남기고 거짓을 돌려준다.
  - 정점 입력 타입 거르기(SSD5 (4))는 traits를 받지 않는다(한계 — 엔진 정점 입력 타입이 기본 하나뿐이다. UE `FVertexFactoryShaderPermutationParameters`처럼 머티리얼 사실이 필요한 정점 입력 타입이 생기면 같은 바이트 인자를 더한다).
  - 열거는 ShaderCore `EnumerateMaterialShaderCombinations`다(아래 SSD88). MaterialCook의 job 목록·퍼뮤테이션 보고(MS3e)와 라이브러리 단계가 같은 함수를 써서 수가 같다.
- **SSD87 묶음이 단계에 오는 길(MSR17 (a)).**
  - **쿠킹 패키지 목록.** `CookArtifactRequest::packages`(AssetCooker)는 이번 게시가 담을 매니페스트 항목이다: 이번에 쿠킹한 것, 재사용한 것, 부분 쿠킹이면 이전 매니페스트에서 바뀌지도 지워지지도 않은 것. AssetId 순 `Span<const CookedManifestEntry* const>`이고 엔진 전용 쿠킹은 빈다. 단계가 도는 때 패키지 파일은 이미 `Packages/`에 있다(`CookPublisher::Put`이 옮긴다) — 경로는 `cookedRoot` + `AppendCookedPackagePath(asset, packageSha256)`다.
  - **묶음 원천.** ShaderCompiler `MaterialShaderBundleSource::Collect(request, sink)`가 그 패키지들의 머티리얼 셰이더 묶음을 sink에 넘긴다(`Add` — 단계가 복사한다). 패키지별 실패는 원천이 `sink.Report`(그 머티리얼 asset의 오류 진단)로 남기고 다음 패키지로 간다. 조용히 빼지 않는다.
  - **등록.** 원천은 ShaderCompiler의 프로세스 표 `MaterialShaderBundleSources()`(칸 하나 — 같은 칸에 둘이면 `AlreadyExists`, 단계가 도는 동안 등록·해제는 `Busy`)에 구현 모듈(MaterialCook) 수명 객체가 `Startup`에서 명시 등록한다(SSD41과 같은 원칙). 시험은 `ShaderLibraryCookStageConfig::bundles`로 준다.
  - **원천이 없을 때.** 엔진 전용 쿠킹이거나 등록된 원천이 없으면 `Project` 라이브러리를 만들지 않는다. 원천이 없는 프로젝트 쿠킹은 Log Info("no material shader bundle source")를 남긴다 — MaterialCook이 없으면 머티리얼 패키지는 기본 처리기로 쿠킹되어 셰이더 집합이 없으므로 기능이 줄지 않는다.
  - **권장 원천 구현(머티리얼 세션 몫, MaterialSystem 12.8절 MS3f).** 패키지 대표 타입이 `Material`이거나 자기 `MaterialArtifact`를 가진 `MaterialInstance`면 쿠킹 패키지를 읽어 형식별 (셰이더 집합 id, 사용 대상 정점 입력 타입 목록)을 얻는다. 생성 원문·traits는 셰이더 집합 id로 다시 조회한다: 번역 너겟 bucket에 셰이더 집합 id를 키로 하는 조회 Record(값 = 생성 원문·layout 서명·traits — 값으로 셰이더 집합 id를 다시 계산해 대조)를 함께 둔다. 적중하지 않으면(캐시 없음·지워짐) 에디터 패키지에서 같은 번역 코드로 다시 번역하고, 다시 계산한 셰이더 집합 id가 패키지 값과 다르면 그 머티리얼 쿠킹 오류다. 그래서 재사용한(Cook이 불리지 않은) 대상도 같은 길로 온다. 사용 대상은 번역 결과가 아니라 머티리얼 쪽 값이라(8.4절) 패키지에서 읽는다.
  - **버린 대안.**
    - `CookArtifactRequest`에 처리기가 Cook 중 넘긴 묶음 칸: 재사용 대상은 Cook이 불리지 않아 묶음이 빠진다. 다 쿠킹하면 재사용이 사라지고, 빼면 라이브러리가 조용히 모자란다.
    - 셰이더 단계가 머티리얼 패키지를 직접 읽음: ShaderCompiler가 Material·MaterialSchema에 의존한다(셰이더 시스템은 머티리얼을 모른다 — 1절).
    - 생성 원문을 쿠킹 패키지에 넣음: 출시 패키지에 셰이더 원문이 들어간다(크기·노출). UE도 패키지에는 hash만 둔다.
    - 너겟 bucket을 훑음: 너겟 저장소는 지워질 수 있는 캐시이고 열거 계약이 없으며 낡은 항목이 섞인다.
    - 처리기가 Cook에서 셰이더까지 컴파일하고 단계는 결과만 모음: 재사용 대상 문제가 그대로이고 컴파일 길이 둘이 된다. 단계가 컴파일하면 너겟 적중으로 재사용 비용이 작다(SSD13 — job 키까지는 늘 계산).
    - UE처럼 이전 라이브러리를 읽어 이어 붙이고 참조 없는 것을 지움: 결과가 쿠킹 순서·이력에 기대게 된다. Rocks는 매니페스트 전체에서 다시 모아 같은 입력이면 같은 byte다(10절 결정성).
- **SSD88 Project 라이브러리 만들기(MSR17 (b)·(d)).**
  - **묶음.** `MaterialShaderBundle{formatId, shaderSetId, materialSource, traits, vertexInputTypes, asset}`다. `vertexInputTypes`는 사용 대상(정점 입력 축 타입이 곱할 정점 입력 타입 id)이고 등록부에 있어야 한다. `asset`은 진단용 머티리얼이다.
  - **엔진 열거에서 빼기.** `EnumerateShaderLibraryCombinations`는 `ShaderTypeMaterialShader` 타입을 건너뛴다(엔진 라이브러리·런타임 완결성 검사 둘 다 — 머티리얼 조합의 빠짐은 MSR10 대체다).
  - **정규화.** `CookShaderLibraries`·`CompileShaderLibrary`의 `ShaderLibraryCookDesc::materialBundles`는 `Project` 라이브러리에서만 받는다(`Engine`이면 `InvalidArgument`). 형식마다 그 형식 id의 묶음을 (묶음 id, 셰이더 집합 id, asset) 순으로 정렬한다. 같은 셰이더 집합 id는 하나로 합친다: 원문·traits byte가 같아야 하고(다르면 `Inconsistent`), 정점 입력 타입은 합집합, asset은 가장 작은 id다. 같은 묶음 id의 다른 셰이더 집합 id는 `Collision`이다. 등록부에 없는 정점 입력 타입은 `UnknownVertexInput`이다.
  - **진단.** 문제는 형식 줄 `bundleProblems`(종류·묶음 id·두 셰이더 집합 id·두 asset)와 영어 Log Error로 남고, 그 형식은 결과 `BundleFailed`로 파일을 만들지 않는다. 충돌 문구는 묶음 id(16 hex)·두 셰이더 집합 id(64 hex)·두 머티리얼 AssetId를 담는다("Material shader sets … and … share the shader library bundle id … in <형식> (64-bit prefix collision); change one of the materials"). 단계는 문제마다 진단 하나를 낸다: 충돌 `code None, error AlreadyExists`(asset·related = 두 머티리얼), 그 밖 `error InvalidArgument`(asset), setting = 형식 순번. 정렬 뒤 판정하므로 결정적이다(같은 입력 같은 진단 순서).
  - **열거.** 묶음마다 `EnumerateMaterialShaderCombinations(types, 묶음의 정점 입력 타입, facts, traits, bundleId, includeDevelopment, out)`(out 뒤에 더한다)다. 거르기 순서는 SSD5와 같고 (3)이 `materialShouldCompile(traits, …)`다. 정점 입력 축이 없는 머티리얼 타입(전체 화면 pass)은 정점 입력 타입 "없음" 하나다. 소속이 `Project`인 비머티리얼 타입은 지금처럼 소속으로 열거된다(직접 호출 — 단계는 SSD91로 막는다).
  - **job.** 묶음의 `materialSource`를 `ShaderCompileJob::materialSource`로, `warningsAsErrors = false`(16.4절 SSD79)로 둔다. 레이아웃 서명은 지금 pass 타입 표의 서명이다(머티리얼 layout 서명을 항목 서명에 넣는 것은 MSR14). 항목 키의 묶음 id는 묶음 id다. 실패 job 줄(`ShaderLibraryCookJobFailure`)에 묶음 id·asset을 담고, 단계는 그 asset으로 진단을 낸다(형식별 텍스처 예산 오류 MS-T10이 그 머티리얼에 붙는다).
  - **cookKey.** SSD46 항목 칸에 묶음 id(u64, 타입 해시 앞)를 더하고 `ShaderLibraryCookKeyVersion`을 2로 올린다(같은 job 키·다른 묶음 id의 두 쿠킹을 가른다). 단계 정체성 version Guid를 바꾼다.
  - **단계.** 엔진 라이브러리 뒤에 형식마다 `Project` 라이브러리를 만든다(원천이 있을 때 — 묶음이 없어도 빈 라이브러리를 만든다: 부분 쿠킹이 이전 `Project` 항목을 남기지 않게 한다). 재사용·게시는 `Engine`과 같다(이름 `Project`). 보고서 절에 `materialBundles`(정규화 뒤 묶음 수 합)·`projectEntries`를 더한다.
- **SSD89 형식 플랫폼 분류(MSR18).**
  - 형식 정의에 필수 속성 `platformClass`(문자열 배열, 어휘 `Mobile`·`Pc`·`Console`, 중복 금지, 빈 배열 허용)를 둔다. UE의 세 bool이 서로 독립이므로 하나만 고르는 열거가 아니라 집합이다(MaterialSystem 12.8절 "platformClass"를 이 집합으로 읽는다 — `isMobile`·`isPc`·`isConsole`은 각 원소의 유무).
  - 값: `D3D12_SM6`·`D3D11_SM5`·`VULKAN_SM5`·`METAL_SM5` = [`Pc`], `GLES31_ANDROID` = [`Mobile`], `GLES31_PC` = [`Pc`, `Mobile`](UE `OPENGL_PCES3_1`). 자리만 둔 형식(`VULKAN_ANDROID`·`METAL_IOS`)은 속성을 받지 않는다(SH6·SH5에서 [`Mobile`]로 넣는다).
  - 검증: 어휘 밖 `InvalidValue`, 중복 `DuplicateValue`, 없음 `MissingProperty`. `OpenGL` backend(OpenGL ES — ES 3.1 기능 수준)는 `Mobile`을 담아야 한다(`InvalidValue`). UE `IsMobilePlatform`이 기능 수준 ES3_1로 판정하는 것과 같은 결과가 되게 하는 Rocks 규칙이다. 기능 수준 칸(MSR9)이 생기면 "Mobile ⇔ 기능 수준 Mobile"로 바꾼다.
  - API: ShaderCore `ShaderPlatformClassBits`(`ShaderPlatformClassMobile`·`Pc`·`Console`)·`AllShaderPlatformClasses`, `ShaderFormatDefinition::platformClasses`, `ShaderFormatFacts::platformClasses`(`MakeShaderFormatFacts`가 옮긴다). 거르기 함수가 읽는 형식 사실이므로 라이브러리 머리에도 담는다(SSD90).
  - 버전: 형식 정의 schema는 1 그대로다(하위호환 없음 — 모든 정의 파일을 함께 고친다). 형식 정의 byte가 바뀌어 job 키 3행이 바뀌므로 모든 셰이더가 다시 컴파일된다. 출력 코드는 같으므로 ShaderFormat 처리기 버전은 올리지 않는다(12.1절 규칙 — 처리기 버전은 출력이 바뀔 때).
- **SSD90 라이브러리 형식 v2.** SSD7 머리의 형식 사실 빈 byte(offset 115)를 u8 플랫폼 분류 비트로 쓰고, `Engine` 라이브러리 항목의 묶음 id 0 규칙(SSD85)을 읽기 검사에 더해 `ShaderLibraryVersion`을 2로 올린다. 읽기: 버전이 2가 아니면 `UnsupportedVersion`, 분류 비트가 `AllShaderPlatformClasses` 밖이면 `CorruptPackage`. v1 reader는 두지 않는다(엔진 라이브러리는 다시 쿠킹한다 — `asset-cook --engine`).
- **SSD91 경계(지금 하는 것과 후속).**
  - 지금: 머티리얼 묶음만 담는 `Project` 라이브러리의 쿠킹(SSD85–SSD88), 거르기 interface(SSD86), 형식 분류(SSD89).
  - 후속(그대로 "ML5b·RR9 뒤"): 소속이 `Project`·`ProjectPlugin`인 셰이더 타입·정점 입력 타입(단계는 지금처럼 `Unsupported` — 16.1절 SSD45 3번), `/Project`·플러그인 원문 mount, 플러그인·청크 라이브러리 분할(12.3절), 런타임의 `Project` 라이브러리 열기와 셰이더 집합(RR9 — SSD47 끝 문장), 머티리얼 layout 서명의 항목 칸(MSR14), 머티리얼 조합 빠짐의 대체(MSR10, MaterialRuntime), PSO 미리 준비(MRB6).
- **SSD92 MaterialCook과 셰이더 타입 등록부(MRD18).** MaterialCook은 `RendererShaders`를 링크하지 않는다. 쿠킹할 pass 셰이더 타입은 ShaderCore 셰이더 타입 등록부의 `ShaderTypeMaterialShader` 타입이고, 등록부는 셰이더 라이브러리 단계와 같은 원천(`ShaderCookRegistrySource` — 제품 `ModuleShaderCookRegistrySource`)에서 받는다. `RendererShaders`는 그 원천이 시작하는 엔진 모듈 집합에 들어 있으면 된다(BuildTargets 3.10절). Renderer 3.2절을 이에 맞춰 고쳤다(Renderer 개정 14).

**API(머티리얼 세션이 쓰는 것).**

| 자리 | 이름 | 쓰임 |
|---|---|---|
| ShaderCore `ShaderLibrary.h` | `MaterialShaderBundleId(const Sha256Digest&)` | 셰이더 집합 id → 묶음 id(쿠커·MaterialRuntime) |
| ShaderCore `ShaderLibrary.h` | `ShaderLibraryKindOf(uint64 bundleId, ShaderTypeOwner)` | 항목의 라이브러리 |
| ShaderCore `ShaderType.h` | `ShaderMaterialShouldCompileFunction`, `ShaderTypeDesc::materialShouldCompile` | pass 타입(RendererShaders·시험 타입)의 traits 거르기 |
| ShaderCore `ShaderLibraryContents.h` | `EnumerateMaterialShaderCombinations` | MS3e job 목록·퍼뮤테이션 보고(단계와 같은 열거) |
| ShaderCore `ShaderFormatTypes.h`·`ShaderFormatFacts.h` | `ShaderPlatformClassBits`, `ShaderFormatFacts::platformClasses` | 번역 대상의 `isMobile`·`isPc`·`isConsole` |
| ShaderCompilerCommon `ShaderFormatDefinition.h` | `ShaderFormatDefinition::platformClasses` | 형식 정의에서 직접 읽을 때 |
| ShaderCompiler `MaterialShaderBundleSource.h` | `MaterialShaderBundle`, `MaterialShaderBundleSource`, `MaterialShaderBundleSink`, `MaterialShaderBundleSources()` | 묶음 원천 구현·등록(MaterialCook 수명 객체) |

**한계.** 정점 입력 타입 거르기에 traits가 없다(SSD86). 항목 레이아웃 서명은 pass 타입 것뿐이다(MSR14). `Project` 라이브러리는 런타임이 아직 열지 않는다(RR9). 원천이 묶음을 모으는 비용(패키지 읽기·조회)은 쿠킹마다 든다.

완료 기준(EngineTests): 묶음 id golden(앞 8 byte little-endian, 0 → 1)과 라이브러리 배정, `Engine` 라이브러리의 묶음 id 거부(만들기·열기), 라이브러리 v2 머리(분류 비트 왕복·범위 밖 손상·버전 1 거부), 등록부의 거르기 칸 어긋남 거부, 엔진 열거가 머티리얼 타입을 건너뜀, 머티리얼 열거의 traits 전달·정점 입력 부분집합·결합 거르기, 형식 정의 `platformClass`(저장소 값·음성 대조 넷)와 형식 사실 복사, 묶음 정규화(같은 집합 합침·`Inconsistent`·`Collision`·`UnknownVertexInput` — 결정적 순서), 머티리얼 묶음 `Project` 라이브러리 컴파일(생성 원문 include·묶음 id 키·`warningsAsErrors` 끔·cookKey가 묶음 id로 달라짐), 단계의 `Project` Produce·재사용·충돌 진단·원천 없음, 쿠커가 단계에 넘기는 `packages`(새로 쿠킹·재사용).
