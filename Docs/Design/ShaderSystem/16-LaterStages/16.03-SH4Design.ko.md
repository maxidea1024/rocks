# 셰이더 시스템 설계 — 16.3 SH4 설계

[16장](README.ko.md) · [목차](../README.ko.md)

### 16.3 SH4 설계(개정 60, 2026-11-27)

SH4는 16장 표의 SH4 행(감시 재컴파일·오류 위치·디버그 심볼·PSO 교체)이고 RenderBase 18.4절 SM12 행이다. 완료 기준("저장 후 10초 안 반영", 계획 I5)은 그대로다. 결정은 권장안으로 확정했고 애매한 곳은 UE 5.8을 따랐다(SSD67–SSD78). 교체 규칙 자체(새 집합·프레임 경계·실패 시 이전 유지)는 RenderBase 9.8절 RR8로 이미 구현되어 있고, SH4는 그 `Propose`를 부르는 쪽과 그 앞뒤(재컴파일·오류·심볼)를 만든다.

**UE 5.8 방식.**

**결정.**

- **SSD67 범위와 하위 단계.**

  | 단계 | 범위 | 시험 |
  |---|---|---|
  | SH4a | 오류 위치(SSD72): 진단 해석 `ParseShaderDiagnostics`, 가상 → 디스크 경로, 공급자 로그 | 해석 golden(DXC·FXC·전처리기·이어지는 줄·중복), 경로 풀기 |
  | SH4b | 디버그 심볼(SSD73·SSD74): `debugSymbols` 열기, 형식별 값 3, 라이브러리 밖 심볼 파일, 설정(SSD75) | 형식별 값 3 있음·없음, 키가 다름, 심볼을 꺼도 출력 byte 불변, 심볼 파일 |
  | SH4c | 감시 재컴파일(SSD68–SSD71·SSD76·SSD77): 의존 지도, `ShaderLibraryReloader`, 공급자 감시 스레드, revision·통지, `EngineRenderResources` 교체 연결, Sandbox 화면 경로 | 의존 집합·include 변경·무관 변경·실패 유지·revision, RenderBase 교체(가짜 공급자) |
  | SH4d | Sandbox self-test(여덟 장치 픽셀 변화)·저장 → 반영 시간 측정·사람 확인 경로(SSD78) | self-test |

- **SSD68 감시 자리.** 감시·재컴파일은 Development 공급자 모듈(`DevelopmentShaderProvider`, Release 밖에서만 링크 — RenderBase 9.12절 4항)이 소유한다. 재사용할 수 있고 도구 없이 시험할 수 있는 부분(진단 해석, 의존 지도, 라이브러리 다시 만들기, 감시 경로 변환)은 Developer `ShaderCompiler`에 두고, 공급자는 스레드와 연결만 한다. RenderBase는 `ShaderProvider` interface에 revision 조회와 reload 통지 기다리기를 더할 뿐이다(SSD76 — 기본 구현은 "재컴파일 없음").
  - 근거: UE도 셰이더 컴파일을 허용하는 실행의 컴파일 관리자가 감시를 건다(`WITH_EDITOR` + CVar). Rocks에서 그 자리는 Release 밖에서만 링크되는 공급자 모듈이고, 그러면 Release 실행 파일에 감시·재컴파일 코드가 들어갈 길이 없다(9절 정책이 이미 Release의 Developer 모듈 링크를 막는다).
  - 버린 안: (가) RenderBase가 감시 — Runtime 모듈이 원문 트리·컴파일러를 알아야 하고 Release에 들어간다. (나) 실행 파일(Sandbox)이 감시 — 실행 파일마다 사본이 생긴다(9.12절 버린 안과 같은 이유). (다) 감시 스레드까지 ShaderCompiler에 — 쿠커·`shader-compile` 명령도 같은 모듈을 쓰는데 그들에게 감시는 필요 없다. 스레드 수명은 공급자 수명과 같아야 한다.
- **SSD69 바뀐 파일 → 의존 셰이더.** 라이브러리를 만들 때 job마다 전처리 include 폐포(`PreprocessedShader::includes` — 엔트리·`Platform.rsh`·include·정점 입력 원문, 비활성 구역 include 제외)를 모아 보고서에 "원문 → 셰이더 타입(이름 해시)" 표로 낸다(`ShaderLibraryCookReport::sources`). 재컴파일기는 형식마다 이 표를 합집합으로 쌓는다(줄이지 않는다 — 조건부 include가 다음 컴파일에서 살아날 수 있다). 감시 이벤트는 "다시 확인할 경로" 힌트로만 쓴다(`DirectoryWatch.h` 이식 계약).
  - 받는 확장자: `.rsf`·`.rsh`·`.h`(3절 가상 경로 규칙의 원문 확장자 — UE는 `.usf`·`.ush`·`.h`). 그 밖은 버린다.
  - 표에 있는 경로면 그 타입들이 영향받는다. 표에 없는 경로는 무시한다(어떤 셰이더도 읽지 않았다). 단, 직전 재컴파일이 실패했으면 원문 확장자의 어떤 변경이든 다시 시도한다(없던 include 파일을 만든 경우 — 실패한 전처리는 폐포를 남기지 않는다).
  - Overflow(이벤트 손실)·Renamed·Removed는 모두 "그 경로가 바뀜"으로 다룬다. Overflow는 전부가 바뀐 것으로 본다. RootRemoved는 Error 로그를 남기고 그 루트 감시를 멈춘다.
  - UE와의 차이(개선 — UE 한계를 같은 단계에서 고친다): UE 저장 감시는 엔트리 파일 이름만 보아 include만 바꾸면 다시 컴파일하지 않는다. Rocks는 include 폐포를 써서 `recompileshaders changed`와 같은 정확도를 저장마다 낸다.
- **SSD70 재컴파일 = 형식 라이브러리 다시 만들기.** 영향받는 타입이 있으면 지금까지 만든 형식마다 처음과 같은 desc로 `CompileShaderLibrary`를 다시 부른다. 너겟 캐시가 내용 주소이므로 영향받지 않은 job은 적중이고(키 5행 = 전처리 결과), 바뀐 job만 워커로 간다. 새 byte가 이전과 같으면 revision을 올리지 않는다(주석만 바꾼 경우 — `#line`만 다르면 코드가 같을 수 있다).
  - 근거: 라이브러리는 항목 표·cookKey가 한 묶음이라(12.2.1절) 일부 항목만 갈아 끼우면 같은 byte 규칙(쿠킹과 공급자가 같은 byte, SH2e 완료 기준)을 따로 지켜야 한다. 다시 만들기는 그 규칙을 그대로 쓴다. 의존 지도가 틀려도(예: 생성 include) 결과가 낡지 않는다.
  - 버린 안: 영향받은 job만 컴파일해 옛 라이브러리에 끼우기 — 위 규칙의 중복 구현이고 지도 오류가 낡은 코드로 남는다. 비용(모든 job 전처리·너겟 조회)은 측정으로 본다(16.3절 끝 구현 메모).
  - 한계: 한 번의 재컴파일은 만든 형식 모두를 차례로 다시 만든다(self-test처럼 여러 장치를 거친 실행은 형식이 넷이다). 장치가 쓰지 않게 된 형식을 빼는 일은 후속(공급자가 형식 사용을 모른다).
- **SSD71 실패.** job이 하나라도 실패하면 그 형식의 라이브러리를 바꾸지 않고 revision도 그대로다 — 현재 셰이더 집합이 유지된다(계획 14.1절 "hot reload 실패 시 이전 검증 버전 유지", RenderBase 9.8절). 진단을 SSD72로 해석해 로그에 남기고 통지(SSD76)에 싣는다. 다음 저장이 다시 시도한다. 셰이더 집합 검사 실패(서명 불일치 등)는 RenderBase `ShaderSetSlot::Propose`가 거부하고 현재를 유지한다(9.8절 그대로).
- **SSD72 오류 위치.** ShaderCompiler `ShaderDiagnostics.h`.
  - `ShaderDiagnostic`: 가상 경로, 줄(1부터, 0 = 모름), 열(1부터, 0 = 모름), 심각도(`Error`·`Warning`·`Note`), 문구, 이어지는 줄(도구가 위치 줄 뒤에 붙이는 원문 줄·`^` 표지 — UE `HighlightedLine`·`HighlightedLineMarker`).
  - `ParseShaderDiagnostics(text, out)`: 줄마다 가상 경로(3절 규칙을 통과하는 `/…` 토큰)로 시작하는 위치를 찾는다. 받는 꼴: clang·DXC `경로:줄:열: 심각도: 문구`, `경로:줄: …`, MSVC·FXC `경로(줄,열): 심각도 X####: 문구`, `경로(줄,열-열): …`, `경로(줄): …`, Rocks 전처리기 `경로:줄: <ShaderSourceError 이름>: 문구`(심각도 Error). 위치 앞의 머리말(`DXC compile failed: `·`FXC: `)은 건너뛴다. 위치가 없는 줄은 앞 진단의 이어지는 줄이 되고, 앞 진단이 없으면 위치 없는 진단 하나가 된다. 경고는 결정 7로 오류지만 도구가 `warning:`으로 쓴 줄은 그대로 Warning이다(`-WX`가 그 뒤에 오류를 따로 낸다).
  - 중복 제거: 형식·퍼뮤테이션마다 같은 원문 오류가 반복되므로 (경로, 줄, 열, 심각도, 문구)가 같으면 하나로 합치고 몇 job에서 났는지 센다.
  - 경로: `ShaderSourceTree::ResolveDiskPath(가상 경로, out)`가 mount 표로 디스크 경로를 만든다(UE `GetShaderSourceFilePath`). 메모리 원문(`<루트>/Generated/…`)은 디스크 경로가 없다.
  - 로그(영어, `LogDevelopmentShaderProvider` Error): 진단마다 한 줄 `{디스크 경로}({줄},{열}): error: {문구}`(디스크 경로가 없으면 가상 경로) — Visual Studio·VS Code 출력 창에서 눌러 이동하는 MSVC 꼴(UE와 같은 이유). 그 뒤 이어지는 줄을 들여 쓴다. 마지막에 요약 한 줄(실패 job 수·형식·첫 타입). 위치를 해석하지 못한 진단은 원문을 그대로 남긴다.
- **SSD73 디버그 심볼(값 3 `DebugSymbols`).** SC9 `debugSymbols=true`를 연다(파서·키·워커가 받는다). 키 6행이 옵션을 `WriteReflected`로 쓰므로 켜면 모든 키가 달라진다(UE도 `CFLAG_GenerateSymbols`가 컴파일 환경으로 키에 든다). false의 출력은 바뀌지 않으므로 처리기 버전은 올리지 않는다.
  - 값 3 배치(`ShaderDebugSymbols` — ShaderCompilerCommon, 워커와 메인이 같이 쓴다): u32 배치 버전(1), u8 종류(`Pdb` 1·`SpirvModule` 2), u16 파일 이름 byte 수와 이름(디렉터리 없는 이름, 비면 메인이 `<job 키 hex 64자>.<확장자>`로 정한다), 나머지는 내용. 읽기 손상은 `CorruptData`다.
  - `D3D12_SM6`(DXC DXIL): `-Zi -Qstrip_debug -Zsb`를 더한다(UE와 같다). 값 0은 PDB를 뗀 DXIL(디버그 이름 part가 PDB 이름을 가리킨다), 값 3은 DXC `DXC_OUT_PDB`와 그 이름(`<hash>.pdb`)이다. 서명 검사(10절)는 그대로다.
  - `D3D11_SM5`(FXC): `D3DCOMPILE_DEBUG | D3DCOMPILE_DEBUG_NAME_FOR_BINARY`로 컴파일하고 `D3DGetBlobPart(D3D_BLOB_PDB)`가 값 3, `D3DGetBlobPart(D3D_BLOB_DEBUG_NAME)`의 이름이 파일 이름, `D3DStripShader(D3DCOMPILER_STRIP_DEBUG_INFO)`가 값 0이다(UE `D3DShaderCompiler.cpp`의 같은 함수). 대체 경로(DXC → SPIR-V → HLSL 5.0 → FXC)는 마지막 FXC에서 같게 한다 — 그 PDB의 원문은 SPIRV-Cross가 만든 HLSL이다(한계).
  - `VULKAN_SM5`(DXC SPIR-V): 같은 원문을 `-Zi`로 한 번 더 컴파일한 SPIR-V(OpSource·OpString·OpLine — 확장 없이 core SPIR-V, `spirv-val` 통과)가 값 3(이름 빔 → `.spv`)이다. 값 0은 심볼을 끈 job과 같은 byte다(같은 원문·인자로 따로 컴파일하므로).
  - `GLES31_PC`(ESSL 텍스트)·`METAL_SM5`(MSL 텍스트): 값 3을 두지 않는다(job은 성공). UE OpenGL도 심볼이 없다. Metal의 `-frecord-sources`·`metallibsym`은 SH5다.
  - 버린 안: SPIR-V debug module을 Rocks 고쳐 쓰기(binding 재배치·location)까지 거친 판으로 — 고쳐 쓰기가 OpLine 등 디버그 명령을 다룬다는 보장을 새로 세워야 한다. 값 3은 DXC 출력 그대로이고 binding 번호가 값 0과 다를 수 있다(한계 — 원문 줄 대응을 보는 용도). NonSemantic.Shader.DebugInfo(`-fspv-debug=vulkan-with-source`)는 장치에 `VK_KHR_shader_non_semantic_info`를 요구하므로 쓰지 않는다.
- **SSD74 심볼 파일.** 값 3은 쿠킹 라이브러리에 넣지 않는다(12.3절). `ShaderLibraryCookDesc::symbolDirectory`가 비지 않으면 라이브러리 만들기가 성공한 job의 값 3을 `<symbolDirectory>/<형식 id>/<이름>`에 쓴다(임시 파일 → `FileSystem::Replace`. 같은 byte면 쓰지 않는다. PDB 이름은 출력 binary hash라 같은 이름에 다른 PDB가 올 수 있고 — 주석만 바꾼 경우 — 최신 원문을 따라야 하므로 덮어쓴다). 형식 줄에 쓴 수·같아서 둔 수·실패 수를 남기고, 심볼 쓰기 실패는 라이브러리 실패가 아니다(Warning). 공급자의 위치는 `<너겟 root>/Saved/ShaderSymbols`(UE `<ProjectSaved>/ShaderSymbols/<형식>`, 엔진만 쓰면 `Engine/Saved` — `.gitignore`에 이미 있다).
- **SSD75 설정(CVar, `DevelopmentShaderProvider` 모듈 `RegisterSettings`).** 모두 부팅 값이다(켜고 끄면 전체 키가 바뀌거나 감시 스레드가 생긴다).
  - `shader.recompile_on_save`(bool, 기본 **true**): UE `r.ShaderCompiler.RecompileShadersOnSave` 대응. 기본값이 UE(false)와 다르다: Rocks는 에디터와 게임 실행이 나뉘지 않고, 이 모듈은 Release 밖 개발 실행에만 있으며, 감시는 OS 통지라 유휴 비용이 거의 없다. UE가 끄는 이유(에디터에서 머티리얼까지 다시 컴파일되는 비용)는 엔진 셰이더만 다시 만드는 Rocks에 해당하지 않는다.
  - `shader.symbols`(bool, 기본 false): UE `r.Shaders.Symbols`(만들기 + 쓰기) 대응. 켜면 모든 job이 `debugSymbols=true`이고 SSD74 위치에 심볼 파일을 쓴다. 만들기·쓰기를 나누는 설정(`GenerateSymbols`·`WriteSymbols`)·경로 바꾸기(`SymbolPathOverride`)·`r.Shaders.Optimize` 대응은 후속이다(요구가 생기면).
- **SSD76 revision과 교체 연결(RenderBase 9.8절).**
  - RenderBase `ShaderProvider`에 `LibraryRevision(formatId, library)`(그 형식으로 마지막에 공급한 라이브러리의 revision, 1부터. 0 = 다시 만들지 않는 공급자·모르는 형식)와 `WaitForReload(afterSequence, timeoutMilliseconds, ShaderReloadNotice&)`(재컴파일 한 번이 끝날 때마다 오르는 순번이 afterSequence보다 커질 때까지 기다린다 — 시험·도구의 gate. 기본 구현은 바로 false)를 더한다. 통지 `ShaderReloadNotice`: 순번, 성공 여부, 바뀐 형식 수, 실패 job 수, 첫 진단의 가상 경로·줄·열·문구(고정 버퍼), 걸린 시간(감지 → 끝, ms).
  - `EngineRenderResources`가 집합을 `ShaderSetSlot`으로 갖고 `ApplyShaderUpdates(PipelineCache*)`를 둔다. 주인(렌더 lane 처리기)이 프레임 packet 작업 맨 앞에서 부른다: (1) 공급자 경로로 열었고 `LibraryRevision`이 지금 집합의 revision보다 크면 같은 desc로 새 집합을 `OpenFromProvider`해 `Propose`한다(검사 실패면 거부 — 로그와 함께 그 revision을 기억해 매 프레임 다시 열지 않는다), (2) `ApplyPending(cache)`가 교체하면 내장 자원 팩의 셰이더 항목을 새 집합에서 다시 찾는다(`BuiltinResources::AdoptShaders` — 장치 자원은 그대로), (3) `CollectRetired`. 돌려주는 값은 교체 여부이고, 교체했으면 주인이 자기 파이프라인 요청(집합 포인터·항목 번호)을 다시 만든다. 옛 집합의 파이프라인 캐시 항목은 `ApplyPending`이 회수한다(epoch 키 — PSO 교체).
  - 공급자는 다시 만드는 동안 lane을 막지 않는다: 요청 응답(라이브러리 byte 복사)은 짧은 잠금으로, 다시 만들기는 그 밖에서 한다. 처음 만드는 형식의 요청만 컴파일을 기다린다(지금과 같다).
  - 쿠킹 라이브러리로 연 집합은 다시 열지 않는다(UE도 쿠킹 실행은 ODSC 없이 다시 컴파일하지 않는다).
- **SSD77 감시 스레드.** 공급자가 첫 라이브러리를 만든 뒤(mount 표가 정해진 뒤) 스레드 하나를 띄운다. mount마다 `DirectoryWatcher`를 열고(같은 스레드 규칙), 돌기: 모든 감시기 `Poll`(기다리지 않음) → 바뀐 경로가 있으면 남은 이벤트를 모두 받아 합친 뒤 재컴파일 한 번 → 없으면 정지 event를 `WatchIdleMilliseconds`(100 ms)까지 기다린다. 재컴파일 중 온 이벤트는 다음 번에 처리한다. 종료는 정지 event다(`Shutdown`이 스레드를 join한 뒤 워커를 멈춘다).
  - 저장 시점 맞추기(debounce)는 하지 않는다: 타이머로 "쓰기가 끝났겠지"를 짐작하지 않는다(시각 의존 금지). 편집기가 파일을 두 번에 나눠 쓰면 첫 재컴파일이 반쯤 쓴 원문으로 실패하고(오류 로그) 다음 이벤트의 재컴파일이 성공한다 — 결과는 마지막 저장을 따른다.
  - 재컴파일 진입점 `DevelopmentShaderProvider::NotifySourcesChanged(가상 경로 목록)`는 공개이고 동기다(감시 스레드와 시험이 같은 함수를 부른다). 시험은 감시기 없이 이 함수로 변경을 넣는다.
- **SSD78 확인.** Sandbox `--self-test`(와 짧은 범위 `--self-test-shader-reload`)가 장치마다: self-test 원문 디렉터리 `/Plugin/SandboxReload`(실행마다 `Engine/Intermediate/SandboxShaderReload/<PID>`에 시험 원문을 복사)의 include 파일 `ReloadColor.rsh`를 고쳐 쓰고, 공급자 통지를 gate로 기다린 뒤 `ApplyShaderUpdates`로 교체해 전체화면 픽셀이 새 색이 되는지 본다. 같은 실행에서 문법 오류를 쓰면 통지가 실패·진단 위치(`/Plugin/SandboxReload/ReloadColor.rsh`, 줄)를 싣고 픽셀이 그대로인지 본다. 저장 → 교체 시간은 재고 로그에 남긴다(단언하지 않는다 — 완료 기준 10초는 측정으로 확인). 사람 확인은 `Sandbox --engine --window`에서 엔진 셰이더를 고쳐 저장하는 것이다(16.3절 끝 "사람 확인").

**한계.** 형식 라이브러리 전체를 다시 만든다(SSD70). 쿠킹 라이브러리로 연 실행은 다시 컴파일하지 않는다. 셰이더 타입 추가·삭제(C++ 등록)는 다시 시작해야 한다(UE도 같다). 장치 셰이더를 이미 만든 파이프라인은 다음 프레임 경계까지 옛 코드로 그린다(9.8절). 엔진 셰이더 원문 디렉터리 밖(프로젝트 라이브러리 RR9)은 그 단계에서 같은 경로를 쓴다.

**PG5 메모(개정 62, 2026-11-27 — [진행 보고](../../ProgressReporting/README.ko.md) 8장·12장).** 공급자의 컴파일을 진행 보고와 대기 작업에 이었다.

- 진행 작업: 형식 라이브러리 처음 만들기는 Background 작업 "Compiling shaders"(취소 불가 — 취소하면 렌더 집합이 열리지 않는다), 감시 재컴파일(`Reload`·`NotifySourcesChanged`)은 "Recompiling shaders"(사용자 취소 가능, 외부 token = 대기 작업 token)다. 둘 다 작업 수준 계수를 관리자 sink로 채운다. hub가 꺼져 있으면 작업 없이 컴파일한다(UE `FAsyncCompilationNotification`의 "Compiling Shaders" 알림 자리 — 에디터가 그린다, 진행 보고 9.4절).
- 재컴파일 취소: 재빌더가 `Cancelled`를 돌려주면 이전 라이브러리를 유지하고(SSD71과 같다) Info "Shader recompile was cancelled; the previous shaders stay"와 실패 통지(`message` = `Cancelled`)를 낸다. Error가 아니다(사용자가 고른 일이다).
- 대기 작업 "Shaders": 공급자가 Engine `CountedPendingWork`(`RunBefore` "Textures")를 갖고(`PendingWork()`), 만들기·재컴파일을 그 일 구간으로 감싸며 그 token을 취소에 잇는다. 모듈 수명 객체가 엔진 등록소 호스트 서비스에 등록하고 `Shutdown`에서 뗀다. 엔진 종료(`PendingWork().Shutdown`)가 진행 중 컴파일을 취소하고 기다린다. 공급자 `Shutdown`도 먼저 대기 작업을 닫는다.
- 엔진 셰이더 준비 진행: 공급자는 모든 컴파일의 sink에 `EngineShaderHost::ReportPreparation…`을 더한다. 호스트가 `SetPreparationProgress`로 받는 곳을 걸어 두면(Sandbox 시작 화면 `Shaders` 단계 — [시작 화면](../../SplashScreen/08-StartupWeights.ko.md) 8.3절) 거기로 간다(RenderBase 9.12절 6항).
