# 변경 통지(CU5)

이 문서는 UiToolkit Core 계약 CU5(7절 표 — UE 5.8 `PreEditChange`·`PostEditChangeChainProperty`·`EPropertyChangeType`과 `INotifyFieldValueChanged`·`FFieldId` 대응)를 정한다. 세 부분이다: 실행 중 필드 변경 통지(3.1절 — 객체 필드가 바뀌었을 수 있음을 구독자에게 알린다), 생성 setter(3.2절 — UiToolkit UD7, 비교 → 대입 → 반영 → 통지), 편집 통지(3.3절 — 편집기·도구가 필드를 바꾸기 전·후에 타입 hook과 편집 관찰자에 변경 종류·경로·출처를 알린다). 이 세션이 맡는다(사용자 결정 2026-11-28 — 설계 교차 검증·단계마다 리뷰 필수).

- 개정 3(2026-11-28): 재검증 반영 — 통지는 처리 표시·잠금·묶음 게시가 끝난 뒤(CN-D11), Registry 참조 API의 필드 판정은 등록 때 만든 offset 범위 표(CN-D10), 통지 빠른 경로의 비용(CN-D12), 대상별 구독 목록(CN-D4), `ROCKS_SETTER`·`ROCKS_GETTER` 어휘 규칙·EditorOnly 예외·선언 순서(CN-D13), ReadOnly 검사 위치와 World 참조 필드 범위(CN-D14), 편집 부분 실패에도 전 객체 `AfterEdit`(CN-D19), undo는 기록 값 복원(setter 검증을 거치지 않음 — CN-D19), hook 감지는 매개변수 형식으로(CN-D17), Reserved 객체 setter(CN-D9).
- 개정 2(2026-11-28): 설계 교차 검증 반영. 사용자 결정 둘: setter는 매크로 선언 + 생성 정의(`ROCKS_SETTER` — UD7 개정, BS8b 유지), 편집 쓰기도 setter 경유. 그 밖: 슬롯 hot 레코드에 칸이 없어 flag bit + cold 표(CN-D4), SL 5.5·SE-W8·ER CR7의 이벤트 slot 표와 같은 표(CN-D4), 통지 지점 하나(CN-D10), Registry 참조 필드의 setter 금지·제자리 쓰기 통지(CN-D14), "통지 = 바뀌었을 수 있음, 놓침 없음" 일반 규칙과 host 사본(CN-D3·CN-D21), UE 다중 선택 순서·Interactive 경계·Pre 실패 취소·편집 가능 판정(CN-D17–CN-D19), 출처 칸·Prefab 관계(CN-D16·CN-D20), 깊이 초과는 성공 + 진단(CN-D6), 통지 중 수명·묶음 게시·종료(CN-D11), Rocks 이름(CN-D16·CN-D17), ReadOnly·Setter 조합(CN-D14), 비교는 A5b 같음(CN-D15), undo 통지(CN-D19), CN5 선행 분리.
- 개정 1(2026-11-28): 첫 판.

## 3. 결정

### 3.1 실행 중 필드 변경 통지(CN1)

- **CN-D1 opt-in 지정자 `Notify`(UE `FieldNotify`):** `ROCKS_PROPERTY(Notify)`인 클래스 필드만 통지 대상이다. struct 멤버에는 쓸 수 없다(RMC — struct 값은 그것을 담은 최상위 필드의 변경으로 통지한다, UE도 struct 멤버 FieldNotify는 없다). 이벤트 필드·`ROCKS_NATIVE`·`EditorOnly` 필드와 `EditorOnly` 함수에는 쓸 수 없다(이벤트는 값이 아니고, EditorOnly 멤버는 게임 빌드에 없어 그 빌드의 구독자가 가리킬 대상이 없다). `ROCKS_FUNCTION(Notify)`는 매개변수가 없고 값을 돌려주는 `Pure` `const` 함수(계산 값 — UE와 같은 조건)에 쓰며 그 값이 바뀌었을 수 있음을 코드가 알린다(CN-D9). 모든 필드를 대상으로 하지 않는 이유: 쓰기마다 비용과 번호 공간이 든다(UE도 opt-in).
- **CN-D2 통지 번호:** 타입 등록이 기반 체인부터 통지 대상(필드 → 함수, 각각 선언 순서)에 0부터 번호를 준다(UE `IndexOf_X = Super::Max + n`과 같은 배치). 번호는 등록 때 정해지는 실행 중 내부 값이다 — 컴파일 상수가 아니므로 다른 모듈의 파생이 기반 번호를 몰라도 되고, 저장하지 않으며, 타입 revision(SE-O2)마다 새로 정해진다. 조회는 `TypeLease::NotifyIndex(id)`(등록 때 만든 정렬 표 — 이분 탐색). 상한은 이름 있는 상수 `MaxNotifyTargets`(타입 체인당 4,096, 넘으면 등록 InvalidArgument).
- **CN-D3 식별과 의미:** 공개 API의 통지 대상은 안정 ID다(`NotifyTarget{Guid id}` — 필드는 FieldId, 함수는 FunctionId). UE의 `FName` 대신 ID를 쓰는 이유는 이름 바꾸기·도구 이름과 무관하게 구독이 유지되고 Sparks·UI 컴파일러가 schema의 ID를 그대로 쓰기 때문이다. **통지의 의미는 "바뀌었을 수 있음"이고 놓침은 없다:** 값이 바뀐 모든 쓰기는 통지를 낸다(CN-D10), 같은 값을 쓴 경우에도 통지가 나갈 수 있다(하위 경로·컨테이너 쓰기 — CN-D10). 옛 값은 싣지 않는다 — 값 기준 판정이 필요한 구독자(Sparks `Changed` — CN-D21)는 마지막으로 전달한 값을 스스로 쥔다.
- **CN-D4 저장:** 객체에 멤버를 더하지 않는다(1M 객체 — GcScale 원칙). 슬롯 hot 레코드(64 byte, `static_assert`로 고정 — 빈칸이 없다)의 `indexed`·`linked` bool 두 칸을 flag byte 하나로 합치고 그 byte에 "통지 상태 있음" bit를 둔다. 상태 자체는 Registry의 지연 표 `ObjectSlotTable`(슬롯 index → 항목 번호 — 첫 구독 때 만들고 비면 반환)에 있고, 항목은 구독 번호 비트 집합과 대상별 구독 목록이다(통지 번호마다 Core `MulticastDelegate` 하나 — 번호 순 정렬 배열에 구독이 있는 번호만 — 와 "전체" 목록 하나). 통지는 그 번호의 목록과 "전체" 목록만 부르므로 비용은 그 대상의 구독자 수에 비례한다(객체 하나의 구독 전체를 훑지 않는다). 구독자가 없는 객체의 통지는 hot 레코드 bit 하나를 읽고 끝난다(UE의 비트 검사와 같다 — CN-D12 bench). 구독자가 있어도 그 통지 번호의 비트가 꺼져 있으면 목록을 훑지 않는다. 이 표는 SL 5.5·연동 요구 SE-W8·ER CR7(23장)의 "발행자 객체에 지연 할당하는 이벤트 slot 표"와 같은 표다 — CN1이 표와 native 필드 `Changed` 몫을 만들고, 확장 이벤트·World 이벤트·Actor 물리 이벤트 칸은 EI3가 같은 항목에 더한다(CN5). 슬롯 flag 병합: `indexed`·`linked`(지금 `bool` 두 칸 — 이름 색인 잠금 경로 `ObjectRegistryNames.cpp`만 쓴다)를 bit로 바꾸고, 회수의 `slot.indexed || slot.linked` 판정(`ObjectRegistryGcReclaim.cpp:176`)을 새 bit에 맞춘다. GC 시험(GcScale 시험 묶음) 전부와 hot 레코드 크기 static_assert로 확인한다.
- **CN-D5 API(`Object/FieldNotifications.h` — ObjectRegistry 멤버):**
  - `TrySubscribe(access, object, NotifyTarget, Delegate<void(ObjectHandle, Guid)>) → Result<FieldNotifyHandle>` — native 구독(lambda·raw·C1 생존 판정 대상). 대상이 그 타입에 없으면 NotFound, `Notify`가 아니면 InvalidArgument, 객체가 살아 있지 않으면 Registry 오류. 구독 하나가 한 대상만 받으므로 구독자는 거를 필요가 없다.
  - `TrySubscribeAll(access, object, delegate)` — 모든 통지 대상(UE에 없음 — 디버거·Inspector 갱신·Sparks host의 발행자 단위 연결). 비트 집합을 전부 켠다.
  - `Unsubscribe(handle)`(없으면 false)·`UnsubscribeAll(access, object)`·`CompactNotifications(access, object)`.
  - `Notify(access, object, NotifyTarget)`·생성 코드용 `NotifyIndex(access, object, index)`.
  - 구독은 객체를 GC root로 만들지 않는다. 구독자 생존은 delegate 대상이 판정한다(C1). 구독 lambda의 코드가 든 동적 모듈은 해제 전에 구독을 지운다(ED8의 모듈 사이 규칙과 같다 — native 이벤트 구독과 같은 계약).
- **CN-D6 전달 시점과 깊이:** 통지는 동기다(UE와 같다) — `Notify`가 돌아오기 전에 구독자가 불린다. Rocks Borrow는 계수형이라 쓰기 Borrow 안에서 불린 구독자도 같은 객체를 읽을 수 있다. 통지 동안 발행자 Borrow가 남아 있으므로 구독자가 부른 `Collect`는 Busy다(이벤트 발행과 같다 — ED16 `broadcastFromFrame`). 구독자 안의 쓰기가 낸 통지는 중첩된다. 깊이는 Registry 단위로 센다(다른 객체로 이어지는 연쇄 포함). 상한 `MaxNotifyDepth`(16 — SL 5.4 연쇄 상한과 같은 수)를 넘는 통지는 구독자를 부르지 않고 버리며 진단(`ObjectStats::droppedNotifications`와 Registry 진단 hook)을 남긴다 — 쓰기 자체는 이미 끝났으므로 쓰기의 결과는 Success다(Busy는 "아무것도 안 바뀜"의 뜻이라 쓰지 않는다). Sparks는 thunk가 큐 항목만 기록하므로(SL 5.5) 재진입하지 않는다.
- **CN-D7 발행 중 구독 변경:** Core `MulticastDelegate` 의미를 따른다 — 발행 중 추가는 다음 통지부터, 제거는 즉시 호출 대상에서 빠진다(EV1b `Event`와 같다). UE `FFieldMulticastDelegate`는 발행 중 추가도 같은 발행에서 부른다 — Rocks는 이벤트와 통지의 의미를 하나로 맞춘다(버린 대안: UE를 그대로 — 같은 엔진 안에서 두 multicast 의미가 갈라진다).
- **CN-D8 스레드·문맥:** 객체 소유 스레드와 접근 문맥에서만 구독·통지한다(ED12와 같다). 다른 스레드의 변경은 소유 스레드로 넘긴 뒤 통지한다.
- **CN-D9 코드의 통지:** 생성 setter(CN-D13)가 없는 필드와 계산 값 함수는 코드가 알린다 — 생성 멤버 `NotifyChanged(member)`(UE `BroadcastFieldValueChanged`)와 비교·대입·통지를 한 번에 하는 `SetAndNotify(member, value)`(UE `UE_MVVM_SET_PROPERTY_VALUE` — 같으면 false, 비교는 CN-D15). 둘 다 `Object`의 Registry 접근자(CN2에서 protected로 더한다 — 지금 `registry_`는 private이고 friend는 ObjectRegistry뿐)·`Handle()`과 현재 접근 문맥(ObjectAccessScope)을 쓴다. Registry가 없는 인스턴스(생성자 안, RawSource 클래스 기본값 인스턴스)와 아직 게시되지 않은 객체(ConstructionContext의 Reserved 단계)에서는 통지하지 않고 Success다.
- **CN-D10 통지 지점은 하나:** 같은 변경이 두 번 나가지 않게 한 지점에서만 낸다. `Setter` 필드(CN-D13)는 생성 setter가 낸다 — 리플렉션·경로·편집 쓰기가 setter를 거치므로(CN-D14) 다른 지점이 다시 내지 않는다. `Setter`가 없는 `Notify` 필드는 중앙 쓰기 지점이 낸다: `FieldWriteOperation::operator()`(등록된 최상위 쓰기 — 수동 함수표 포함)와 속성 경로 실행기(하위 경로 쓰기 — ReflectionFoundations 7.1절의 `steps[0]` 규칙), Registry 참조·컨테이너 API(`SetReference`·`ObjectRefArray`·`ObjectRefMap`·`StructRefArray` 변경 — owner 필드가 `Notify`면 — SL 5.3의 `Targets.Add(e)`가 쓰기인 것과 같다). 이 API는 멤버 참조(owner 저장소 안의 주소)만 받고 FieldId를 모르므로, 타입 등록이 `Notify` 필드의 owner 저장소 안 byte 범위(생성 `RuntimeFieldOps`의 offset·크기 칸 — 생성 코드의 `offsetof`)로 "범위 → 최상위 필드 통지 번호" 표를 만들고, API가 owner 슬롯의 통지 bit가 켜져 있을 때만 주소로 그 표를 찾는다(struct 안 참조·배열 원소도 최상위 필드 범위 안이다). API에 필드 인자를 더하지 않는 이유: 모든 호출처와 생성 코드가 바뀌고, 구독자가 없는 대부분의 호출에서 쓰이지 않는다. 최상위 단일 값 쓰기는 값이 같으면 내지 않고(CN-D15), 하위 경로·컨테이너 쓰기는 비교 없이 낸다(보수적 — CN-D3의 "바뀌었을 수 있음"). `RuntimeFieldOps` 끝에 `setter` thunk(생성 setter로 쓰는 경로 — CN-D14)와 `notifyIndex` 칸을 더한다(ReflectionFoundations 7.1절 — "hook 칸은 그 단계에서 `RuntimeFieldOps` 끝에 더한다"). staged 쓰기(로드·생성 — 게시 전 객체)는 통지하지 않는다(SL 5.3 — 초기값은 `Changed`가 아니다).
- **CN-D11 파괴·회수·종료:** `RequestDestroy`가 그 객체의 통지 상태를 비우고(구독자에게 알리지 않는다), 회수가 표 항목을 반환한다. 통지 중에 비우면 목록은 `Clear`만 하고(Core `MulticastDelegate`는 발행 중 이동·파괴가 Fatal이다) 항목 반환은 가장 바깥 통지가 끝난 뒤로 미룬다 — 표 항목은 주소가 고정이다(chunk 저장). `Discard`(부분 트리 폐기)·Registry `Shutdown`도 같은 정리를 한다. 해제 handle은 그 뒤 무효다(Unsubscribe는 false). **통지는 쓰기를 한 API가 처리 표시(`processing_`)와 잠금을 푼 뒤 낸다:** Registry API 안의 쓰기(배열 비우기가 `processing_` 동안 간선을 집계하고 잠금 아래에서 게시하는 것 — `ObjectRegistryArrayEdges.cpp:400-422` — 등)는 바뀐 (객체, 통지 번호)를 그 호출의 지역 목록에 모았다가 표시와 잠금을 푼 뒤 낸다. 묶음 게시(`ObjectBatchPublish` — 그 `End`가 필드 게시다)는 `End`가 끝난 뒤 낸다. 그 구간 안에서 코드가 `Notify`를 부르면 Busy다(구독자를 부르지 않는다 — 그 구간은 다른 변경·Borrow가 Busy이고 콜백이 없다는 계약이 그대로다).
- **CN-D12 비용:** 통지 빠른 경로는 소유 스레드·접근 문맥 검사(CN-D8) → handle의 chunk·슬롯 주소(세대 비교) → hot 레코드 통지 bit이고, Registry gate 잠금을 쥐지 않는다(구독 상태는 소유 스레드만 바꾼다 — CN-D8). bit가 켜져 있을 때만 통지 번호 조회(`TypeLease::NotifyIndex` — 생성 setter·코드 경로는 bit를 먼저 보고 번호를 찾는다)와 목록 호출을 한다. bench — 구독자 없는 통지 1M회(목표: 위 세 단계, 할당 없음), 구독자 있음·그 번호 비트 꺼짐, 구독자 n명 발행, 구독·해제 1M회.

### 3.2 생성 setter·getter(CN2 — UD7 개정)

- **CN-D13 선언은 매크로, 정의는 생성(사용자 결정 2026-11-28):** 클래스 본문의 `ROCKS_SETTER(SetText, text)`가 `Result<void> SetText(const decltype(text)& value) noexcept;`(값 형식이 nothrow 복사 스칼라면 값 매개변수)를 선언하고, 메타 컴파일러가 정의를 모듈 생성 `.cpp`에 쓴다. UD7 원안(`ROCKS_GENERATED_BODY`를 파일·줄 매크로로 펼쳐 자동 선언)은 리플렉션 헤더가 자기 생성 헤더를 include해야 해서 BuildTargets BS8b(2026-11-21 사용자 결정 — 그 방식을 버린 안으로 확정)와 부딪혀 버린다. 생성 정의의 순서는 UE 패턴과 같다: 값 같음(CN-D15 — 같으면 Success, 통지 없음) → 대입(할당 실패면 그 오류, 값 그대로) → `ROCKS_PROPERTY(Apply = Method)`가 있으면 `Method()` 호출(반환 형식 `void`, noexcept) → `Notify`면 통지(CN-D10). `ROCKS_GETTER(GetText, text)`는 `const T& GetText() const noexcept`를 같은 방식으로 만든다. `ROCKS_PROPERTY(Getter = Method)`(`T Method() const noexcept`)가 있으면 리플렉션 읽기가 그 함수를 거친다(UE `Getter` — Widget이 Element의 현재 값을 읽는 경우, UiToolkit 5.3절). 매크로가 가리키는 멤버가 리플렉션 필드가 아니거나 형식·이름이 맞지 않으면 RMC, 같은 필드에 `ROCKS_SETTER`가 둘이면 RMC다. 이름은 사용자가 정한다(UE `Setter = Name`처럼 — 기본 `SetX` 철자 강제 없음). 어휘 규칙: `ROCKS_SETTER`·`ROCKS_GETTER`는 메타 컴파일러가 감지하는 리플렉션 매크로라 BuildTargets 3.4의 어휘 검사 목록에 넣는다. 필드 선언 뒤에 와야 한다(`decltype(text)` — 매개변수 형식은 complete-class 문맥이 아니다, 어기면 RMC). EditorOnly 필드의 setter는 그 필드와 같은 `#if ROCKS_WITH_EDITOR_DATA` 블록 안에 둔다 — 그 블록에 `ROCKS_PROPERTY`만 허용하는 3.4 규칙에 `ROCKS_SETTER`·`ROCKS_GETTER`를 예외로 더한다(편집기에서 그 필드를 편집할 때 setter가 필요하다).
- **CN-D14 쓰기 경로 통일(사용자 결정 2026-11-28 — 편집도 setter 경유):** setter가 있는 필드는 리플렉션 쓰기(`FieldWriteOperation`)·속성 경로 쓰기·편집 쓰기(`EditField` — CN-D19)·Sparks host 쓰기(`ScriptWritable` — EI2)가 모두 생성 setter를 거친다(UE `CallSetter`와 같고, UE Details 패널과 다르다 — UE는 Details 쓰기 뒤 `PostEditChangeProperty`로 따로 맞춰 같은 동기화를 두 번 쓴다). 하위 경로 쓰기는 최상위 값을 사본으로 읽어 고친 뒤 setter에 넘긴다(UE `PerformOperationWithSetter`). 그래서 setter가 거부하는 값(예: Static 컴포넌트의 Mobility — ER 24장)은 편집기에서도 진단으로 막힌다. 제한:
  - **Registry 참조를 담는 필드(`ObjectRef`·`ObjectRefArray`·`ObjectRefMap`·`StructRefArray`, 참조를 담은 struct)에는 `ROCKS_SETTER`를 쓸 수 없다(RMC):** 사본을 만들면 간선·클러스터 계수·관찰자 delta가 깨지고 큰 배열은 원소 하나에 O(n)이다. 이런 필드는 Registry API로 제자리에 쓰고, `Notify`면 그 API가 통지한다(CN-D10). 장부 갱신이 필요하면 `Apply` 대신 소유 타입의 전용 API를 쓴다.
  - **`ReadOnly`와 setter는 함께 쓸 수 있다:** `ReadOnly`는 "setter 없이 메모리에 직접 쓰는 리플렉션 쓰기를 거부"한다는 뜻으로 고친다(ReflectionFoundations 954행 정의 개정 — CN2). setter가 있으면 모든 쓰기가 setter로 가므로 `ReadOnly` 필드도 쓸 수 있다(UiToolkit 7.3절 "`Edit`이고 `ReadOnly`이며 setter가 있으면 setter로 편집"과 같다). 구현: `ReadOnly`는 하위 멤버·원소로 전파되고(`PropagateFieldFlags` — ReflectionFoundations 625행) 쓰기 검사(`ValidateFieldWrite`)가 setter 경로 앞에서 거부하므로, 경로의 `steps[0]` 필드에 setter가 있으면 그 경로의 ReadOnly 검사를 건너뛰고 setter로 보낸다. World 필드는 `ReadOnly`를 유지한 채 setter를 더한다(CN5 — World 세션). 단 `actors`·`components`·`rootComponent`는 Registry 참조 필드라 setter를 둘 수 없다(위 제한) — ER 4.6절의 "ReadOnly를 setter로 푼다"는 `relativeTransform`·`enabled` 같은 값 필드에만 해당한다. SparksBinding의 `ReadOnly`+`ScriptWritable` 거부(RMC2603 대역의 그 검사)는 setter가 있으면 허용으로 고친다(CN2).
  - **실행 조건:** setter는 보통 멤버 함수라 호출자가 그 객체를 쥐고 있다. 생성자 안·Registry 밖 인스턴스(RawSource 기본값)에서는 대입과 `Apply`만 하고 통지하지 않는다(CN-D9). staged 쓰기(로드)는 setter를 거치지 않는다 — 값만 놓고, 반영은 소유 타입의 로드 뒤 처리(Widget `ApplyAllProperties` 등)가 한다. 리플렉션·경로 쓰기가 setter를 부를 때는 지금처럼 `ResolveForWrite`(encode 고정 중 Busy, 변경 표지 올림)를 거친 뒤 부른다. `DestroyRequested` 객체는 리플렉션 쓰기 규칙(지금과 같다)을 따른다.
- **CN-D15 값 같음:** setter·`SetAndNotify`·최상위 쓰기의 "같은 값" 판정은 RuntimeClassMetadata A5b의 같음(인코딩 byte 같음, 참조는 대상 정체성)과 같다 — 스칼라·enum은 비트 같음(`0.0`과 `-0.0`은 다름, NaN payload 구별), String·Text는 인코딩 byte, struct·컨테이너는 원소별. SL 5.3의 비교 규칙과도 같다. 비교할 수 없는 형식(InstancedStruct 등)은 늘 다르다로 본다.

### 3.3 편집 통지(CN3)

- **CN-D16 `EditChange`(`Object/EditChange.h` — 형식은 늘 컴파일, hook·관찰자는 편집 빌드만):** `{object, memberField(최상위 FieldId), path(PropertyPath — 하위 경로 포함), kind(EditChangeKind 비트), origin, objectIndex(다중 선택의 순번), batchSize(같은 편집의 객체 수)}`. `EditChangeKind`(UE `EPropertyChangeType` 대응, 이름은 Rocks식 — UE 이름은 2절 표에만): `General`(종류 미정 — UE Unspecified)·`Committed`(확정 값 — ValueSet)·`Interactive`(드래그 중 — 끝나면 `Committed`가 이어진다)·`ElementAdded`·`ElementRemoved`·`Cleared`·`ElementMoved`·`ElementDuplicated`·`ResetToDefault`·`ReferenceReplaced`(에셋 통합·reload — Redirected)·`EditabilityToggled`(ToggleEditable). 조합(`Committed | ResetToDefault`)을 허용한다. `EditOrigin`: `User`(Inspector·도구의 사용자 편집)·`Propagation`(원형 → 인스턴스 전파 — Prefab PF7)·`Undo`(undo·redo 적용)·`Tool`(명령·스크립트 도구). 관찰자는 출처로 거른다(예: override 기록은 `User`만 — 전파 쓰기가 사용자 편집으로 잡히지 않게).
- **CN-D17 타입 편집 hook:** 클래스가 `Result<void> BeforeEdit(const EditChange&) noexcept`·`void AfterEdit(const EditChange&) noexcept`·`void AfterUndo(const UndoEvent&) noexcept`·`bool CanEdit(const EditQuery&) const noexcept`(UE `CanEditChange` — Inspector가 행을 잠글지 묻는다, `EditQuery{memberField, path}`) 가운데 필요한 것을 선언하면 메타 컴파일러가 감지해 편집 빌드의 생성 연산표(`RuntimeTypeOps::editHooks`, `ROCKS_WITH_EDITOR`)에 싣는다. 감지 기준은 매개변수 형식이다 — 매개변수가 `EditChange`·`UndoEvent`·`EditQuery`인 멤버만 hook이고(그 형식이 편집 전용이라 오탐이 없다), 같은 이름이라도 다른 매개변수면 hook이 아니다(RMC를 내지 않는다 — 게임 코드의 `CanEdit` 같은 흔한 이름을 막지 않게). 반환 형식·noexcept·const가 어긋난 hook 매개변수 선언은 RMC다. 선언은 `#if ROCKS_WITH_EDITOR` 안에 둘 수 있다(리플렉션 매크로가 아니므로 BuildTargets 3.4 규칙에 걸리지 않는다. 두 조합 AST 비교는 리플렉션이 아닌 멤버 함수를 비교하지 않으므로 더할 것이 없다). 기반 체인에서 가장 가까운 선언을 부르고, 기반 hook은 파생이 직접 부른다(UE `Super::PostEditChangeProperty`와 같다). 가상 함수 대신 연산표인 이유: Object 기반에 vptr을 두지 않는다(파생인 Widget·Component는 가상 함수가 있지만 Object 수명·생성 규칙은 연산표가 중심이다). `BeforeEdit` 실패는 그 편집 전체를 취소한다(CN-D19 — UE에는 취소가 없고 `CanEditChange`만 있다, 값 검증을 hook에 둘 수 있게 더한다).
- **CN-D18 편집 관찰자:** Registry 범위 관찰자 목록 `EditObservers`(UE 전역 `OnObjectPropertyChanged` 계열)에 Inspector 갱신·Transaction 기록(CU4)·패키지 dirty 표시·override 기록이 구독한다. 관찰자는 `OnBeforeEdit(batch)`·`OnAfterEdit(batch)`·`OnEditCancelled(batch)`를 받는다. 편집 기능이 없는 빌드(`ROCKS_WITH_EDITOR` 0)에는 없다.
- **CN-D19 편집 쓰기 진입점 `EditField`와 순서:** `EditField(access, objects, path, value, kind, origin)`이 다중 선택 편집을 UE 순서로 한다(`PropertyHandleImpl.cpp:543-698`): (1) 모든 객체의 `CanEdit` — 하나라도 거짓이면 진단, 아무것도 하지 않음; (2) 관찰자 `OnBeforeEdit` → 객체마다 타입 hook `BeforeEdit`(객체 순서대로) — 하나라도 실패하면 이미 Before를 받은 관찰자에 `OnEditCancelled`를 보내고 쓰지 않는다(앞 객체도 쓰지 않았으므로 되돌릴 것이 없다); (3) 객체마다 쓰기(setter 경유 — CN-D14, 필드 통지 포함 — CN-D10). 쓰기 실패는 예외가 아니라 정상 경로다(다중 선택에 Static과 Movable 컴포넌트가 섞이면 setter 거부가 흔하다): 실패한 객체를 건너뛰고 나머지를 계속 쓴다; (4) 모든 객체가 `AfterEdit`을 받는다(UE는 Post를 늘 전 객체에 부른다) — `EditChange::applied`(이 객체에 쓰였는지)와 `result`(실패면 그 오류)로 구별하고, 관찰자 `OnAfterEdit`은 객체별 결과를 함께 받는다(Transaction은 쓰인 객체만 기록 — 부분 실패를 숨기지 않는다). `EditField`의 반환은 전부 성공이면 Success, 하나라도 실패면 첫 실패 오류와 실패 수다. **Interactive 경계:** `BeginInteractiveEdit(objects, path)`가 (1)·(2)를 한 번 하고, 드래그 동안 `EditField(..., Interactive)`는 (3)·(4)만(Before 생략 — UE와 같다), `EndInteractiveEdit(Committed)`가 마지막 값으로 (3)·(4)를 한 번 더 하고 끝을 관찰자에 알린다(Transaction은 Begin에서 시작 값을, End에서 확정을 기록 — CU4). 취소(`EndInteractiveEdit(Cancelled)`)는 시작 값으로 되쓴 뒤 `OnEditCancelled`다. **undo·redo:** Transaction 적용은 기록한 값을 그대로 되쓴다 — setter의 검증을 거치지 않는다(기록 값은 기록 당시 유효했던 상태이고, 현재 다른 값과 맞물려 setter가 거부하면 복원이 실패하기 때문이다. UE Transaction도 객체 상태를 직렬화로 복원한다). 되쓴 필드마다 `Apply`(CN-D13)를 부르고 `Notify` 필드면 통지한 뒤, 객체마다 `AfterUndo`(UE `PostEditUndo`)를 부른다. origin은 `Undo`다.
- **CN-D20 기존 경로와 Prefab:** 지금 편집 성격의 쓰기를 하는 곳을 `EditField`로 옮긴다 — 패키지 편집 명령(AssetEditCommandlet의 경로 쓰기 — origin `Tool`), 클래스 기본값 되돌리기(A5b2 — `ResetToDefault`), UI `WidgetFieldBindings::Write`(CN5). 로드·쿠킹·저장 경로는 편집이 아니다. Prefab 제자리 전파(PF7)의 계기는 revision 비교(로드 또는 `RebasePrefabInstance` — Prefab 3.7절)이고 편집 관찰자가 아니다: CN3은 그 전파가 쓰는 쓰기 경로(setter·`EditField`, origin `Propagation`)만 준다. 전파 판정(override 집합이 1차, 인코딩 비교는 확인)은 Prefab 문서 그대로다.

### 3.4 Sparks·UI·World

- **CN-D21 Sparks `Changed`:** SL 5.3의 native 필드 `Changed`는 `Notify` 필드에만 있다. 실행 host(EI3)는 발행자마다 `TrySubscribeAll`로 연결하고 thunk가 큐 항목을 기록한다. 값 기준 판정(조각 시작 값과 끝 값이 다를 때만 전달)은 host가 한다: 구독한 (발행자, 필드)마다 마지막으로 전달한 값의 사본을 쥐고(값 비교는 CN-D15), 조각 끝에 현재 값과 비교한다. 비용은 구독 필드 수 × 값 크기다(컨테이너는 원소별 사본) — host가 그 수를 진단으로 낸다. Pre 통지(옛 값 싣기)를 두지 않는 이유: 모든 쓰기 경로가 옛 값 사본을 만들어야 하고(구독자가 없어도 경로마다 비용), 값 기준이 필요한 곳은 Sparks host뿐이다.
- **CN-D22 schema `changed`:** `ScriptReadOnly`·`ScriptWritable` 필드가 `Notify`면 binding schema 필드에 `changed: true`를 쓴다(SL 10.2 — SparksBinding EI1d의 통지 몫). descriptor 필드 flag `Notify`를 싣는다(descriptor schema 9 — 다른 모듈의 파생이 기반 필드의 `changed`를 안다). 계산 속성(SE-R7의 getter·setter 쌍)의 `changed`는 EI1d가 계산 속성과 함께 정한다.
- **CN-D23 UI:** UI의 `WidgetFieldBindings`(지금 UI 전용 multicast)는 CN1의 구독·통지 위에 다시 만든다(UI 세션 — CN5). Widget 속성은 UiToolkit 5.3절 예시에 `ROCKS_SETTER` 한 줄을 더한 꼴이다(`ROCKS_PROPERTY(Category = "Content", Multiline, Apply = ApplyText, Notify) Text text;` + `ROCKS_SETTER(SetText, text)` — 5.3절 예시를 CN2 때 고친다).
- **CN-D24 복제:** RepNotify(복제 수신 뒤 hook)는 별개다(네트워크 단계). 복제 수신이 `Notify` 필드를 쓰면 CN-D10대로 통지가 나간다(SL 5.3 "스크립트 밖의 쓰기(복제 수신·native)는 엔진이 적용하는 batch 하나를 한 조각으로 본다").

## 4. 버린 대안

- **모든 필드 통지(opt-out):** 쓰기마다 구독 검사 비용과 통지 번호가 든다. UE도 opt-in이다.
- **객체 멤버로 통지 상태(UE `UWidget::EnabledFieldNotifications`처럼 객체 안 비트 배열):** 1M 객체 × 칸 하나가 메모리 예산을 깬다(GcScale). 슬롯 flag bit와 지연 표로 같은 비용을 낸다.
- **슬롯 hot 레코드에 표 번호(uint32):** 칸이 없다(64 byte 고정). 레코드를 키우면 모든 handle 조회의 캐시 줄이 늘어난다.
- **이름(FName) 기반 식별:** 이름 바꾸기·도구 이름이 구독을 깬다. Rocks는 안정 ID 체계가 있다.
- **비동기 통지(큐):** C++·UI 바인딩은 setter 직후 반영을 기대한다(UE와 같다). 큐가 필요한 Sparks는 thunk에서 큐로 간다(SD78과 같은 구조).
- **편집 hook을 가상 함수로 / 표지 매크로로:** Object 기반에 vptr을 두지 않는다. 표지 매크로를 `#if ROCKS_WITH_EDITOR` 안에 두면 BuildTargets 3.4 규칙(조건 블록 안 리플렉션 매크로 금지)에 걸린다 — 시그니처 감지로 한다.
- **`ROCKS_GENERATED_BODY`를 파일·줄 매크로로 펼쳐 setter 자동 선언(UD7 원안):** BS8b와 충돌한다(사용자 결정으로 매크로 선언 + 생성 정의).
- **Details식 직접 메모리 쓰기 + 편집 hook 동기화(UE):** 같은 장부 갱신을 setter와 편집 hook에 두 번 쓰게 된다(사용자 결정으로 편집도 setter 경유).
- **Pre 통지로 옛 값 전달:** CN-D21.

## 5. 한계·후속

- Interactive 병합·undo 기록 형식은 CU4 Transaction 단계다. 이 문서의 `EditChangeKind`·`EditOrigin`과 CN-D19 경계가 그 입력이다.
- 통지 번호는 타입 revision(SE-O2)마다 새로 정해진다 — 구독은 ID로 하므로 reload 경계에서 구독을 새 번호로 옮기는 일은 SE-O2 구현이 한다.
- 계산 값 함수의 `Notify`는 코드가 알려야 한다(자동 의존 추적은 없다 — UE와 같다).
- Registry 참조 필드에는 생성 setter가 없다(CN-D14) — 그런 필드의 장부 갱신은 소유 타입의 API로 한다.
