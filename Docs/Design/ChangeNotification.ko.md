# 변경 통지(CU5)

이 문서는 UiToolkit Core 계약 CU5(7절 표 — UE 5.8 `PreEditChange`·`PostEditChangeChainProperty`·`EPropertyChangeType`과 `INotifyFieldValueChanged`·`FFieldId` 대응)를 정한다. 세 부분이다: 실행 중 필드 변경 통지(3.1절 — 객체 필드가 바뀌었을 수 있음을 구독자에게 알린다), 생성 setter(3.2절 — UiToolkit UD7, 비교 → 대입 → 반영 → 통지), 편집 통지(3.3절 — 편집기·도구가 필드를 바꾸기 전·후에 타입 hook과 편집 관찰자에 변경 종류·경로·출처를 알린다). 이 세션이 맡는다(사용자 결정 2026-11-28 — 설계 교차 검증·단계마다 리뷰 필수).

- 개정 8(2026-11-28): CN2b 구현 설계 — CN2b를 쓰기 경로의 setter 경유로 좁히고 `Getter` 지정자는 CN2c로 나눔. setter thunk는 `RuntimeFieldOps::setter`(`Result<void>(Object&, const void* value)` — 필드 형식의 값을 받아 생성 setter를 부른다), 생성 헤더의 `GeneratedType<C>::SetterOf<Member>()`가 멤버 → thunk(없으면 nullptr)를 답해 파생·다른 모듈의 상속 필드 함수표도 descriptor 변경 없이 싣는다. 쓰기는 상자 경유(최상위 필드를 `DetachedValue`로 분리 → 같은 경로 연산을 ReadOnly 허용으로 상자에 → 값 트리 검증 → 변경 표지 대조 → setter) — 등록된 write(`FieldWriteOperation`)와 경로 연산이 같은 함수를 쓴다. setter는 public·protected(파생 생성 코드가 부른다 — RMC2903). setter 필드의 CN1b 통지 지점은 내지 않는다(setter가 낸다). ## 3. 결정

### 3.1 실행 중 필드 변경 통지(CN1)

- **CN-D1 opt-in 지정자 `Notify`(UE `FieldNotify`):** `ROCKS_PROPERTY(Notify)`인 클래스 필드만 통지 대상이다. struct 멤버에는 쓸 수 없다(RMC — struct 값은 그것을 담은 최상위 필드의 변경으로 통지한다, UE도 struct 멤버 FieldNotify는 없다). 이벤트 필드·`ROCKS_NATIVE`·`EditorOnly` 필드와 `EditorOnly` 함수에는 쓸 수 없다(이벤트는 값이 아니고, EditorOnly 멤버는 게임 빌드에 없어 그 빌드의 구독자가 가리킬 대상이 없다). `ROCKS_FUNCTION(Notify)`는 매개변수가 없고 값을 돌려주는 `Pure` `const` 함수(계산 값 — UE와 같은 조건)에 쓰며 그 값이 바뀌었을 수 있음을 코드가 알린다(CN-D9). 모든 필드를 대상으로 하지 않는 이유: 쓰기마다 비용과 번호 공간이 든다(UE도 opt-in).
- **CN-D2 통지 번호:** 타입 등록이 통지 대상에 0부터 번호를 준다: 기반 타입의 번호를 그대로 앞에 두고(기반 lease로 얻은 번호가 파생 객체에서도 같은 대상이다 — UE `IndexOf_X = Super::Max + n`과 같은 배치), 자기 Notify 필드(schema 순서 — 파생 schema가 다시 싣는 상속 필드는 기반 몫이고 그 Notify flag는 기반과 같아야 한다, 다르면 기존 상속 필드 대조가 TypeMismatch로 거부한다), 자기 Notify 함수(선언 순서)가 뒤에 온다. 대상 ID(필드 FieldId·함수 FunctionId)가 겹치면 InvalidArgument다. 번호는 등록 때 정해지는 실행 중 내부 값이다 — 컴파일 상수가 아니므로 다른 모듈의 파생이 기반 번호를 몰라도 되고, 저장하지 않으며, 타입 revision(SE-O2)마다 새로 정해진다. 조회는 `TypeLease::NotifyIndex(id)`(등록 때 만든 정렬 표 — 이분 탐색). 상한은 이름 있는 상수 `MaxNotifyTargets`(타입 체인당 4,096, 넘으면 등록 InvalidArgument).
- **CN-D3 식별과 의미:** 공개 API의 통지 대상은 안정 ID다(`NotifyTarget{Guid id}` — 필드는 FieldId, 함수는 FunctionId). UE의 `FName` 대신 ID를 쓰는 이유는 이름 바꾸기·도구 이름과 무관하게 구독이 유지되고 Sparks·UI 컴파일러가 schema의 ID를 그대로 쓰기 때문이다. **통지의 의미는 "바뀌었을 수 있음"이고 놓침은 없다:** 값이 바뀐 모든 쓰기는 통지를 낸다(CN-D10), 같은 값을 쓴 경우에도 통지가 나갈 수 있다(하위 경로·컨테이너 쓰기 — CN-D10). 옛 값은 싣지 않는다 — 값 기준 판정이 필요한 구독자(Sparks `Changed` — CN-D21)는 마지막으로 전달한 값을 스스로 쥔다.
- **CN-D4 저장:** 객체에 멤버를 더하지 않는다(1M 객체 — GcScale 원칙). 슬롯 hot 레코드(64 byte, `static_assert`로 고정 — 빈칸이 없다)의 `indexed`·`linked` bool 두 칸을 flag byte 하나로 합치고 그 byte에 "통지 상태 있음" bit를 둔다. 상태 자체는 Registry의 지연 표(슬롯 index → 상태 — Core `HashMap`, 첫 구독 때 만들고 비면 반환. SlotCold에 칸을 두면 슬롯마다 8 byte가 늘어 버렸다)에 있고, 항목은 구독 번호 비트 집합과 대상별 구독 목록이다(통지 번호마다 Core `MulticastDelegate` 하나 — 번호 순 정렬 배열에 구독이 있는 번호만 — 와 "전체" 목록 하나). 통지는 그 번호의 목록과 "전체" 목록만 부르므로 비용은 그 대상의 구독자 수에 비례한다(객체 하나의 구독 전체를 훑지 않는다). 구독자가 없는 객체의 통지는 hot 레코드 bit 하나를 읽고 끝난다(UE의 비트 검사와 같다 — CN-D12 bench). 구독자가 있어도 그 통지 번호의 비트가 꺼져 있으면 목록을 훑지 않는다. 이 표는 SL 5.5·연동 요구 SE-W8·ER CR7(23장)의 "발행자 객체에 지연 할당하는 이벤트 slot 표"와 같은 표다 — CN1이 표와 native 필드 `Changed` 몫을 만들고, 확장 이벤트·World 이벤트·Actor 물리 이벤트 칸은 EI3가 같은 항목에 더한다(CN5). 슬롯 flag 병합: `indexed`·`linked`(지금 `bool` 두 칸 — 이름 색인 잠금 경로 `ObjectRegistryNames.cpp`만 쓴다)를 bit로 바꾸고, 회수의 `slot.indexed || slot.linked` 판정(`ObjectRegistryGcReclaim.cpp:176`)을 새 bit에 맞춘다. GC 시험(GcScale 시험 묶음) 전부와 hot 레코드 크기 static_assert로 확인한다.
- **CN-D5 API(`Object/FieldNotifications.h` — ObjectRegistry 멤버):**
  - `TrySubscribe(access, object, NotifyTarget, Delegate<void(ObjectHandle, Guid)>) → Result<FieldNotifyHandle>` — native 구독(lambda·raw·C1 생존 판정 대상). 대상이 그 타입에 없으면 NotFound, `Notify`가 아니면 InvalidArgument, 객체가 살아 있지 않으면 Registry 오류. 구독 하나가 한 대상만 받으므로 구독자는 거를 필요가 없다.
  - `TrySubscribeAll(access, object, delegate)` — 모든 통지 대상(UE에 없음 — 디버거·Inspector 갱신·Sparks host의 발행자 단위 연결). 전체 목록이 있으면 통지가 번호 bit와 무관하게 그 목록을 부른다.
  - `Unsubscribe(handle)`(없으면 false)·`UnsubscribeAll(access, object)`(구독을 비우기만 한다 — 같은 통지 안의 새 구독은 남는다)·`CompactNotifications(access, object)`(생존 판정이 거짓인 구독을 지운다, 통지 중에는 Busy). 해제 handle은 구독 목록의 일련번호(Registry 단위)를 싣는다 — 목록이나 상태가 사라졌다 다시 생기면 Core `DelegateHandle` 값이 다시 같아질 수 있어(목록마다 1부터) 옛 handle이 남의 새 구독을 지우지 않게 일련번호까지 대조한다.
  - `Notify(access, object, NotifyTarget)`·생성 코드용 `NotifyIndex(access, object, index)`.
  - 구독은 객체를 GC root로 만들지 않는다. 구독자 생존은 delegate 대상이 판정한다(C1). 구독 lambda의 코드가 든 동적 모듈은 해제 전에 구독을 지운다(ED8의 모듈 사이 규칙과 같다 — native 이벤트 구독과 같은 계약).
- **CN-D6 전달 시점과 깊이:** 통지는 동기다(UE와 같다) — `Notify`가 돌아오기 전에 구독자가 불린다. Rocks Borrow는 계수형이라 쓰기 Borrow 안에서 불린 구독자도 같은 객체를 읽을 수 있다. 통지 동안 발행자 Borrow가 남아 있으므로 구독자가 부른 `Collect`는 Busy다(이벤트 발행과 같다 — ED16 `broadcastFromFrame`). 구독자 안의 쓰기가 낸 통지는 중첩된다. 깊이는 Registry 단위로 센다(다른 객체로 이어지는 연쇄 포함). 상한 `MaxNotifyDepth`(16 — SL 5.4 연쇄 상한과 같은 수)를 넘는 통지는 구독자를 부르지 않고 버리며 `ObjectStats::droppedNotifications`에 센다(로그 경로가 생기면 경고 — Registry 진단 hook은 아직 없다) — 쓰기 자체는 이미 끝났으므로 쓰기의 결과는 Success다(Busy는 "아무것도 안 바뀜"의 뜻이라 쓰지 않는다). Sparks는 thunk가 큐 항목만 기록하므로(SL 5.5) 재진입하지 않는다.
- **CN-D7 발행 중 구독 변경:** Core `MulticastDelegate` 의미를 따른다 — 발행 중 추가는 다음 통지부터, 제거는 즉시 호출 대상에서 빠진다(EV1b `Event`와 같다). 정리 중 재진입: 구독을 지우거나 비우면 포획한 값의 소멸자가 돌고(RAII 구독 guard처럼 같은 객체의 다른 구독을 해제할 수 있다), Core `MulticastDelegate`는 발행·제거 도중 이동·파괴가 Fatal이다 — 그래서 해제·비우기·Compact·발행 동안 그 객체의 진행 중 작업 수를 올려 안쪽 호출이 목록을 옮기거나 상태를 반환하지 않게 하고, 빈 목록은 지역 배열로 옮긴 뒤 상태 갱신이 끝나고 파괴한다(상태 반환도 표에서 뗀 뒤 파괴). UE `FFieldMulticastDelegate`는 발행 중 추가도 같은 발행에서 부른다 — Rocks는 이벤트와 통지의 의미를 하나로 맞춘다(버린 대안: UE를 그대로 — 같은 엔진 안에서 두 multicast 의미가 갈라진다).
- **CN-D8 스레드·문맥:** 객체 소유 스레드와 접근 문맥에서만 구독·통지한다(ED12와 같다). 다른 스레드의 변경은 소유 스레드로 넘긴 뒤 통지한다.
- **CN-D9 코드의 통지(CN2a):** 생성 setter(CN-D13)가 없는 필드와 계산 값 함수는 코드가 알린다 — `Object`의 protected 멤버 템플릿 `NotifyChanged<&C::member>()`(UE `BroadcastFieldValueChanged` — 필드와 `Notify` 계산 값 함수 모두)와 비교·대입·통지를 한 번에 하는 `SetAndNotify<&C::member>(value)`(UE `UE_MVVM_SET_PROPERTY_VALUE` — `Result<bool>`, 같으면 false·대입·통지 없음, 비교는 CN-D15, 대입 규칙은 CN-D13의 setter와 같다). 대상은 멤버 포인터 템플릿 인자로 고르고, 메타 컴파일러가 `Notify` 대상을 선언한 클래스마다 생성 헤더에 `GeneratedType<C>::NotifyId<Member>()`(constexpr — 멤버 포인터 → 필드·함수 ID, `Notify` 대상이 아니면 static_assert)를 낸다. 기반 클래스의 멤버는 멤버 포인터 형식이 기반을 가리키므로(`int32 Base::*`) 기반의 생성 표가 답한다 — 그래서 두 함수는 그 멤버 클래스의 생성 헤더가 보이는 번역 단위에서 쓴다. 문자열 이름이나 런타임 조회를 쓰지 않는 이유: 철자 오류와 `Notify`가 아닌 대상을 컴파일 때 막고, 빠른 경로에 이름 조회를 더하지 않는다. 멤버 비교는 템플릿 인자 동등성(`detail::SameMemberV` — `IsSameV<MemberTag<A>, MemberTag<B>>`)이다: virtual 멤버 함수 포인터의 `==`는 값이 정해지지 않아 상수식이 아니다(clang 거부 확인). 재정의한 virtual 계산 값 함수는 선언한 기반의 이름(`&Base::Function`)으로 쓴다(`&Derived::Function`은 파생을 가리키는 다른 형식이라 파생 표에서 찾지 못한다 — static_assert 문구가 안내한다). 두 함수는 명시적 객체 매개변수(C++23 `this Self& self`)로 호출 클래스를 받아 멤버의 클래스가 그 기반인지 컴파일 때 본다(UE는 매크로의 `ThisClass`로 같은 일을 한다 — 무관한 클래스의 멤버로 하향 변환해 쓰는 UB를 막는다). 본체(`detail::SetterAccess` — `Object/ObjectSetter.h`)는 생성 헤더가 include하므로, 부르는 코드는 그 클래스의 생성 헤더를 include한 .cpp에 둔다(리플렉션 헤더의 인라인 본문은 메타 단계 Clang 실행이 생성 헤더 없이 읽어 불완전 형식 오류다 — `NativeTypeKey`와 같은 제약). `Object.h`가 본체를 직접 include하지 못하는 이유: `ValueSame`·`ValueCopy`가 끌어오는 참조 형식 헤더가 `Object.h`를 include한다. 생성 setter가 있는 필드에는 `SetAndNotify`를 쓸 수 없다(생성 `GeneratedType<C>::HasSetter<Member>` static_assert — setter가 `Apply`까지 하므로 우회하면 CN-D10의 한 지점이 깨진다). bitfield 필드는 멤버 포인터를 만들 수 없어 대상이 아니다(그런 필드의 코드 쓰기는 `ObjectRegistry::Notify`를 직접 쓴다). 통지는 `Object`의 비공개 진입점이 `ObjectRegistry::NotifySelf(handle, object, id)`로 낸다 — `Registry()` 접근자는 두지 않는다(Registry 전체를 파생 클래스에 열 이유가 없다). 접근 문맥은 `Destroy`와 같은 규칙(실행 scope, 없으면 Registry 기본 문맥 — 엄격 모드면 scope 누락 실패)이고 소유 스레드여야 한다. Borrow는 요구하지 않는다(호출자가 그 객체의 멤버 함수 안에 있다 — `NotifyChecked`가 통지 동안 Borrow를 잡는다). 통지할 쓰기(`Notify` 필드의 생성 setter·`SetAndNotify`)는 대입 전에 접근 문맥·스레드·종료를 본다(`ObjectRegistry::CheckSelfAccess` — 다른 스레드의 쓰기는 그 자체가 경쟁이고, 이 오류들은 쓰기 전에 알 수 있다). 대입 뒤에 남는 실패는 처리 표시·묶음 게시 구간의 Busy뿐이다. Registry가 없는 인스턴스(생성자 안 — `registry_`는 생성자 반환 뒤에 놓인다, RawSource 클래스 기본값 인스턴스)와 아직 게시되지 않은 객체(ConstructionContext의 Reserved 단계)에서는 통지하지 않고 Success다. 대입 뒤 통지의 실패(Busy)는 그 오류이고 값은 이미 새 값이다(`SetAndNotify`는 그때 "바뀌었음"을 돌려주지 못한다 — 쓰기 경로의 통지 실패를 무시하는 CN1b와 달리 코드 호출자는 오류를 알아야 한다).
- **CN-D10 통지 지점은 하나:** 같은 변경이 두 번 나가지 않게 한 지점에서만 낸다. `Setter` 필드(CN-D13)는 생성 setter가 낸다 — 리플렉션·경로·편집 쓰기가 setter를 거치므로(CN-D14) 다른 지점이 다시 내지 않는다. `Setter`가 없는 `Notify` 필드는 중앙 쓰기 지점이 낸다: `FieldWriteOperation::operator()`(등록된 최상위 쓰기 — 수동 함수표 포함)와 속성 경로 실행기(하위 경로 쓰기 — ReflectionFoundations 7.1절의 `steps[0]` 규칙), Registry 참조·컨테이너 API(`SetReference`·`ObjectRefArray`·`ObjectRefMap`·`StructRefArray` 변경 — owner 필드가 `Notify`면 — SL 5.3의 `Targets.Add(e)`가 쓰기인 것과 같다). 이 API는 멤버 참조(owner 저장소 안의 주소 — StructRefArray 원소 블록 안 참조는 그 배열)만 받고 FieldId를 모르므로, owner 슬롯의 통지 bit가 켜져 있을 때만 owner 타입의 `Notify` 필드마다 생성 `RuntimeFieldOps::storage` thunk(그 객체에서 멤버의 주소·크기를 잰다)로 주소를 담은 최상위 필드를 찾는다(struct 안 참조·배열도 최상위 필드 범위 안이다). 등록 때 offset 표를 만들지 않는 이유: `offsetof`는 표준 배치가 아닌 클래스(기반이 있는 리플렉션 클래스)에서 쓸 수 없어 GC 참조 위치 표(M3 — `Object/ReferenceLayout.h`)처럼 실제 객체에서 재야 하고, 이 판정은 구독자가 있는 owner의 Registry API 쓰기에서만 `Notify` 필드 수만큼 돈다. 참조·컨테이너를 담을 수 있는 `Notify` 필드(강한 참조, struct·배열·Map·Set·정적 배열·Optional<struct> — 통째 쓰기가 없는 aggregate)는 storage가 필수다(없으면 등록 InvalidArgument — 생성 코드는 bitfield가 아닌 `Notify` 필드마다 싣는다). API에 필드 인자를 더하지 않는 이유: 모든 호출처와 생성 코드가 바뀌고, 구독자가 없는 대부분의 호출에서 쓰이지 않는다. 최상위 단일 값 쓰기는 값이 같으면 내지 않고(CN-D15 — 구독자가 있을 때만 쓰기 전에 등록된 read로 읽어 비교한다. 구독자 없는 쓰기에 읽기 비용을 더하지 않는다. 강한 참조 필드의 최상위 쓰기는 생성 write가 부르는 `SetReference`가 낸다 — 옛 handle과 같으면 내지 않는다), 하위 경로·컨테이너 쓰기는 비교 없이 낸다(보수적 — CN-D3의 "바뀌었을 수 있음"). `RuntimeFieldOps` 끝에 `storage`(CN1b)와 `setter` thunk(CN2 — 생성 setter로 쓰는 경로 — CN-D14)를 더한다(ReflectionFoundations 7.1절 — "hook 칸은 그 단계에서 `RuntimeFieldOps` 끝에 더한다"). 통지 번호는 칸에 두지 않고 구독자가 있을 때만 `TypeLease::NotifyIndex`로 찾는다(CN-D12). **한 연산 안의 중복:** 경로 쓰기가 Registry API를 부르면(struct 안 참조·ObjectRefArray 원소·StructRefArray 원소) 경로 진입점과 그 API가 같은 대상을 알린다 — 통지 묶음(`NotifyGroup` — `ObjectRegistry::BeginNotifyGroup`, 소유 스레드)이 그 사이의 통지를 (객체, 번호)마다 한 번으로 모았다가 가장 바깥 묶음이 끝날 때 낸다. 경로 연산 진입점이 게시된 객체의 변경마다 연다. 모을 자리를 할당하지 못하면 바로 낸다(중복은 "바뀌었을 수 있음"에 맞고 놓침은 없다). 묶음 게시(`ObjectBatchPublish`) 안의 게시는 통지하지 않고(그 구간의 `Notify`는 Busy — CN-D11), 사용자(경로 hook 상자 — 경로 진입점, 대입 묶음 — ReflectionText)가 `End` 뒤에 게시한 최상위 필드를 `NotifyIfTarget`(통지 대상이 아닌 ID는 무동작)으로 알린다. staged 쓰기(로드·생성 — 게시 전 객체)는 통지하지 않는다(SL 5.3 — 초기값은 `Changed`가 아니다).
- **CN-D11 파괴·회수·종료:** `RequestDestroy`가 그 객체의 통지 상태를 비우고(구독자에게 알리지 않는다), 회수가 표 항목을 반환한다. 통지 중에 비우면 목록은 `Clear`만 하고(Core `MulticastDelegate`는 발행 중 이동·파괴가 Fatal이다) 항목 반환은 가장 바깥 통지가 끝난 뒤로 미룬다 — 상태와 목록 delegate는 `UniquePtr`라 표가 다시 배치돼도 주소가 고정이다. 살아 있지 않은 객체(파괴 요청·Discard·도달 불가)의 통지는 구독이 남아 있어도 부르지 않고 성공이다(쓰기 경로의 결과가 구독 유무로 갈리지 않게). `Discard`(부분 트리 폐기)된 객체는 Alive가 아니어서 그 순간부터 통지가 구독자를 부르지 않고(통지는 발행자를 Borrow로 붙잡는데 Alive만 된다), 상태는 회수 때 반환된다(GC Retire·Discard·`Shutdown`의 수집 모두 회수 경로 `DestroyReclaimed`에서 — 잠금 밖). 해제 handle은 그 뒤 무효다(Unsubscribe는 false). **통지는 쓰기를 한 API가 처리 표시(`processing_`)와 잠금을 푼 뒤 낸다:** Registry API 안의 쓰기(배열 비우기가 `processing_` 동안 간선을 집계하고 잠금 아래에서 게시하는 것 — `ObjectRegistryArrayEdges.cpp:400-422` — 등)는 바뀐 (객체, 통지 번호)를 그 호출의 지역 목록에 모았다가 표시와 잠금을 푼 뒤 낸다. 묶음 게시(`ObjectBatchPublish` — 그 `End`가 필드 게시다)의 게시는 통지하지 않고, 게시한 호출자가 `End` 뒤에 게시한 최상위 필드를 `NotifyIfTarget`으로 알린다(CN-D10 — 공개 묶음 게시 API의 계약). 그 구간 안에서 코드가 `Notify`를 부르면 Busy다(구독자를 부르지 않는다 — 그 구간은 다른 변경·Borrow가 Busy이고 콜백이 없다는 계약이 그대로다).
- **CN-D12 비용:** 통지 빠른 경로는 소유 스레드·접근 문맥 검사(CN-D8) → handle의 chunk·슬롯 주소(세대 비교) → hot 레코드 통지 bit이고, Registry gate 잠금을 쥐지 않는다(구독 상태는 소유 스레드만 바꾼다 — CN-D8). bit가 켜져 있을 때만 통지 번호 조회(`TypeLease::NotifyIndex` — 생성 setter·코드 경로는 bit를 먼저 보고 번호를 찾는다)와 목록 호출을 한다. bench — 구독자 없는 통지 1M회(목표: 위 세 단계, 할당 없음), 구독자 있음·그 번호 비트 꺼짐, 구독자 n명 발행, 구독·해제 1M회.

### 3.2 생성 setter·getter(CN2 — UD7 개정)

- **CN-D13 선언은 매크로, 정의는 생성(사용자 결정 2026-11-28):** 클래스 본문의 `ROCKS_SETTER(SetText, text)`가 `Result<void> SetText(detail::SetterParam<decltype(text)> value) noexcept;`를 선언하고(`SetterParam<T>`는 산술·enum 스칼라면 `T`, 그 밖은 `const T&`), 메타 컴파일러가 정의를 모듈 생성 `.cpp`에 쓴다. 매크로는 끝 `;`까지 펼치므로 `ROCKS_GENERATED_BODY()`처럼 세미콜론 없이 쓴다. UD7 원안(`ROCKS_GENERATED_BODY`를 파일·줄 매크로로 펼쳐 자동 선언)은 리플렉션 헤더가 자기 생성 헤더를 include해야 해서 BuildTargets BS8b(2026-11-21 사용자 결정 — 그 방식을 버린 안으로 확정)와 부딪혀 버린다. 생성 정의의 순서는 UE 패턴과 같다: 값 같음(CN-D15 — 같으면 Success, 대입·`Apply`·통지 없음) → 대입 → `ROCKS_PROPERTY(Apply = "Method")`가 있으면 `Method()` 호출 → `Notify`면 통지(CN-D9의 진입점 — CN-D10, 통지 실패는 그 오류를 돌려주고 값은 이미 새 값이다). `Notify` 필드의 setter는 맨 앞에서 접근 문맥·스레드·종료를 본다(CN-D9 — 실패면 아무것도 바꾸지 않는다). 정의는 생성 소스의 전역 범위에 한정 이름과 끝 반환형으로 쓴다(`auto NS::C::SetText(...) noexcept -> Result<void>` — rocks 밖 이름공간의 클래스도 받고, `::rocks::Result<void> ::NS::C::…`는 한 이름으로 읽힌다). **대입:** 단일 값 복사(산술·enum·Guid·Name 등 `IsPlainCopy`)는 바로 대입하고, 할당하는 값(String·Soft·Text·배열·Map·Set·Optional·struct)은 사본을 먼저 만든 뒤(`ValueCopy` — 실패면 그 오류, 멤버는 그대로이고 `Apply`·통지 없음) 할당 없는 교환으로 넣는다(옛 값은 setter가 돌아가기 전에 반환한다). 사본의 allocator는 멤버 자신의 allocator(`GetAllocator()`가 있는 형식 — String·Array·Map·Set·Soft의 경로), 없으면(Text·Optional·struct·InstancedStruct) 객체 Registry의 객체 allocator, Registry도 없으면(생성자 안) Unsupported다. 복사할 수 없는 형식(`ValueCopy::Supported` 거짓)의 필드에 `ROCKS_SETTER`를 쓰면 생성 정의가 static_assert로 막는다. **`Apply`:** 값은 같은 클래스(또는 기반)의 `void Method() noexcept` 비 static 멤버 함수 이름이다(오버로드가 있으면 그 모양 하나를 `static_cast`로 고른다)(지정자 문법상 따옴표 문자열 — `MaxElements` 외 지정자 값은 문자열이다). `ROCKS_SETTER`가 없는 필드의 `Apply`는 RMC2904다(리플렉션 쓰기는 setter를 거칠 때만 `Apply`를 부르므로 setter 없는 `Apply`는 어느 경로에서도 불리지 않는다 — CN3 undo도 setter 있는 필드에만 부른다). 함수가 없거나 그 모양이 없으면 생성 정의의 static_assert(RMC2904 문구)가 막는다(메타 컴파일러가 C++ 오버로드 해석을 다시 하지 않는다 — `requires { static_cast<void (C::*)() noexcept>(&C::Method); }`). **getter:** `ROCKS_GETTER(GetText, text)`는 `const decltype(text)& GetText() const noexcept { return text; }`로 매크로가 바로 정의한다(대입·통지가 없어 생성 정의가 필요 없고, 인라인이라 모듈 경계 export도 필요 없다). 메타 컴파일러는 대상 검사만 한다. `ROCKS_PROPERTY(Getter = "Method")`(`T Method() const noexcept`)는 리플렉션 읽기가 그 함수를 거치게 하는 다른 기능이고 CN2b다(UE `Getter` — Widget이 Element의 현재 값을 읽는 경우, UiToolkit 5.3절). **검사(RMC2903):** 매크로가 가리키는 이름이 그 클래스가 선언한 `ROCKS_PROPERTY` 필드가 아님(상속 필드·`ROCKS_NATIVE`·없는 이름), struct의 멤버(setter·getter는 `ROCKS_CLASS`만 — struct 값은 담은 필드로 쓴다), 이벤트 필드, bitfield, Registry 참조를 담는 필드(CN-D14 제한 — getter는 허용), 같은 필드에 `ROCKS_SETTER`(또는 `ROCKS_GETTER`)가 둘, 함수 이름이 ASCII 식별자가 아님. 이름은 사용자가 정한다(UE `Setter = Name`처럼 — 기본 `SetX` 철자 강제 없음). 필드 선언 앞에 매크로를 두면 `decltype(text)`가 이름을 찾지 못해 Clang 컴파일 오류다(매개변수 형식은 complete-class 문맥이 아니다 — 메타 단계의 Clang 실행이 먼저 낸다). 어휘 규칙: `ROCKS_SETTER`·`ROCKS_GETTER`는 메타 컴파일러가 감지하는 리플렉션 매크로라 BuildTargets 3.4의 어휘 검사 목록에 넣는다. EditorOnly 필드의 setter·getter는 그 필드와 같은 `#if ROCKS_WITH_EDITOR_DATA` 블록 안에 둔다 — 그 블록에 `ROCKS_PROPERTY`만 허용하는 3.4 규칙에 `ROCKS_SETTER`·`ROCKS_GETTER`를 예외로 더하고(편집기에서 그 필드를 편집할 때 setter가 필요하다), 생성 정의도 같은 조건 블록 안에 쓴다. 블록 밖에 두면 게임 빌드에서 필드가 없어 컴파일 오류다.
- **CN-D14 쓰기 경로 통일(사용자 결정 2026-11-28 — 편집도 setter 경유):** setter가 있는 필드는 리플렉션 쓰기(`FieldWriteOperation`)·속성 경로 쓰기·편집 쓰기(`EditField` — CN-D19)·Sparks host 쓰기(`ScriptWritable` — EI2)가 모두 생성 setter를 거친다(UE `CallSetter`와 같고, UE Details 패널과 다르다 — UE는 Details 쓰기 뒤 `PostEditChangeProperty`로 따로 맞춰 같은 동기화를 두 번 쓴다). 하위 경로 쓰기는 최상위 값을 사본으로 읽어 고친 뒤 setter에 넘긴다(UE `PerformOperationWithSetter`). 그래서 setter가 거부하는 값(예: Static 컴포넌트의 Mobility — ER 24장)은 편집기에서도 진단으로 막힌다. 제한:
  - **Registry 참조를 담는 필드(`ObjectRef`·`ObjectRefArray`·`ObjectRefMap`·`StructRefArray`, 참조를 담은 struct)에는 `ROCKS_SETTER`를 쓸 수 없다(RMC):** 사본을 만들면 간선·클러스터 계수·관찰자 delta가 깨지고 큰 배열은 원소 하나에 O(n)이다. 이런 필드는 Registry API로 제자리에 쓰고, `Notify`면 그 API가 통지한다(CN-D10). 장부 갱신이 필요하면 `Apply` 대신 소유 타입의 전용 API를 쓴다.
  - **`ReadOnly`와 setter는 함께 쓸 수 있다:** `ReadOnly`는 "setter 없이 메모리에 직접 쓰는 리플렉션 쓰기를 거부"한다는 뜻으로 고친다(ReflectionFoundations 954행 정의 개정 — CN2). setter가 있으면 모든 쓰기가 setter로 가므로 `ReadOnly` 필드도 쓸 수 있다(UiToolkit 7.3절 "`Edit`이고 `ReadOnly`이며 setter가 있으면 setter로 편집"과 같다). 구현: `ReadOnly`는 하위 멤버·원소로 전파되고(`PropagateFieldFlags` — ReflectionFoundations 625행) 쓰기 검사(`ValidateFieldWrite`)가 setter 경로 앞에서 거부하므로, 경로의 `steps[0]` 필드에 setter가 있으면 그 경로의 ReadOnly 검사를 건너뛰고 setter로 보낸다. World 필드는 `ReadOnly`를 유지한 채 setter를 더한다(CN5 — World 세션). 단 `actors`·`components`·`rootComponent`는 Registry 참조 필드라 setter를 둘 수 없다(위 제한) — ER 4.6절의 "ReadOnly를 setter로 푼다"는 `relativeTransform`·`enabled` 같은 값 필드에만 해당한다. SparksBinding의 `ReadOnly`+`ScriptWritable` 거부(RMC2603 대역의 그 검사)는 setter가 있으면 허용으로 고친다(CN2).
  - **실행 조건:** setter는 보통 멤버 함수라 호출자가 그 객체를 쥐고 있다. 생성자 안·Registry 밖 인스턴스(RawSource 기본값)에서는 대입과 `Apply`만 하고 통지하지 않는다(CN-D9). staged 쓰기(로드)는 setter를 거치지 않는다 — 값만 놓고, 반영은 소유 타입의 로드 뒤 처리(Widget `ApplyAllProperties` 등)가 한다. 리플렉션·경로 쓰기가 setter를 부를 때는 지금처럼 `ResolveForWrite`(encode 고정 중 Busy, 변경 표지 올림)를 거친 뒤 부른다. `DestroyRequested` 객체는 리플렉션 쓰기 규칙(지금과 같다)을 따른다.
  - **경유 방식(CN2b):** setter가 있는 최상위 필드(`RuntimeFieldOps::setter`)에 대한 게시된 객체의 변경은 모두 같은 함수(`detail::RunThroughSetter`)를 지난다: 변경 표지(MutationStamp)를 읽고 → 최상위 필드를 상자(`DetachedValue` — 지금 값의 깊은 사본, ReadOnly 허용)로 분리 → 원래 경로 연산을 상자에 그대로(값 종류·대상 타입·enum·상한·Name·참조 검증은 상자 위 경로가 같은 코드로 한다 — ReadOnly만 허용) → 바뀐 것이 없는 연산(이미 있는 Set 원소의 InsertKey)은 setter를 부르지 않음 → 상자 값 트리의 검증 hook(InvalidArgument — 그 실패는 경로 실패 `StructValidation`) → 변경 표지가 그대로인지(아니면 Busy — 분리 중의 재진입 변경을 덮지 않게, hook 상자와 같은 규칙) → 쓰기 Borrow(`ResolveForWrite` — encode 고정 중 Busy, 변경 표지 올림) 아래, 호출자의 접근 문맥을 실행 scope(`ObjectAccessScope`)로 두고 `setter(object, 상자 값)` — setter의 접근 검사·통지가 경로 API가 받은 문맥을 쓴다(엄격 모드 포함). 전체를 통지 묶음으로 감싸 통지는 쓰기 Borrow를 놓은 뒤 나간다(CN1b와 같다 — 구독자의 encode·Collect가 그 Borrow에 막히지 않게). setter·변경 표지의 실패는 경로 실패 단계 0(사유 None)으로 남는다. 최상위 단일 값 쓰기(등록된 write와 경로의 최상위 값)도 한 단계 경로로 같은 함수를 지난다 — 단일 값 변환·검증 코드를 하나로 둔다. 상자는 작은 값(`DetachedInlineBytes` 64 byte·정렬 16 이하 — 단일 값·String·작은 struct)을 인라인 저장소에 담아 할당하지 않고, thunk는 상자 값을 교환으로 가져가 사본이 하나뿐이다(UE `PerformOperationWithSetter`의 임시 값 하나와 같다). 경로 실행기는 최상위 함수표를 찾은 직후(4단계) setter 필드면 프레임의 ReadOnly를 지우고, 값 검증(5·6단계 — 검증 오류가 할당 오류보다 먼저인 계약 유지) 뒤 hook 우회 자리에서 setter를 남기고 돌아온다(값 트리 검증은 setter 경유가 하므로 hook 상자를 따로 쓰지 않는다). 최상위 단일 값은 등록된 write(`FieldWriteOperation` — setter가 있으면 ReadOnly만 빼고 같은 검증 뒤 같은 함수로)가 보낸다. staged 객체·상자 대상 경로는 setter를 거치지 않는다(CN-D14 — 로드·생성 값). 통지: setter가 낸다(같은 값은 생략 — CN-D15) — `FieldWriteOperation`과 경로 진입점은 setter 필드에 CN1b 통지를 내지 않는다. setter의 실패(접근·할당·Busy)는 쓰기의 실패로 그대로 돌아간다. **thunk 배치:** 생성 헤더의 `GeneratedType<C>::SetterOf<Member>()`(constexpr — `MemberTag` 비교, setter 없으면 nullptr)가 인라인 람다 thunk를 돌려주고, 생성 함수표는 그 클래스가 선언한 setter 필드의 칸에만 싣고, 상속 필드의 setter는 등록이 기반 레코드의 함수표에서 물려받는다(path가 있는 항목 — 기반 thunk는 파생 객체에도 맞다). 파생 생성 소스에 기반의 생성 헤더가 보이지 않을 수 있어(Asset·Component 등 import 기반) 생성 코드로 잇지 않는다. thunk는 생성 setter와 같은 순서(Notify면 접근 검사 → 같은 값이면 끝 → 대입 → Apply → 통지)이되 대입이 상자 값의 교환이다(`SetterAccess::AssignOwned` — 할당 실패 없음). 람다는 `GeneratedType<C>`(C의 friend) 안이라 파생·다른 모듈에서 인스턴스화돼도 private setter·Apply를 부른다 — setter 접근 수준 제한은 없다. 다른 모듈의 파생 함수표가 쓰려면 클래스가 export돼야 하는 것은 생성 setter와 같다(5절). 등록은 setter 필드가 강한 참조(값·원소)이거나 path thunk가 없으면 InvalidArgument, 값 타입 해석 뒤 struct 대상(필드·원소·Optional 내부)이 강한 참조를 담으면 InvalidArgument다(수동 함수표 포함 — 메타 컴파일러의 RMC2903과 같은 규칙). UE와 다른 점: UE는 객체 참조 속성에도 Setter를 허용한다(Rocks Registry 참조는 간선 장부 때문에 제자리 쓰기만).
- **CN-D15 값 같음:** setter·`SetAndNotify`·최상위 쓰기의 "같은 값" 판정은 RuntimeClassMetadata A5b의 같음(인코딩 byte 같음, 참조는 대상 정체성)과 같다. SL 5.3의 비교 규칙과도 같다. 형식별 규칙(`Object/ValueSame.h`의 `detail::ValueSame<T>` — `ValueCopy`와 같은 형식 집합, CN2a): bool·정수·enum은 값 같음, 실수는 비트 같음(`0.0`과 `-0.0`은 다름, NaN payload 구별), Name은 토큰 `==`에 표시 번호(`displayId`)까지(Name `==`는 ASCII 대소문자를 무시하지만 저장 표시는 다르다 — CN1b와 같다), WeakObjectRef는 대상 handle(null끼리 같다), Guid·AssetId·Digest·ClassRef는 그 형식의 `==`, String은 UTF-8 byte, Soft 참조는 자산 ID와 경로 byte, 배열·정적 배열은 길이와 원소별, Map·Set은 개수와 순서대로 원소별(저장 순서가 인코딩 순서다 — 같은 내용의 다른 순서는 다르다), Optional은 유무와 값, 생성 struct는 리플렉션 base 하위 객체 → `ROCKS_PROPERTY` 멤버별(생성 `GeneratedType<S>::SameValue` — EditorOnly 멤버는 조건 블록 안, Binds 미러의 실제 Core 값 타입도 같은 특수화를 받아 실수가 비트로 비교된다). `ROCKS_NATIVE` 멤버가 있는 struct는 늘 다르다(저장하지 않는 멤버만 다른 새 값을 같다고 보면 setter가 대입을 건너뛴다), Text는 이력 구조(`Text::IsIdentical` — 같은 노드면 바로 같음, 아니면 형태·원문 byte·ID·source revision·Format 패턴과 인자 이름·값을 재귀로 비교, `TextResolveLimits`의 깊이·작업 상한을 넘으면 다르다로 본다 — 할당 없음). 비교할 수 없는 형식(InstancedStruct, 그 밖에 규칙이 없는 형식)은 늘 다르다로 본다. CN1b의 최상위 쓰기 비교(`FieldValue` — 등록된 read 사본)에서 Text는 늘 다르다로 보고, CN2b가 같은 `Text::IsIdentical`로 바꾼다.

### 3.3 편집 통지(CN3)

- **CN-D16 `EditChange`(`Object/EditChange.h` — 형식은 늘 컴파일, hook·관찰자는 편집 빌드만):** `{object, memberField(최상위 FieldId), path(PropertyPath — 하위 경로 포함), kind(EditChangeKind 비트), origin, objectIndex(다중 선택의 순번), batchSize(같은 편집의 객체 수)}`. `EditChangeKind`(UE `EPropertyChangeType` 대응, 이름은 Rocks식 — UE 이름은 2절 표에만): `General`(종류 미정 — UE Unspecified)·`Committed`(확정 값 — ValueSet)·`Interactive`(드래그 중 — 끝나면 `Committed`가 이어진다)·`ElementAdded`·`ElementRemoved`·`Cleared`·`ElementMoved`·`ElementDuplicated`·`ResetToDefault`·`ReferenceReplaced`(에셋 통합·reload — Redirected)·`EditabilityToggled`(ToggleEditable). 조합(`Committed | ResetToDefault`)을 허용한다. `EditOrigin`: `User`(Inspector·도구의 사용자 편집)·`Propagation`(원형 → 인스턴스 전파 — Prefab PF7)·`Undo`(undo·redo 적용)·`Tool`(명령·스크립트 도구). 관찰자는 출처로 거른다(예: override 기록은 `User`만 — 전파 쓰기가 사용자 편집으로 잡히지 않게).
- **CN-D17 타입 편집 hook:** 클래스가 `Result<void> BeforeEdit(const EditChange&) noexcept`·`void AfterEdit(const EditChange&) noexcept`·`void AfterUndo(const UndoEvent&) noexcept`·`bool CanEdit(const EditQuery&) const noexcept`(UE `CanEditChange` — Inspector가 행을 잠글지 묻는다, `EditQuery{memberField, path}`) 가운데 필요한 것을 선언하면 메타 컴파일러가 감지해 편집 빌드의 생성 연산표(`RuntimeTypeOps::editHooks`, `ROCKS_WITH_EDITOR`)에 싣는다. 감지 기준은 매개변수 형식이다 — 매개변수가 `EditChange`·`UndoEvent`·`EditQuery`인 멤버만 hook이고(그 형식이 편집 전용이라 오탐이 없다), 같은 이름이라도 다른 매개변수면 hook이 아니다(RMC를 내지 않는다 — 게임 코드의 `CanEdit` 같은 흔한 이름을 막지 않게). 반환 형식·noexcept·const가 어긋난 hook 매개변수 선언은 RMC다. 선언은 `#if ROCKS_WITH_EDITOR` 안에 둘 수 있다(리플렉션 매크로가 아니므로 BuildTargets 3.4 규칙에 걸리지 않는다. 두 조합 AST 비교는 리플렉션이 아닌 멤버 함수를 비교하지 않으므로 더할 것이 없다). 기반 체인에서 가장 가까운 선언을 부르고, 기반 hook은 파생이 직접 부른다(UE `Super::PostEditChangeProperty`와 같다). 가상 함수 대신 연산표인 이유: Object 기반에 vptr을 두지 않는다(파생인 Widget·Component는 가상 함수가 있지만 Object 수명·생성 규칙은 연산표가 중심이다). `BeforeEdit` 실패는 그 편집 전체를 취소한다(CN-D19 — UE에는 취소가 없고 `CanEditChange`만 있다, 값 검증을 hook에 둘 수 있게 더한다).
- **CN-D18 편집 관찰자:** Registry 범위 관찰자 목록 `EditObservers`(UE 전역 `OnObjectPropertyChanged` 계열)에 Inspector 갱신·Transaction 기록(CU4)·패키지 dirty 표시·override 기록이 구독한다. 관찰자는 `OnBeforeEdit(batch)`·`OnAfterEdit(batch)`·`OnEditCancelled(batch)`를 받는다. 편집 기능이 없는 빌드(`ROCKS_WITH_EDITOR` 0)에는 없다.
- **CN-D19 편집 쓰기 진입점 `EditField`와 순서:** `EditField(access, objects, path, value, kind, origin)`이 다중 선택 편집을 UE 순서로 한다(`PropertyHandleImpl.cpp:543-698`): (1) 모든 객체의 `CanEdit` — 하나라도 거짓이면 진단, 아무것도 하지 않음; (2) 관찰자 `OnBeforeEdit` → 객체마다 타입 hook `BeforeEdit`(객체 순서대로) — 하나라도 실패하면 이미 Before를 받은 관찰자에 `OnEditCancelled`를 보내고 쓰지 않는다(앞 객체도 쓰지 않았으므로 되돌릴 것이 없다); (3) 객체마다 쓰기(setter 경유 — CN-D14, 필드 통지 포함 — CN-D10). 쓰기 실패는 예외가 아니라 정상 경로다(다중 선택에 Static과 Movable 컴포넌트가 섞이면 setter 거부가 흔하다): 실패한 객체를 건너뛰고 나머지를 계속 쓴다; (4) 모든 객체가 `AfterEdit`을 받는다(UE는 Post를 늘 전 객체에 부른다) — `EditChange::applied`(이 객체에 쓰였는지)와 `result`(실패면 그 오류)로 구별하고, 관찰자 `OnAfterEdit`은 객체별 결과를 함께 받는다(Transaction은 쓰인 객체만 기록 — 부분 실패를 숨기지 않는다). `EditField`의 반환은 전부 성공이면 Success, 하나라도 실패면 첫 실패 오류와 실패 수다. **Interactive 경계:** `BeginInteractiveEdit(objects, path)`가 (1)·(2)를 한 번 하고, 드래그 동안 `EditField(..., Interactive)`는 (3)·(4)만(Before 생략 — UE와 같다), `EndInteractiveEdit(Committed)`가 마지막 값으로 (3)·(4)를 한 번 더 하고 끝을 관찰자에 알린다(Transaction은 Begin에서 시작 값을, End에서 확정을 기록 — CU4). 취소(`EndInteractiveEdit(Cancelled)`)는 시작 값으로 되쓴 뒤 `OnEditCancelled`다. **undo·redo:** Transaction 적용은 기록한 값을 그대로 되쓴다 — setter의 검증을 거치지 않는다(기록 값은 기록 당시 유효했던 상태이고, 현재 다른 값과 맞물려 setter가 거부하면 복원이 실패하기 때문이다. UE Transaction도 객체 상태를 직렬화로 복원한다). 되쓴 필드마다 `Apply`(CN-D13)를 부르고 `Notify` 필드면 통지한 뒤, 객체마다 `AfterUndo`(UE `PostEditUndo`)를 부른다. origin은 `Undo`다.
- **CN-D20 기존 경로와 Prefab:** 지금 편집 성격의 쓰기를 하는 곳을 `EditField`로 옮긴다 — 패키지 편집 명령(AssetEditCommandlet의 경로 쓰기 — origin `Tool`), 클래스 기본값 되돌리기(A5b2 — `ResetToDefault`), UI `WidgetFieldBindings::Write`(CN5). 로드·쿠킹·저장 경로는 편집이 아니다. Prefab 제자리 전파(PF7)의 계기는 revision 비교(로드 또는 `RebasePrefabInstance` — Prefab 3.7절)이고 편집 관찰자가 아니다: CN3은 그 전파가 쓰는 쓰기 경로(setter·`EditField`, origin `Propagation`)만 준다. 전파 판정(override 집합이 1차, 인코딩 비교는 확인)은 Prefab 문서 그대로다.

### 3.4 Sparks·UI·World

- **CN-D21 Sparks `Changed`:** SL 5.3의 native 필드 `Changed`는 `Notify` 필드에만 있다. 실행 host(EI3)는 발행자마다 `TrySubscribeAll`로 연결하고 thunk가 큐 항목을 기록한다. 값 기준 판정(조각 시작 값과 끝 값이 다를 때만 전달)은 host가 한다: 구독한 (발행자, 필드)마다 마지막으로 전달한 값의 사본을 쥐고(값 비교는 CN-D15), 조각 끝에 현재 값과 비교한다. 비용은 구독 필드 수 × 값 크기다(컨테이너는 원소별 사본) — host가 그 수를 진단으로 낸다. Pre 통지(옛 값 싣기)를 두지 않는 이유: 모든 쓰기 경로가 옛 값 사본을 만들어야 하고(구독자가 없어도 경로마다 비용), 값 기준이 필요한 곳은 Sparks host뿐이다.
- **CN-D22 schema `changed`:** `ScriptReadOnly`·`ScriptWritable` 필드가 `Notify`면 binding schema 필드에 `changed: true`를 쓴다(SL 10.2 — SparksBinding EI1d의 통지 몫). descriptor의 필드·함수 flag `Notify`(descriptor schema 9)는 CN1a가 싣는다 — 파생 모듈이 상속 필드를 schema에 다시 실을 때 flag를 잃지 않고, 기반 체인의 Notify 함수가 통지 번호에 들어간다. 계산 속성(SE-R7의 getter·setter 쌍)의 `changed`는 EI1d가 계산 속성과 함께 정한다.
- **CN-D23 UI:** UI의 `WidgetFieldBindings`(지금 UI 전용 multicast)는 CN1의 구독·통지 위에 다시 만든다(UI 세션 — CN5). Widget 속성은 UiToolkit 5.3절 예시에 `ROCKS_SETTER` 한 줄을 더한 꼴이다(`ROCKS_PROPERTY(Category = "Content", Multiline, Apply = ApplyText, Notify) Text text;` + `ROCKS_SETTER(SetText, text)` — 5.3절 예시를 CN2 때 고친다).
- **CN-D24 복제:** RepNotify(복제 수신 뒤 hook)는 별개다(네트워크 단계). 복제 수신이 `Notify` 필드를 쓰면 CN-D10대로 통지가 나간다(SL 5.3 "스크립트 밖의 쓰기(복제 수신·native)는 엔진이 적용하는 batch 하나를 한 조각으로 본다").

## 4. 버린 대안

- **모든 필드 통지(opt-out):** 쓰기마다 구독 검사 비용과 통지 번호가 든다. UE도 opt-in이다.
- **객체 멤버로 통지 상태(UE `UWidget::EnabledFieldNotifications`처럼 객체 안 비트 배열):** 1M 객체 × 칸 하나가 메모리 예산을 깬다(GcScale). 슬롯 flag bit와 지연 표로 같은 비용을 낸다.
- **슬롯 hot 레코드에 표 번호(uint32):** 칸이 없다(64 byte 고정). 레코드를 키우면 모든 handle 조회의 캐시 줄이 늘어난다.
- **이름(FName) 기반 식별:** 이름 바꾸기·도구 이름이 구독을 깬다. Rocks는 안정 ID 체계가 있다.
- **비동기 통지(큐):** C++·UI 바인딩은 setter 직후 반영을 기대한다(UE와 같다). 큐가 필요한 Sparks는 thunk에서 큐로 간다(SD78과 같은 구조).
- **편집 hook을 가상 함수로 / 표지 매크로로:** Object 기반에 vptr을 두지 않는다. 표지 매크로를 `#if ROCKS_WITH_EDITOR` 안에 두면 BuildTargets 3.4 규칙(조건 블록 안 리플렉션 매크로 금지)에 걸린다 — 시그니처 감지로 한다.
- **`ROCKS_GENERATED_BODY`를 파일·줄 매크로로 펼쳐 setter 자동 선언(UD7 원안):** BS8b와 충돌한다(사용자 결정으로 매크로 선언 + 생성 정의).
- **Details식 직접 메모리 쓰기 + 편집 hook 동기화(UE):** 같은 장부 갱신을 setter와 편집 hook에 두 번 쓰게 된다(사용자 결정으로 편집도 setter 경유).
- **Pre 통지로 옛 값 전달:** CN-D21.

## 5. 한계·후속

- Interactive 병합·undo 기록 형식은 CU4 Transaction 단계다. 이 문서의 `EditChangeKind`·`EditOrigin`과 CN-D19 경계가 그 입력이다.
- 통지 번호는 타입 revision(SE-O2)마다 새로 정해진다 — 구독은 ID로 하므로 reload 경계에서 구독을 새 번호로 옮기는 일은 SE-O2 구현이 한다.
- 계산 값 함수의 `Notify`는 코드가 알려야 한다(자동 의존 추적은 없다 — UE와 같다).
- Registry 참조 필드에는 생성 setter가 없다(CN-D14) — 그런 필드의 장부 갱신은 소유 타입의 API로 한다.
- 객체 소멸자·회수 중의 setter·코드 통지는 Registry 상태에 따라 Busy·StaleHandle이다(값은 Busy면 이미 새 값). 소멸 중에는 통지할 대상이 없으므로 쓰지 않는다.
- 생성 setter는 모듈의 생성 소스에 정의되므로 모듈 API 매크로가 없는 클래스의 setter는 다른 모듈에서 링크되지 않는다(다른 비인라인 멤버 함수와 같다).
- CN2a와 CN2b 사이에는 리플렉션·경로·Sparks 쓰기가 setter를 거치지 않는다 — setter 필드도 그 경로에서는 `Apply` 없이 값이 바뀌고 CN1b 지점이 통지한다. CN2b가 setter 경유로 바꾸고 그 필드의 CN1b 통지 지점을 끈다(이중 통지 없음 시험).
- InstancedStruct 필드의 setter는 담긴 struct가 참조를 담으면 실행 중 Unsupported다(`ValueCopy`의 TryClone — 담긴 타입이 정해지지 않아 메타 단계에서 막지 못한다).
- `NotifyChanged`·`SetAndNotify`는 C++23 명시적 객체 매개변수를 쓴다(코드베이스 첫 사용) — Mac 빌드는 Apple clang 17(Xcode 16.3) 이상이 필요하다(Mac 빌드 확인 때 BuildTargets 도구 최소 버전에 적는다).
- setter 경유 리플렉션 쓰기는 상자 분리와 상자 위 경로 실행으로 경로 실행을 두 번 한다(bench: 할당 0, 약 0.5–0.6µs — 직접 write는 약 0.09µs). 단일 값은 등록된 write가 이미 검증한 FieldValue를 상자 없이 임시 값으로 바꿔 thunk에 넘기는 빠른 길로 줄일 수 있다(Sparks host 쓰기 EI2가 잦아지면 측정 뒤). 컨테이너 원소 하나의 쓰기는 최상위 값 전체를 복사한다(O(n) — UE `PerformOperationWithSetter`와 같다).
- 리플렉션 쓰기(setter 경유·hook 상자)는 상자를 객체 Registry의 allocator로 복사해 교환하므로 필드의 할당 버퍼가 그 allocator 것으로 바뀐다(코드 setter는 필드 자신의 allocator — CN-D13). 버퍼는 allocator와 함께 옮겨 가므로 정확성 문제는 없다.
- 통지하는 setter는 접근 검사를 대입 전(`CheckSelfAccess`)과 통지(`NotifySelf`·`NotifyChecked`)에서 거듭 한다(정확성 문제 없음, 접근 문맥 조회 한 번 더) — 비용이 측정으로 드러나면 검사한 문맥을 넘기는 경로로 바꾼다.
- bitfield 필드에는 `ROCKS_SETTER`·`NotifyChanged`·`SetAndNotify`를 쓸 수 없다(CN-D9·CN-D13 — 멤버 포인터가 없다). 코드는 `ObjectRegistry::Notify`로 알린다. UE도 bitfield bool의 Setter는 드물다 — 필요해지면 생성 `Get_`·`Set_` 접근자 위에 더한다.
