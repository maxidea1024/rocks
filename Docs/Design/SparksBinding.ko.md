# Sparks 엔진 binding(EI1)

이 문서는 Sparks 엔진 연동의 첫 단계 EI1(SparksEngineIntegration 3절 — 실제 엔진 선언에서 binding schema `<모듈>.sparkbind.json`을 생성하고 컴파일러가 실제 엔진 API로 타입을 검사한다)을 어떻게 만드는지 정한다. schema 파일 형식은 SL 10.2절 "binding schema 파일 형식"이 정본이고, 이 문서는 C++ 리플렉션 선언 → schema 항목의 규칙(노출 지정자·타입 대응·이름·검사)과 생성 위치·시험을 정한다. 리플렉션 지정자 목록의 정본은 구현 문서 ReflectionMetadata(지정자 표)다.

- 개정 6(2026-11-27): EI1c 설계(9절 B20–B29) — 이벤트 노출 지정자 `ScriptAssignable`(UE `BlueprintAssignable`), 노출 규칙·이름(필드 규칙, `Changed` 예약)·인자 표기, descriptor schema 8, 출력, 스크립트 단계 안 native 발행의 전달(EventReflection ED11 열린 결정 확정 — C++ 구독자는 발행 때, Sparks handler는 큐), `ScriptBroadcast`·`publisher`는 뒤로.
- 개정 5(2026-11-26): EI1b 설계(7절 B11–B19) — 함수 노출 지정자 `ScriptCallable`(UE `BlueprintCallable`)과 그 계약, 시그니처 표기, 이름(도구 이름·`TryX` → `X`·멤버 이름 공간), 효과·일회성·초당 값 지정자, descriptor schema 6, 엔진 함수 지정. 계산 속성은 EI1d로 옮김(getter·setter FunctionId 칸과 CU5 setter 통지가 함께 필요하다 — SL 10.2).
- 개정 4(2026-11-26): 구현 리뷰 반영(6절) — `NotScriptType`은 노출만 끊고 확장 가능 상속은 이어진다(UE `NotBlueprintType`·`Blueprintable`), hook 이름 검사는 `object` 종류만, EditorOnly 타입의 노출 필드는 RMC2607, 미러 대상은 RMC2601, descriptor reader가 생성기가 만들지 않는 조합을 거부, 시험 보강.
- 개정 3(2026-11-26): EI1a 구현(6절 — 메타 컴파일러 `SparksBinding`·`SparksNames.json`, descriptor schema 4, 빌드 게시, 컴파일러의 struct `base`·타입 인자 `?` 거부, World 타입 지정자, 시험).
- 개정 2(2026-11-26): 리뷰 반영 — 컨테이너 타입 인자에 `?` 없음(B4), struct 상속(`base`·`ScriptType` 상속 — SL 10.2 개정), 상속을 끊는 `NotScriptType`·`NotScriptExtensible`, descriptor schema 4(B2), 언어 이름 충돌은 메타 컴파일러가 이름 표 파일로(B6 — SL 10.3대로, 표는 C++ 시험이 컴파일러와 대조), `Soft<T>`·`Class<T>`·Flags enum·Binds 미러·`Asset` 규칙, C++ 시험의 모듈 목록과 출력 폴더 찾기(B9), 빌드 연결 항목(B2), escape(B8), 노출 범위(3절).
- 개정 1(2026-11-26): 첫 판 — EI1a 설계(B1–B10). 노출은 UE처럼 opt-in(사용자 결정 2026-11-26).

## 1. 나눔

| 단계 | 내용 | 선행 |
|---|---|---|
| EI1a 타입·필드 | 노출 지정자(SE-R3 중 타입·필드 몫), 메타 컴파일러의 `.sparkbind.json` 생성(SE-R4 — 타입·필드·enum), 컴파일러의 struct 상속·schema 표기 검사, 엔진 핵심 World 타입에 지정자, 생성된 schema로 Sparks 컴파일 시험 | 없음(지금 리플렉션으로 된다) |
| EI1b 함수 | `ROCKS_FUNCTION`의 schema `functions`(SE-R1 — 시그니처·효과·`TryX` 이름, 7절) | UiToolkit CU2(FR1 — 끝남) |
| EI1c 이벤트 | `FieldKind::Event` 필드의 schema `events`(SE-R2 — `Params`, 9절. 발행 측 `publisher`는 네트워크 단계) | UiToolkit CU3(EventReflection EV2·EV3a — 끝남) |
| EI1d 편집 메타·통지 | 필드 `changed`(CU5), 단위·범위(CU1)의 schema 반영, 계산 속성(getter·setter 쌍 — schema 필드에 getter·setter FunctionId 칸, 개정 5에서 EI1b에서 옮김) | UiToolkit CU1·CU5 |

EI1a가 끝나면 컴파일러가 실제 엔진 타입·필드를 읽어 타입 검사하고 언어 서버가 그것을 자동완성·hover에 보인다(실행은 EI2 — host가 없다).

## 2. 결정

- **B1 노출은 opt-in(UE `BlueprintType`·`BlueprintReadOnly`와 같다):** 지정자가 없는 리플렉션 타입·필드는 schema에 나오지 않는다. 지정자(이름은 Rocks식 — UE 대응은 괄호):
  - `ROCKS_CLASS`·`ROCKS_STRUCT`·`ROCKS_ENUM`의 `ScriptType`(`BlueprintType`): 스크립트에 타입으로 보인다. 클래스와 struct는 기반 체인에서 상속되고(UE `IsScriptExposedClass`·`IsScriptExposedStruct`가 super 체인을 걷는다), `NotScriptType`(`NotBlueprintType`)이 그 타입과 파생에서 상속을 끊는다(파생이 다시 `ScriptType`을 쓰면 다시 노출 — UE와 같다). enum은 자기 것만 본다(UE `IsScriptExposedEnum`).
  - `ROCKS_CLASS`의 `ScriptExtensible`(`Blueprintable`): Sparks class가 상속할 수 있다. `ScriptType`을 함께 뜻하고 기반에서 상속되며 `NotScriptExtensible`(`NotBlueprintable`)이 끊는다(schema `scriptExtensible: true`). 확장 상속은 노출과 따로 내려간다 — `NotScriptType` 클래스 아래에서 다시 `ScriptType`을 쓴 파생은 확장 가능을 잃지 않는다(UE `NotBlueprintType`은 `BlueprintType`만 끄고 `Blueprintable` 상속은 그대로다). descriptor의 `ScriptExtensible` flag는 이 상속 값이라 숨은 클래스에도 있을 수 있다(개정 4).
  - `ROCKS_PROPERTY`의 `ScriptReadOnly`(`BlueprintReadOnly`)·`ScriptWritable`(`BlueprintReadWrite`): 필드가 읽기 전용(`access` 생략) 또는 읽기·쓰기(`access: "readWrite"`)로 보인다. 둘 다 쓰면 오류, 리플렉션 `ReadOnly` 필드(리플렉션 쓰기 경로가 거부한다)에 `ScriptWritable`이면 오류다. `ScriptName = "X"`: 스크립트 이름을 덮는다(SL 10.3절 — `ScriptReadOnly`·`ScriptWritable` 없이 쓰면 오류).
  - enum의 `Hidden` 열거자(`ROCKS_ENUMERATOR(Hidden)` — `Count` 같은 표지)는 `cases`에 넣지 않는다(UE `IsScriptExposedEnumEntry`). 그래서 case 번호는 C++ 값·선언 번호와 다를 수 있다 — 실행 host(EI2)는 case 이름으로 대응한다.
  - `EditorOnly` 타입은 상속으로 노출되지 않는다(출시 빌드에 없다 — 조용히 빠진다). `EditorOnly` 타입·필드에 노출 지정자를 직접 쓰면 오류다.
- **B2 생성 위치와 빌드 연결:** 메타 컴파일러가 모듈마다 descriptor(`<출력>/Metadata/<M>.rocksmeta.json`) 옆에 `<M>.sparkbind.json`을 같은 실행에서 쓴다(같은 staging·게시 규칙). 노출 타입이 없는 모듈도 `types: []` 파일을 쓴다(빌드 출력 목록이 지정자에 따라 바뀌지 않게). 빌드 쪽: 모듈 배치(`MetadataLayout`)에 schema 경로 칸, 메타 컴파일러 출력 옵션(`--binding-schema`), 런너(`MetadataRunner`)의 stage 경로·게시 목록·생성 확인. 런너가 매번 돌므로 증분 key는 바뀌지 않는다.
  - **descriptor schema 4:** 다른 모듈이 기반·필드 대상의 노출과 상속 이름을 판정하도록 싣는다 — 타입 flag `ScriptType`·`ScriptExtensible`(실효 — 상속·끊기를 마친 값, class·struct·enum), 필드 flag `ScriptReadOnly`·`ScriptWritable`, 필드 key `scriptName`(없으면 빈 글자). reader는 엄격하므로 판 번호를 올린다(옛 판 거부 — 하위호환 없음). flag 쓰기 순서는 기존 flag 뒤 위 순서.
  - 런타임 생성 코드(TypeSchema flag)는 바꾸지 않는다 — 실행 host(EI2)가 생기면 그때 정한다.
- **B3 타입 종류:** `ROCKS_CLASS` 중 기반 체인에 `rocks::Asset`(AssetRuntime)이 있으면 `asset`, 아니면 `object`. `rocks::Asset` 자신은 노출할 수 없다(도구 이름 `Asset`이 언어 소유 이름(`Asset(...)` 리터럴)이라 — 오류). `ROCKS_STRUCT`는 `struct`, `ROCKS_ENUM`은 `enum`, `interface`는 CU9 뒤. `base`는 직접 기반이 노출 타입이면 그 이름, 아니면 쓰지 않는다(`Actor`의 기반 `Object`는 노출하지 않는다). 기반 체인이 노출 → 비노출 → 노출로 끊기면(`NotScriptType` 아래에서 다시 `ScriptType`) 그 타입의 `base`는 가장 가까운 노출 조상이 아니라 생략이다(비노출 조상의 필드는 보이지 않는다 — UE와 같다).
  - **struct:** `base`는 기반 struct가 노출 타입일 때 그 이름이다(SL 10.2 개정 — 필드 상속만, struct 사이 변환·대입은 없다). struct `constructible`은 EI1a에서 쓰지 않는다 — 엔진 struct의 이름 지정 생성은 host의 struct 초기화(EI2)와 함께 정하므로 `false`를 쓴다.
- **B4 타입 대응(필드 `type` 표기 — SL 3.6 정규형):** `?`는 필드 타입의 최상위에만 붙는다 — 컨테이너 타입 인자 안의 객체 참조는 `T`·`Soft<T>`로 쓴다(SL 4장 "타입 인자에는 `?`를 쓸 수 없다", 원소 읽기는 그 규칙대로 `T?`).

| C++ 값 종류(ValueKind) | 최상위 표기 | 타입 인자 안 |
|---|---|---|
| Bool, Int8–Int64, UInt8–UInt64, Float32, Float64 | `bool`, `int8`–`int64`, `uint8`–`uint64`, `float32`, `float64`(SL 4장 — C++ 타입과 같은 Sparks 타입) | 같음 |
| Utf8String, Text | `string`, `Text` | 같음 |
| Enum | 그 enum의 스크립트 이름(`ScriptType`이어야 한다, Flags enum은 노출할 수 없다 — Sparks enum은 값 하나) | 같음 |
| Struct — `CoreTypeBindings` 수학 미러 | `binds` 철자로: `Vector2/3/4<float·double>` → `vec2`/`vec3`/`vec4`, `Quaternion<…>` → `quat`, `Rotator<…>` → `Rotator`, `Transform`·`Transform3<…>` → `Transform`, `LinearColor` → `Color`(SL `Color`는 선형 float RGBA). 표 밖의 미러(`Color` 8비트·`IntVec*`·`FrameRate`·커브)와 enum 미러(`InterpCurveModeBinding`)는 노출할 수 없다 | 같음 |
| Struct — 그 밖 | 그 struct의 스크립트 이름(`ScriptType`이어야 한다) | 같음 |
| ObjectReference, WeakObjectReference | `T?`(T는 대상 클래스의 스크립트 이름 — SL 4장 "그 밖의 객체 필드". `Required`도 `T?`) | `T` |
| SoftObjectReference | `Soft<T>?`(T는 `asset` 종류 — SL SD19, 빈 값이 있다) | `Soft<T>` |
| ClassReference | 노출할 수 없다(EI1a — `Class<T>`는 full 전용이고 schema 필드를 core 패키지가 읽는 규칙·실행이 없다, host와 함께) | — |
| Optional | 내부 표기 + `?`(내부는 값 종류뿐이다 — 참조는 Optional 내부가 될 수 없다) | 노출할 수 없다 |
| Array, Map, Set | `Array<T>`, `Map<K, V>`, `Set<T>`(원소·키·값이 "타입 인자 안" 열로 표기될 때) | 노출할 수 없다(중첩 컨테이너는 리플렉션에 없다) |
| Name, Guid, AssetId, Digest256, StaticArray, InstancedStruct, Opaque | 노출할 수 없다(Sparks에 대응 타입이 없다 — `Name`·태그 사전은 SE-G2, 에셋 id는 `Soft<T>`로) | — |

  노출 지정자를 쓴 필드의 타입이 표로 표기되지 않거나 대상(enum·struct·클래스)이 노출 타입이 아니거나 `Soft<T>`의 대상이 `asset`이 아니면 오류다(UE UHT의 "type is not supported by blueprint"와 같다 — 조용히 빼지 않는다).
- **B5 이름(SL 10.3절 개정):** 타입 이름은 실효 타입 도구 이름(`Name =` 지정, 없으면 한정하지 않은 C++ 이름 — `rocks::Actor` → `Actor`, enum은 한정하지 않은 C++ 이름)이고 PascalCase여야 한다. 필드 이름은 `ScriptName`, 없으면 도구 이름(`Name =`, 없으면 C++ 이름에서 끝의 `_`를 뗀 것)의 첫 글자를 대문자로 바꾼 것이며, 그 밖의 `_`가 있으면 `ScriptName`이 필요하다(오류). enum case는 열거자 도구 이름(`ToolPrefix`를 뗀 것)이고 대문자로 시작해야 한다. 기반 체인(import 기반 포함 — descriptor schema 4의 `scriptName`·노출 flag로)을 포함한 한 타입의 노출 필드 이름이 겹치면 오류, 한 패키지(`Rocks`)의 노출 타입 이름이 대소문자 무시로 겹치면 오류다(이 모듈과 import한 모듈 사이).
- **B6 언어 이름과의 충돌(SL 10.3절대로 메타 컴파일 오류):** 노출 타입 이름이 언어 소유 이름(SL 3.7절 표 — 내장 타입·prelude·prelude 타입·`Asset` 같은 리터럴 이름)이거나, 노출 필드 이름이 키워드이거나, `object` 종류 타입의 노출 필드 이름이 hook 이름과 겹치면(컴파일러 `HookForMemberName`과 같은 집합 — hook, `On` + hook, Unity 별칭) 오류다. 메타 컴파일러는 이 이름들을 데이터 파일 `Programs/Rocks.MetaCompiler/SparksNames.json`(키워드·언어 소유 이름·hook·Unity 별칭)에서 읽고, C++ 시험이 그 파일을 컴파일러 공개 목록(`LanguageKeywordAt`·`LanguageHooks`·`UnityAliases`·언어 소유 이름 판정)과 집합으로 대조한다(사본이 어긋나지 않게 — SparksTools T13·LC8g 문법 키워드 시험과 같은 방식). reader의 S1120 검사(키워드·타입 이름의 언어 소유 이름)는 손으로 쓴 schema·손상 방어로 그대로 둔다 — 생성 경로에서는 메타 컴파일러가 먼저 막으므로 파일 하나가 통째로 버려지는 일이 생기지 않는다.
- **B7 ID:** 타입 `id`는 TypeId, 필드 `id`는 FieldId(리플렉션 identity — `.rocksids.json`과 같은 32자리 소문자 16진)를 그대로 쓴다. Sparks 쪽 manifest와 같은 ID 공간이다(SE-R8). 필드는 선언한 타입에만 나오므로(B8) 상속이 ID를 겹치게 하지 않는다.
- **B8 출력 형식:** SL 10.2 형식 1, `package: "Rocks"`, `module`은 C++ 모듈 이름. 타입은 스크립트 이름 byte 순, 필드는 선언 순서(자기 필드만 — 상속 필드는 기반 타입에 있다), 기본값인 선택 key는 쓰지 않는다. JSON은 들여쓰기 2칸·LF·끝 LF 하나(C# `System.Text.Json` `WriteIndented` + `"\n"`, encoder는 `UnsafeRelaxedJsonEscaping` — 기본 encoder는 `<`·`>`를 escape해 `Array<Actor>`가 정규형이 아니다. descriptor writer와 같다).
- **B9 시험:**
  - C#(`Rocks.ToolTests` meta 묶음 — Clang으로 픽스처 헤더를 돌린다): 지정자 사례마다 생성 schema golden(타입 셋 종류·`ScriptType` 상속과 `NotScriptType` 끊기·`ScriptExtensible` 상속과 끊기·class·struct `base`와 생략·EditorOnly 파생 제외·타입 대응표 전부·최상위 `?`와 인자 안·미러·이름 변환·`ScriptName`·Hidden case·빈 모듈), 오류 사례마다 RMC 코드(B10)·위치, import 모듈의 노출 기반·필드 이름 겹침(descriptor schema 4 왕복).
  - C++(EngineTests): 시험 실행 파일 위치에서 빌드 출력의 `Metadata/`를 찾아(실행 파일 `<출력>/bin/` → `<출력>/Metadata/` — 없으면 실패, 개정 4) 목록으로 정한 모듈(`CoreTypeBindings`·`World`·`Gameplay` 등 — 도구·픽스처 모듈과 남은 옛 파일이 섞이지 않게)의 schema를 넣어 Sparks 패키지(실제 `Actor`·`Component`·`SceneComponent`·`Pawn` 필드를 읽는 모듈)를 컴파일해 진단 0과 필드 타입이 기대와 같음. `SparksNames.json` ↔ 컴파일러 목록 대조(B6). SparksCompiler 시험: struct `base`(멤버 찾기·순환·기반 종류), schema 타입 인자 안의 `?` 거부(S1120).
  - 시험용 가짜 엔진 schema(`SparksTestHost/Schema`)와 conformance는 그대로다(실제 엔진이 바뀌어도 언어 시험이 흔들리지 않게).
- **B10 오류 코드:** RMC2601–(CompilerDiagnostics 등록부의 메타 컴파일러 대역 RMC1000–4999 안 — 세부 코드 표는 ReflectionMetadata에 26xx "Sparks binding"으로 더한다): 지원하지 않는 필드 타입, 노출하지 않은 대상 타입·`Soft<T>` 대상 종류, 노출 지정자 충돌(`ScriptReadOnly`·`ScriptWritable` 함께, `ReadOnly`와 `ScriptWritable`, 지정자 없는 `ScriptName`, `ScriptType`과 `NotScriptType` 함께), 이름의 `_`·형식, 이름 겹침(필드·타입), 언어 이름 충돌(B6), `EditorOnly`와 노출, `Asset` 노출, 비노출 타입의 노출 필드(클래스에 `ScriptType`이 없음 — "타입에 `ScriptType`을 붙인다"). 메시지·도움말은 영어.

## 3. EI1a에서 지정자를 붙이는 엔진 타입

- **지정자:** `Actor`(`ScriptExtensible` — 가짜 schema처럼 확장 가능), `Component`(`ScriptType` — 확장은 `ScriptableComponent`(EI3)), 그리고 그 필드 타입이 쓰는 enum·struct에 `ScriptType`(`ComponentMobility` 등). `SceneComponent`·`Pawn`은 상속으로 노출된다.
- **상속으로 노출되는 범위:** World·Gameplay의 `Actor`·`Component` 파생 전부(2026-11-26 기준 약 58개 — Light·ReflectionCapture·CameraDirector 등, `Actor` 파생은 확장 가능까지)와 시험 픽스처 모듈의 파생(`SaveActor` 등 — 픽스처 모듈의 schema는 B9 C++ 시험이 읽지 않는다). UE도 `BlueprintType`·`Blueprintable`이 그렇게 퍼진다. 스크립트에 보이면 안 되는 파생은 구현 때 목록을 보고 `NotScriptType`·`NotScriptExtensible`을 붙인다(5절 구현 표에 남긴다).
- **필드:** 지금 리플렉션된 것 중 스크립트가 읽을 만한 것만 `ScriptReadOnly`로 — `Enabled`, `RootComponent`, `Components`(`Array<Component>`), `RelativeTransform`(`Transform`), `Mobility`, `Visible`·`HiddenInGame`, `AttachParent`(`SceneComponent?`). `attachSocket`(socket 이름 문자열)은 빼 둔다(SL 10.3 "등록된 이름은 검증 타입" — 사전이 생긴 뒤). 쓰기(`ScriptWritable`)는 실행 host가 쓰기 경로·검증을 갖춘 EI2 뒤에 정한다 — EI1a에서는 픽스처만 쓴다.
- `ScriptableComponent`·`LevelScript`·`WorldService`·`World`는 타입이 생기는 EI3 몫이다(SE-W4).

## 4. 버린 대안

- **opt-out(SL 10.1 첫 예시 — 리플렉션 타입·필드를 모두 읽기 전용으로 노출, `ScriptHidden`으로 뺌):** 2026-11-26 엔진 빌드에서 리플렉션 타입 220개·필드 1,642개(AssetCooker·ShaderCompiler·NodeGraph 같은 도구 내부 포함)가 비프로그래머 대상 언어의 자동완성에 쏟아지고, 이름 규칙 오류가 노출할 생각이 없던 필드에서 기존 빌드를 깬다. UE도 opt-in이다(사용자 결정).
- **descriptor를 읽는 별도 생성기:** descriptor에 필요한 정보는 거의 있지만 오류를 C++ 원문 위치로 알리려면 메타 컴파일러의 모델이 필요하고, 빌드 action이 하나 더 생긴다. 같은 실행에서 쓴다.
- **런타임 `TypeSchema`/`FieldSchema` flag에 스크립트 노출을 싣기(UE `CPF_BlueprintVisible`):** 지금 그것을 읽을 런타임(host)이 없고 생성 코드가 바뀌면 모든 리플렉션 모듈이 다시 빌드된다. host(EI2)가 FieldId → 쓰기 권한을 알아야 할 때 schema 파일 또는 flag 중에서 정한다.
- **언어 이름 충돌을 schema reader에서만 보기(개정 1):** reader의 S1120은 파일 하나를 통째로 버리므로 이름 하나가 World schema 전체를 지우고 그 사실이 시험에서만 드러난다. SL 10.3도 메타 컴파일 오류로 정했다. 이름 표 사본은 대조 시험으로 맞춘다.
- **struct 상속 필드를 펼쳐 쓰기(SL 10.2를 고치지 않고):** 기반 struct도 노출하면 같은 FieldId가 두 타입에 나와 ID 유일성(SL 10.2)을 깬다.
- **C++ 시험이 `Metadata/`의 모든 schema를 읽기:** 도구·픽스처 모듈과 지운 모듈·다른 타깃의 남은 파일이 섞여 결과가 빌드 이력에 따라 달라진다.

## 5. 한계·후속

- 생성된 schema를 Sparks 도구가 찾는 경로는 지금 `--schema <출력>/Metadata`(CLI·언어 서버 설정 — 비재귀 열거, `.sparkbind.json`만)다. 작업 공간 설정(`SparksWorkspace.json5`)과 설치 SDK에 schema 싣기는 EI 후속(SparksTools 13절) — 설치 SDK는 descriptor를 `Metadata/<M>/` 하위 폴더에 두므로 그대로는 `--schema` 한 폴더에 맞지 않는다.
- 함수·이벤트·계산 속성이 없어 실제 엔진 타입으로 할 수 있는 것은 필드 읽기와 타입 검사뿐이다(EI1b·EI1c).
- 대소문자 무시 타입 이름 겹침은 import 관계가 없는 형제 모듈 사이에서는 메타 컴파일러가 보지 못한다(reader가 같은 철자만 S1120 — 대소문자만 다른 두 이름은 Sparks에서는 다른 이름이라 동작은 맞다).
- `Class<T>` 필드·쓰기 가능 엔진 필드·struct 이름 지정 생성은 host(EI2)와 함께.

## 6. 구현(EI1a — 개정 3)

- **메타 컴파일러:** `Specifiers`(지정자 — `ScriptTypeSpec`, PROPERTY `ScriptReadOnly`·`ScriptWritable`·`ScriptName`, RMC2603·RMC2604는 지정자 해석 때), `SchemaModel`(`ClassModel.Script` 선언값과 실효 `ScriptType`·`ScriptExtensible`), `SparksBinding.cs`(`Resolve` — 실효 노출과 RMC2601·2602·2604–2608 검사, `Write` — schema byte), `CompilerDriver`(검증 뒤 `Resolve`, descriptor와 함께 쓰기·`--check` 대조), `CompilerOptions`(`--binding-schema`). 이름 표는 embedded resource `SparksNames.json`(언어 소유 이름·hook·Unity hook 별칭 — 키워드는 넣지 않았다: 필드 이름은 PascalCase로 강제되고 키워드는 모두 소문자라 겹칠 수 없다).
- **descriptor schema 4:** 타입 flag `ScriptType`·`ScriptExtensible`(class·struct·enum — enum flag 검사를 `Flags` 하나에서 집합으로), 필드 flag `ScriptReadOnly`·`ScriptWritable`, 필드 key `scriptName`. 옛 판(3)은 RMC1000.
- **빌드:** `MetadataModule.BindingSchema`(descriptor 옆), 런너가 stage 경로를 넘기고 생성 확인·게시 목록에 넣는다.
- **컴파일러(SparksCompiler):** schema 표기의 타입 인자 안 `?` 거부(`SchemaInput` — S1120), struct `base` 허용(`BindingSchema`·`BindSetup` 같은 종류 판정), 엔진 struct의 기본값 판정·이름 지정 생성이 기반 체인의 필드를 기반부터 본다(`CheckStructs`·`CheckCalls` — 멤버 찾기는 이미 체인을 걸었다, 대입은 참조 타입만 기반을 보므로 struct 사이 변환이 생기지 않는다). 공개 목록 `LanguageOwnedNameCount`·`LanguageOwnedNameAt`(`LanguageCatalog.h` — 이름 표 대조용).
- **엔진 지정자:** `Actor`(`ScriptExtensible` — 필드 `Components`·`RootComponent`·`Enabled`), `Component`(`ScriptType` — `Enabled`), `SceneComponent`(필드 `RelativeTransform`·`AttachParent`·`AbsoluteLocation`·`AbsoluteRotation`·`AbsoluteScale`·`Mobility`·`Visible`·`HiddenInGame` — `attachSocket`은 뺐다), `ComponentMobility`(`ScriptType`). 상속으로 World·Gameplay의 `Actor`·`Component` 파생이 타입으로 보인다(필드 없음). `NotScriptType`을 붙인 파생은 아직 없다 — 생성된 World schema에 스크립트가 보면 안 되는 타입이 없었다.
- **시험:**
  - C# meta(`MetaTests.SparksBinding`): `Meta.SparksBindingSchemaFromSpecifiers`(타입 여덟·숨는 여섯, 필드 스물셋의 표기 — 정수 열 종류·Map enum 키·`Array<Soft<T>>`·`Optional<enum>`·Map struct 값 포함, 상속·끊기, struct base, asset 종류, Hidden case, descriptor flag·`scriptName`, 형식 — LF·2칸·escape 없음), `…ForModuleWithoutExposedTypes`(빈 types byte), `…MathMirrors`(`Vector3<double>` → `vec3`, 미러 `ScriptType` RMC2607), `…SchemaIsChecked`(`--check` stale RMC4000), 거부 묶음 여덟(RMC2601–RMC2608, 사례 32 — Guid·정적 배열·EditorOnly 클래스 필드 포함). 모듈 사이(`ModuleMetaTests.SparksBinding` — `Meta.SparksBindingAcrossModules`: import 기반의 상속 노출·확장, import enum 대상, 기반 `ScriptName`과 겹침 RMC2605, 노출하지 않은 import 대상 RMC2602). probe ID 명세에 시험 이름을 더했다. 기존 descriptor 판 시험을 4로.
  - C++: `SparksBinding_NamesMatchCompiler`(이름 표 ↔ 컴파일러 목록 집합), `SparksBinding_EngineSchemasCompile`(빌드 출력 `Metadata/`의 `CoreTypeBindings`·`World`·`Gameplay` schema로 실제 필드를 읽는 모듈이 진단 0 — 실행 파일 위치에서 `<출력>/Metadata/`를 찾고 없으면 실패), `SparksTypes_EngineStructBase`(기반 필드 읽기·생성의 기반 필드 요구·기본값 판정의 기반 필드(Sparks struct 필드)·struct 사이 대입 거부·다른 종류 기반과 순환 S1120), reader 시험의 타입 인자 `?` 거부 다섯과 struct `base` 허용.
- **리뷰 반영(개정 4):** 손으로 만든 descriptor 조각이 든 기존 시험(`Meta.ArrayDescriptorTraitsAndVisibilityAreChecked`)에 `scriptName`. `NotScriptType` 아래의 확장 상속(위 B1). hook 이름 검사를 `object` 종류로(asset 필드 `Update`는 받는다). EditorOnly 클래스의 노출 필드는 RMC2607(RMC2608의 안내가 맞지 않는다), 미러 대상 필드는 RMC2601("ScriptType을 붙인다"가 RMC2607로 이어지지 않게). 이름 표 적재를 AST 예외 변환 밖으로(RMC2001로 바뀌지 않게). descriptor reader가 Flags enum의 `ScriptType`, EditorOnly 타입의 노출, `ReadOnly` + `ScriptWritable`을 거부. 주석 자리.
- **한계:** 타입 이름 겹침(RMC2605의 타입 쪽)은 기존 도구 이름 규칙(RMC2203 — 모듈·import 범위 대소문자 무시 유일)이 먼저 막아 닿지 않는 방어 검사다. 필드 이름 겹침 메시지의 두 필드 순서는 FieldId 순이다(결정적). 생성된 schema를 쓰는 Sparks 시험은 빌드 출력 배치(`<출력>/bin/`의 실행 파일)에 기댄다 — 다른 배치로 시험 실행 파일을 옮기면 실패한다(플랫폼 조건 등록은 정책 검사(플랫폼 경계)에 걸려 쓰지 않는다). 엔진 struct는 `constructible: false`라 실제 엔진 struct의 생성 시험은 없다(손으로 쓴 schema로만). `Class<T>` 필드는 노출할 수 없다(5절).

## 7. EI1b 함수(개정 5)

- **B11 노출 지정자:** `ROCKS_FUNCTION(ScriptCallable)`(UE `BlueprintCallable`)이 함수를 schema `functions`에 싣는다. opt-in이고(B1과 같다) 노출 타입(실효 `ScriptType`)의 함수만 된다 — 노출하지 않은 타입의 `ScriptCallable`은 RMC2608, `EditorOnly` 함수의 `ScriptCallable`은 RMC2607(출시 빌드에 없다 — 편집기 버튼 `@editorButton`은 그 단계에서). 함수는 선언한 타입에만 나오고 Sparks는 기반 체인으로 찾는다(필드와 같다, B8). 함께 쓰는 지정자(모두 `ScriptCallable`이 있어야 한다 — 없으면 RMC2603):
  - `ScriptName = "X"`: Sparks 이름을 덮는다(B13).
  - `ScriptEffects = "spawn, io"`: schema `effects`(SL §3.13 — `spawn`·`acquire`·`readiness`·`io`·`wallClock`, 중복·모르는 이름은 RMC2603). 쓰기 순서는 위 목록 순서로 정규화한다.
  - `ScriptOneShot`: schema `oneShot`(handle 없는 일회성 효과 — SL §7.1).
  - `ScriptPerSecond = "velocity, spin"`: 그 매개변수의 `perSecond`(SL 10.3 "이동 API는 초당 값") — 이름이 매개변수가 아니거나 겹치면 RMC2603, 형식이 `float32`·`float64`·`vec2`·`vec3`·`vec4`·`Rotator`가 아니면 RMC2601.
  - `Pure`(리플렉션 지정자 — FunctionReflection FD6)가 schema `pure`다. `Pure`와 `ScriptEffects`·`ScriptOneShot`은 함께 쓸 수 없다(RMC2603 — reader 규칙과 같다).
- **B12 `ScriptCallable`의 계약:** SL 10.2 함수 표의 항목 중 실행 계약 둘은 지정자 하나가 약속한다(따로 적지 않는다 — 노출할 함수마다 같은 문구를 되풀이하게 되고, 빠뜨리면 노출 불가라는 SL 규칙이 지정자 자체와 같아진다): 입력 오류로 Fatal하지 않는다(`NoFatalOnInput` — 잘못된 인자·null 참조는 `Result` 실패나 무시, SL §8.4), Game lane(World 게임 스레드 접근 문맥 — FunctionReflection FD8)에서만 부른다. 파괴 대기(PendingDestroy — World 파괴 지연 동안 Registry는 살아 있다고 본다, FD8) 대상의 동작은 함수마다 맡기지 않고 실행 host(EI2)가 한곳에서 정한다: `Const` 함수는 부르고(읽기 허용), 그 밖의 노출 함수는 부르지 않고 효과 없이 돌아간다(SL 10.2 "쓰기는 효과 없음" — 개정 5 리뷰: 함수마다 guard를 두면 빠뜨린 함수가 파괴 대기 객체를 고친다). 나머지(`ThreadSafe`·`Deterministic`·`MaySafepoint`·최대 작업량·취소·권한)는 실행 host(EI2)·네트워크 단계가 key와 함께 정한다. 자원 정책은 반환 타입이 정한다(유지 자원 타입이면 유지 자원, `ScriptOneShot`이면 일회성 효과, 그 밖은 값).
- **B13 이름:** `ScriptName`, 없으면 실효 도구 이름(FR1 `Name = "…"`, 없으면 C++ 이름 — SL 10.3의 "C++ 이름 그대로"를 도구 이름으로 고친다: 런타임 조회 `FindFunctionByName`·치트·UI 바인딩이 도구 이름을 쓴다). `Result`를 돌려주는 함수의 이름이 `Try` + 대문자로 시작하면 `Try`를 뗀다(SD44 — `TryWorldTransform` → `WorldTransform`, `ScriptName`이 있으면 그것을 그대로 쓴다). 결과는 PascalCase ASCII이고 `_`가 없어야 하며, `Try` + 대문자로 시작하면 안 된다(SL §8 — 노출 API 이름에 `Try` 접두를 쓰지 않는다) — 아니면 RMC2604. 필드·함수는 한 이름 공간이다(SL §3.1): 보이는 사슬(B5 — import 기반 포함)의 노출 필드·함수 이름이 겹치면 RMC2605, 쓰기 가능한 필드 X가 있는 사슬에서 `SetX` 노출도 RMC2605(SL 10.3 — 필드에 대입한다), `object` 종류의 함수 이름이 hook 계열(B6)이면 RMC2606(`Actor::Destroy` → `ScriptName = "RequestDestroy"`). 필드·함수 이름이 예약 이름(SL 부록 A — 언어 소유 이름, 핵심 엔진 타입, 문맥 이름 `World`·`Time` 등, RPC 접두, `Changed`: 컴파일러 `IsReservedName`과 같은 집합)이면 RMC2606이다 — 파생 Sparks class 본문의 이름 해석이 상속 멤버를 prelude·문맥 이름보다 먼저 골라(SL 3.9) `TryParse` → `Parse` 같은 멤버가 prelude `Parse`를 조용히 가린다(개정 5 리뷰, 필드도 같다). 이름 표 `SparksNames.json`의 `reservedNames`(언어 소유 이름 밖의 것)를 대조 시험이 컴파일러 `ReservedNameAt`과 맞춘다. 매개변수 이름은 C++ 이름 그대로이고 lowerCamel ASCII(`_` 없음)여야 하며 키워드가 아니어야 한다(RMC2604·RMC2606 — 바꾸는 지정자는 없다: C++ 매개변수 이름을 고친다, UE도 매개변수 이름이 핀 이름이다). 키워드 표는 `SparksNames.json`에 더하고(`keywords`) 대조 시험이 컴파일러 `LanguageKeywordAt`와 맞춘다.
- **B14 시그니처 표기:** 매개변수·반환 형식은 B4 표의 최상위 열이다(`Array<int32>`·`vec3`·`Mode`·`Actor?`·`Soft<Sound>?`·`string`). `StringView`는 `string`. `ObjectHandle`은 대상이 `rocks::Object`라 노출할 수 없다(RMC2602 — `WeakObjectRef<T>`를 쓴다). 반환: `void`·`Result<void>`(`Result<void>`), 값 `T`, `Result<T>` → `Result<T>`. `Result<T>`의 T가 nullable 표기(객체 참조·`Soft`·`Optional`)면 RMC2601(Sparks `Result<T?>`는 S0401 — 성공 값이 null인 계약은 host와 함께 정한다). schema key: `name`, `id`(FunctionId), `static`(C++ `static`), `parameters`(`name`·`type`·`perSecond`), `returns`(void면 생략), `effects`, `pure`, `oneShot` — 기본값인 key는 쓰지 않는다(B8). `async`·`typeParameters`(`Find<T: Component>` — FR1은 함수 템플릿을 받지 않으므로 `ClassRef` 인자 규칙과 host와 함께)·`overridable`(FR3)은 쓰지 않는다.
- **B15 descriptor schema 6:** 함수 flag에 `ScriptCallable`, 함수 key `scriptName`(노출 함수의 최종 Sparks 이름 — B13 변환을 마친 값, 노출하지 않은 함수는 빈 글자). 다른 모듈이 기반 체인의 노출 함수 이름과 겹침(RMC2605)을 본다. 효과 등 나머지는 그 모듈의 schema에만 있다.
- **B16 출력:** 함수는 선언 순서로 그 타입의 `fields` 뒤에 `functions` 배열로 쓴다(노출 함수가 없으면 key가 없다).
- **B17 엔진 함수 지정(EI1b):** `SceneComponent`의 `SetRelativeLocation`(`Result<void>`, `vec3`), `TryWorldTransform`(`Pure` — `WorldTransform`, `Result<Transform>`), `WorldLocation`(`Pure`, `vec3`), `SetMobility`(enum 인자), `IsVisible`(`Pure`). 기본 인자가 있는 `SetVisibility`·오버로드된 `AttachTo`·`Detach`는 FR1 규칙(기본 인자·오버로드 금지)으로 리플렉션하지 않는다 — 다른 이름 함수가 필요해지면 World 세션과 정한다. `SetRelativeLocation`은 EI1d에서 계산 속성 `RelativeLocation`(SL 10.2 예)이 생기면 같은 값을 쓰는 setter라 노출을 거둔다(SL 10.3 — 초기 단계라 호환을 두지 않는다).
- **B18 시험:** C# meta — 노출 함수의 schema golden(static·매개변수 표기 전부·반환 셋·`TryX`·`ScriptName`·효과 정규화·oneShot·perSecond·pure·선언 순서·노출하지 않은 함수 제외), 거부 사례마다 RMC 코드(지정자 없이 쓴 부속 지정자, Pure와 효과, 모르는·겹친 효과, perSecond 이름·형식, 이름 형식·`Try` 접두·`_`, 매개변수 이름 형식·키워드, 필드와 함수 겹침, 기반 함수와 겹침, hook 이름, EditorOnly, 비노출 타입, `ObjectHandle`, `Result<T?>`, 노출하지 않은 매개변수 타입), 모듈 사이(import 기반의 노출 함수 이름과 겹침 — descriptor schema 6 왕복). C++ — 실제 World schema로 `SetRelativeLocation`·`WorldTransform`·`WorldLocation`·`SetMobility`·`IsVisible`을 부르는 Sparks 모듈이 진단 0(`SparksBinding_EngineSchemasCompile`), 이름 표 대조에 키워드.
- **B19 버린 대안:** `ScriptCallable` 없이 `ROCKS_FUNCTION`을 모두 노출(opt-out) — 필드와 같은 이유(B1·4절)로 버린다. 계약 항목마다 지정자(`NoFatalOnInput` 등) — 노출 함수 전부에 같은 지정자가 붙고 빠뜨림이 곧 노출 불가라 지정자 하나와 다르지 않다. 함수 이름을 C++ 이름 그대로(SL 10.3 원문) — FR1의 도구 이름(`Name =`)과 Sparks 이름이 갈라져 같은 함수를 두 이름으로 찾게 된다. 계산 속성을 EI1b에 — schema 필드에 getter·setter FunctionId 칸이 없어 host가 부를 함수를 모르고, SL 10.2가 CU5 setter 통지와 함께 정하라고 한다(EI1d).

## 8. 구현(EI1b — 개정 5)

- **메타 컴파일러:** `Specifiers.Function`(FUNCTION 지정자 `ScriptCallable`·`ScriptName`·`ScriptEffects`·`ScriptOneShot`·`ScriptPerSecond` — 부속 지정자 단독·`Pure`와 효과·모르는·겹친 효과·빈 목록 항목은 RMC2603, `ScriptName` 형식 RMC2604), `FunctionSpec`의 Sparks 칸, `SparksBinding.Functions.cs`(`CheckFunction` — RMC2601·2602·2604·2606–2608, `FunctionName` — B13 이름, `Returns` — B14 반환 표기, `WriteFunctions` — B16), `SparksBinding.CheckMemberNames`(필드·함수 한 이름 공간 — 함수는 사슬의 타입마다 기반부터, 쓰기 가능 필드의 `SetX`, RMC2605), 필드·함수 예약 이름(RMC2606 — `SparksNames.IsReserved`), `Notation`의 안내 문구를 필드·함수로 나눔. `CheckFunction`이 내는 코드는 RMC2601–RMC2604·RMC2606–RMC2608(perSecond 이름은 RMC2603). 이름 표 `SparksNames.json`에 `keywords`(33개 — 매개변수 이름 검사)·`reservedNames`(24개 — 언어 소유 이름 밖의 예약 이름), 컴파일러 공개 목록 `ReservedNameCount`·`ReservedNameAt`(`LanguageCatalog.h`).

## 9. EI1c 이벤트(개정 6)

- **B20 노출 지정자:** 이벤트 필드(`ROCKS_PROPERTY(Params = …) rocks::Event<…>` — EventReflection ED14·ED18)의 `ScriptAssignable`(UE `BlueprintAssignable`)이 그 이벤트를 schema `events`에 싣는다. Sparks는 `on X.Event(...)`로 연결하고 `await X.Event`로 기다린다(SL 5.2). opt-in이다(B1과 같다). 함께 쓰는 지정자는 `ScriptName = "X"`(Sparks 이름 — B22)뿐이다. 지정자 오류는 필드(B10)와 같은 코드다: `ScriptName` 단독(`ScriptAssignable`·`ScriptReadOnly`·`ScriptWritable` 중 하나도 없음)·`ScriptAssignable`과 `ScriptReadOnly`·`ScriptWritable` 함께·이벤트가 아닌 필드의 `ScriptAssignable`은 RMC2603. 이벤트의 `ScriptReadOnly`·`ScriptWritable`은 RMC2805 그대로다(이벤트는 값이 아니다 — RMC2805는 이벤트에 쓸 수 없는 값 필드 지정자). 구현 문서 ReflectionMetadata의 지정자 표·26xx 코드 표에 `ScriptAssignable`과 이벤트 사례를 더한다.
  - `ScriptBroadcast`(UE `BlueprintCallable` 멀티캐스트 — Sparks가 엔진 이벤트를 `emit`)는 EI1c에 넣지 않는다: Sparks의 엔진 이벤트 `emit`은 S0811이고(SL 5.2 — 멤버 이벤트는 선언한 클래스만 `emit`), 그것을 풀려면 schema key·컴파일러 예외·VM의 native 발행 thunk(발행 frame — `RuntimeEventOps::broadcastFromFrame` 위 안전 래퍼)가 함께 있어야 하며 그 실행은 host(EI2) 몫이다. 필요한 엔진 이벤트가 생기면 EI2와 함께 정한다.
- **B21 노출 규칙:** 노출 타입(실효 `ScriptType` — 아니면 RMC2608)의 `object` 종류에만 둔다. `asset` 종류의 노출 이벤트는 RMC2607이다(노출할 수 없는 멤버 — SL 5.5 "공유 에셋은 이벤트를 노출하지 않는다", schema `events`는 `object`만 — SL 10.2). `EditorOnly` 이벤트와 `EditorOnly` 타입의 노출 이벤트는 RMC2607이다(출시 빌드에 없다). 저장·복제 flag(`Transient`·`SaveGame`·`DuplicateTransient`·`NonTryoutDuplicateTransient`)는 노출과 무관하다 — Sparks 연결은 저장되지 않는다(SL 5.5 — 연결은 session이 다시 만든다).
- **B22 이름:** 필드 규칙(B5)과 같다 — `ScriptName`, 없으면 도구 이름(`Name =`, 없으면 C++ 이름에서 끝의 `_`를 뗀 것)의 첫 글자를 대문자로 바꾼 것이고, 그 밖의 `_`나 형식 오류는 RMC2604다. SL 10.3의 "이벤트 이름은 C++ 이름 그대로"를 이 규칙으로 고친다(같은 절의 "리플렉션 필드(이벤트 필드 포함)" 문장과 맞춘다 — C++ 이벤트 필드는 `changed`처럼 lowerCamel인 경우가 많다). 예약: 언어 소유 이름(RMC2606), `Changed`(SL 5.2 — `X.Changed`는 늘 필드 X의 변경이라 이벤트 이름이 될 수 없다, RMC2606), `object` 종류의 hook 이름(RMC2606 — 필드와 같은 집합). 필드·함수·이벤트는 한 이름 공간이고 보이는 기반 사슬까지 겹칠 수 없다(RMC2605 — SL 10.2 "필드·함수·이벤트 이름은 한 이름 공간").
- **B23 인자:** schema `parameters`는 `Params` 이름(ED18 — lowerCamel·겹침 없음은 이미 RMC2803)과 인자 칸의 B4 최상위 표기다(함수 매개변수와 같다, B14): `const T&`는 T의 표기, `const String&`는 `string`, `WeakObjectRef<T>`는 `T?`, `ObjectHandle`은 RMC2602(대상이 `rocks::Object`라 노출 타입이 아니다 — `WeakObjectRef<T>`를 쓴다), 노출하지 않은 enum·struct는 RMC2601·RMC2602. 인자 이름이 Sparks 키워드면 RMC2606이다. 인자 없는 이벤트는 `parameters`를 쓰지 않는다. handler 인자 대조(정확히 같은 타입·앞에서부터 필요한 만큼 — SL 5.2)는 Sparks 컴파일러가 이 표기로 한다.
- **B24 발행 측:** `publisher`는 쓰지 않는다(기본 `all` — SL 10.2). 서버·소유 클라이언트 발행(`Publisher` 지정자)은 네트워크 단계에서 복제와 함께 정한다(ED11).
- **B25 descriptor schema 8:** 이벤트 필드의 flag에 `ScriptAssignable`(flag 순서 끝), 이벤트 필드 key에 `scriptName`(노출 이벤트의 최종 Sparks 이름, 노출하지 않으면 빈 글자 — 함수 B15와 같다). 다른 모듈이 기반 사슬의 노출 이벤트 이름과 겹침(RMC2605)을 본다. reader는 flag와 이름이 함께 있고 이름이 PascalCase이며 `Changed`가 아니고, 이벤트가 `EditorOnly`가 아니며 타입이 `ScriptType`임을 본다(RMC1000 — 생성기가 만들지 않는 조합). 옛 판(7)은 RMC1000이다.
- **B26 출력:** 이벤트는 선언 순서로 그 타입의 `functions` 뒤에 `events` 배열로 쓴다(자기 이벤트만 — 상속 이벤트는 기반 타입에 있다, B8. 노출 이벤트가 없으면 key가 없다). 항목 key 순서는 `name`·`id`(FieldId)·`parameters`(`name`·`type`).
- **B27 스크립트 단계 안 native 발행의 전달(EventReflection ED11 열린 결정):** `Event::Broadcast`는 스크립트 단계 안팎 모두 C++ 구독자(native 구독·리플렉션 바인딩)를 발행 때 바로 부른다(ED6 — UE `Broadcast`와 같다). Sparks 연결은 native 구독이고 그 thunk는 큐 항목만 기록한다(SL 5.5 — 인자는 깊게 복사, ED11). 그래서 스크립트 단계 안의 native 발행이 큐로 보내는 것은 Sparks handler 몫뿐이고, Sparks handler는 그 단계의 전달 순회에서 실행된다(재진입 없음 — SL 5.4). SL 5.4 "전달 순회"의 "스크립트 단계 안의 native `Broadcast`도 큐 항목으로 기록한다 … handler(C++·Sparks)를 연결 순서대로"를 이 규칙으로 고친다(SD78).
  - 큐 항목: 발행 1회는 (session, 발행자, 이벤트) 항목 하나다(SL 5.4 — 항목을 꺼낼 때 그 시점의 활성 연결을 모두 실행하고, 발행 시점의 연결 목록을 보관하지 않으며, 상한은 항목 수다). 연결마다 항목을 만들지 않는다. 기록 방법(session마다 이벤트별 native 구독 하나를 두고 그 thunk가 기록하거나, 연결 thunk가 같은 발행을 합치는 것)은 host(EI2)가 연결 표와 함께 정한다.
  - 깊이·이월·상한(SL 5.4): 실행 조각 안의 native 발행(조각이 부른 `ScriptCallable` 엔진 함수 안 포함)은 그 조각의 `emit`과 같은 깊이(d+1)다. 전달 순회가 끝난 뒤(활성 전환·파괴 적용 중)나 스크립트 단계 밖의 native 발행은 다음 스크립트 단계로 이월한다(입력 batch — 새 루트, 재검증 규칙). native 발행 항목은 엔진발 항목이라 큐가 넘치면 같은 종류를 합치고 넘친 수를 집계한다(조각의 `BudgetExceeded`가 아니다).
  - 전달 순회의 handler: Sparks `emit`·`Changed` 항목은 C++·Sparks handler를 연결 순서로, native 이벤트 항목은 Sparks handler만 실행한다(native 이벤트의 C++ 구독자는 발행 때 이미 불렸다).
  - 한계: 같은 이벤트의 C++ 구독자와 Sparks handler 사이에는 연결 순서가 없다(C++ 구독자가 먼저). `ScriptCallable` 함수 안의 발행은 C++ 구독자를 동기로 부르므로 그 함수의 `pure`·`effects` 선언은 구독자가 낸 효과를 덮지 않는다(C++ 구독자는 엔진 코드 — 함수 계약 B12의 범위 밖). C++ 구독자가 Sparks `overridable` 함수(가상 함수 재정의)를 부르면 그 실행은 발행 안에서 일어난다(재진입 — 실행 host EI2가 실행 조각 안의 중첩 호출 규칙을 정한다).
  - 버린 대안: (가) 이벤트에 host hook을 두어 스크립트 단계 안의 발행 전체(C++ 구독자 포함)를 큐로 미룸 — `Event`(ObjectRuntime)가 Sparks 실행 상태를 알게 되고, C++ 호출자가 `Broadcast` 직후 구독자의 효과를 기대하는 UE 의미가 스크립트 단계 안에서만 바뀌며, 모든 발행이 단계 판정 비용을 낸다. (나) Sparks handler도 발행 때 바로 실행 — SL 5.4의 재진입 없음·연쇄 상한·이월 규칙이 native 발행 경로에서 깨진다.
- **B28 엔진 이벤트 지정:** 2026-11-27 엔진 모듈(World·Gameplay 등)에는 리플렉션 이벤트 필드가 없다. UI 브랜치(feature/ui-framework)의 위젯 이벤트는 병합 뒤 UI 세션이 `ScriptAssignable`을 정한다(UI 노출은 WidgetAsset schema — SL 5.2 `Widget.이름.이벤트` — 와 함께).
