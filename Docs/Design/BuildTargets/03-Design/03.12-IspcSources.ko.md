### 3.12 ISPC 원본(2026-11-27 — 텍스처 압축 TC3 요구)

ISPC(Intel Implicit SPMD Program Compiler) 원본(`.ispc`)을 모듈의 일부로 컴파일한다. 첫 소비자는 ThirdParty `IspcTextureCompressor`(BC6H·BC7 인코더 — [AssetSystem 12.17.6절](../../AssetSystem/12-Textures/12.17-CompressionStage.ko.md))다. 사용자 결정(2026-11-27)으로 출력 byte가 호스트 CPU와 무관하도록 결정적으로 빌드한다.

**지금 빌드 시스템에서 걸리는 점**(2026-11-27 조사):
- 엔진 모듈은 `*.cpp`·`*.mm`만 모은다. ThirdParty manifest는 `.c`·`.cpp`·`.cc`만 받는다(`ThirdPartyManifest.cs` 271·478–486). `ActionGraph.LanguageOf`는 그 밖을 C++로 본다.
- action 출력 헤더를 다른 compile의 include 디렉터리로 쓰는 선례가 없다. include 디렉터리는 계획 때 있어야 하고(`ActionGraph.cs` 279–285), `InputSnapshot`이 빌드 앞뒤로 헤더 목록을 비교한다(`NativeBuildEngine.cs` 227–238).
- action key에는 도구 경로만 들어가고 도구 내용은 들어가지 않는다(`ActionGraph.cs` 27–60). 툴체인 지문(`ToolchainFingerprint`)과 도구 빌드 ID(`BuildInfo`)는 Compile·Archive·Link만 본다.

| BD48 | **생성 헤더**: 위치는 `<out>/Ispc/<모듈>/`이다. 계획 단계에서 디렉터리를 만들어 두고 그 모듈 Private include 디렉터리에 더한다. 그 디렉터리는 produced 출력이므로 `InputSnapshot` 비교와 `BuildInputs.Listing`에서 뺀다. `.isph`(ISPC include)를 헤더 확장자 목록(`IncrementalStore.cs` 194 `HeaderExtensions`)에 더해 새로 생긴 같은 이름 `.isph`를 놓치지 않는다. 같은 모듈의 C++ compile은 모든 Ispc action에 의존하고 헤더를 DeclaredInputs로 받는다(PCH 소비 선례 — `Pch.cs` 248–299). 헤더는 Private이다(다른 모듈은 모듈의 공개 C++ API만 본다). |
| BD49 | **증분 key**: action Identity에 ISPC 버전 문자열·실행 파일 sha256·타깃·arch·인자를 넣는다. 실행 파일 해시는 도구를 찾을 때 한 번만 잰다(툴체인 key처럼 — DeclaredInputs로 두면 snapshot 앞뒤로 매번 해시한다). include한 `.isph`는 depfile(`-MMM`)로 2단 key에 들어간다. |

**구현 세부**(BS12 구현 2026-11-27 — 실측으로 정한 것):
- **탐색 위치**: `ROCKS_ISPC`(툴체인 환경에 있으면 그것, 없으면 프로세스 환경) → `%LOCALAPPDATA%\Rocks\toolchains\ispc-<버전>`(macOS `~/Library/Application Support/Rocks/toolchains`, Setup 기본) → 저장소 `out/toolchains/ispc-<버전>`(`InstallIspc.ps1` 기본)이다. 빌드 엔진이 빌드 대상에서 닿는 모듈(`LinkClosure.Reachable`)에 ISPC 원본이 있을 때만 찾는다(`IspcTools.DiscoverAsync`). 시험은 `NativeBuildRequest.Ispc`로 직접 준다.
- **stage 실행**(`NativeAction.StageWorkingDirectory`): 도구를 action 임시 디렉터리에서 돌리고 `{OUTPUTn}`·`{DEPFILE}`을 그 안의 파일 이름으로 펼친다. Windows에서는 절대 경로 인자(원본·`-I` 디렉터리)도 stage 기준 상대 경로로 바꿔 넘긴다(POSIX는 절대 경로 그대로 — 커널이 `..`를 실제 디렉터리로 풀어 출력이 symlink면 엉뚱한 곳을 가리킨다). **Windows ISPC 1.32.0은 명령줄의 비 ASCII 절대 경로 파일을 열지 못한다**(실측 — `File "...한글..." does not exist`, 같은 파일의 상대 경로는 연다). 상대 경로에는 공통 조상(사용자 폴더 등)이 빠지므로 저장소 위 폴더 이름이 한글이어도 된다. 상대 경로 자체에 비 ASCII가 남으면(저장소 안 한글 폴더, 출력이 다른 비 ASCII 폴더) 계획 단계에서 `ArgumentException`으로 알린다. action key와 도구 빌드 ID는 계획의 절대 경로 인자를 그대로 쓴다(실행 철자는 출력 위치만의 함수다).
- **의존 기록**: `-MMM` 파일은 원본 자신을 포함해 한 줄에 경로 하나이고 상대 경로는 stage 기준이다(`IspcTools.ParseDependencies` — `DependencyFileFormat.Lines`). 생성 헤더 주석은 `// k_ispc.h`처럼 `-h` 이름만 적는다(실측).
- **산출물 선언 입력**: C++ compile의 선언 입력인 생성 헤더는 BuildInfo Prepare(action 실행 전) 때 없을 수 있다. 도구 빌드 ID 입력은 다른 action의 산출물인 선언 입력을 존재 검사 전에 건너뛴다(그 내용은 `.ispc` 원본·`.isph` 입력이 대신한다).
- **낡은 생성 헤더**: 성공한 빌드가 `<out>/Ispc/<모듈>/`에서 이번 계획이 만들지 않은 파일을 지운다(object 디렉터리 정리와 같은 단계). 남으면 이름을 바꾼 원본의 옛 헤더가 증분 빌드에서만 include되어 깨끗한 빌드와 결과가 갈린다.
- **ISPC만 있는 모듈**: 서드파티 정적 라이브러리만 된다. 엔진 모듈은 C++ 원본이 함께 있어야 한다(Modular 공유 라이브러리의 API 매크로·export 판정이 C++ 원본 기준이다 — 입력 검증이 거부).
- **계획만**(`--plan-only`): 빌드 대상에 ISPC 원본이 있으면 계획만 세울 때도 ISPC가 있어야 한다(Ispc action 인자가 도구를 담는다). IDE 계획은 ISPC 없이 된다.
- **신원 정의**: ThirdParty 모듈 규칙이 `ispcUnits`가 있으면 `ROCKS_ISPC_IDENTITY="ispc <버전> <고정 인자>"`를 소비자 정의(`ConsumerDefines`)로 낸다(`IspcTools.IdentityDefine`). manifest `ispcUnits`는 code 라이브러리만, 비지 않은 `.ispc` 목록, 같은 파일 이름 금지, 고정 원본 파일(정책 검사)이다.

**시험**(Rocks.Build.Tests `IspcTests`, Rocks.ToolTests ThirdParty manifest 시험):
- 계획 모양: 인자와 타깃(X64·Arm64), `--opt=fast-math`·다중 타깃 거부, object가 archive에 들어감, C++ compile이 Ispc action 뒤.
- 증분: `.ispc`·`.isph`(depfile)·ISPC 실행 파일·버전이 바뀌면 다시 실행되고, 그대로면 cached다. 생성 헤더가 `InputSnapshot` 오류를 내지 않는다.
- 도구: 없음·버전 다름의 진단, ISPC 원본이 없는 빌드는 ISPC를 찾지 않음.
- manifest: `ispcUnits` 필드·확장자 검사·Android Unsupported.
- 생성 헤더 결정성: 깨끗한 빌드 두 번의 `_ispc.h` byte가 같다. 같은 basename 원본 둘은 거부한다.
- 빌드 ID·신원: 원본 내용·인자가 바뀌면 도구 빌드 ID가 바뀌고, 호스트 경로가 달라도 같다. 생성 정의 `ROCKS_ISPC_IDENTITY`가 버전·타깃을 담는다. `ToolchainFingerprint`는 Ispc 유무와 무관하다.

**UE와 다른 점**: UE UBT도 `.ispc`를 컴파일한다(모듈 규칙의 ISPC 원본, 생성 헤더는 Intermediate). 그러나 UE 기본은 플랫폼의 여러 타깃과 dispatch다. Rocks는 결정성을 위해 아키텍처당 타깃 하나이고 fast-math·FMA를 끈다(SIMD 폭은 x64 4 — UE avx2보다 느릴 수 있다, TC5에서 잰다).

**한계**: Linux 호스트 패키지는 BS6(Linux 보류) 때 더한다. Windows Arm64 호스트 패키지는 없다(그 호스트는 지금 빌드 호스트가 아니다). macOS의 ISPC object 최소 OS(`LC_BUILD_VERSION` minos)가 C++ 쪽 `-mmacosx-version-min`과 맞는지는 Mac 확인 때 `otool -l`로 본다(BD47의 배포 대상 인자 — ISPC 1.32.0에 맞출 인자가 없으면 링크 경고 여부를 적는다). 도구 빌드 ID 입력은 ISPC 원본 디렉터리의 헤더 이름 목록만 센다 — 그 밖의 `.isph`(`#include "../common/x.isph"`)는 action key(의존 기록)만 잡는다(C++ include 디렉터리 밖 헤더와 같은 규칙). x64와 Arm64 사이의 출력 byte 동일은 IEEE 연산만 쓰는 커널에 한해 기대하는 성질이다. 커널마다 확인한다(12.17.6절 결정성 시험).
