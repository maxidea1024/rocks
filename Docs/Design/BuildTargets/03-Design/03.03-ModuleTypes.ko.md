### 3.3 모듈 type

type 값은 `{ Runtime, Developer, Editor, ServerOnly, ClientOnly }`다(BD4). 들어갈 수 있는 타깃은 3.1절 표다.

| type | UE 5.8 대응 | 비고 |
|---|---|---|
| Runtime | `RuntimeAndProgram` | Rocks는 Program에도 넣는다(UE `Runtime`은 Program에서 빠진다) |
| Developer | `DeveloperTool` | 지금과 같다. UE `Developer`(Editor·Program 전용)는 두지 않는다 |
| Editor | `Editor` + Program의 `CompileWithEditor` | UE `EditorAndProgram`은 모든 Program에 들어가지만 Rocks는 `CompileWithEditor` Program에만 들어간다 |
| ServerOnly | `ServerOnly` | Client에서 뺀다. Program에는 들어간다(서버 시험) |
| ClientOnly | `ClientOnly` | Server에서 뺀다. Program에는 들어간다 |

**type을 정하는 곳**:
- 게임·플러그인 모듈: 기술자 `modules[].type`(지금과 같다). 이번 타깃에 들어갈 수 없는 모듈은 빌드에서 뺀다(지금 게임 빌드 연동 4단계).
- 엔진 모듈(Core·Engine): 규칙 기반 클래스 `SourceModuleRules`에 `ModuleType` 속성을 더한다. 기본값은 `Group` 폴더에서 온다(`Runtime`→Runtime, `Developer`→Developer, `Editor`→Editor). `ServerOnly`·`ClientOnly`는 규칙이 명시한다. 엔진 모듈은 **걸러 내지 않고 검사만 한다.** 타깃 도달 집합에 들어갈 수 없는 type의 모듈이 있으면 빌드 오류다. UE도 엔진 모듈은 기술자 type으로 걸러 내지 않고 타깃 참조로 정해진다. Rocks는 거기에 검사를 더한다.
- 설치 SDK manifest의 `SdkModule`에 type을 싣는다. 게임 빌드가 같은 검사를 한다.

**type 사이 의존 규칙(BD25)**: 모듈 A가 모듈 B에 의존하려면, A가 들어갈 수 있는 (타깃 종류, 구성) 집합이 B의 집합에 포함되어야 한다. 그렇지 않으면 A를 넣는 타깃에서 B가 빠져 빌드가 깨진다(예: Runtime 모듈이 ClientOnly 모듈에 의존하면 모든 Server 타깃이 실패한다). 3.1절 표에서 나오는 결과는 다음과 같다. 위반은 타깃과 무관하게 규칙 로드 때 오류다. 의존에는 실행 중 적재 관계(`DynamicModules` — [모듈 로더](../../ModuleLoader.ko.md) 3.8절)도 든다. Monolithic이 그 모듈을 링크하기 때문이다(UE도 동적 적재 모듈을 같은 검사에 넣는다).

| 모듈 type | 의존할 수 있는 type |
|---|---|
| Runtime | Runtime |
| Developer | Runtime·Developer |
| ClientOnly | Runtime·ClientOnly |
| ServerOnly | Runtime·ServerOnly |
| Editor | 모든 type |

**Release 배제 정책(BD20)**: `ReleaseExclusion`의 검사 대상을 `Type == Game`에서 Game·Client·Server로 넓힌다. UE도 Editor·Program이 아닌 모든 타깃의 Shipping을 같은 대상 범위로 본다(`UEBuildTarget.cs:3918` `CheckForEULAViolation` — 검사 내용은 NonRedist 라이선스로 다르다). 평가 플랫폼은 타깃 종류별이다: Game·Client는 Windows x64·macOS arm64·Android arm64, Server는 Windows x64·macOS arm64·Linux x64(BS6 뒤) Release 규칙이다. 그리고 `<계층>/Source/Editor/` 모듈(type Editor)이 Game·Client·Server 타깃에 닿는 것은 구성과 무관하게 정책 오류로 막는다. [셰이더 시스템](../../ShaderSystem/09-ToolLoadingReleaseExclusion.ko.md) 9절의 Release 배제 대상("Type == Game")도 Game·Client·Server로 읽는다.

**BS2b 구현 세부(개정 31).**
- `Descriptors.ModuleType`에 `ServerOnly`·`ClientOnly`를 더한다. 기술자 `modules[].type`은 UE와 같은 철자(`"ServerOnly"`·`"ClientOnly"`)를 받는다. 엔진 모듈은 `SourceModuleRules.ModuleType`(지금 있는 칸, 기본은 Group 폴더)을 재정의해 정한다. 정책 `module-type-group`은 `Runtime` 폴더의 모듈에 Runtime·ServerOnly·ClientOnly를 허용한다.
- 판정은 Rocks.Build `ModuleTypeRules` 한 곳이다.
  - `Allows(타깃 종류, 구성, type)`는 3.1절 표다(Developer는 Game·Client·Server의 Release에서 빠지고, Editor는 Editor 타깃과 `CompileWithEditor` Program에만 든다).
  - `MayDependOn(A, B)`는 위 표를 손으로 적지 않고 `Allows`에서 계산한다: 모든 (타깃 종류, Program 속성, 구성)에서 A가 들어가면 B도 들어가야 한다. 결과가 위 의존 표와 같은지 시험이 대조한다.
  - `ExclusionReason`은 빠지는 이유 문장이다(기술자 모듈 거르기와 아래 검사가 같은 문장을 쓴다).
- **규칙 로드 때 의존 검사(BD25)**: `ModuleTypeRules.ValidateDependencies`가 실행 파일이 아닌 모든 모듈의 두 의존 목록과 `DynamicModules`를 `MayDependOn`으로 검사한다. 엔진은 `RuleLoader.LoadAll`이 모든 규칙 모듈로 부른다. 게임은 계획 단계가 거르기 전 모든 프로젝트 모듈(기술자 type — 게임 모듈 규칙은 type 칸을 쓰지 않으므로 `DescriptorModuleSet.WithDescriptorTypes`)과 SDK 모듈(manifest type)로 부른다. 실행 파일은 한 타깃에만 들어가므로 이 검사 대신 아래 도달 검사를 받는다(시험 실행 파일이 Developer 시험 지원 모듈에 의존하는 것은 정상이다). 서드파티 모듈은 Runtime이다.
- **빌드 입력의 도달 검사**: `ModuleTypeRules.ValidateReach`다. 계획 단계(엔진·게임 Layout)가 메타 생성 전에 부르고(빠질 모듈의 메타·컴파일 오류보다 이유를 먼저 낸다), `InputValidation.Validate`가 빌드 대상(`Targets`, 비면 모든 모듈)에서 링크 의존·플러그인 모듈·동적 모듈로 닿는 모듈마다 `Allows(request.Target, request.Configuration, type)`를 검사한다. 엔진 저장소 빌드와 SDK 게임 빌드가 같은 검사를 받는다. 기술자 모듈은 먼저 걸러지므로(`DescriptorModuleSet`) 이 검사에 걸리는 것은 엔진 모듈과 SDK 모듈이다. UE는 엔진 모듈을 type으로 검사하지 않는다(타깃 빌드가 링크에서 깨진다). Rocks는 이유를 말하는 오류로 앞당긴다.
- **기술자 모듈 거르기**: `Apply`가 기술자의 type을 모듈 입력(`NativeModuleInput.Type`)에 싣는다. `DescriptorModuleSet.Resolve`가 타깃 종류 대신 `TargetKind`를 받아 `CompileWithEditor` Program에 Editor 모듈을 넣는다(지금까지는 Editor 타깃이 없어 Editor 모듈을 늘 뺐다). `enabledByDefault` 플러그인은 Program이 아닌 모든 타깃(Game·Client·Server·Editor)에 켠다(BD34는 Game·Program만 있을 때 쓰였다 — UE도 Program만 기본 플러그인을 받지 않는다).
- **SDK manifest**: `SdkModule`에 `Type`(type 이름)을 싣고 manifest 버전을 올린다. 게임 빌드는 그 값을 `NativeModuleInput.Type`으로 넘겨 위 도달 검사를 받는다. 이름이 없거나 모르는 값이면 SDK 검증 오류다.
- **Release 배제(BD20)**: `ReleaseExclusion`이 Game·Client·Server 타깃을 검사한다. 평가 플랫폼은 그 타깃 종류가 허용하는 플랫폼(3.1절 표, `RuleLoader.ValidateTargetKind`와 같은 표)만이다. 새 규칙 `release-editor-module`은 도달 집합의 type Editor 모듈을 거부한다. Release가 아닌 구성의 Editor 모듈 도달은 위 빌드 입력 검사가 막는다.
- 오디오 모듈의 ClientOnly 표시(AD24)는 오디오 세션이 BS2b 뒤에 한다. 그래픽 backend의 ClientOnly 표시는 BS7이다.
- 시험: `Allows` 표(다섯 종류 × Program 속성 × 구성), `MayDependOn` 대 의존 표, 규칙 로드 의존 거부(의존·동적 모듈, 실행 파일 예외), 도달 검사(Developer in Release Game, ServerOnly in Client, ClientOnly in Server, Editor in Program), 기술자 거르기의 새 이유, SDK manifest type 왕복과 누락 거부, Release 배제의 Client·Server와 `release-editor-module`, `module-type-group`의 ServerOnly·ClientOnly 허용.

채택하지 않은 UE type은 9.1절이다.
