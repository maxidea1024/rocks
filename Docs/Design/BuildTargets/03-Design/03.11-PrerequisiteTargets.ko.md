### 3.11 선행 타깃

Sandbox(Game 타깃)의 Development 셰이더 공급자는 ShaderCompileWorker 실행 파일을 띄운다([셰이더 시스템](../../ShaderSystem/16-LaterStages.ko.md) 16.1절 SSD19). 지금까지는 self-test 전에 `RocksTarget=ShaderCompileWorker`를 손으로 따로 빌드해야 했다. 동반 타깃(3.1절 `CompanionTargets`)은 쓸 수 없다. 이유는 셋이다.
1. 동반 타깃은 Program 주 타깃만 둔다(3.1절 개정 32 — 동반 모듈은 주 타깃의 종류·구성으로 type 검사를 받으므로 Release Game은 동반 Program의 Developer 모듈을 거부한다).
2. 동반 타깃은 주 타깃과 한 빌드로 컴파일되므로 매크로 조합(3.2절)이 같아야 한다. 워커는 `WithEditorData`(`ROCKS_WITH_EDITOR_DATA=1`)이고 Game은 0이다.
3. 동반 타깃은 빌드 정보 TU를 공유하므로 동반 실행 파일의 `CurrentTargetType()`이 주 타깃 종류(Game)가 된다.

그래서 **주 타깃 전에 다른 타깃을 그 타깃 자기 규칙으로 따로 빌드하는** 속성을 둔다(BD44). 시험 동반 타깃 `TestPrograms`(3.8절 BS8d6 — `test`가 하니스 전에 따로 빌드한다)를 `build`로 넓힌 모양이다.

**속성.** `TargetRules.PrerequisiteTargets`(기본 빈 목록)는 `PrerequisiteTarget` 목록이다.
- `PrerequisiteTarget(string Name)`: 선행 타깃 이름이다(대소문자까지 구별한다).
- 조건 칸 `Platforms`(`NativePlatform` 목록)와 `Configurations`(`NativeConfiguration` 목록)를 둔다. null은 조건이 없다는 뜻이다. 구성 값은 빌드 구성 그대로 쓴다. 플러그인 조건(3.6절)과 달리 Asan·Coverage를 Debug로 묶지 않는다. 선행 타깃은 같은 구성으로 빌드되므로 구성마다 따로 적는다.
- Sandbox는 `[new("ShaderCompileWorker") { Platforms = [Windows, MacOS], Configurations = [Debug, Development] }]`를 적는다. Release Sandbox에는 공급자가 없다. Android Sandbox는 APK라 워커 프로세스를 띄우지 않는다.

**빌드 동작.**
1. `build`·`test`는 규칙 로드와 주 타깃 계획(플러그인 적용·type 도달 검사) 뒤, 메타 생성 전에 선행 타깃을 빌드한다. 하나라도 실패하면 주 타깃을 빌드하지 않고 FAIL로 끝낸다. 주 타깃의 `build-evidence`에는 단계 `prerequisite`로 남는다(명령·종료 코드·시간).
2. 선행 타깃마다 `build --target <이름>`을 같은 프로세스 안에서 부른다. 이 빌드는 주 타깃 명령의 옵션(구성·도구 체인·플랫폼·빌드 방식·jobs·규칙 어셈블리)을 그대로 받는다. 규칙은 선행 타깃 자기 것이다. 종류·매크로 조합·링크 방식·플러그인·동반 타깃·빌드 정보 TU(`CurrentTargetType()`)가 모두 선행 타깃의 값이다.
3. 순서는 깊이 우선 후위다. 선행 타깃의 선행 타깃을 먼저 빌드하고, 같은 타깃은 한 번만 빌드한다. 주 빌드가 평탄한 목록을 만들고 안쪽 빌드는 선행 타깃을 다시 펼치지 않는다. UE BuildMode가 makefile의 `PreBuildTargets`를 descriptor 목록에 더하고 중복을 빼는 것과 같다.
4. 출력은 선행 타깃 자기 기본 출력 디렉터리(`out/dotnet-<플랫폼>-<타깃 소문자>-<구성>`)다. 주 명령에 `--output <경로>`가 있으면 `<경로>-<타깃 소문자>` 형제 디렉터리다. 이 규칙은 `TestPrograms`와 같은 함수로 계산한다. Sandbox는 기본 출력 이름 규칙으로 형제 디렉터리 `out/<도구>-<플랫폼>-shadercompileworker-<구성>/bin`에서 워커를 찾는다(`Programs/Sandbox/Private/SandboxShaders.cpp` `FindWorker`).
5. 선행 타깃을 빌드하지 않는 문맥은 다음과 같다.
   - 조건 칸에 맞지 않는 문맥.
   - 주 타깃이 Developer 모듈을 빼는 구성. Game·Client·Server의 Release가 여기에 든다(3.3절 `ModuleTypeRules.Allows(종류, 구성, Developer)`). 조건 없는 선행 타깃도 이 구성에서는 빌드하지 않는다. 출시 빌드는 개발 도구를 만들지 않는다.
   - 그 구성을 `Configurations`에 명시하면 규칙 로드 오류다(명시한 의도를 조용히 버리지 않는다).
6. `--plan-only on`, `--files`(파일 하나 컴파일), unity-profile 실행은 선행 타깃을 빌드하지 않는다. 이 실행들은 주 타깃의 계획·일부 컴파일만 다루기 때문이다. `sdk` export와 설치 SDK `game`은 선행 타깃을 가진 타깃을 거부한다. 게임 규칙의 선행 타깃은 SDK가 싣는 프로그램 타깃이 있어야 하므로 후속이다.

**규칙 로드 검사**(`RuleLoader.LoadAll` — 모든 타깃, 모두 `ArgumentException`):
- 빈 이름, 없는 타깃, 자기 자신, 같은 목록 안 중복.
- 선행 타깃이 Program이 아님. Program은 구성과 무관하게 Developer 모듈을 받으므로, 선행 타깃 빌드가 주 타깃의 구성에 따라 깨지지 않는다.
- 빈 조건 목록, 조건 값 중복, 정의되지 않은 enum 값.
- 주 타깃이 Developer 모듈을 빼는 구성을 `Configurations`에 명시함(5항).
- 순환(선행 타깃 그래프). 오류 문구에 경로를 적는다(예: `A -> B -> A`).
- 동반 타깃(3.1절)이 선행 타깃을 가짐. 동반 타깃은 주 타깃 빌드에 모듈만 합쳐지므로 선행 타깃이 조용히 빠진다.

**IDE.** Visual Studio NMake Build는 `IdeBuild` → CLI `build`를 부르므로 선행 타깃도 함께 빌드된다. 솔루션의 프로젝트 의존(ProjectDependencies)은 두지 않는다. 순서는 CLI가 정하고, 솔루션 빌드의 동시 실행은 IDE 빌드 잠금이 순차로 만든다([프로젝트 파일](../../ProjectFiles.ko.md) 7.2절). Clean·Rebuild는 주 타깃 출력만 비운다(7.3절). 선행 타깃은 자기 프로젝트가 따로 있고, Sandbox Rebuild 때마다 워커까지 처음부터 컴파일하지 않게 하려는 것이다. UE CleanMode는 `PreBuildTargets`도 지운다(7절).

**UE 근거.**
- `TargetRules.PreBuildTargets`(`UBT/Configuration/Rules/TargetRules.cs:2885-2888` — "targets which should be built before this target is built")가 일반 구조다.
- `Modes/BuildMode.cs:1473-1482`는 makefile의 `PreBuildTargets`를 빌드할 descriptor 목록에 더한다. 건너뛰기 옵션은 `-SkipPreBuildTargets`(75-76행)다.
- `Modes/CleanMode.cs:112-121`은 Clean 때도 같은 목록을 더한다.
- 에디터의 워커 의존은 VS 프로젝트 생성기의 `bEditorDependsOnShaderCompileWorker`(`ProjectFiles/VisualStudio/VCProject.cs:2204, 2254-2257`, 설정 `VCProjectFileGenerator.cs:93-96`)다. 생성기가 Editor 타깃 빌드 명령에 `ShaderCompileWorker Win64 Development`를 덧붙인다. 워커는 자기 타깃 규칙으로 따로 빌드된다.
- Rocks는 생성기 특례 대신 타깃 규칙(UE `PreBuildTargets` 구조)으로 둔다. 그래서 CLI·IDE·`Rocks.proj`가 같은 경로를 쓴다. 구성은 주 타깃과 같다(UE 생성기는 Development로 고정한다).

**버린 안.**
- Game 타깃에 동반 허용: 이유 1은 풀 수 있지만 이유 2(매크로 조합)·3(빌드 정보 TU 공유)이 남는다.
- 워커를 Game 매크로로 하나 더 두기(예: Game 조합 워커 타깃): 워커 타깃이 두 벌이 되고 실행 파일 이름이 겹친다. 동반 방식이라 `CurrentTargetType()`이 여전히 Game이다.
- `TestPrograms` 재사용: `test` 전용이고, 실행 파일 경로를 하니스에 넘기는 뜻과 실행 파일 하나 제약을 가진다.
- `Rocks.proj`·스크립트에서 두 번 부르기: CLI·IDE·MSBuild 경로마다 따로 적어야 하고 규칙에 의존이 드러나지 않는다.

**한계.**
- 선행 타깃은 따로 빌드하므로 Core 등 공유 모듈을 타깃마다 다시 컴파일한다(출력 디렉터리가 타깃마다다). Sandbox 첫 빌드가 워커 폐포만큼 길어진다.
- `--output`을 준 Sandbox 빌드는 워커를 형제 출력(`<경로>-shadercompileworker`)에 두지만, Sandbox의 워커 탐색은 기본 출력 이름 규칙만 안다. 그런 빌드는 워커를 실행 파일 옆에 두어야 한다.
- 선행 타깃의 Clean은 따로 한다.

**단계**: BS11(구현 세부는 이 절이 전부다). 시험은 `Rocks.Build.Tests`의 `PrerequisiteTargetTests`다. 양성으로 선행 타깃 규칙과 매크로 보존·후위 순서와 중복 제거·조건·Program 주 타깃의 Release를 확인하고, 음성으로 없는 이름·자기 자신·중복·순환·Program 아님·빈 조건·Release 명시·출시 타깃 Release 건너뜀·선행 타깃을 가진 동반 타깃을 확인한다. 실제 확인은 `RocksTarget=Sandbox` Debug 빌드가 워커를 먼저 빌드하고 `Sandbox --self-test`의 그리기 시험이 PASS하는 것이다.
