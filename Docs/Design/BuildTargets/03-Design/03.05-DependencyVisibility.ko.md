### 3.5 모듈 의존 공개 범위

`NativeModuleInput.Dependencies`를 `PublicDependencies`·`PrivateDependencies` 두 목록으로 바꾼다(BD7). 하위 호환 이름은 두지 않는다. 규칙 기반 클래스의 `RequiredModules`도 같은 두 속성으로 바꾼다.

**컴파일 환경**(UE `UEBuildModule.cs:607-647`과 같은 규칙):
- 모듈 M의 **공개 환경** = M의 public include·public define + M의 각 공개 의존 D의 공개 환경(재귀).
- 모듈 M의 **컴파일 환경** = M의 공개 환경 + M의 private include·private define + M의 각 비공개 의존 D의 공개 환경.
- 비공개 의존의 공개 의존은 M에게 보이지만, M의 소비자에게는 보이지 않는다.
- `AdditionalInputs`(compile key 입력)도 같은 규칙으로 전파한다.

**링크**: 정적 링크이므로 실행 파일은 두 목록을 모두 따라간 도달 집합 전체를 링크한다. `ActionGraph`의 `Closures`(BuildInfo 도구 빌드 ID 입력)와 순환 검사(`ActionGraph.cs:80`)도 두 목록을 모두 따라간다. UE도 비공개 의존을 링크한다(`UEBuildModule.cs:999-1020` `SetupPrivateLinkEnvironment`).

**리플렉션 메타데이터(BD8)**: 메타 컴파일러가 모듈 M을 처리할 때 쓰는 모듈 범위는 M의 컴파일 환경에 보이는 모듈과 같다. 바꿀 곳은 다음과 같다.
- import 범위(`MetadataRunner.cs:46, 262`)
- AST include 순서(`MetadataLayout.cs:156-183`)
- 생성 헤더 해석 `DependsOn`(`MetadataLayout.cs:395-406` — "도달"이 아니라 "보임")
- 전파 define(`MetadataRunner.cs:131`)

공개 헤더의 리플렉션 타입이 다른 모듈의 리플렉션 타입을 기반·필드로 쓰면, 그 모듈은 공개 의존이어야 한다. 이 조건은 공개 헤더 검사가 함께 잡는다.

**공개 헤더 검사(BD9)**: `CheckPublicHeaders`는 모듈마다 **그 모듈의 공개 환경만으로** 각 공개 헤더를 컴파일한다.

**include-only 의존은 두지 않는다**(BD10, UE `PublicIncludePathModuleNames`·`PrivateIncludePathModuleNames`). UE에서는 순환 의존을 끊는 수단이다(`UEBuildModule.cs:1382` 안내 문구). Rocks는 계층 규칙으로 순환을 금지하고, header-only 모듈은 일반 의존으로 쓴다.

**정책 검사(BD11)**:
- 모듈의 소스·헤더가 include한 Rocks 헤더는 컴파일 환경에 보이는 모듈의 것이어야 한다. 판정은 컴파일러가 낸 의존 기록(depfile)의 실제 경로로 소유 모듈을 찾아서 한다. include 디렉터리 이름만으로는 같은 상대 경로가 여러 모듈에서 보일 수 있기 때문이다. depfile 파서는 [유니티 빌드·PCH](../../UnityBuildPch.ko.md) UB0의 것을 쓴다. 그래서 BS1은 UB0의 depfile 파서 부분 뒤다(유니티·PCH 본체와는 무관하다).
- 한 모듈을 두 목록에 같이 적으면 오류다.
- 공개 헤더가 쓰지 않는 공개 의존은 진단한다. 판정은 공개 헤더 검사의 depfile로 한다.

**서드파티 모듈(BD21)**: private 의존이 생기면 UE 방식으로 바꾼다. 서드파티 모듈은 자기 include·define을 public으로 내고, 소비 모듈은 `PrivateDependencies`로 쓴다. `ConsumerIncludeDirectories`·`ConsumerDefines` 우회는 없앤다(BS3). "엔진 공개 헤더는 서드파티 헤더를 include하지 않는다"([저장소 구성](../../../Guides/RepositoryLayout.ko.md) "외부 헤더는 소비 모듈의 Private 구현에만 노출") 규칙은 공개 헤더 검사(BD9)가 자동으로 잡는다.

**시험 실행 파일(BD22 — 개정 27에서 구현 방식을 바꿨다: 아래 "BS1 구현 세부"의 시험 소스 묶음. 묶음은 컴파일 환경이 아니라 BD11 검사의 보이는 모듈을 정한다)**: 시험 모듈(`FoundationTests`·`EngineTests`)의 각 `<Module>/Tests/` 소스는 시험 대상 모듈의 컴파일 환경 전체(비공개 의존 포함)와 그 모듈의 `Private/` 폴더를 받는다. 지금 `NativeModuleInput.Sources`는 문자열 목록이라(`NativeBuildModels.cs:206`) 소스마다 환경을 줄 수 없으므로 `NativeModuleInput`에 **소스 묶음** `SourceGroups`를 더한다. 묶음은 (소스 목록, 추가 비공개 의존, 추가 private include 디렉터리)이고, 묶음의 소스는 모듈 컴파일 환경에 묶음의 추가분을 더한 환경으로 컴파일한다. (개정 27에서 버린 원안: 묶음의 소스를 모듈 컴파일 환경에 묶음의 추가분을 더한 환경으로 컴파일하고, 시험 규칙은 대상 모듈마다 묶음 하나를 만든다 — 추가 비공개 의존 = 대상 모듈과 그 두 의존 목록, 추가 include = 대상 모듈 `Private/`. 지금 방식은 아래 "BS1 구현 세부"다.) 지금 시험 실행 파일이 상위 모듈만 나열하고 하위 의존 전파에 기대며(`FoundationTests.Build.cs`의 "lower dependencies propagate"), `Core/Source/Runtime` 루트 include로 비공개 헤더를 여는 것(83–85행)을 이 규칙으로 바꾼다. BD11의 소유 모듈 판정은 묶음 환경을 쓴다. 정적 라이브러리로 나누지 않으므로 시험 등록(정적 초기화)이 링커에 의해 빠지는 문제가 없다. [유니티 빌드·PCH](../../UnityBuildPch.ko.md)의 묶음 TU는 소스 묶음 경계를 넘지 않는다(환경이 다른 소스를 한 TU로 묶을 수 없다).

**설치 SDK**: `SdkModule`(`InstalledSdk.cs:14`)의 `Dependencies`를 두 목록으로 바꾼다(`Reachable` `:49`, 검증 `:455-469`도 같다). SDK 게임 빌드는 같은 규칙으로 컴파일 환경을 만든다.

**그 밖의 소비처**: `DescriptorModules.cs:170`(빠진 모듈 참조 검사)과 `ReleaseExclusion.cs:124`(도달 검사)는 두 목록을 모두 따라간다.

**전환**: 기존 모듈은 먼저 모두 공개 의존으로 옮긴다(동작 불변, BS0). 그 뒤 공개 헤더 검사와 진단으로 공개 헤더가 쓰지 않는 의존을 비공개로 내린다(BS3).

**BS0 구현 세부(개정 5).**
- `NativeModuleInput.PublicDependencies`·`PrivateDependencies`(문자열 목록)와 둘을 차례로 잇는 읽기 전용 `AllDependencies`(공개 다음 비공개)를 둔다. `Dependencies`는 없앤다. 규칙 기반 클래스(`SourceModuleRules`)는 추상 `PublicDependencies`와 기본이 빈 `PrivateDependencies`를 둔다(`RequiredModules`는 없앤다). 다른 규칙(Program·서드파티·게임 템플릿)은 `NativeModuleInput`을 직접 채운다.
- 보임(컴파일 환경)은 Rocks.Build `ModuleVisibility.Of`(대상 모듈은 두 목록, 그 밖은 공개 목록만 따라가는 의존 우선 후위 순서)로 한 곳에서 계산한다. 쓰는 곳: 액션 그래프의 include·정의·`AdditionalInputs`·공유 PCH 후보, 메타데이터의 AST include·전파 정의·생성 헤더 `DependsOn`. 공유 PCH 제공 모듈의 closure(포함 검사·공유 정의·후보 순위)는 그 제공 모듈의 공개 환경(`ModuleVisibility.PublicClosure` — 자기와 공개 목록만)이다(리뷰 반영).
- 메타데이터 import 범위(BD8 개정)는 보임이 아니라 도달(두 목록)이다. 메타 컴파일러는 import한 descriptor의 타입을 모두 잇는데(그 모듈의 private 타입 포함), 그 타입이 비공개 의존 모듈의 타입을 쓰면 그 descriptor도 있어야 집합이 닫힌다. import는 타입 정보이지 헤더 노출이 아니므로 공개 범위를 넓히지 않는다. 버린 안: 메타 컴파일러가 다른 모듈의 private 타입을 잇지 않고 건너뛰게(다른 모듈 private 타입의 해석 규칙이 새로 필요하다).
- 공개 헤더 검사(`PublicHeaderChecks`)는 아직 도달한 라이브러리를 모두 공개 의존으로 두는 검사다(BD9 아님). 그래서 BS1 전에는 의존을 비공개로 내리지 않는다(BS0 → BS1 → BS3 순서). 시험 실행 파일의 하위 의존 전파(BD22)도 같다. 순서는 공개 목록을 먼저 따라가므로, 모든 의존이 공개인 지금은 전환 전 도달 순서와 같다.
- 도달(링크·빌드 대상·순환 검사·`Closures`·모듈 표 행 의존·진입점 판정·SDK·기술자·Release 배제·`DynamicModules` 겹침)은 `AllDependencies`를 따른다.
- 한 모듈을 두 목록에 함께 적으면 입력 오류다(BD11의 첫 항목 — 규칙 값만 보므로 BS1의 depfile 없이 지금 한다).
- 설치 SDK manifest 12: `SdkModule.Dependencies`를 `PublicDependencies`·`PrivateDependencies`로 나눈다. SDK 게임 빌드는 같은 보임 규칙을 쓴다.
- 전환 검증(완료 기준): 모든 타깃(Foundation·EngineTests·Engine·Sandbox·Commandlet·벤치 여섯·ShaderToolSpike·WorldBench)의 Debug `compile_commands.json`이 전환 전과 byte 단위로 같다.

**BS1 구현 세부(개정 27).** BS1을 둘로 나눈다. BS1a는 모듈별 공개 헤더 검사(BD9), BS1b는 include 소유 모듈 검사와 시험 소스 묶음(BD11·BD22 개정)과 쓰지 않는 공개 의존 진단이다. BS1a가 먼저다(BS1b의 진단이 BS1a 검사의 depfile을 쓴다).

*BS1a 모듈별 공개 헤더 검사(BD9).*
- 공개 헤더 검사를 모듈마다 따로 둔다: 검사 대상 모듈 M마다 검사 모듈 `PublicHeaderChecks_<M>`(정적 라이브러리, 유니티·PCH 끔)을 만들고 그 공개 의존은 M 하나다. 그래서 M의 공개 헤더는 **M의 공개 환경만으로** 컴파일된다(M의 public include·define과 M의 공개 의존의 공개 환경 — 3.5절 첫 규칙). 지금은 검사 모듈 하나가 도달한 라이브러리를 모두 공개 의존으로 두어, 헤더가 의존하지 않은 모듈의 헤더도 열렸다.
- 검사 대상: 타깃 도달 집합의 라이브러리 모듈 가운데 서드파티가 아닌 것(지금과 같다), 그 모듈의 public include 디렉터리 아래 `*.h`(지금과 같다). 헤더마다 검사 TU 하나(`#include <상대 경로>`)다.
- 검사 모듈은 `CheckPublicHeaders` 타깃에만 만들고 실행 파일에 링크하지 않는다(지금과 같다). 정적 라이브러리라 Modular 타깃에서는 공유 라이브러리가 되므로 `CheckPublicHeaders`는 Monolithic 타깃만 켠다(Modular면 입력 오류).
- 버린 안: 검사 모듈 하나에 소스 묶음마다 다른 환경(BD22 원안의 SourceGroups) — 아래 BD22 개정과 같은 이유로 묶음별 컴파일 환경을 두지 않는다. 검사 모듈을 모듈마다 두면 지금 빌드 기구(모듈 단위 정의 헤더·유니티·PCH)를 그대로 쓴다.
- 검사 모듈의 종류(`Type`)는 대상 모듈의 것이다(Release 배제·type 의존 규칙이 같게 본다). 공개 리플렉션 헤더가 있는 모듈은 메타 생성 Public 폴더가 public include에 있으므로 생성 헤더(`.generated.h`)도 단독으로 검사한다(의도 — 생성 헤더도 스스로 컴파일되어야 한다).
- 결과: 헤더가 자기 모듈의 의존 목록 밖 모듈의 헤더를 include하면 검사 컴파일이 실패한다. 첫 실행(2026-11-23, Windows Debug — Foundation·EngineTests): 위반 0건(BS0이 모든 의존을 공개로 두었고 의존 목록이 빠짐없다).
- 시험: 통합 시험 `PublicHeaderCheckTests`(모듈마다 검사 모듈, 의존하지 않은 모듈의 헤더를 include한 공개 헤더는 그 검사만 실패, 의존을 적으면 통과).

*BS1b include 소유 모듈 검사(BD11)와 시험 소스 묶음(BD22 개정).*
- **소유 영역**: 헤더 경로를 담는 가장 긴 모듈 폴더(`ModuleDirectory`)의 모듈 M이 소유한다. 소유는 셋으로 나눈다. **공개 영역**은 M의 public include 디렉터리와 M의 메타 생성 Public 폴더(`<out>/Generated/<M>/Public`)다. **시험 영역**은 `<M 폴더>/Tests/`다. **비공개 영역**은 M 폴더의 나머지(`Private/` 등)와 메타 생성 Private 폴더다. 경로 비교는 플랫폼 경로 비교(Windows·macOS는 대소문자 무시)와 경로 성분 경계로 하고, 심볼릭 링크·subst 드라이브는 풀지 않는다(PathSpelling과 같다).
- **`ModuleDirectory` 필수**: 서드파티가 아니고 소스나 public include가 있는 모든 모듈은 `ModuleDirectory`가 있어야 한다(입력 오류). 지금 없는 규칙(PlatformBase·PlatformWindow·D3D11Graphics·D3D12Graphics·Dxgi·OpenGLGraphics와 Programs 규칙)에 자기 폴더를 넣는다. include 디렉터리로 소유를 정하는 대체 규칙은 두지 않는다(시험 실행 파일의 루트 include처럼 넓은 디렉터리가 다른 모듈의 파일을 가로챈다).
- **보지 않는 경로**: 저장소 밖(시스템·SDK·툴체인), 출력 폴더의 그 밖 파일(정의 헤더·빌드 정보), 서드파티 루트 가운데 서드파티 모듈 폴더가 아닌 곳(데이터 라이브러리 — 개정 29부터 서드파티 모듈 폴더는 소유가 있다, BS3a), 어떤 모듈 폴더에도 없는 경로(시험 지원 `Core/Source/Developer/TestSupport`는 모듈이 아니라 시험 실행 파일의 소스·include다).
- **보이는 것**: 모듈 M의 소스에는 M의 세 영역과, M의 컴파일 환경에 보이는 모듈(`ModuleVisibility.Of`) X의 공개 영역이 보인다.
- **include 허가(개정 28)**: M의 public·private include 디렉터리 가운데 다른 모듈 폴더 안의 것은 그 디렉터리의 파일을 M에 보여 준다. 규칙이 다른 모듈의 비공개 헤더를 일부러 보여 주는 길이다(지금은 AsyncCompression이 같은 코덱·블록 인코딩을 쓰려고 Compression `Private/`를 받는다 — BS8d2). 모듈 폴더 밖의 넓은 디렉터리(시험 실행 파일의 `Core/Source/Runtime` 같은 루트 include)는 허가가 아니다. 묶음 대상 T의 허가는 T의 시험에도 보인다.
- **시험 소스 묶음(BD22 개정)**: `NativeModuleInput.SourceGroups`는 (폴더, 대상 모듈 T, 추가 모듈 목록, 내부 모듈 목록)의 목록이다. 그 폴더 아래 소스에는 다음이 보인다.
  - T의 세 영역.
  - T의 컴파일 환경에 보이는 모듈 X의 공개 영역과 시험 영역(다른 모듈 시험 도우미 — 예 AssetCooker 시험이 AssetDatabase `Tests/`의 도우미를 쓴다).
  - 추가 모듈 Y의 공개·시험 영역(Y의 시험 도우미 — 개정 28)과 Y의 공개 환경(`PublicClosure`)에 있는 모듈의 공개 영역.
  - 내부 모듈 Z의 세 영역(개정 28 — 시험이 다른 모듈의 시험 접근 헤더를 쓰는 명시적 접근. 예 AssetRuntime `PackageInternal.h`, PlatformBase `VirtualMemoryTestAccess.h`).
  - 호스트(시험 실행 파일 모듈) 자신의 세 영역.
  - 겹치는 묶음 폴더는 가장 긴 폴더가 이긴다. 묶음 밖 호스트 소스(`Programs/FoundationTests/Private`·`/Engine`)는 호스트 모듈의 보임을 쓴다(합집합).
  - **컴파일 환경은 바꾸지 않는다.** 모듈 하나의 환경(정의 헤더·include·PCH)은 그대로다. 유니티 묶음만 소스 묶음 경계를 넘지 않는다(묶음 TU를 한 묶음으로 판정하기 위해서다. 지금의 경로 해시 분할 전에 소스 묶음으로 먼저 나누므로 시험 유니티 TU가 한 번 모두 다시 만들어진다).
  - 시험 규칙(`FoundationTests.Build.cs`)은 시험 대상 모듈 T마다 묶음 (`<T 폴더>/Tests`, T, 추가 모듈)을 만든다. 추가 모듈은 그 시험이 쓰는 fixture 모듈(`ReflectionTestFixtures`·`AssetTestFixtures` 등)과 `DynamicModuleTestApi`를 묶음마다 명시한다(모든 묶음에 붙이면 fixture의 공개 의존이 검사를 덮는다). 첫 실행의 위반은 시험을 그 헤더를 쓸 수 있는 상위 모듈의 `Tests/`로 옮기거나, 시험 전용 접근 수단이 정당하면 묶음 추가 모듈로 푼다(옮김은 동작 불변 이동이다).
  - 시험 지원 코드(`Core/Source/Developer/TestSupport` — 모듈이 아니라 시험 실행 파일의 소스)는 호스트를 대상으로 하고 PlatformBase를 내부 모듈로 둔 묶음이다(크래시·파일 probe가 PlatformBase 내부를 읽는다). 대상이 호스트이므로 호스트의 세 영역, 호스트 컴파일 환경 모듈의 공개·시험 영역, PlatformBase 비공개 영역이 보인다.
  - 첫 실행(2026-11-23, Windows Debug — Core·Foundation·EngineTests): 묶음 추가 모듈 없이 832건. 시험이 fixture·상위 모듈 헤더를 쓰는 것(공개 영역)은 묶음마다 추가 모듈로, 시험 접근 헤더는 내부 모듈로, AsyncCompression의 Compression 비공개 헤더는 include 허가로 풀어 0건이다. RenderBase 시험의 추가 모듈이 많은 것(Engine·World·Config 등 — 통합 시험)은 상위 모듈 `Tests/`로 옮길 후보로 남긴다(옮김은 그 모듈을 맡은 세션의 몫).
  - 시험 실행 파일의 컴파일 환경은 묶음 대상 모듈 환경의 합집합이다. 규칙 로더가 각 묶음 대상 T와 T의 두 의존 목록(서드파티 제외 — 공개 include가 없고 전역 상태 서드파티는 직접 소비 모듈이 하나여야 한다)을 호스트의 비공개 의존에 자동으로 더한다(BS3이 의존을 비공개로 내려도 시험 규칙을 고칠 필요가 없다). 비공개 헤더 include 철자(`<Module/Private/X.h>` — `Core/Source/Runtime` 같은 루트 include)는 그대로이고, 루트 include로 다른 모듈의 파일이 열리는 것은 이 검사가 막는다.
  - 버린 안(원안): 묶음마다 컴파일 환경(묶음별 정의 헤더·include·PCH 후보)을 따로 두기. 묶음마다 정의 헤더와 공유 PCH 선택을 따로 해야 해 액션 그래프가 크게 바뀌고 액션이 는다(사용자 결정 2026-11-23). 한계: 헤더 없이 쓰는 다른 모듈의 정의(정의 헤더가 합집합이다)는 잡지 못한다.
- **검사 대상 기록**: 빌드가 성공한 뒤에만 검사하므로 모든 컴파일 액션의 의존 기록(`DependencyRecord` — `<obj>.deps`, 툴체인 헤더와 계획 산출물은 이미 빠져 있다)은 이번 실행에서 게시했거나 증분 검증(`IncrementalStore.IsCurrent`)한 것이다. 기록을 다시 읽는다(증분 검증이 읽은 것을 넘겨 받지 않는다 — 한계: 기록 수천 개를 빌드마다 읽는다). 기록이 없거나 깨졌으면 건너뛰지 않고 위반으로 센다. 보임은 (모듈, 소스 묶음)마다 한 번 계산하고, 폴더는 끝 구분자를 붙여 정규화한 접두 비교다. 지난 실행의 보고 파일은 실행 전에 지우고, 소유 검사로 실패한 빌드는 도구 빌드 ID를 확정하지 않는다. 위반은 빌드 실패다(오류 줄: 소스, 헤더, 소유 모듈·영역, 보는 쪽 — 앞 40줄을 실패 문구에, 전체를 출력 폴더 `include-ownership.txt`에 쓰고 위반이 없으면 지운다). 경로별 소유 판정은 한 빌드 안에서 캐시한다. 여러 모듈이 같은 폴더를 쓰면(Launch 시험 프로그램 셋의 `Programs/LaunchTests`) 그 모두가 소유하고 하나라도 보이면 된다.
- **공유 PCH**: PCH를 쓰는 TU의 의존 기록에는 PCH 입력 헤더가 들어 있다(UnityBuildPch 4.1절). 소비 TU 검사에서는 그 PCH 액션 기록에 든 경로를 뺀다. 공유 PCH 액션은 제공 모듈의 공개 환경(제공 모듈의 공개 영역과 `PublicClosure`의 공개 영역)으로, 모듈 PCH(`PrivatePchHeader` — 그 모듈의 컴파일 인자로 만든다)는 그 모듈의 보임으로 검사한다. 한계: PCH에 든 헤더를 소스가 직접 include해도 잡지 못한다(정밀 확인은 `--pch off` 빌드).
- **쓰지 않는 공개 의존 진단**: BS1a 검사 모듈의 의존 기록에 공개 의존 D가 소유한 헤더가 하나도 없으면 M의 공개 의존 D는 공개 헤더가 쓰지 않는 것이다. 빌드가 알림 한 줄(`Unused public dependencies: M: D, …`)로 모아 낸다(오류 아님 — BS3이 비공개로 내린다). 간접 include도 쓴 것으로 센다(보수적). D의 public include 디렉터리가 D 폴더 밖에 있으면 그 아래 헤더도 D를 쓴 것으로 센다. 한계: 공개 헤더가 없는 모듈(검사 모듈이 없다)은 진단하지 않고, 정의만 쓰는 의존은 "안 씀"으로 본다. BS3의 완료 기준은 여러 타깃의 진단을 합쳐 판정한다.
- **설치 SDK 게임 빌드**: 엔진 헤더가 저장소 밖이라 보지 않는다(한계 — SDK 모듈의 include 디렉터리로 소유를 정하는 것은 후속).
- 시험(`Rocks.Build.Tests` `IncludeOwnershipTests` — `--group ownership`): 바른 include(공개 의존의 공개 헤더, include 허가, 묶음 대상 환경의 시험 도우미, 추가 모듈의 시험 도우미, 내부 모듈의 비공개 헤더, 소유 없는 경로 무시)의 통과와 보고 파일 없음, 위반 넷(의존하지 않은 모듈의 공개 헤더, 의존 모듈의 비공개 헤더, 묶음 밖 시험 도우미, 내부 모듈 없는 비공개 헤더)의 빌드 실패·문구·보고 파일, 유니티 묶음이 소스 묶음 경계를 넘지 않음, 쓰지 않는 공개 의존 알림. 실제 저장소 타깃(Core·Foundation·EngineTests·Sandbox·Commandlet·EngineModular)이 검사를 통과한다. 한계: PCH 입력 제외는 저장소 타깃 빌드로만 확인했다(시험 fixture는 PCH가 없다).

**BS3 구현 세부(개정 29).** BS3을 둘로 나눈다. BS3a는 서드파티 모듈 전환(BD21), BS3b는 쓰지 않는 공개 의존을 비공개로 내리기다.

*BS3a 서드파티를 모듈 의존으로(BD21).*
- 코드 라이브러리(`ThirdParty.json` `kind` 없음 — 지금 `ThirdPartyModuleRules`)는 include 디렉터리를 public include로, `consumerDefines`를 **소비자 정의**로 낸다(라이브러리 빌드 define은 지금처럼 private이다). 소비자 정의는 새 모듈 칸 `NativeModuleInput.ConsumerDefines`다: 그 모듈에 의존하는 모듈만 받고 자기 컴파일에는 넣지 않는다(CMake INTERFACE 정의와 같다). public define으로 내면 라이브러리 원본이 같은 매크로를 스스로 `#define`해(예 lz4 `LZ4_HC_STATIC_LINKING_ONLY`, zstd `ZSTD_STATIC_LINKING_ONLY`) 재정의 오류가 난다 — UE는 서드파티를 미리 빌드해 이 문제가 없다. UE External 모듈이 `PublicSystemIncludePaths`·`PublicDefinitions`를 내는 것과 같다(include는 system include가 아니라 지금처럼 보통 include다 — 어댑터 TU의 경고 규칙은 그대로다).
- header-only 라이브러리(`kind: headers` — VulkanHeaders)와 binary 라이브러리(`kind: binary` — DirectXShaderCompiler·D3DCompiler·SpirvCross·SpirvTools·MetalToolchain, 실행 중 적재하는 도구라 링크하지 않는다)도 모듈 규칙을 둔다. 소스 없이 public include·public define만 내는 모듈이다(`ThirdParty = true`). 데이터 라이브러리(`kind: data`)는 모듈이 없다.
- 서드파티 모듈의 `ModuleDirectory`는 라이브러리 폴더다. 그래서 include 소유 검사가 서드파티 헤더도 본다(BS1b의 "서드파티는 BS3" 해제): 공개 영역은 manifest include 디렉터리, 나머지는 비공개다.
- 소비 모듈은 `ConsumerIncludeDirectories`·`ConsumerDefines` 대신 서드파티 모듈을 **비공개 의존**으로 적는다(공개 헤더가 서드파티 헤더를 include하지 않으므로 — 공개 헤더 검사가 자동으로 잡는다). 서드파티끼리(OpusFile → Ogg·Opus, Vorbis → Ogg)도 비공개 의존이다. 두 우회 함수는 없앤다(하위 호환 없음).
- 시험 실행 파일이 어댑터 시험으로 직접 include하는 서드파티(EngineTests의 VulkanHeaders·SpirvReflect·SpirvCross·SpirvTools·MikkTSpace)는 호스트의 비공개 의존이고, 그 시험 묶음의 추가 모듈이다.
- 전역 상태 서드파티의 직접 소비 모듈 하나 규칙(BD29)은 그대로다(Sodium → Crypto).
- **설치 SDK**: 소스에서 빌드하는 서드파티(Lz4·Zlib·Zstd 등)는 소스 폴더가 곧 공개 include 루트다. SDK는 공개 include 루트를 복사할 때 번역 단위(`.c .cc .cpp .cxx .c++ .m .mm`)를 빼고 헤더만 싣는다(라이브러리는 object로 실린다). 소비자 정의는 SDK 모듈의 정의에 합친다 — SDK에서는 라이브러리가 이미 빌드되어 있으므로 소비자에게는 공개 정의와 같다.
- 버린 안: 서드파티 include를 system include로 넘기기(`PublicSystemIncludePaths`) — 어댑터가 서드파티 헤더 경고를 엔진 경고 규칙으로 보는 지금 정책(셰이더 시스템 8절 등)을 바꾸게 된다. 필요해지면 따로 정한다.

*BS3b 쓰지 않는 공개 의존 내리기.*
- BS1b의 알림(`Unused public dependencies`)에 나온 공개 의존을 그 모듈의 비공개 의존으로 옮긴다(모듈 규칙의 `PublicDependencies` → `PrivateDependencies`).
- 옮기면 그 의존의 공개 환경이 소비 모듈에 더는 전파되지 않는다. 소비 모듈의 소스가 그 헤더를 직접 썼으면(전이 공개 의존에 기대던 것) 컴파일이나 include 소유 검사가 실패하므로, 그 소비 모듈에 빠진 의존을 직접 적는다(UE도 쓰는 모듈은 자기 의존 목록에 적는다).
- **리플렉션 등록 사슬**: 모듈 생성 소스의 `RegisterModuleTypes`는 리플렉션이 없는 모듈을 건너 닿는 리플렉션 모듈의 등록 함수를 직접 부르고 그 생성 헤더를 include한다(리플렉션이 없는 모듈에는 등록 함수가 없다 — 예 AssetCooker → AssetDatabase → HostConfig → Config·TraceControl). 그래서 리플렉션이 없는 모듈 M의 공개 의존 D가 리플렉션 모듈이거나 리플렉션 모듈에 닿으면 D는 공개로 둔다(쓰지 않는 공개 의존 진단이 빼낸다). M에 리플렉션이 있으면 M의 등록 함수가 D 쪽을 덮으므로(M은 비공개 의존도 본다) D를 내려도 된다. 첫 시도(진단을 고치기 전 35건을 모두 내림)에서 AssetCooker·ShaderCompiler 생성 소스가 Config·TraceControl 생성 헤더를 찾지 못해 깨졌다.
  - 버린 안: 리플렉션 모듈에 닿는 모든 모듈에 중계 등록 함수를 생성해 사슬이 직접 의존만 부르게 하기(리플렉션이 없는 모듈 다수에 생성 TU가 생겨 메타 배치가 크게 바뀐다).
- 공개 헤더가 없는 라이브러리 모듈(공개 헤더 검사 모듈이 없다)은 진단 대상이 아니라 이번에 옮기지 않는다(한계).
- 완료 기준: 저장소 타깃(Foundation·EngineTests·Sandbox·Commandlet)의 알림 합집합이 0, 우회 0, 빌드 통과.
- 다른 세션이 맡은 모듈의 규칙도 고친다(의존 목록만 — 동작 불변). 고친 모듈 목록을 각 세션에 알린다.

**[유니티 빌드·PCH](../../UnityBuildPch.ko.md)와의 관계**: 8.4절 공유 PCH의 "제공 모듈의 public include closure"는 이 문서의 공개 환경이다. 소비 모듈이 고르는 제공 모듈의 후보(같은 절 248행 "도달 집합에 있는 제공 모듈")는 "컴파일 환경에 보이는 제공 모듈"로 바꾼다. UE도 공개 closure와 직접 비공개 의존만 본다(`UEBuildModule.cs:1169-1206` `InternalGetAllDependencyModulesForPCH`).
