### 3.38 읽기 손상 오류 `CorruptData` 이전(개정 35)

Core `ErrorCode::CorruptData`(AU4 — 3.36절)가 생긴 뒤 에셋 계열은 읽기 손상을 이 값으로 옮겼다(Docs/Design/AssetSystem 19장). 오디오도 같은 규칙을 따른다. 플랫폼 데이터 해석, 런타임 디코더, 원본 디코더가 손상 입력을 아직 `InvalidArgument`로 내고 있으므로 이 절에서 옮긴다. 이 절은 앞 절(3.24·3.25–3.32절 등)의 "손상은 InvalidArgument" 문장을 대체한다.

#### 3.38.1 분류

AssetSystem 19.1절 표를 그대로 쓴다.
- 읽은 byte가 구조·길이·필드·체크섬·형식 규칙을 어기면 `CorruptData`다. 비유한 표본도 여기에 든다.
- 호출자 인자·호출 순서 위반은 `InvalidArgument`로 남는다.
- 한도 초과는 `CapacityExceeded`, 모르는 변형(형식 판·부호화)은 `Unsupported`다.

오디오에서 갈리는 곳은 다음 표와 같다.

| 곳 | `CorruptData` | `InvalidArgument`(그대로) | 그 밖 |
|---|---|---|---|
| `AudioPlatformDataView::Parse` | 크기·magic·예약 칸 ≠ 0, codec id 0, 머리 규칙(채널·마스크·rate·frame·loop·넘침), 메타 크기·채움, 청크 표 | — | 형식 판 ≠ `AudioPlatformDataVersion`은 `Unsupported`(새 판), codec id가 표 범위 밖이면 `Unsupported` |
| `VerifyAudioChunk` | payload 크기 ≠ 표, SHA-256 불일치 | — | — |
| PCM16·ADPCM 디코더 `Open` | 채널·rate 규칙, codec 머리가 비지 않음 | 머리 codec이 그 디코더가 아님 | bitstream 판은 `Unsupported` |
| PCM16·ADPCM 디코더 `BeginChunk` | pre-roll ≠ 0, payload byte 수가 frame 수와 맞지 않음 | 열지 않음, payload 길이 ≠ 청크 표, 시작 frame이 청크 밖 | — |
| `ContinueChunk`·`DecodeNext`(모든 codec) | `ContinueChunk`의 청크 검사(PCM16·ADPCM은 `BeginChunk` 규칙, Opus는 패킷 구조), ADPCM `DecodeNext`의 블록 손상(`DecodeAdpcmFrames`), Opus 패킷 디코드 실패 | 순서 규칙 위반, 출력 버퍼, 열린 청크 없음 | — |
| Opus 디코더 `Open` | 채널·rate·마스크 규칙, codec 머리(`ParseOpusCodecHeader`), libopus 상태 크기·초기화 실패(codec 머리 검증 뒤라 사실상 도달하지 않는다 — 실패하면 머리 값이 libopus가 받지 않는 조합이라는 뜻이므로 데이터 쪽으로 둔다) | 머리 codec이 Opus가 아님 | bitstream 판은 `Unsupported` |
| Opus 디코더 청크 검사 | frame 수가 960의 배수가 아님, 길이 접두·패킷 길이·패킷 frame 수, 패킷 수와 frame 합 불일치 | 열지 않음, payload 길이 ≠ 청크 표, 시작 frame이 청크 밖 | libopus 상태 reset 실패는 그대로 `InvalidArgument`(내부 오류 — 데이터와 무관) |
| `DecodeAdpcmBlock`·`DecodeAdpcmFrames` | 블록이 짧음, 계수 번호 범위 밖, payload 크기가 frame 수와 맞지 않음 | frames 0·범위 밖, out 크기·채널, 시작 frame 범위 | — |
| `DecodeAudioPlatformData` | 디코더가 청크 frame 수보다 많이 또는 적게 냄 | payload가 다 없는 보기 | 디코더 없음 `NotFound` |
| 원본 디코더(WAV·AIFF·MP3·FLAC·Vorbis·Opus), Ogg page 검사 | 빈 파일, 형식 표지 불일치(RIFF·FORM·fLaC·OpusHead 등 — 임포터가 형식을 먼저 고르므로 표지가 틀리면 손상이다), 필수 chunk·frame·STREAMINFO 없음, 크기·길이 불일치, CRC·MD5 불일치, page 손상·누락·잘림, 비유한 표본, vorbisfile·opusfile 열기·읽기 오류 | — | 모르는 판·기능(`OV_EVERSION`·`OV_EIMPL`, `OP_EVERSION`·`OP_EIMPL`)·다중화·모르는 부호화는 `Unsupported`, opusfile `OP_EFAULT`(할당 실패)는 `OutOfMemory`, libFLAC 디코더 초기화 실패(메모리 제외)와 vorbisfile `OV_EFAULT`(콜백·내부 논리 오류)는 `InvalidArgument` |

- 위층은 하부의 `CorruptData`를 그대로 넘긴다.
  - 임포터는 이미 디코더 오류를 `InvalidSource` 진단과 함께 그대로 넘긴다.
  - `SoundClip::LoadCookedPcm`은 지금 `InvalidArgument`를 `CorruptData`로 바꿔 주는데, 이 매핑을 없애고 하부 값을 그대로 넘긴다. 그러면 하부의 호출자 오용(`InvalidArgument`)이 손상으로 둔갑하지 않는다.
  - 형식 판이 다른 데이터(`Unsupported`)는 `LoadCookedPcm`에서도 `Unsupported`로 남는다(더 새 쿠커의 데이터 — 손상이 아니다).
  - 예외 하나: `LoadCookedPcm`은 `SoundPcm::TryAllocate`의 `InvalidArgument`를 `CorruptData`로 옮긴다. 넘기는 차원(채널·rate·frame)이 읽은 머리에서 온 값이라, 범위 밖이면 데이터가 손상된 것이다. `DecodeSoundClipSource`도 같다.
  - reader가 준 byte에 payload가 모자라면(잘림) `CorruptData`다. `DecodeAudioPlatformData`는 같은 경우를 `InvalidArgument`(호출자가 일부만 넘긴 보기)로 내므로, `LoadCookedPcm`이 그 앞에서 판정한다.
- 19.1절에는 내부 오류 범주가 없다. 데이터와 무관한 라이브러리 내부·콜백 오류는 `InvalidArgument`로 두고 이 표에 따로 적는다(libFLAC 초기화, vorbisfile `OV_EFAULT`, libopus 상태 reset 실패).
- 공개 헤더의 오류 주석을 같이 고친다(`AudioPlatformData.h`·`AudioDecoder.h`·`Adpcm.h`·`OpusCodecHeader.h`·`OpusAudioDecoder.h`·`SourceAudio.h`).
- 시험: 손상 입력 시험의 기대값을 `CorruptData`로 바꾸고, 인자 오용 시험은 그대로 둔다. 둘이 한 시험에 섞인 곳은 나눈다.

#### 3.38.2 버린 안

- **모든 디코더 실패를 `CorruptData`로**: 호출 순서 위반(열지 않고 `BeginChunk`, 이어지지 않는 `ContinueChunk`)은 데이터를 다시 만들어도 고쳐지지 않는다. 호출자 버그이므로 `InvalidArgument`로 남긴다.
- **payload 길이 ≠ 청크 표를 `CorruptData`로**: payload는 호출자가 `AudioPlatformDataView::ChunkPayload`로 잘라 넘기는 값이라, 길이가 다르면 호출자가 다른 청크를 넘긴 것이다. 손상된 byte는 내용 규칙(패킷 구조·SHA)이 잡는다. `VerifyAudioChunk`는 같은 크기 불일치를 `CorruptData`로 낸다. 이 함수는 저장소(sidecar 등)에서 읽은 byte를 디코더에 주기 전에 확인하는 자리라, 크기가 다르면 읽은 데이터가 잘린 것이다(AU6 청크 캐시는 Verify를 먼저 부른다).
- **형식 판 불일치를 `CorruptData`로**: 새 쿠커가 쓴 데이터를 옛 실행이 읽는 경우라 다시 쿠킹하면 풀린다. 그래도 데이터는 손상이 아니라 모르는 변형이다(19.1절 — `Unsupported`).
