### 3.46 AU6b — sidecar 스트리밍·청크 캐시·준비 티켓(개정 54–55)

AU6a는 압축 플랫폼 데이터 전체를 메모리에 둔 채 실시간 디코드한다(3.40절). AU6b는 압축 payload를 패키지 밖 sidecar에 두고, 재생에 필요한 청크만 비동기로 읽어 캐시한다. 선행 PR12(AssetSystem 20절 — sidecar 형식·쿠킹 배치·`StreamedBulk` 범위 읽기)는 끝났다(PR12c c81f526a8). 범위가 넓어 셋으로 나눈다. 설계 교차 검증 1회를 반영했다(개정 55).

| 단계 | 내용 | 선행 |
|---|---|---|
| AU6b1 | 쿠킹 배치(스트리밍 clip은 메타 + 청크 0을 패키지에, payload 영역을 sidecar에), `SoundClip::streamedPayload`, 읽기 경계 `SoundStreamedPayload`(AudioAssets 인터페이스 — `StreamedBulk` 어댑터는 EngineAudio), `LoadCooked`의 sidecar 경로, 엔진 로드 도우미 `LoadCookedClip`, 패키지만 있는 데이터는 AU6a 경로 | PR12a–c |
| AU6b2 | `AudioChunkCache`(엔진에 하나 — 상한·LRU·pin·초과 할당), `CachedAudioChunkSource`(재생 작업마다), 비동기 읽기·완료 깨우기·미리 읽기·우선순위 올리기, IO 핀, 읽기 실패, 로딩 동작(Retain·Prime·OnDemand)의 청크 1 의미, 주인 없는 항목 정리, 종료 순서(`EngineAssetsSubsystem` 뒤 등록) | AU6b1 |
| AU6b3 | 준비 티켓(`PreparePlayback`·`Query` — 3.12.4절), `PlayOptions::notReady`, 굶음 Skip 정책 — 요구만, 세부는 착수 전 절 | AU6b2 |

약칭: SW = `Engine/Private/SoundWave.cpp`, ASC = `Engine/Private/AudioStreamingCache.cpp`, SWL = `Engine/Classes/Sound/SoundWaveLoadingBehavior.h`, AS20 = `Docs/Design/AssetSystem/20-StreamingBulk.ko.md`.

#### 3.46.1 UE 동작(근거)

- **청크 배치**(SW 880–900): 스트리밍 wave의 청크마다 bulk 하나다. 청크 0(zeroth chunk — 첫 청크 목표 `ZerothChunkSize`)은 늘 인라인(`BULKDATA_ForceInlinePayload`)이고, 나머지는 `Force_NOT_InlinePayload`(쿠킹 `.ubulk`)다. 첫 오디오 청크(청크 1)는 선택으로 인라인할 수 있다(pre-buffering — SW 2366–2368).
- **청크 0은 늘 메모리에 있다**: 스트리밍 wave는 PostLoad에서 로딩 동작과 상관없이 `LoadZerothChunk()`를 부르고(SW 2464–2469), 그 결과를 `ZerothChunkData` 사본으로 둔다(SW 654–714·2491–2516).
- **스트리밍 결정**(SW 4118–4135 `IsStreaming`): `ForceInline`·procedural이 아니면 스트리밍한다. 쿠킹 때 정해진다.
- **로딩 동작은 청크 1에 적용한다**(SWL 25–34, SW 2366–2412):
  - `RetainOnLoad`: 청크 1을 캐시에 넣고 wave가 살아 있는 동안 내보내지 않는다(`RetainCompressedAudio`).
  - `PrimeOnLoad`: 로드 때 청크 1을 캐시에 청하지만 고정하지 않는다(`RequestChunk(…, 1, …)` — 청크가 둘 이상일 때만, SW 2400–2408).
  - `LoadOnDemand`: 재생할 때 읽는다. 기본값이다(`au.streamcache.SoundWaveDefaultLoadingBehavior` — SW 59).
- **캐시**(ASC): 엔진에 하나(`FCachedAudioStreamingManager`)다.
  - 상한은 플랫폼 설정 `CacheSizeKB`(Windows `[WindowsTargetPlatform.WindowsTargetSettings]` 65536 = 64 MiB — BaseEngine.ini 3417, 플랫폼마다 다르다)이고 LRU로 내보낸다. 쓰는 중인 청크는 내보내지 않는다.
  - 같은 청크는 재생끼리 공유한다(`FChunkKey` = wave + 청크 번호).
  - 우선순위: 재생에 필요해지면 미리 읽기보다 올린다(ASC 845–856 `bNeededForPlayback`·`UpdatePriority`). 재생 중 굶으면 `AIOP_MAX`로 올린다(ASC 2116–2142 `HandleStarvation`). UE `UpdatePriority`는 진행 중 요청에도 효과가 있다.
  - 요청 해제는 기다리지 않게 백그라운드 task로 넘긴다(ASC 1825–1853).

#### 3.46.2 AU6b1 — 쿠킹 배치

**스트리밍 여부는 쿠킹 때 정한다**(UE와 같다 — 3.40.3절의 런타임 결정을 고친다):
- 패키지만(sidecar 없음):
  - `loadingBehavior`가 `ForceInline`인 clip
  - loop 구간이 `StreamMinLoopSeconds`보다 짧은 looping clip(로드 때 통째 디코드 — 3.40.3절)
  - 청크가 하나뿐인 clip(청크 0이 payload 전체라 sidecar에 둘 것이 없다)
- 나머지(분류의 `Inherited`·`RetainOnLoad`·`PrimeOnLoad`·`LoadOnDemand`)는 sidecar다. 런타임 로딩 동작(3.46.5절)은 청크 1을 어떻게 캐시할지만 정한다. 그래서 쿠킹은 런타임 CVar(`audio.stream.defaultloading`)를 몰라도 된다.
- 서버 프로필은 지금 sidecar 출력이 없어 패키지에 전체를 둔다(PR12b 어댑터 — AS20 20.5 2). 서버의 헤더만 쿠킹(3.11.5절 마지막 줄)은 BS7 몫이다.

**배치**(AS20 20.1 2·3.30.1절 위치 불변 규칙):
- 패키지 bulk `platformData` = 플랫폼 데이터 앞부분 [0, 메타 + 청크 0 끝)이다. 머리·청크 표는 그대로라 청크 위치·SHA가 나누기 전과 같다.
- sidecar bulk `streamedPayload` = payload 영역 전체다(청크 0 포함). `CookChainedBulkSource::Add(payload, PackageBulkPlacement::Sidecar)`로 더한다.
- 패키지만인 clip은 지금처럼 `platformData` 하나에 전체를 넣고 `streamedPayload`는 비운다.
- 너겟 값(플랫폼 데이터 byte)은 바뀌지 않는다. 배치는 패키지를 쓸 때 정한다(AS20 20.1 6).
- 청크 0이 늘 상주하므로(3.46.5절) sidecar clip의 첫 청크 목표 byte 기본값을 작게 둔다: 시작 수위(`StreamStartFrames` 4096 frame)를 덮는 크기를 목표로 한다(UE `ZerothChunkSize` 취지). 목표 청크 byte(256 KiB)는 그대로다. 이 기본값은 쿠킹 처리기 옵션이고 너겟 키에 들어간다(쿠킹 결과가 바뀐다 — TestContent 재쿠킹).

**`SoundClip::streamedPayload`**(`BulkDataRef`, ROCKS_PROPERTY — 쿠킹 패키지에만 있다. 에디터 패키지에서는 비어 있다). 새 리플렉션 필드라 `.rocksids.json`에 등록한다.

#### 3.46.3 AU6b1 — 읽기 경계와 로드

**`SoundStreamedPayload`**(AudioAssets — `AudioAssets/SoundStreamedPayload.h`): sidecar payload 범위 읽기 인터페이스다. 시험이 가짜를 쓰게 하고, AssetManager의 스레드 규칙(Game 스레드 열기·AudioRT 금지·callback 스레드)을 오디오 계약 하나로 감싼다.
```cpp
class SoundStreamedPayload {            // Read는 여러 스레드 동시(AudioRT 제외)
public:
    virtual uint64 Bytes() const noexcept = 0;
    // destination에 [offset, offset + size)를 읽기 시작한다. 완료는 아무 스레드에서 callback 정확히 한 번
    // (Read가 돌아오기 전일 수도, Read를 부른 스레드일 수도 있다). 즉시 실패(범위·할당·종료)는 반환값이고
    // callback이 없다. destination은 callback이 돌아올 때까지 산다.
    virtual Result<SoundPayloadRead> Read(uint64 offset, Span<uint8> destination,
                                          SoundReadPriority priority, SoundReadCallback callback,
                                          void* context) noexcept = 0;
};
// SoundPayloadRead: move-only 손잡이 — Cancel·SetPriority·State. Pending 소멸 금지(StreamedBulk 규칙).
// Read·Cancel은 callback을 그 자리(부른 스레드, Read가 손잡이를 돌려주기 전)에서 부를 수 있다 — 호출자는 자기
// 잠금을 쥐지 않고 부르고, Read 전에 받을 자리·상태를 준비한다. SetPriority는 callback을 부르지 않는다.
// callback 안에서 Read·Cancel·SetPriority를 다시 불러도 되고 자기 손잡이를 파괴해도 된다(PR12c 확인 — rocks-2c).
```
- 엔진 구현 `StreamedBulkPayload`(EngineAudio)는 `StreamedBulk`·`BulkReadHandle`을 감싸고, 즉시 실패와 Pending 소멸 Fatal을 그대로 옮긴다. 우선순위는 Low·Normal·High·Critical이다.
- 블록 해시 검증은 에셋 쪽이 한다(AS20 20.1 8). 그래서 sidecar에서 온 Ready 청크는 이미 검증된 byte다. 오디오는 `VerifyAudioChunk`를 다시 하지 않는다(3.40.2절 `AudioChunkSource` 계약 문구를 고친다).

**로드**: `SoundClip::LoadCooked(allocator, reader, context, decoders, options, streamed)`에 `SharedPtr<SoundStreamedPayload> streamed`를 더한다.
- `streamedPayload`가 비었으면 지금 경로(통째·상주 실시간)다. `streamed`는 null이어야 한다(아니면 InvalidArgument).
- `streamedPayload`가 있고 `streamed`가 null이면, 그 bulk가 패키지 안에 있는 경우다(sidecar 출력이 없는 서버 프로필 — PR12b 어댑터가 패키지 안으로 돌린다). reader로 `platformData`(메타 + 청크 0)와 `streamedPayload`(payload 전체)를 읽어 이어 붙이고 지금의 상주 경로로 간다. reader가 그 bulk를 못 주면(sidecar라 메모리에 없음) 그 오류다.
- `streamedPayload`가 있고 `streamed`가 있으면 sidecar 경로다.
  - `Bytes()`가 머리의 payloadBytes와 다르면 InvalidArgument다.
  - reader로 `platformData`(메타 + 청크 0)를 읽어 `Parse`한다(일부 payload — 3.30.1절). 청크 0을 `VerifyAudioChunk`로 본다(패키지 bulk는 Prepare SHA도 보지만 겹쳐도 해가 없다).
  - `SoundStreamData`를 sidecar 형태로 만든다: 메타·청크 0 사본(모든 로딩 동작 — UE zeroth chunk), `streamed` 공유 참조, 실효 로딩 동작.
  - 디코더 표에 codec이 있는지 본다(없으면 NotFound — 지금과 같다).
  - 재사용 키가 같아 로드를 건너뛸 때는 `streamed`를 쓰지 않는다(호출자가 열지 않아도 된다 — `LoadCookedClip`이 키를 먼저 본다).

**엔진 로드 도우미** `AudioEngineSubsystem::LoadCookedClip(SoundClip&, Package&, AssetManager&, const AssetLease&)`(Game 스레드):
1. 재사용 키가 같으면 아무것도 하지 않는다.
2. `streamedPayload`가 있으면 `AssetManager::OpenStreamedBulk(lease, clip.streamedPayload)` → `StreamedBulkPayload`. Unsupported(그 bulk가 패키지 안 — 서버 프로필)면 `streamed` 없이 3으로 간다(상주 경로). 그 밖의 오류는 로드 실패다.
3. `LoadCooked`(reader는 `Package::BulkBytes`, 디코더 표·로드 옵션은 엔진 값).
4. 로딩 동작 후크(3.46.5절): Prime·Retain을 캐시에 건다. 장치가 없으면(캐시 없음) 건너뛴다.
- 쿠킹 clip을 쓰는 호스트(Sandbox 등)는 이것 하나를 부른다.

**수명 계약**(AS20 20.2 3 종료):
- `StreamedBulk`는 `SoundStreamData`가 쥐고, 재생 스냅숏·청크 캐시 항목이 공유한다.
- registry가 가진 `SoundClip` 객체의 스냅숏은 `AssetManager` 소멸의 `registry.Reset()`에서 `StreamedBulkSystem`보다 먼저 풀린다(AssetRuntime `AssetManager.cpp` — Fatal 검사보다 앞). 그래서 clip 객체 자체는 문제가 없다.
- 문제는 AssetManager 밖에서 쥔 참조다: 게임이 쥔 `SoundSourceRef`·컴포넌트·묶음 명령, 오디오의 재생·캐시. 오디오는 자기 정리에서 모두 놓고(3.46.6절), 게임 코드는 lease처럼 AssetManager보다 먼저 놓아야 한다.

**`SoundStreamData`**: 지금의 "전체 byte 사본"에 sidecar 형태를 더한다.
- `HasAllPayload()`(상주) 또는 `Streamed()`(sidecar 참조)다. 둘 중 하나다.
- `View()`는 메타와 청크 0을 덮는 `AudioPlatformDataView`다. `Chunk0()`은 청크 0 payload다.
- 캐시 키를 위한 프로세스 안 유일 번호 `Serial()`을 둔다(같은 데이터를 쓰는 재생끼리 청크를 공유한다).
- 로딩 동작 고정 토큰 칸(`SoundStreamRetention` — AudioAssets의 가상 소멸 기반 클래스, 엔진이 채운다)을 둔다. `SoundStreamData`는 재생이 공유하는 불변 값이라 토큰은 `SoundClip`의 네이티브 필드에 둔다(clip 수명 = Retain 수명).

#### 3.46.4 AU6b2 — 청크 캐시

**`AudioChunkCache`**(EngineAudio, `AudioEngineSubsystem`이 서비스와 함께 만든다 — 엔진에 하나):
- 상한 CVar `audio.stream.cachekb`(Boot, 기본 65536 — UE Windows 값)다. 청크 버퍼 byte 합으로 센다.
- Boot 검사: 상한 < `audio.stream.maxstreams` × 2 × 최대 청크 byte(쿠킹 목표 256 KiB)면 그 값으로 올리고 Warning을 낸다(재생마다 현재 + 다음 청크를 둘 수 있게).
- **항목**: 키 = (`SoundStreamData::Serial()`, 청크 번호). 상태 {Submitting, Loading, Ready, Failed}, 버퍼, 사용 pin 수, 미리 읽기 pin 수, 고정(Retain) 수, 마지막 사용 순번(LRU), 우선순위, 읽기 손잡이, IO 핀 수, `SharedPtr<SoundStreamedPayload>`(읽는 동안과 캐시에 있는 동안 sidecar를 쥔다).
  - 항목은 하나씩 할당한 노드라 주소가 고정이다(callback context = 노드 주소). 노드는 IO가 끝나고(Submitting·Loading이 아님) pin·IO 핀이 모두 0일 때만 지운다.
- **잠금**: `platform::Mutex` 하나다. 쓰는 스레드는 디코드 서비스(얻기·놓기·미리 읽기), 에셋 worker(완료), 제어 스레드(작업 생성·회수, 주인 없는 항목 정리, Prime·Retain 후크), Game 스레드(종료)다. AudioRT는 쓰지 않는다.
  - payload의 `Read`·`Cancel`·`SetPriority`는 잠금 밖에서 부른다(callback이 그 자리에서 불릴 수 있다 — 3.46.3절).
  - 손잡이 경합은 IO 핀으로 막는다(AS20 20.6 11과 같은 방식): 잠금 안에서 IO 핀을 올리고, 잠금 밖에서 `SetPriority`·`Cancel`을 부르고, 잠금 안에서 내린다. 완료는 상태·결과를 정하되, IO 핀이 0이 아니면 손잡이 해제를 미룬다(마지막 핀을 내리는 쪽이 놓는다).
- **읽기 내기**: 잠금 안에서 항목을 Submitting으로 만들고 버퍼 byte를 예약한다. 잠금 밖에서 버퍼를 할당하고 `Read`를 부른다.
  - Read가 돌아오기 전에 완료가 왔으면(같은 스레드 포함) 완료가 상태를 Ready·Failed로 정해 두었다. Read가 돌아오면 잠금 안에서 손잡이를 저장하거나(아직 Loading이면) 바로 놓는다(이미 끝났으면 — 손잡이는 Done이다).
  - Read 즉시 실패: 항목을 Failed로 두고 그 error를 낸다(예약 byte를 돌려준다).
  - 할당 실패: 같다(OutOfMemory). allocator는 다른 스레드 해제가 되는 엔진 allocator다(축출은 서비스, 실패는 worker, 종료는 Game 스레드에서 놓는다).
- **얻기**(`Acquire(data, index, urgency)`):
  - Ready면 사용 pin을 올리고 payload를 준다(미리 읽기 pin이 있으면 사용 pin으로 바꾼다).
  - Submitting·Loading이면 Pending이다. urgency에 맞게 우선순위를 올린다(아래).
  - 없으면 읽기를 낸다(Pending).
  - Failed면 Failed(그 error)다.
- **상한과 초과 할당**: 새 버퍼가 상한을 넘으면 pin·고정이 없는 Ready 항목을 LRU 순으로 내보낸다. 그래도 모자라면:
  - urgency가 Playback·Starving(재생에 필요)이면 상한을 넘어 할당한다. 넘친 byte를 `cacheOvercommitBytes`(현재값)로 센다. 놓아 상한 밑이 되면 다시 내보낸다. 그래서 재생은 늘 진행한다(영구 Pending이 없다).
  - 미리 읽기·Prime은 내지 않는다(`cacheDenials`를 센다).
- **미리 읽기**(`Prefetch`): 없으면 Normal 우선순위로 읽기를 내고 미리 읽기 pin 하나를 쥔다. 디코더가 그 청크를 `TryAcquire`하면 사용 pin으로 바뀌고 `Release(index)` 때 놓인다. 닿지 못한 채 작업이 끝나면(정지·실패) 작업 회수 때 놓는다. 작업마다 미리 읽기 pin은 최대 하나다.
- **놓기**: 사용 pin을 내린다. Failed 항목은 pin이 모두 0이 되면 지운다(다음 재생이 다시 읽는다). Loading 항목은 pin이 0이어도 읽기를 끝까지 둔다(결과를 캐시한다 — 취소는 종료 때만).
- **완료**(callback — worker 또는 그 자리): 잠금 안에서 상태를 Ready(성공)·Failed(CorruptData·IO 오류·Cancelled)로 정한다. IO 핀이 0이면 손잡이를 놓는다(callback 안 자기 손잡이 파괴 허용 — AS20 20.6 7). pin·고정이 없는 Failed 항목은 지운다. 잠금 밖에서 디코드 서비스 깨우기 신호를 울린다(`RealtimeWakeSignal::Signal` — 잠금 없음).
- **주인 없는 항목 정리**(`Trim`, 제어 묶음마다): `SoundStreamedPayload` 참조를 캐시만 쥔(clip·재생이 모두 놓은) Ready 항목을 지운다. 그래서 clip을 내리면 버퍼와 열린 sidecar 파일이 남지 않는다(옛 revision 포함 — 3.11.5절).

**우선순위와 urgency**(UE 재생 필요·굶음 승격):

| urgency | 언제 | 우선순위 |
|---|---|---|
| Prefetch | 디코더가 청크 i를 열 때 i + 1 미리 읽기, Prime | Normal |
| Playback | 디코더가 지금 필요한 청크(시작 전 시작 수위 대기 포함, SeekRestart 되찾기의 첫 청크) | High |
| Starving | voice가 시작한 뒤 링의 읽을 frame이 시작 수위(`StreamStartFrames`) 밑인데 필요한 청크가 아직 없음 | Critical |

- 올리기는 `SetPriority`다. 에셋은 제출 전 요청에만 효과가 있다(진행 상한 8 — AS20 20.6 7). UE `UpdatePriority`는 진행 중 요청에도 효과가 있다(07장).
- "시작 뒤"는 서비스가 링의 첫 소비를 보고 안다(링 읽기 위치 > 0). 그래서 `AudioChunkSource::TryAcquire(index, AudioChunkUrgency)`로 넘긴다(상주 구현은 무시한다).

**`CachedAudioChunkSource`**(재생 작업마다, `AudioChunkSource` 구현 — 3.40.2절 자리):
- `TryAcquire(0)`은 `SoundStreamData::Chunk0()`으로 바로 Ready다. 그 밖은 캐시 얻기다.
- 미리 읽기 감기: 디코더가 청크 i를 열면 공급자에게 `Prefetch(i + 1)`을 부른다. loop면 다음 청크가 loop 끝을 넘을 때 loop 시작 청크로 감는다. 감기는 디코더가 정한다(loop 구간을 아는 쪽 — 지금 `index + 1 < chunkCount` 조건을 고친다).
- 작업을 회수할 때(제어 스레드 — 서비스 반납 뒤) 쥔 pin을 모두 놓는다.

**읽기 실패**: Failed 청크를 얻은 작업은 `MarkFailed` → voice `StreamFailed` → 재생 `Failed`다(3.40.2절과 같은 경로). 계수 `chunkReadFailures`를 센다.

#### 3.46.5 AU6b2 — 로딩 동작(청크 1)

청크 0은 모든 동작에서 `SoundStreamData`에 상주한다(UE zeroth chunk — 첫 음에 IO가 없다). 로딩 동작은 청크 1(첫 오디오 청크 다음 — UE 청크 1)에 적용한다. 청크가 둘 이상일 때만이다(SW 2400–2408).

| 동작 | 청크 1 | 후크(`LoadCookedClip`) |
|---|---|---|
| `RetainOnLoad` | 캐시에 읽고 clip이 살아 있는 동안 고정한다(내보내지 않음) | `AudioChunkCache::Retain(data, 1)` → 토큰(`SoundStreamRetention`)을 clip에 둔다. 토큰 소멸이 고정을 푼다 |
| `PrimeOnLoad` | 로드 때 캐시에 청하되 고정하지 않는다(LRU를 따른다) | `AudioChunkCache::Prefetch(data, 1)`(pin 없음) |
| `LoadOnDemand`(기본) | 재생 때 읽는다 | 없음 |
| `Inherited` | 런타임 실효 값(`EffectiveLoadingBehavior` — 3.40.3절) | 실효 값의 후크 |

- Retain 토큰은 캐시 핵심 객체를 공유 참조로 쥔다. 캐시가 종료한 뒤의 토큰 소멸은 아무 일도 하지 않는다(종료가 이미 고정을 모두 풀었다).
- Retain 고정은 상한을 넘어 할당할 수 있다(Playback과 같다 — 고정은 에셋이 요구한 상주다).

#### 3.46.6 AU6b2 — 종료 순서

- `AudioEngineSubsystem`은 엔진 subsystem 목록에서 `EngineAssetsSubsystem` 뒤에 등록한다. Engine은 역순으로 정리하므로 오디오가 먼저 정리된다(AS20 20.2 3 종료). 등록 순서를 확인하는 assert를 Initialize에 둔다(`EngineAssetsSubsystem`이 있으면 그보다 뒤).
- 캐시 종료 대기의 진행 전제: 완료 callback은 AssetManager worker(WorkerScheduler)에서 온다. 오디오 정리 동안 그 worker는 살아 있다(EngineAssets가 뒤에 정리된다). 또한 `SoundPayloadRead::Cancel`은 callback을 그 자리에서 줄 수 있으므로(3.46.3절) 캐시는 두 경우를 모두 받는다.
- `Drain`(3.40.2절 종료 순서에 더함):
  1. 믹서 drain
  2. 장치 Close
  3. 서비스 `Shutdown`: 작업 반납
  4. context `Abandon`: 재생 스냅숏·작업(청크 공급자의 pin) 참조를 놓는다.
  5. **캐시 `Shutdown`**(새 단계):
     - 새 얻기·미리 읽기·Retain을 막는다. Retain 고정을 모두 푼다.
     - Submitting·Loading 항목마다 IO 핀을 올리고 잠금 밖에서 `Cancel`한다.
     - 모든 callback이 돌아올 때까지 기다린다(조건 변수 — 시간 대기 없음, 명시 gate).
     - 버퍼와 `SoundStreamedPayload` 참조를 모두 놓는다.
- 그래서 오디오 정리가 끝나면 오디오가 쥔 `StreamedBulk`가 없다. 남은 것은 게임이 쥔 참조뿐이다(3.46.3절 계약).

#### 3.46.7 AU6b3 — 요구(세부는 착수 전 절)

- 준비 티켓 `PreparePlayback(sound, startFrame, preRollFrames)` → `AudioReadyTicket`, `Query` → {Pending, Ready, MissedDeadline, Unavailable, Cancelled, Failed}(3.12.4절). 청크 캐시의 시작 청크(와 다음 청크) 얻기·pin으로 만든다.
- `PlayOptions::notReady`: `StartWhenReady`(기본 — 지금 동작: 시작 대기 3.40.1절), `FailIfNotReady`, `SkipToNow`.
- 굶음 Skip 정책(`SoundClip` 설정 — 3.12.3절): 굶은 시간만큼 원본 위치를 건너뛰어 transport를 유지한다(박자 음악 — AU10 BeatClock 전 필요).

#### 3.46.8 시험

**AU6b1**
- 쿠킹:
  - 스트리밍 clip은 패키지 bulk = 메타 + 청크 0, sidecar = payload 전체다.
  - `ForceInline`·짧은 loop·청크 하나는 패키지만이다.
  - 같은 처리기를 두 번 쿠킹하면 byte가 같다.
  - 서버(출력 없음)는 패키지만이다.
  - 너겟 값은 배치와 상관없다. 첫 청크 기본 목표가 시작 수위를 덮는다.
- 로드(가짜 `SoundStreamedPayload`):
  - sidecar 경로의 `SoundStreamData`는 청크 0 밖 payload를 메모리에 두지 않는다. 가장 큰 할당 < 플랫폼 데이터 크기다.
  - 청크 0 손상은 CorruptData다.
  - `Bytes()` 불일치·null `streamed`는 InvalidArgument다. 패키지만인데 `streamed`가 있으면 InvalidArgument다.
  - 패키지만인 clip은 AU6a 경로 그대로다(회귀 — 출력·할당).
  - 재사용 키가 같으면 `LoadCookedClip`이 sidecar를 열지 않는다.
  - 어댑터 `StreamedBulkPayload`가 즉시 실패와 Pending 소멸 Fatal을 그대로 옮긴다(실제 AssetManager + gate IO).

**AU6b2**(가짜 payload — 완료를 쌓아 두고 시험이 내보내는 gate, Cancel은 바로 Cancelled, 시간 대기 없음)
- 첫 음 전 IO:
  - 모든 동작에서 첫 블록이 IO 없이 시작한다(청크 0 상주).
  - 3분 곡 상당(청크 다수)에서 첫 음 전 읽기 수 ≤ 1(청크 1 미리 읽기 — Prime·Retain은 로드 때 이미)이다. 전체 read가 없다(06-Phases AU6 완료 조건).
  - 출력이 통째 디코드와 bit까지 같다(Inline 제어 + Manual 렌더 + Inline 서비스).
- 로딩 동작: Retain은 청크 1을 고정해 상한을 넘겨도 내보내지 않고 clip을 내리면 풀린다. Prime은 로드 때 읽고 LRU로 내보낼 수 있다. OnDemand는 재생 때 읽는다. 청크가 하나면 후크가 없다.
- 캐시:
  - 같은 clip 두 재생이 청크를 공유한다(읽기 수 한 번).
  - 상한을 넘으면 pin 없는 Ready를 LRU 순으로 내보낸다.
  - 모두 pin이어도 재생에 필요한 얻기는 초과 할당으로 진행한다(`cacheOvercommitBytes`). 미리 읽기는 `cacheDenials`다. pin이 풀리면 초과분이 회수된다.
  - 미리 읽기 pin은 `Release` 때 풀리고, 닿지 못한 채 끝난 작업은 회수 때 풀린다.
  - loop에서 미리 읽기가 loop 시작 청크로 감긴다.
  - clip을 내리면 `Trim`이 주인 없는 항목을 지우고 가짜 payload의 참조가 0이 된다.
  - 같은 clip 100회 새 재생·정지에서 캐시 byte ≤ 상한이고 항목 수·살아 있는 할당이 수렴한다(06-Phases "100회 seek 메모리 상한").
  - 재생을 멈춘 뒤 도착한 완료는 Ready로 캐시되고 회수된 작업을 건드리지 않는다(06-Phases "늦은 완료 폐기").
- 우선순위: 미리 읽기 Normal, 시작 대기·SeekRestart 첫 청크 High, 시작 뒤 굶음 Critical(가짜 payload가 `SetPriority`를 기록). `SetPriority`와 완료의 순서(gate로 제출 전·후).
- 경합: Read가 돌아오기 전 완료(가짜가 Read 안에서 callback), Read 즉시 실패, Cancel 안 callback, IO 핀이 있는 동안 완료 — 손잡이 해제가 한 번이다.
- 실패: 읽기 CorruptData·IO 오류 → 재생 `Failed`·`chunkReadFailures`가 오른다. pin 0으로 실패한 항목은 지워지고 다음 재생은 다시 읽는다.
- 굶음: 완료를 늦추면 `streamStarvedFrames`가 오르고, 완료 뒤 이어 낸다(Pause 정책).
- 종료:
  - Loading 항목이 남은 채 엔진을 내리면 Cancel·callback 회수 뒤 정리된다.
  - 오디오 정리 뒤 가짜 payload의 살아 있는 손잡이·참조가 0이다. 종료 뒤 Retain 토큰 소멸은 아무 일도 하지 않는다.
  - 등록 순서 assert를 확인한다.
- Thread 서비스·Thread 제어에서 같은 출력과 `Flush` gate를 확인한다.
- 엔진 수준 실제 `StreamedBulk`(AssetManager + gate IO) 한 경로: 디스크 sidecar로 끝까지 재생해 통째 디코드와 같은지 본다.
