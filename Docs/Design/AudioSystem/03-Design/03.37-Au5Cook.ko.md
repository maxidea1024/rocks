### 3.37 AU5 구현 세부 — 디코더 등록·쿠킹 처리기·쿠킹 재생(개정 34)

코덱 계층(플랫폼 데이터 형식·청크 표·`AudioDecoder`·`AudioDecoderTable`·PCM16·ADPCM·Opus 인코더/디코더 — 3.30–3.32절)은 앞당겨 끝났다. AU5에 남은 것은 셋이고, 이 순서로 한다.

| 단계 | 내용 |
|---|---|
| AU5a | 디코더 등록부(`AudioDecoderRegistry` 호스트 서비스), `AudioOpus` 모듈 등록, 엔진 디코더 표 |
| AU5b | `SoundClip` 쿠킹 설정·필드, `SoundClipCookProcessor`(인코드·플랫폼 데이터·너겟 키), Commandlet 연결 |
| AU5c | 쿠킹된 실행의 재생: `SoundClip::LoadCookedPcm`(플랫폼 데이터 전체 디코드 → 재생 PCM) |

플랫폼 재정의(rate 상한 표·품질 배수 — 3.11.3절, UE `FPlatformAudioCookOverrides`)는 TargetProfile에 오디오 칸이 필요하다. 그래서 AU5d로 뒤에 둔다. 그때까지 모든 플랫폼이 같은 결과를 낸다(Windows·macOS·Android의 기본 codec이 같다 — 3.11.2절). sidecar·스트리밍은 AU6이다. AU5는 플랫폼 데이터 전체를 패키지 bulk 하나에 넣는다.

#### 3.37.1 디코더 등록부(AU5a)

`Audio`(Runtime)는 codec 구현 모듈(`AudioOpus` — ClientOnly)을 링크하지 않는다(3.30절). 그래서 출력 backend와 같은 방식으로 호스트 서비스를 거친다(3.33.6절).
- **`AudioDecoderRegistry`**(`Audio/AudioDecoder.h`, `HostServices` 서비스):
  - codec id마다 factory 하나를 쥔다.
  - `SetFactory(codec, factory)`로 넣거나 지운다(nullptr).
  - `Fill(AudioDecoderTable&)`은 등록된 factory를 표에 넣고, 이미 있는 codec은 둔다.
  - 등록·조회는 로더 스레드에서 한다.
- **`AudioOpus` 모듈 Startup**은 등록부가 있으면 Opus factory를 넣고, Shutdown은 지운다. 해제는 지금처럼 거부한다.
- **`AudioEngineSubsystem`**은 Initialize에서 엔진 디코더 표를 만든다. 내장 PCM16·ADPCM에 등록부의 factory를 더하고 `DecoderTable()`로 낸다. 장치가 없는 실행(서버)도 표는 만든다(길이·메타 해석에 쓸 수 있다).
- **호스트 연결**: Sandbox는 출력 backend 등록부와 같은 자리(`AudioHostRegistries`)에서 디코더 등록부도 엔진 수명 동안 올리고, `AudioOpus`를 링크한다. Commandlet도 링크한다(쿠커 모듈 집합 규칙 — 등록부를 올리지 않으므로 모듈은 아무 일도 하지 않는다).
- **등록 순서**: 등록부는 엔진 묶음 시작(엔진 Initialize — 모듈 Startup)보다 먼저 올려야 한다. 늦게 올리면 Opus가 조용히 빠진다(출력 backend 등록부와 같은 규칙).
- **Shutdown**: 마지막 엔진이 묶음을 내리면 모듈 Shutdown이 factory를 지운다. 엔진 표가 factory 포인터를 복사해 쥐어도, 모듈이 해제를 거부하므로(`SupportsUnload` false) 코드가 사라지지 않는다.
- **서버**: `AudioOpus`는 ClientOnly라 Server 타깃 폐포에 들어가지 못한다(ModuleTypeRules가 막는다 — 3.35.11절의 `AudioMiniaudio`와 같다).

#### 3.37.2 `SoundClip` 쿠킹 설정과 필드(AU5b)

- **설정**(사용자 — 임포터가 건드리지 않는다):
  - `compression`(`SoundCompression` — PlatformDefault·Pcm·Adpcm·Opus, 기본 PlatformDefault — 3.9절 압축 형식).
  - `compressionQuality`(uint32 [1, 100], 기본 `DefaultAudioCompressionQuality` = 80 — UE `CompressionQuality`).
  - 품질 상수(`Min`·`Max`·`DefaultAudioCompressionQuality`)는 `Audio/AudioPlatformData.h`에 둔다. 쿠킹 인코더(`AudioTools`)와 `SoundClip` 기본값(`AudioAssets`)이 함께 쓴다.
  - 범위 밖 품질·`compression` 값, 잘못된 loop(파일 loop·`loopOverride`가 (0, 0)이 아닌데 begin ≥ end이거나 end > frame 수)·frame 밖 cue는 쿠킹이 `InvalidSetting`·`InvalidArgument`로 실패한다. 품질을 쓰지 않는 codec에서도 검사한다(설정 오류를 codec에 따라 숨기지 않는다).
- **쿠킹 결과**(런타임): `platformData`(`BulkDataRef` — 에디터 패키지에서는 비어 있다).
- **PlatformDefault 해석**(3.11.2절): Opus. 원본 길이가 `ShortClipSeconds`(1 s) 미만이면 ADPCM이다.
  - 판정은 원본 rate의 임포트 필드로 하는 정수 비교 `frameCount < sampleRate × ShortClipSeconds`다. float 나눗셈이 없어 경계가 정확하고, AU5d의 rate 재정의와도 무관하다.
  - 44.1 kHz면 44099 frame은 ADPCM, 44100 frame은 Opus다.
- **쿠킹 채널**: 1–2다. 더 많은 채널은 원본 채널 배치(채널 마스크) 임포트 필드가 필요하고 다채널 출력은 AU9라서, 그 전에는 쿠킹이 `UnsupportedSourceFormat`·`Unsupported`로 실패한다.
  - 원본 사실(임포트 결과) 오류는 설정 오류와 나눈다: rate가 [8000, 192000] 밖이면 `UnsupportedSourceFormat`·`Unsupported`, 채널 0·frame 0은 `InvalidSource`·`CorruptData`다.
  - 한계: 쿠킹 실패는 프로젝트 쿠킹 전체를 멈춘다. 3채널 이상 원본이 있는 프로젝트는 AU9 전까지 쿠킹하지 못한다.
- **서버 패키지**(한계): 3.11.5절은 서버 패키지에 오디오 payload를 넣지 않는다. 그런데 TargetProfile에는 아직 서버 여부·오디오 칸이 없어서, AU5에서는 서버용 쿠킹에도 payload가 들어간다. 개정 36: 이 제외는 텍스처와 같이 쓰는 프로파일 칸(UE `AllowAudioVisualData`)이 필요해 전용 서버 단계(BS7)로 미룬다(3.39.5절).
- **채널 마스크**: mono는 FC, stereo는 FL·FR이다(3.30.1절).

#### 3.37.3 `SoundClipCookProcessor`(AU5b, `AudioTools`)

`CookProcessor`를 구현하고 `SoundClip` 타입에 등록한다. 등록 함수는 `RegisterSoundClipCookProcessor`이고, Commandlet `ProductCookProcessors` 묶음에 더한다.

`Cook` 순서는 텍스처 처리기와 같은 모양이다.
1. **대표 `SoundClip`을 찾는다.** 원본이 없으면(`source.format` None·bulk 빔 — 메모리 생성 clip) `InvalidSource`·`NotReady`로 실패한다.
2. **원본 bulk를 읽어 planar float로 푼다.** 에디터 재생과 같은 함수를 쓴다. `AudioAssets`에 `DecodeSoundClipSource`를 두고 `LoadEditorPcm`도 이것을 쓴다(손상 `CorruptData`). 이 함수는 byte만 받으므로 `#if ROCKS_WITH_EDITOR_DATA` 밖에 둔다.
3. **codec을 정한다**(3.37.2절).
4. **쿠킹 배치(layout)를 계산한다.** 인코드와 떼어 둔 순수 함수 `ComputeCookedLayout(fields, codec)`이고, 적중·미적중 모두 같은 값을 쓴다. 적중이면 인코드가 없으므로, 위치 환산이 리샘플 단계 안에 있으면 7번에서 쓸 값이 없다.
   - 인코딩 rate: Opus는 48 kHz, PCM16·ADPCM은 원본 rate다. (개정 36: 3.39.3절 `SoundCookEncodingRate`가 대체 — PCM16·ADPCM은 대상 프로파일 재정의로 낮출 수 있다.)
   - 유효 frame: `CookResampledFrames`다(같은 rate면 그대로).
   - 위치: 파일 loop·`loopOverride`·cue·재생 loop 구간을 `CookResampledPosition`(동률은 짝수 — 3.11.2절)으로 바꾼다.
   - clip 전체 loop((0, 0))인지는 **환산 전 원본 값**으로 정한다. 환산 뒤 (0, 0)이 된 짧은 loop(96 kHz [0, 1) → 48 kHz)는 전체가 아니라 아래 정리로 [0, 1)이 된다.
   - loop 구간 정리: `begin = min(begin, frames − 1)`, `end = min(max(end, begin + 1), frames)`로 한다. 그러면 길이가 0이 되면 1 frame이 되고, begin이 끝으로 반올림돼도 frame 수를 넘지 않는다. 재생 loop·파일 loop·`loopOverride`에 같은 함수를 써서, 머리 loop와 필드가 늘 맞는다.
   - cue는 `min(position, frames)`로 자른다.
5. **너겟 키**(3.11.4절 — 로딩 동작 같은 재생 정책은 넣지 않는다)를 만든다.
   - 순서: 머리 `WriteNuggetKeyHeader(SoundNuggetProcessorId, 프로젝트 세대)` → TypeId → 원본 bulk SHA·byte 수·저장 형식·채널·rate·frame → 정한 codec → 재생 loop 구간(원본 rate) → 청크 배치(`targetChunkBytes`·`firstChunkBytes`) → `WriteNuggetEncoder(인코더 이름·판, 설정 byte)` → 쿠킹 리샘플러 판(쓸 때) → `AudioPlatformDataVersion`.
   - 인코더 판 문자열에는 `encoderVersion`·`bitstreamVersion`과 고정 SIMD 수준을 넣는다. 툴체인 지문에는 target triple만 있고 ThirdParty libopus의 SIMD define은 없기 때문이다.
   - (개정 36: 키에는 codec 뒤에 인코딩 rate가 들어가고, 품질은 대상 프로파일 배수를 곱한 실효 품질이다 — 3.39.4절.) 품질은 인코더 설정 byte에 넣는다. 품질을 쓰는 codec(Opus)만 넣고, PCM16·ADPCM은 빈 값이다. 그래서 품질만 바꿔도 PCM16·ADPCM은 적중한다.
   - 채널 처리는 원본 SHA와 채널 수가 이미 덮는다(AU5에는 채널 변환이 없다).
   - SCC 키는 텍스처처럼 `NuggetSccKey({assetId, 지역 키})`이고, 버킷은 새 `NuggetBucketAudio`(NuggetRecord.h 버킷 목록 옆)다.
   - 값은 하나다(플랫폼 데이터 byte).
6. **적중이면 수용 검사를 한다.** 텍스처 `CookAcceptHit`와 같은 역할이다.
   - `AudioPlatformDataView::Parse`가 성공해야 한다.
   - 머리의 codec·채널·채널 마스크·rate·유효 frame·loop가 4번 layout과 같아야 한다.
   - 하나라도 다르면 `Reject`한 뒤 다시 만든다. `verifyNuggets`면 다시 만들어 byte를 대조한다(다르면 진단).
   - **미적중이면 만든다.** (개정 36: 인코딩 rate가 원본과 다르면 리샘플하고, 인코드 전에 clip 정규화를 한다 — 3.39.4절.) 원본 PCM을 Opus·48 kHz가 아니면 쿠킹 리샘플러로 바꾸고(3.31절), `Pcm16Encoder`·`AdpcmEncoder`·`OpusAudioEncoder`로 인코드한 뒤 `WriteAudioPlatformData`로 byte를 만든다. 머리 loop는 layout의 재생 loop 구간이다(전체 loop면 0).
7. **쿠킹 패키지를 쓴다.** 에디터 객체에 쿠킹 값을 잠시 쓰되, 할당 없는 교환으로 한다. `cues`는 이름 `String`을 가진 배열이라, 원래 값을 복사해 두었다가 되돌리는 방식이면 복사·되돌리기 모두 할당 실패가 날 수 있다.
   1. 쿠킹 값을 모두 지역 변수에 먼저 만든다: `platformData`(`CookChainedBulkSource`에 더한 ref), `sampleRate`·`frameCount`(인코딩 rate·유효 frame), 파일 loop·`loopOverride`·cue(인코딩 rate 위치). 여기서 실패하면 객체는 손대지 않은 상태다.
   2. 객체 필드와 swap·move한다(실패하지 않는다).
   3. `WriteCookedPackage`를 부른다.
   4. 성공·실패와 상관없이 다시 swap한다(실패하지 않는다).
   - 쿠킹된 객체가 보는 위치는 모두 인코딩 rate 기준이다(3.30.1절 "cue는 쿠킹 필드").
8. **미적중이면 Put한다.** Conflict는 `NuggetConflict` 경고다.

정체성은 둘이다(텍스처와 같은 이유 — R-0).
- `SoundClipCookProcessorId`: 플랫폼 데이터 채우기 배치.
- `SoundNuggetProcessorId`: 너겟 값의 뜻.

`EditorOnly`(`source`)는 `WritePackage`가 뺀다.

#### 3.37.4 쿠킹 재생(AU5c)

- **`SoundClip::LoadCookedPcm(Allocator&, SoundBulkReader reader, void* context, const AudioDecoderTable&)`**: reader는 `Result<Span<const uint8>>(*)(void*, const BulkDataRef&)`이다(WorldIntegration `PlatformBulkReader`와 같은 모양 — 호출자가 `Package::BulkBytes`를 넘긴다). 동작:
  1. `platformData`를 읽는다.
  2. `AudioPlatformDataView::Parse` 뒤 `DecodeAudioPlatformData`로 전체를 디코드한다(청크 SHA 확인 포함).
  3. 결과로 재생 PCM(`SoundPcm`)을 만든다.
- **재사용**: 같은 ref(`SameContent`)를 이미 올렸으면 아무것도 하지 않는다.
  - 키는 흩어진 `editorPcm*` 필드에 칸을 더하지 않는다. 비리플렉션 `SoundPcmKey { origin(에디터·쿠킹), ref, format, channels, rate, frames }` 하나를 `ROCKS_NATIVE`로 두고 에디터·쿠킹이 함께 쓴다(AU4의 `SoundEditorPcmKey`를 대체한다).
  - 이 키는 `#if` 밖에 두므로 에디터 데이터 없는 빌드에서도 쓰인다(쓰지 않는 필드 경고가 없다).
- **머리 대조**: 머리의 채널·rate·유효 frame이 `SoundClip` 필드와 다르면 `CorruptData`다. 그대로 두면 재생 PCM 차원 검사(`FillPlayable`)가 원인 표시 없이 계속 `NotReady`를 낸다.
- **오류**:
  - `platformData` 없음(`NotReady`).
  - 형식·청크 손상, 머리·필드 불일치(`CorruptData`).
  - 디코더 없음(`NotFound` — `AudioOpus`를 링크하지 않은 실행).
  - 채널이 2보다 많음(`Unsupported`).
  - 읽기 오류.
- **부르는 쪽**: 에셋을 로드한 게임 코드가 부른다(`AssetManager::With`·`Package::BulkBytes`). 준비 티켓으로 자동화하고 청크 단위로 스트리밍하는 일은 AU6이다. 게임 스레드에서 동기로 디코드한다(한계 — 짧은 clip은 문제없고, 긴 음악은 AU6 전까지 로드 때 디코드 비용이 든다).

#### 3.37.5 시험

- **AU5a**:
  - 등록부 Set·지우기·`Fill`(이미 있는 codec은 유지).
  - `AudioOpus` 모듈이 등록부에 넣는다.
  - 엔진 디코더 표에 PCM16·ADPCM·(링크했으면) Opus가 있다.
- **AU5b**(6.2절 완료 기준):
  - 같은 입력이면 같은 플랫폼 데이터 byte다(두 번 쿠킹).
  - 설정(Opus 품질·codec·loop)이 바뀌면 새 키다(빌드 수가 오른다). 같은 설정은 적중이다(다시 연 캐시). PCM16은 품질만 바꾸면 적중이다.
  - 키에 넣지 않는 설정(`looping`·볼륨·cue 이름·로딩 동작)을 바꿔도 적중하고, 쿠킹 패키지에는 바뀐 값이 들어간다.
  - 미적중 쿠킹과 다시 연 캐시의 적중 쿠킹이 같은 쿠킹 패키지 byte를 낸다(44.1 kHz Opus, cue·loop 포함).
  - 적중 값이 손상되었거나 머리가 layout과 다르면 `Reject` 뒤 다시 만들고 Put한다. `verifyNuggets` 불일치는 진단이 나온다.
  - PlatformDefault 해석: 44.1 kHz에서 44099 frame은 ADPCM, 44100 frame은 Opus.
  - 44.1 kHz 원본의 Opus 쿠킹은 48 kHz다. loop·cue 위치 환산(동률 짝수, 길이 0 → 1, 끝 경계)을 확인한다. 48 kHz 원본 Opus는 리샘플하지 않고 위치가 그대로다. 44.1 kHz PCM16은 rate가 그대로다.
  - 쿠킹 패키지에 `source`가 없고 `platformData`가 있다. 쿠킹 뒤 에디터 객체는 원래 값이고, 쓰기 실패를 주입해도(잘못된 bulk 정렬) 원래 값이다.
  - 3채널은 실패하고, 원본 없는 clip도 실패한다.
- **AU5c**:
  - 쿠킹 → 로드 → `LoadCookedPcm` → 재생.
  - PCM16은 원본과 1 LSB 안이고, ADPCM·Opus는 디코드 허용오차 안이다(3.24·3.32절 값).
  - 손상 payload(청크 byte 하나 바꿈)와 머리·필드 불일치는 `CorruptData`다.
  - 디코더가 없으면 `NotFound`, 같은 ref는 다시 올리지 않는다.

#### 3.37.6 버린 안

- **`Audio` 모듈이 `AudioOpus`를 직접 링크**: Runtime → ClientOnly 의존이라 BD25가 막는다. 서버 빌드가 libopus를 끌어온다.
- **쿠킹 rate·위치를 별도 쿠킹 필드로 두기**(`cookedSampleRate` 등): 런타임 코드가 에디터·쿠킹 두 벌의 필드를 골라 읽어야 한다. 쿠킹 때 같은 필드를 인코딩 rate 값으로 바꿔 쓰면(텍스처가 `platformData`를 잠시 채우는 것과 같은 방식) 런타임은 한 벌만 본다.
- **너겟 키에 프로파일 id**: 플랫폼 결과가 같은데 플랫폼마다 따로 만든다. 프로파일 값은 AU5d에서 정규화된 설정으로만 키에 들어간다(텍스처와 같다).
