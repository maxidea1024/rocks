### 3.40 AU6 구현 세부 — 스트리밍 재생(개정 37)

AU5c는 쿠킹 clip을 로드할 때 플랫폼 데이터 전체를 게임 스레드에서 PCM으로 푼다(3.37.4절). 48 kHz 스테레오 3분 곡이면 PCM이 69 MB다(3.12.3절). AU6은 압축 데이터를 재생하면서 조금씩 푼다(실시간 디코드).

AU6 전체(06-Phases 표)는 sidecar 게시·청크 캐시·비동기 IO·준비 티켓을 포함한다. 그런데 선행 PR12(AssetSystem 개정 — 재생 준비 티켓·sidecar 범위 읽기)가 아직 없다. 그래서 둘로 나눈다.

| 단계 | 내용 | 선행 |
|---|---|---|
| AU6a1 | 믹서 스트림 원본: `AudioStreamRing`(SPSC planar PCM 링), 스트림 clip 등록, AudioRT 시작 대기·소비·굶음·스트림 실패 끝 | AU5 |
| AU6a2 | 청크 공급 인터페이스 `AudioChunkSource`(AU6a는 상주 구현), 스트림 생산자 `AudioStreamDecoder`, 디코드 서비스 `AudioStreamService`(전용 스레드·Inline 펌프) | AU6a1 |
| AU6a3 | EngineAudio 연결: `SoundClip::loadingBehavior`, 로드 때 디코드 방식 결정(통째·실시간), `LoadCookedStream`, 스트리밍 재생 경로·슬롯 회수, CVar, Sandbox | AU6a2 |
| AU6b | sidecar 게시, `AudioChunkCache`(같은 `AudioChunkSource` 뒤), 비동기 IO, 준비 티켓·`AssetLease`, 굶음 Skip 정책, RetainOnLoad·PrimeOnLoad의 캐시 의미 | AU6a, PR12 |

AU6a는 압축 데이터 전체를 메모리에 둔 채(패키지 bulk에서 공유 불변 버퍼로 복사) 실시간 디코드한다. 이것은 UE의 non-streaming 실시간 디코드(`DTYPE_RealTime` — `AudioDevice.cpp:7020–7030`)와 같은 모양이다. 그래서 PR12 없이도 PCM 전체를 풀지 않는다. 디코드 worker·링·시작 위치·loop·실패 경로도 sidecar 없이 시험할 수 있다. 대가로 압축 byte가 상주한다(Opus 128 kbps 3분 ≈ 2.9 MB). AU6b가 청크 캐시로 이것을 줄인다.

#### 3.40.1 믹서 스트림 원본(AU6a1)

**`AudioStreamRing`**(`Audio/AudioStreamRing.h`):
- 채널 1–2의 planar float 링이다. 용량은 frame 단위이고 만들 때 한 번 할당한다.
- 생산자 하나(디코드 서비스)와 소비자 하나(AudioRT)다. 쓰기 위치·읽기 위치는 단조 증가하는 uint64 원자값이고, 서로 다른 cache line에 둔다.
- 상태: `Running`·`Ended`(non-loop의 마지막 frame까지 썼다)·`Failed`(디코드·데이터 오류).
  - 상태는 쓰기 위치 word의 위 2 bit에 넣는다(아래 62 bit가 위치). 그래서 생산자의 Release 저장 하나로 PCM·위치·상태가 함께 보이고, 읽는 순서 문제가 없다.
  - `Ended` 불변식: non-loop면 Ended 때의 쓰기 위치 = frameCount − startFrame이다. 생산자는 디코더가 청크 frame 수와 다르게 내면 Ended 대신 Failed를 출판한다(`DecodeAudioPlatformData`와 같은 규칙).
- 생산자 API: `WritableFrames()`, `Write(PlanarConstView)`(쓰기 전에 유한성을 본다 — 비유한이면 쓰지 않고 `MarkFailed`, `RegisterClip`이 NaN을 막는 것과 같은 이유), `MarkEnded()`, `MarkFailed()`.
- 소비자 API(할당·대기 없음): `ReadableFrames()`, `Peek(frames, out)`, `Consume(frames)`, `State()`.
- 위치 초기화: 슬롯을 다시 쓸 때 제어 쪽만 위치를 0으로 돌린다(3.40.2절 회수 뒤). 서비스 Start 큐와 AudioRT 명령 큐의 Release로 넘어간다.
- 링 용량: 최소 `StreamRingMinFrames`(= 2 × `MaxBlockFrames` = 8192)다. 조각 하나가 요구하는 입력(`needed`)은 `MaxBlockFrames`(4096) 이하라서, 용량이 이보다 작으면 영구히 굶는다. CVar는 이 아래로 내려가지 않는다.

**스트림 clip**: `AudioMixer::RegisterStreamClip(AudioStreamClipDesc)`이다.
- desc 칸: 링 포인터, 채널, rate, 총 frame, **startFrame, loop 여부, loop 구간**.
- 생산자와 RT가 같은 값을 쓰도록 한 곳에 둔다. `PreparePlay`가 넘긴 startFrame·loop가 desc와 다르면 InvalidArgument다.
- SPSC라서 스트림 clip에는 voice가 하나만 묶인다. 이미 묶인 voice가 있으면(users > 0) `PreparePlay`가 InvalidArgument다.
- 상주 clip과 같은 `AudioClipId` 공간과 해제 규칙(`UnregisterClip` — 묶인 voice가 있으면 Busy)을 쓴다. 링 메모리는 해제가 성공한 뒤에만 돌려준다.

**AudioRT 소비**(`FillInput`·`AdvanceCursor`·`RenderVoice`의 스트림 갈래):
- **시작 대기**(UE `FMixerSource::IsPreparedToInit` — `AudioMixerSource.cpp:1011`이 첫 디코드까지 시작을 미루는 것과 같다):
  - Play 명령이 적용돼도, 링의 읽을 frame이 min(`StreamStartFrames`, 남은 원본 frame) 이상이 되거나 상태가 Ended·Failed가 될 때까지 voice는 시작하지 않는다.
  - 기다리는 동안은 출력도 cursor 진행도 없다. `startMixFrame`은 실제로 시작한 블록 frame이다.
  - 기다린 frame은 `streamStartDelayFrames`로 센다. 굶음(`streamStarvedFrames`)과는 따로 센다.
  - 그래서 Thread 방식에서도 첫 음이 거짓 굶음 없이 시작한다. Inline 시험은 렌더 전에 펌프해 지연 0을 만든다.
  - 기다리는 중 Stop이 오면 바로 끝난다(낼 소리가 없다).
- 링의 첫 frame은 desc의 startFrame이다. 생산자가 재생 순서대로 쓴다(loop면 감아서). 그래서 RT는 링을 앞에서부터 읽기만 하고, `sourceCursor`는 끝 판정·위치 보고에만 쓴다.
- non-loop의 원본 끝 뒤는 지금처럼 0 꼬리이고 링을 읽지 않는다. 필요한 링 frame 수는 min(needed, 남은 원본 frame)이다.
- **굶음**(링에 필요한 만큼이 없음):
  - 리샘플러에 `OutputFramesFor(availableInput)`(가진 입력으로 낼 수 있는 출력 frame 수)를 더한다. 낼 수 있는 만큼 정상으로 내고, 나머지 구간만 무음으로 둔다.
  - 무음 구간에서는 리샘플러·cursor·필터를 움직이지 않는다(이어 재생 — 3.12.3절 Pause 정책). 그래서 param이 일정하면, 굶은 출력은 굶지 않은 출력 사이에 0 구간만 끼운 열과 bit까지 같다.
  - 그 frame 수를 `AudioMixerCounters::streamStarvedFrames`에 더한다(`CounterSnapshotWords`도 늘린다).
  - **Stopping**(fade 중)인 voice는 굶은 구간에서도 fade를 무음으로 진행하고 fade 끝 판정을 한다. 그래서 생산자가 멈춰도(긴 hitch, 서비스가 먼저 종료) Stop·StopAll·종료 drain이 끝난다. 자연 끝 판정만 PCM이 올 때까지 미룬다.
- **Ended인데 모자람**: 상태가 Ended인데 남은 원본 frame만큼의 PCM이 링에 없으면(불변식 위반) `StreamFailed`로 끝낸다. 영구히 굶지 않게 한다.
- **스트림 실패**: 상태가 `Failed`이고 읽을 PCM을 다 냈으면 voice가 새 terminal 사유 `AudioVoiceEndReason::StreamFailed`로 끝난다.
- **refill 알림**: 블록을 렌더한 뒤, 상태가 `Running`인 스트림 링의 읽을 frame이 refill 수위(용량의 절반) 아래면 생성 때 받은 `RealtimeWakeSignal`을 Signal한다.
  - 이 신호는 렌더 깨우기와 다른 인스턴스다.
  - Signal은 Exchange 하나라 잠금이 없고(3.2절), 시스템 호출은 디코드 스레드가 잠들어 있을 때만 난다.
  - 신호가 없으면(Inline 시험) 아무것도 하지 않는다.

#### 3.40.2 청크 공급·생산자·서비스(AU6a2)

**`AudioChunkSource`**(`Audio/AudioChunkSource.h`): 생산자가 청크 payload를 얻는 인터페이스다. AU6b의 청크 캐시가 같은 자리에 들어가므로 지금 둔다.
- `TryAcquire(index)` → Ready(span)·Pending·Failed, `Release(index)`, `Prefetch(index)`다.
- 계약:
  - Ready가 준 payload는 **검증된 것**(크기·SHA-256 — `VerifyAudioChunk`)이다.
  - Release할 때까지 산다(디코더 `BeginChunk`의 "청크를 다 낼 때까지 산다" 계약).
- AU6a 구현 `ResidentAudioChunkSource`:
  - 상주 byte로 바로 Ready를 낸다.
  - 검증은 로드 때 한 번 한다(`LoadCookedStream`이 모든 청크에 `VerifyAudioChunk` — 실패는 CorruptData, `LoadCookedPcm`과 같다).
  - Pending은 내지 않는다. 생산자는 Pending이면 그 Pump에서 쓰지 않는다(AU6b 경로).

**`AudioStreamDecoder`**(`Audio/AudioStreamDecoder.h`): 디코더 하나로 링을 채운다.
- 입력: `AudioPlatformDataView`(머리·청크 표), `AudioChunkSource`, 열린 디코더 하나, desc의 startFrame·loop 여부·loop 구간.
- **디코더 생성·Open**은 제어 스레드의 `Start` 안에서 한다. `AudioDecoderTable`은 "제어 쪽에서만 쓴다"(3.30.2절)이고, Open 오류(Unsupported·CorruptData)가 그 재생의 실패로 바로 나간다.
- **시작**: 시작 frame s의 codec frame은 s + encoderDelay다. 그 frame을 담은 청크를 찾아 `BeginChunk(chunk, payload, s + delay)`를 부른다. Opus는 320 ms pre-roll로 수렴한 근사이고(시작 패킷이 스트림 패킷 0–16이면 연속 디코드와 bit까지 같다), 같은 시작은 늘 같은 표본이다(3.32.4절). PCM16·ADPCM은 정확하다.
- **순차 진행**: 청크 끝에서 `ContinueChunk`로 상태를 이어 연다. 그래서 순차 출력은 전체 디코드와 bit까지 같다(3.30.2절). 출력은 유효 frame 구간(앞 delay·끝 padding을 자른 구간)만 링에 쓴다.
- **loop**(UE는 디코더 하나로 `PrepareToLoop` — `AudioDecompress.cpp:574`):
  - loop 끝에 닿으면 그 frame까지 쓰고, 남은 scratch PCM은 loopEnd에서 버린다.
  - 같은 디코더로 `BeginChunk(loop 시작 청크, payload, loopStart + delay)`를 다시 부른다.
  - Opus pre-roll 17패킷 디코드(1 ms 미만)를 링(기본 약 170 ms)이 흡수한다. `BeginChunk`는 결정적이라 이음매 뒤 PCM은 늘 같다.
  - 3.11.3절의 "loop 머리 PCM을 voice 링 옆에 둔다"(`LoopHeadFrames`)는 이 방식으로 대체한다.
  - 짧은 loop의 비용 상한: loop 길이가 `StreamMinLoopSeconds`(= 1 s, 인코딩 rate frame)보다 짧은 looping clip은 바퀴마다 pre-roll을 디코드하는 비용이 커진다. 그래서 로드 때 통째 디코드로 돌린다(3.40.3절).
- **`Pump(budget)`**:
  - 링에 빈 칸이 있는 동안 단위(`MaxFramesPerCall`)를 디코드해 쓴다.
  - 디코드한 단위가 빈 칸보다 크면 남은 부분을 내부 scratch에 두었다가 다음 Pump에서 먼저 쓴다.
  - 할당은 만들 때만 한다(scratch).
- **끝·실패**:
  - non-loop가 마지막 유효 frame까지 쓰면 `MarkEnded()`다.
  - 디코더 오류(`CorruptData` 등), 청크 Failed, 비유한 표본은 `MarkFailed()`이고 그 뒤로는 쓰지 않는다.

**`AudioStreamService`**(`Audio/AudioStreamService.h`): 스트림 슬롯 표와 디코드 실행이다.
- 슬롯은 고정 개수(`audio.stream.maxstreams`)이고, 슬롯마다 링(용량 `audio.stream.ringframes` × 2채널)을 만들 때 미리 잡는다.
- 제어 쪽(제어 pipe 스레드)이 `Start(slot, …)`(디코더 Open 포함)·`Cancel(slot)`을 SPSC 큐로 넘긴다.
  - 큐 용량은 2 × maxstreams다. 슬롯마다 Start·Cancel이 하나씩만 대기하므로 넘치지 않는다.
  - Start와 Cancel 모두 디코드 스레드를 깨운다.
- 서비스는 작업이 끝나거나 취소되면 슬롯을 "반납 가능"으로 출판한다. 디코더·청크 공급자 참조(`SharedPtr<SoundStreamData>` 포함)는 제어 쪽 슬롯 기록이 쥐고, 회수 때 제어 스레드에서 놓는다.
- **슬롯 재사용 규칙**(늦은 완료가 새 작업 링에 섞이지 않게 — 3.12.3절 "(voice generation, seek 번호) 불일치로 버린다"의 구현):
  1. 믹서가 clip 해제에 성공했다.
  2. 서비스가 반납을 출판했다.
  3. 회수는 제어 쪽만 한다.
  - 재생마다 새 슬롯이므로 앞 작업의 PCM은 앞 링에만 간다.
- **실행 방식**:
  - Thread(기본): 전용 `platform::Thread`("AudioDecode", `ThreadPriority::AboveNormal`)다.
    - 활성 슬롯이 있으면 `RealtimeWakeSignal`을 `StreamPumpTimeoutMs`(= 10 ms) 시한으로 기다리고, 없으면 시한 없이 기다린다(모바일 전력).
    - 깨면 큐를 처리하고, 읽을 frame이 적은 슬롯부터 `Pump`한다.
  - Inline: 스레드 없이 호출자가 `PumpAll()`을 부른다. 엔진 Inline 제어 방식에서는 제어 묶음 처리가 `PumpAll`을 부른다. 그래서 엔진 Inline 시험이 따로 훅 없이 결정적이다.
  - `Flush()`(시험·진단): 큐를 처리하고, 모든 활성 슬롯을 가득·Ended·Failed까지 채운 뒤 이벤트로 알린다. Thread 방식 시험은 이 gate로만 순서를 만든다(시간 대기 금지).
  - 전용 스레드를 쓰는 이유: AudioRT는 작업을 제출할 수 없다(할당·잠금 금지 — 3.2절). 제어 pipe는 게임 프레임마다 한 번만 돌아서 게임 프레임이 늦어지면 링이 굶는다. 그래서 refill은 게임 틱과 떨어져 있어야 한다.
- **종료 순서**(3.8절 개정):
  1. 믹서 drain(stop-all → 꼬리).
  2. 스트림 clip 해제.
  3. 서비스 Cancel 전부.
  4. 디코드 스레드 join.
  5. 슬롯 회수.
  - 굶은 Stopping voice도 fade가 끝나므로 1번이 막히지 않는다.

#### 3.40.3 EngineAudio 연결(AU6a3)

**로드 때 디코드 방식 결정**(UE `AudioDevice.cpp:7020–7099`):

| `loadingBehavior`(UE 다섯 값, 기본 `Inherited`) | 결정 |
|---|---|
| `ForceInline` | 스트리밍하지 않는다. 길이가 `audio.decompress.maxseconds`(기본 5 s — UE SoundGroup Default `DecompressedDuration`) 미만이면 통째 디코드(`LoadCookedPcm`, UE `DTYPE_Native`), 아니면 상주 압축 실시간 디코드(`LoadCookedStream`, UE `DTYPE_RealTime`)다. |
| `RetainOnLoad`·`PrimeOnLoad`·`LoadOnDemand` | 스트리밍한다(UE `IsStreaming` — `SoundWave.cpp:4118`). AU6a는 상주 압축 실시간 디코드이고, 첫 청크를 붙잡는 차이는 청크 캐시가 생기는 AU6b에서 나뉜다. |
| `Inherited` | CVar `audio.stream.defaultloading`(기본 `LoadOnDemand` — UE `au.streamcache.SoundWaveDefaultLoadingBehavior` 기본, `SoundWave.cpp:59`)이다. 분류 계층(SoundCategory)은 AU7에서 사이에 들어간다. CVar는 로드 때만 반영된다. |

- looping clip의 loop 길이가 `StreamMinLoopSeconds`보다 짧으면 모든 동작에서 통째 디코드다(3.40.2절 비용 상한).
- `SoundClip::LoadCooked(Allocator&, SoundBulkReader, void*, const AudioDecoderTable&)`가 위 결정을 하고 `LoadCookedPcm` 또는 `LoadCookedStream`을 부른다. 게임 코드는 이것 하나를 부른다.
- **`SoundClip::LoadCookedStream`**:
  - 플랫폼 데이터 byte를 공유 불변 버퍼 `SoundStreamData`(`SharedPtr<const SoundStreamData>` — byte 사본 + `Parse`한 보기 + 청크 검증 완료)로 복사한다.
  - 머리·필드 대조는 `LoadCookedPcm`과 같다. 재사용 키도 같은 `SoundPcmKey`를 쓴다(origin `CookedStream`).
  - 패키지가 재생 중에 내려가도 스냅숏이 버퍼를 붙잡는다.
- **`SoundPlayable`**:
  - `pcm`과 `stream` 중 하나를 쓴다.
  - 채널·rate·frame 수를 pcm과 따로 둔다(`channels`·`sampleRate`·`frames`). 스트림 재생에서 `pcm->` 역참조가 없게 한다(`UpdateSpatial`, `AcquireClip`, `SoundSourceRef::TryCreate`의 검사).
  - `SoundSourceRef::TryCreate`는 둘 중 하나가 있어야 하고, 유한성 검사는 pcm에만 한다(스트림은 생산자가 본다).
- **제어 쪽 재생**(순서):
  1. AcquireVoice.
  2. 스트림 슬롯을 잡는다.
  3. `Start`(디코더 Open).
  4. `RegisterStreamClip`(재생마다 ClipEntry 하나 — pcm 포인터 기준 공유를 건너뛴다).
  5. `PreparePlay`.
  - 실패하면 거꾸로 되돌린다(Cancel·슬롯 회수).
  - 슬롯이 없으면 그 재생은 `Ended(VoiceLimit)`로 끝나고 계수 `streamSlotRejects`가 오른다. 3.35절에서 `Ignored`는 장치 없음이라 따로 둔다.
  - voice가 끝나면: `UnregisterClip` → `Cancel` → 반납 확인 → 슬롯 회수.
  - `CollectTerminals`는 `StreamFailed`를 재생 결과 `Failed`로 옮긴다.
- **에디터 재생**은 바뀌지 않는다(`LoadEditorPcm` — 원본 PCM 전체).
- **seek**: 재생 중 seek API는 두지 않는다. 다른 위치부터 들으려면 새 재생을 연다(`PlayOptions::startFrame`). UE도 `UAudioComponent::PlayInternal`이 재생 중이면 `Stop()` 뒤 다시 연다.
- **CVar**:
  - `audio.stream.ringframes`(기본 `StreamRingMinFrames` 8192 — 48 kHz 약 170 ms, 아래로 못 내림).
  - `audio.stream.maxstreams`(기본 `MixerVoiceHeadroomFactor × audio.voices.max` = 64).
    - voice는 terminal 때 활성 수에서 바로 빠지지만, 슬롯은 해제·Cancel·반납을 거쳐 2–3 묶음 뒤에 풀린다. 그래서 voice 상한보다 넉넉히 둔다.
    - UE는 기본 `LoadOnDemand`라 쿠킹된 효과음이 모두 스트리밍된다.
  - `audio.stream.defaultloading`, `audio.decompress.maxseconds`.
  - 메모리: 링은 8192 × 2 × 4 B = 64 KiB, 64 슬롯이면 4 MiB(+ 재생 중 디코더 상태)다.

#### 3.40.4 시험

- **AU6a1**(Inline, 손으로 채운 링):
  - 링이 차 있으면 상주 clip과 같은 PCM을 낸다.
  - 굶으면 낼 수 있는 만큼 내고 나머지만 무음이다. 이어진 출력은 굶지 않은 출력에 0 구간만 끼운 열과 bit까지 같다(param 일정). `streamStarvedFrames`를 센다.
  - 시작 대기 동안 출력이 없고, 수위가 차면 그 블록에 시작한다(`startMixFrame`·`streamStartDelayFrames`).
  - 굶은 Stopping voice가 fade 길이 뒤에 끝난다.
  - non-loop 끝 꼬리, loop 감기, Ended인데 모자람 → `StreamFailed`, Failed 뒤 남은 PCM을 다 내고 `StreamFailed`.
  - desc와 다른 startFrame·loop, 두 번째 voice 묶음은 InvalidArgument다. refill 신호는 Running·수위 아래에서만 울린다.
- **AU6a2**:
  - 순차 출력은 `DecodeAudioPlatformData` 전체 디코드와 bit까지 같다(PCM16·ADPCM·Opus, 청크 여러 개).
  - 시작 frame s: PCM16·ADPCM은 전체 디코드의 [s, …)와 같고, Opus는 같은 s를 두 번 시작하면 같다.
  - loop:
    - 이음매 앞은 전체 디코드와 같고, 이음매 뒤는 loop 시작에서 새로 연 출력과 같다(여러 바퀴, 링·scratch 경계가 이음매와 겹치는 경우 포함).
    - Opus 전체 loop(loopBegin = 0)는 상주 loop(`LoadCookedPcm`)와 bit까지 같다(시작 패킷 0–16은 정확).
    - 중간 loop 이음매의 오차는 3.32.4절 측정값 2.5e-5 이하다.
  - 손상 청크·비유한 표본은 Failed다. 취소한 작업은 더 쓰지 않는다. 반납 전에는 슬롯을 다시 내주지 않는다(Thread 방식, `Flush` gate).
- **AU6a3**:
  - 쿠킹 Opus 3분 clip(LoadOnDemand)을 스트리밍 재생하면 재생 PCM을 할당하지 않는다(SoundClip에 PCM 없음).
  - startFrame을 바꿔 가며 100번 다시 재생해도 allocator 최대 사용량이 상한 안이다.
  - `ForceInline` 5초 미만은 통째, 이상은 실시간이다. 짧은 loop는 통째다. `Inherited`는 CVar를 따른다.
  - 슬롯이 다 차면 `Ended(VoiceLimit)`와 `streamSlotRejects`가 나온다.
  - 종료 drain이 굶은 스트림 voice로 막히지 않는다.

**완료 조건 배분**(06-Phases AU6 행):
- AU6a 몫: "늦은 완료 폐기"(슬롯 재사용 규칙), "Opus loop 이음매 불연속 없음"(위 loop 시험), "100회 seek 메모리 상한"(seek = 새 재생이므로 100회 재생의 allocator 최대값).
- AU6b 몫: "3분 곡 첫 음 전 전체 read 없음" — AU6a는 로드 때 전체를 읽는다.

#### 3.40.5 버린 안

- **AudioRT가 디코드를 직접**: 디코드 비용이 블록 마감 안에 들어오지 않을 수 있다(Opus 다채널). 디코더 Open은 할당도 한다.
  - UE 렌더 스레드는 디코드 작업의 완료를 기다린다(`ProcessRealTimeSource`의 `EnsureCompletion` — `AudioMixerSourceBuffer.cpp:550`). 그래서 UE는 굶는 대신 멈춘다.
  - Rocks AudioRT는 기다리지 않는다(3.2절). 대신 링이 모자라면 굶는다(7절 차이).
- **제어 pipe에서 refill**: 게임 프레임에 묶여 있어, 로딩 같은 긴 프레임에서 링이 굶는다.
- **`WorkerScheduler` 작업으로 refill**: AudioRT가 작업을 제출하려면 할당이 필요하다. 3.2절 표의 "디코드·IO worker — WorkerScheduler"는 AU6b의 IO 완료 처리에 남긴다.
- **loop 디코더를 미리 하나 더 열기**(초안): 이음매 지연은 없지만 디코더 메모리가 두 배다. 디코더 하나로 다시 여는 비용(Opus 17패킷)은 링이 흡수하고, `BeginChunk`가 결정적이라 출력도 같다.
- **loop 머리 PCM 사본**(3.11.3절 원안): 디코더를 다시 여는 방식이 PCM 사본 없이 같은 결과를 낸다.
- **재생 중 seek(링 비우기)**: RT와 생산자 사이에 링 세대 교체가 필요하다. UE도 다시 시작하므로 새 재생으로 둔다.
- **슬롯이 없을 때 `Ignored`**: 3.35절의 Ignored는 장치 없음 하나만 뜻한다.

#### 3.40.6 남는 것

- 굶음은 voice와 믹스 시계를 어긋나게 한다. 박자 맞춘 음악(BeatClock — AU10) 전에 Skip 정책(AU6b)이 필요하다.
- `AssetLease`(3.8절·3.35절)는 AU6b의 준비 티켓과 함께 넣는다.
