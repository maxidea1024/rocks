## 8. 렌더 그래프 단계와 완료 기준

공통: CPU 시험은 장치 호출을 기록만 하는 기록 backend로 결정적으로 단언한다. GPU 시험은 검증 계층 오류 0(D3D12 debug layer, Vulkan validation, GL debug output — `ValidationErrorCount`, `Device.h`)과 Sandbox self-test 픽셀 대조(채널 ±8, 2%)다.

| 단계 | 내용 | 선행 | 완료 기준 |
|---|---|---|---|
| RG1 | 최소 그래프: 단일 graphics queue, aliasing·병합 끔, 단일 스레드 기록. 자원 생성·import·export, 파라미터 구조체 의존, 점진 culling, 참조 수 수명, 프레임 간 desc 풀과 축출, subresource 상태 추적과 읽기 상태 병합, prologue 즉시 전이, 즉시 실행 모드, 검증, 이벤트 구간 | RB4·RB7·GX1·GX2·GX4·GX5·CP3 | (a) 미사용 체인 제거와 `HasSideEffects`·외부 출력·export 보존 (b) 기대 전이 열 일치, 읽기→읽기 전이 0, UAV→UAV는 생략 표시가 없을 때만 (c) 할당·해제 pass 번호 (d) 즉시·지연 모드 명령 열 동치 (e) 음성 검증: 생산 전 읽기, 한 pass 안 상충 접근, Raster pass의 UAV, `Retire`된 자원 import (f) 풀 축출이 fence 완료 전에는 일어나지 않음(fence gate) (g) D3D12·Vulkan·GLES 미리보기 픽셀 대조 |
| RG2 | 프레임 안 풀 재사용(수명이 겹치지 않는 같은 desc), begin·end 분리 전이, 그래프 안 업로드 | RG1·GX8 | 겹치지 않는 수명의 같은 desc 자원이 실제 객체 하나를 공유, 분리 전이의 begin·end 위치가 기대 열과 일치(native split 없는 backend는 end 하나로 낮춘 열과 일치), 분리 전후 픽셀 동일 |
| RG3 | 병렬 기록, render pass 병합(같은 attachment 연속 raster pass, UE `r.RDG.MergeRenderPasses` — subpass 없음, 개정 40) | RG2·CP2·GX11 | 병렬·직렬 결과 동일, 병합 구간 전이 0, GLES에서 병합 켬·끔 픽셀 동일 |
| RG4 | async compute overlap(fork/join, 수명 연장, 병합과 배타) | RG3·GX1(async compute 표시) | 계획 API06 직렬·비동기 결과 일치, 실제 queue 겹침 계측. 설계·구현: 아래 "RG4 async compute 설계(개정 32)"(D3D12·그래프 구현, Vulkan compute queue 경로는 maintenance9 장치에서 후속) |
| RG5 | transient aliasing. 지원하지 않는 backend는 풀 | RG4·GX12 | alias 켬·끔 픽셀 동일, transient 최대 사용량 감소 계측, 검증 오류 0. 설계·구현: 아래 "GX12·RG5 transient aliasing 설계(개정 33)"(D3D12·Vulkan, async 자원 aliasing은 설정으로만) |
| (결정 R6) | copy queue | — | 확정(개정 32): 그래프 밖 업로드·스트리밍 계층. 그래프 단계 없음 |

**구현(2026-11-17, RG1).** 새 모듈 `Engine/Source/Runtime/RenderGraph`(의존 RenderBase·Graphics·TraceCapture, 3절 배치). 계약은 [렌더 기반 구현](../../Implementation/RenderBase.ko.md) 9절이다. 선행 가운데 RB4(파라미터 구조체)·GX1·GX2·GX4는 아직 없으므로 범위를 줄여 앞당겼다(사용자 지시 "렌더 그래프도 미리 하자").
- 내부 접근 모델: pass마다 자원 접근 목록(`GraphResourceAccess`: 자원·subresource 범위·접근 상태·`NoUavBarrier` 표시)과 렌더 타깃 하나. 지금은 명시 선언 builder `GraphPassAccesses`가 목록을 만든다. 파라미터 구조체(결정 R4, 9.6절)가 들어오면 구조체 layout을 훑는 수집기가 같은 목록을 만들어 형식 지운 진입점 `RenderGraph::AddPassWithAccesses`로 넣는다(UE도 내부는 접근 목록이다, `RenderGraphBuilder.cpp:2384–2532`). 그래서 culling·수명·전이·검증은 수집 경로와 무관하다.
- 완료 기준 상태:
  - (a) 구현·시험: 점진 culling(부수 효과·스왑체인 타깃·import 자원 쓰기는 AddPass 때, export 마지막 생산자는 Execute 때 살린다), 생산자 체인 보존.
  - (b) 구현·시험: 기대 전이 열(attachment 포함), 읽기 → 읽기 전이 0(연속 읽기를 한 상태로 합쳐 첫 pass에서 한 번), UAV → UAV는 생략 표시가 둘 다 없을 때 UAV barrier, mip 범위별 추적과 연속 mip 묶기, 장치에 내린 열 일치와 기록 장치 검증 오류 0.
  - (c) 구현·시험: 첫·마지막 사용 pass와 참조 수(`GraphLifetime`), 제거된 pass는 수명에 들지 않음.
  - (d) 구현·시험: 동치를 "전이를 뺀 장치 호출 열이 같고, 두 모드 모두 각 pass가 맞는 상태를 보며(기록 장치 검증 오류 0), 최종 상태가 같다"로 정했다. 읽기 병합은 앞을 내다봐야 하므로 즉시 모드는 전이가 더 많다. 병합이 없는 그래프는 전이까지 같다.
  - (e) 구현·시험: 생산 전 읽기, 한 pass 안 상충 접근, Raster pass의 UAV, Retire된 자원 import(lease 실패), 그 밖에 생산 전 export·다른 그래프 handle·pass 종류 위반.
  - (f) 구현·시험: 풀 축출은 마지막 사용 fence가 끝나기 전에는 일어나지 않는다(기록 장치 `HoldCompletions`·`CompleteAll` gate).
  - (g) D3D12(하드웨어·WARP)·D3D11(하드웨어·WARP)·OpenGL ES 미리보기(ES 3.2 profile·GL 4.3 core context)·Vulkan(GTX 1060·lavapipe, 검증 층 켬)에서 Sandbox self-test 픽셀 대조(그래프 텍스처 → SRV 합성, culling, history export → import)와 검증 오류 0(D3D12·Vulkan은 전이 before 불일치 포함).
- 스펙과 다르게 한 점:
  - 의존 선언은 파라미터 구조체가 아니라 명시 접근 목록이다(위). 결정 R4는 그대로이고 수집기가 같은 목록을 만든다.
  - GX5는 최소 범위다: begin·end 분리 전이와 pipe가 없고, Raster pass 렌더 타깃 전이(attachment)는 장치 `BeginOffscreen`·`BeginFrame`이 낸다(GX4 attachment 시작이 기록 안으로 들어오면 그래프가 `Transition`으로 낸다). 만든 자원의 첫 전이 before는 `Unknown`(내용 불필요, 장치 추적 상태)이다.
  - 실행 단위: Raster pass마다 장치 기록 하나를 열고(`BeginOffscreen`은 clear만 한다), Compute·Copy pass는 열린 기록에 이어 쓴다. 열린 기록이 없는 Compute·Copy pass와 attachment load(`GraphLoadAction::Load`)는 `Unsupported`다(GX4).
  - 자원 desc는 지금 Graphics desc 그대로다(형식은 [픽셀 형식](../PixelFormat/14-ImplementationStages.ko.md) PF1의 `PixelFormat`). 그래프 텍스처는 RenderTarget 용도·번호표 안의 비압축 형식만, import 텍스처는 mip 수를 `GraphImportOptions::mipLevels`로 받는다(장치에 desc 조회가 없다). 풀 byte 추정은 `PixelFormatInfo` 기준 `MipChainBytes`다. GX2(차원·array·샘플 수·버퍼 용도) 뒤에는 풀 키 비교 함수와 desc 검사만 넓히면 된다.
  - 풀 키에 샘플러를 넣었다(7.4절은 제외). 지금 장치는 텍스처 desc의 샘플러로 묶으므로 빼면 다른 샘플러로 읽힌다. 결정 R12의 바인딩 때 샘플러 지정이 들어오면 뺀다.
  - 해제 pass 번호는 계산·진단만 하고 풀 반환은 그래프 끝이다(프레임 안 재사용은 RG2 완료 기준이다).
  - import lease는 `RenderHandleTable`에 두었다(`AcquireLease`·`ReleaseLease`·`TakeReleasedRetire`, RB2의 `DeviceResourceOwner` 전). lease가 남은 handle의 Retire는 장치 Retire를 미루고 렌더 lane이 lane 작업 끝에 잇는다. export는 새 `RenderHandle`로 소유를 넘기고 그 handle의 Retire가 수명을 정한다.
  - 검증은 모든 구성에서 켜져 있고 실패하면 그래프 전체를 버린다(UE는 디버그 빌드 검사). 그래프 설정 변수(CP4 연결: 즉시 모드·검증 전환)는 아직 없다.
  - `GraphSharedData`(7.3절)는 넣지 않았다.
  - GPU 계측: 그래프의 장치 기록 전체를 GPU 프레임 하나로 묶는다(첫 기록에서 `GpuTrace::BeginFrame`, 마지막 기록에서 `EndFrame`). pass마다 `CpuScope`와 `GpuScope`(pass 이름은 정적 `TraceScopeName`)를 둔다(13.3절 스펙과 다른 점 (4) 해소).
  - 렌더 lane 연결: `RenderFrameContext::Arena()`(그 slot의 FrameArena)를 더했다. 그래프 수명 표는 그 arena에 두고, pass 함수(람다)는 그래프 파괴 때 렌더 lane에서 부순다(arena Reset은 게임 lane에서 일어나기 때문이다).
- 남은 것(RG1): 그래프 설정 변수(CP4), 캡처 도구 수동 확인 기록(13.3절). 그래프 attachment resolve와 그래프 구간 `GraphScope`·번호 trace 표지는 개정 28에서 넣었다(아래 "RG1 남은 것 설계 2"). attachment 기록·렌더 타깃 없는 기록·풀 desc 확장·`GraphTextureView`·`GraphSharedData`·`SceneTextureTable`(`GraphViewTable`)은 개정 26에서 넣었다(아래 "구현(2026-11-19, RG1 남은 것 A–C부)"). export 성공 조건(검증 실패 그래프의 export handle은 Failed)은 RG1에 이미 있다. export한 풀 자원의 fence 뒤 풀 반납(결정 R15)과 Vulkan 픽셀 대조는 끝났다(아래 RG2 구현, 4.4절 GX5 Vulkan).

**파라미터 구조체 수집기(개정 57, 셰이더 시스템 16.2절 SH3c).** 구현했다: `CollectGraphPassAccesses`가 생성 파라미터 구조체의 그래프 멤버를 훑어 명시 선언 builder와 같은 접근 목록을 만들고, 구조체 판 `AddPass`가 그 목록으로 `AddPassWithAccesses`를 부른다(UE `SetupPassResources`). 셰이더가 쓰지 않는 멤버는 자원 지도로 거른다(9.6절). 완료 기준 동치 시험 `RenderGraph_ParameterStructCollectorMatchesExplicitAccesses`(두 경로의 기록 장치 명령 열 동일).

**RG1 남은 것 설계(개정 26).** SH2·RB4·P7·CP4에 기대지 않는 부분을 세 부분으로 나눠 넣는다. 파라미터 구조체 수집기(RB4·SH2·P7)·그래프 설정 변수(CP4)·캡처 도구 수동 기록은 그대로 남는다.
- **A부: attachment 기록과 풀 desc 확장.**
  - 그래프 Raster pass는 장치 `BeginPass`로 연다(`BeginOffscreen` 대신). `GraphRenderTarget`이 색 attachment 0–8(`GraphColorTarget`: 텍스처·load·clear·mip·slice)과 깊이 attachment 하나(`GraphDepthTarget`: 텍스처·깊이·스텐실 load와 clear 값·`readOnly`·mip·slice)를 갖는다. builder는 `RenderTarget`(색 하나를 덧붙임, 기존 호출과 같은 뜻)·`ColorTarget`·`DepthTarget`이다. load `Load`는 attachment를 읽는 것으로도 세어 생산 전 읽기 검사를 받는다(RG1의 `Unsupported`를 없앤다). store는 늘 `Store`다(뒤 pass가 쓰지 않는 attachment의 `DontCare`는 후속 최적화). 깊이 접근은 `DepthWrite`, `readOnly`면 `DepthRead`다.
  - attachment는 그 subresource(`AttachmentSubresource`) 하나의 접근이고 전이는 장치 `BeginPass`가 낸다(접근 기록에 attachment 표시를 두어 그래프는 그 전이를 내지 않는다, RG1의 "렌더 타깃 mip 0" 규칙의 일반화). 같은 (텍스처, mip, slice)를 두 attachment로 붙이면 검증 오류다.
  - 렌더 타깃이 없는 Compute·Copy pass는 열린 기록이 없으면 attachment 없는 `BeginPass`로 기록을 연다(RG1의 `Unsupported`를 없앤다).
  - 풀·그래프 텍스처 desc: 렌더 타깃은 모든 차원과 mip 사슬, 깊이(`DepthStencil`)·`Storage` 그래프 텍스처, MSAA(`sampleCount`)를 받는다. 풀 키에 `sampleCount`를 더한다(차원·깊이·층·mip은 이미 키에 있다). 깊이·Storage는 초기 픽셀이 없다.
  - attachment resolve(`ColorAttachment::resolveTarget`)는 그래프에 아직 넣지 않는다. resolve 뒤 원본·대상의 장치 상태가 backend마다 다르므로(D3D12 RESOLVE_SOURCE·셰이더 읽기, Vulkan TRANSFER_SRC·DST) 그래프가 상태를 추적하려면 장치 계약을 먼저 맞춰야 한다. 장치 쪽 resolve 뒤 상태를 정하는 작업과 함께 넣는다.
- **B부: `GraphTextureView`.** (텍스처, mip 범위, slice 범위, SRV·UAV) 그래프 view를 장치 텍스처 view로 낮추고 접근은 그 범위의 subresource만이다. 겹치는 범위의 SRV·UAV는 한 pass 안 상충이다. GLES는 `TextureViewBaseMip`을 pass 문맥에서 준다.
- **C부: `GraphSharedData`·`SceneTextureTable`과 history export 확인.** 7.5절 규칙대로 넣고, history export 규칙(결정 R15)은 RG2에서 들어간 것을 시험으로 확인한다.

**구현(2026-11-19, RG1 남은 것 A–C부).** 위 설계대로 넣었다. 계약은 [렌더 기반 구현](../../Implementation/RenderBase.ko.md) 9절이다.
- **A부.** `GraphColorTarget`·`GraphDepthTarget`과 builder `RenderTarget`(색 하나 덧붙임)·`ColorTarget`·`DepthTarget`. 색이 `MaxColorTargets`를 넘으면 builder가 개수만 하나 넘겨 두고 `AddPass`가 검증 오류로 거부한다(builder 오류 코드가 아니라 그래프 검증 오류로 세기 위해서다). attachment 접근은 `AttachmentSubresource`의 subresource 하나이며 `SubresourceUse::attachment` 표시로 전이를 장치 `BeginPass`에 맡긴다(RG1의 "렌더 타깃 mip 0" 규칙 대체). 색 attachment의 용도는 `RenderTarget`, 깊이는 `DepthStencil`이어야 하고(import는 대조하지 않는다) 범위는 `IsAttachmentInRange`로 본다. load `Load`·깊이 `readOnly`는 생산 전 읽기 검사를 받는다. `DontCare`는 장치 `LoadAction::DontCare`로 그대로 낮춘다(RG1의 "clear로 낮춤"을 없앴다). 렌더 타깃 없는 Compute·Copy pass는 열린 기록이 없으면 `BeginPass(PassDesc{})`로 연다(`GraphStats::recordings`에 센다). `CreateTexture`의 모양 검사는 `ValidateTextureDesc`를 그대로 쓴다(모든 차원·mip 사슬·`sampleCount`, 용도 `RenderTarget`·`DepthStencil`·`Storage`·`Sampled`). 풀 키에 `sampleCount`를 더했고 깊이·Storage는 렌더 타깃처럼 초기 픽셀 없이 만든다. 기록 장치(`RecordingDevice`)는 `BeginPass`의 attachment subresource 전이를 추적한다.
- **B부.** `GraphTextureView`(handle) · `RenderGraph::CreateTextureView(texture, graphics::TextureViewDesc)` · `GraphPassAccesses::TextureView(view, access)` · `GraphPassContext::View`·`ViewBaseMip`. view 생성은 장치 규칙(`ResolveTextureViewRange`·`ResolveTextureViewFormat`)으로 검사한다(import 텍스처는 2D·2D 배열로 범위만 보고 용도·형식은 장치 view 생성이 본다). 접근 선언은 읽기 view면 SRV(`SrvGraphics`·`SrvCompute`), 쓰기 view면 UAV만 받고, `AddPass`가 view의 텍스처와 푼 범위로 바꿔 subresource 접근으로 펼친다. 그래서 같은 텍스처의 mip k 읽기 view와 mip k + 1 쓰기 view는 한 pass에 함께 있고, 범위가 겹치면 기존 한 pass 안 상충 검사가 거부한다. pass마다 선언한 view 목록을 두고, 장치 view는 그 view를 처음 쓰는 pass의 자원 할당 직후 만들어(`Device::CreateTextureView`) 그래프 끝(`FinishGraph`)에 Retire한다(장치 Retire가 마지막 사용 fence 뒤 해제다). `ViewBaseMip`은 `TextureViewBaseMip(장치 기능, 푼 첫 mip)`이다. 기록 장치에 `CreateTextureView`(범위 규칙만)와 `SetTexture`·`SetWritableTexture`의 view 범위 상태 검사를 더했다(기록 장치는 `textureViewRanges` 거짓이라 CPU 시험이 OpenGL ES 기준 mip 경로를 탄다). 함께 고친 장치 결함: D3D12·Vulkan `SetTexture`의 암묵 전이 판단이 그래픽 읽기 상태(`SrvGraphics`)만 봐서, 그래프가 compute pass 읽기 view를 `SrvCompute`로 바꿔 둔 범위를 다시 셰이더 읽기 전체로 바꿨다(다음 그래프 전이의 before 불일치 검증 오류). 이제 묶인 파이프라인 종류의 읽기 상태(compute면 `SrvCompute`)를 본다. 그래서 compute pass는 `SetPipeline`을 `SetTexture`보다 먼저 부른다(GX5 암묵 전이 규칙).
- **C부.** `RenderGraph/GraphSharedData.h`. `GraphSharedDataType<T>`는 정의 없는 기본 template이고 `ROCKS_DECLARE_GRAPH_SHARED_DATA(Type, Api)`(헤더, 전역 namespace)·`ROCKS_DEFINE_GRAPH_SHARED_DATA(Type)`(cpp 하나 — [빌드 타깃](../BuildTargets/README.ko.md) BS8d4)가 특수화해 이름과 프로세스 안 번호(처음 쓸 때 atomic 계수)를 준다. 등록하지 않은 타입은 컴파일 오류다. `RenderGraph::SharedData()`의 `Create<T>(args…)`(중복은 검증 오류, null)·`Find<T>()`(없으면 null)·`Require<T>()`(없으면 검증 오류, null). 값은 프레임 arena에 만들고 `~RenderGraph`가 그래프 정리 전에 만든 역순으로 소멸자를 부른다. `GraphViewTable<Value>`와 `GraphViewKey{viewSet, view}`: `Add`(중복 키 검증 오류)·`Get`(없으면 검증 오류)·`Find`. history export(결정 R15)는 RG2에 들어간 것을 그대로 쓰고 검증 실패 그래프의 export 0건 시험을 더했다.
- 스펙과 다르게 정한 것: `SceneTextureTable`은 RenderGraph에 고정 타입으로 두지 않고 `GraphViewTable<Value>` template로 두었다. `SceneTextureSet`의 멤버(scene color·깊이·GBuffer·velocity·AO·HZB)는 렌더러가 정하므로 렌더러가 `using SceneTextureTable = GraphViewTable<SceneTextureSet>;`와 등록을 둔다(ViewSet 단위 값 표도 같은 template, view 0). attachment resolve(`resolveTarget`)는 설계대로 그래프에 넣지 않았다.

**RG1 남은 것 설계 2(개정 28): 그래프 attachment resolve와 그래프 구간 `GraphScope`.** 개정 26에서 미룬 둘이다.
- **장치 resolve 뒤 상태 계약(4.4절 GX2 B부 resolve의 상태 규칙을 바꾼다).**
  - 지금(개정 23)은 backend마다 패스 뒤 상태가 다르다: D3D12는 원본 `RESOLVE_SOURCE`·대상은 셰이더 읽기, Vulkan은 원본 `TRANSFER_SRC`·대상 `TRANSFER_DST`(`CopySource`·`CopyDestination`), D3D11·OpenGL ES는 추적 상태가 없다. 그래서 그래프가 패스 뒤 상태를 알 수 없었다.
  - 새 접근 상태 `ResourceAccess::ResolveDestination`(쓰기, UE `ERHIAccess::ResolveDst`)을 더한다. 계약: resolve가 있는 패스가 끝나면(`EndFrame`) 원본(MSAA attachment subresource)은 **`RenderTarget` 그대로**, 대상(resolve mip·slice subresource)은 **`ResolveDestination`**이다. 장치는 resolve에 필요한 원본 전이(D3D12 `RESOLVE_SOURCE`, Vulkan `TRANSFER_SRC`)를 resolve 뒤 attachment 상태로 되돌린다. 대상 전이는 장치가 낸다(attachment 전이와 같이 장치 몫). backend 대응: D3D12 `RESOLVE_DEST`, Vulkan `TRANSFER_DST_OPTIMAL`·`TRANSFER_WRITE`·transfer 단계, D3D11·GLES는 추적 상태만이다. 대상을 다음에 셰이더로 읽으면 명시 전이(그래프) 또는 `SetTexture`의 암묵 전이(GX5)로 셰이더 읽기 상태가 된다.
  - UE와 같은 구조다: RDG는 resolve 대상을 `ResolveDst`로, 원본을 RTV 접근으로 둔다(`RenderCore/Private/RenderGraphBuilder.cpp:185–191`). 원본 전이 되돌림은 장치가 패스 끝에 하는 일이다.
  - 버린 대안: (가) 패스 뒤 원본·대상을 `CopySource`·`CopyDestination`으로 통일 — D3D12는 resolve 상태와 copy 상태가 달라 매번 전이가 하나 더 들고, 원본을 다시 attachment로 쓰는 다음 패스(MSAA 누적)도 전이가 는다. (나) 대상을 셰이더 읽기로 되돌림(지금 D3D12) — 셰이더로 읽지 않는 대상(복사·readback·다음 패스 attachment)에 쓸모없는 전이다.
- **그래프 resolve.** `GraphColorTarget`에 `resolveTarget`(그래프 텍스처)·`resolveMipLevel`·`resolveSlice`를 더한다. 대상의 그 subresource 하나가 이 pass의 `ResolveDestination` 접근이고 attachment 표시라 전이는 장치가 낸다(그래프는 내지 않는다). 대상은 이 pass가 생산자다. 검증(그래프): 대상이 다른 그래프 handle, `RenderTarget` 비트가 없는 그래프 텍스처, 범위 밖·3D, 같은 대상 subresource로 resolve 둘, 원본이 1표본인 그래프 텍스처, 표본 수 2 이상 대상이면 검증 오류다. 형식·크기 일치와 attachment와의 겹침은 장치 `BeginPass`가 본다(실행 오류).
- **그래프 구간 `GraphScope`(7.5절).** pass 묶음 이름 구간이다(UE `RDG_EVENT_SCOPE`·`RDG_EVENT_SCOPE_STAT`, `RenderCore/Public/RenderGraphEvent.h:218, 479–480`. UE 5.8은 `RDG_GPU_STAT_SCOPE`를 없애고 GPU 통계를 `_STAT` 구간으로 옮겼다, 같은 파일 520행).
  - 선언: `GraphScope scope(graph, ShadowsName)`(스택 객체, `RenderGraph::PushScope`·`PopScope`), 번호가 있는 구간은 `GraphScope scope(graph, ViewName, viewIndex)`. 이름은 정적 `TraceScopeName`이다. 구간 안에서 넣은 pass는 그 구간(중첩이면 가장 안쪽)에 속한다. `PopScope` 짝이 없거나 `Execute` 때 열린 구간이 남으면 검증 오류다.
  - 실행: pass를 선언 순서로 실행하며 그 pass의 구간 사슬과 지금 열린 사슬을 비교해 닫을 구간을 닫고 열 구간을 연다. 제거된(culled) pass만 있는 구간은 열지 않는다(UE와 같다). 한 구간은 세 곳에 함께 남는다: CPU trace 구간(CP5, `CpuScope`와 같은 이름 표), GPU 구간(RB7 `GpuTrace`, 시작·끝 timestamp), debug marker(GX9 `PushMarker`·`PopMarker`). 번호가 있는 구간은 연 직후 trace 표지(`ROCKS_TRACE_MARK`)로 번호를 남긴다(7.5절).
  - 장치 기록 경계: Raster pass마다 장치 기록이 새로 열리므로 한 구간이 여러 기록에 걸친다. GPU 구간의 시작·끝 timestamp는 서로 다른 기록에 있을 수 있다(같은 queue의 제출 순서라 시간이 맞다. `GpuTrace`에 RAII 없는 `BeginSpan`·`EndSpan`을 둔다). debug marker는 기록 안에서 짝이 맞아야 하므로(GX9 marker 짝 검사·D3D12 PIX·Vulkan debug label 관례) 기록을 열 때 열린 구간 사슬의 marker를 다시 push하고 기록을 닫을 때 pop한다. 그래서 캡처 도구에는 구간이 기록마다 나뉘어 보인다(이름은 같다).
  - `GpuTrace`가 없으면(`RenderGraphDesc::trace` null) GPU 구간과 marker는 없고 CPU 구간과 trace 표지만 남는다(pass의 `GpuScope`와 같은 규칙).
  - 버린 대안: (가) 구간마다 장치 기록 하나로 묶기 — 구간이 Raster pass 여럿을 가지면 기록이 attachment마다 열려야 해서 불가능하다. (나) marker를 기록 경계 너머로 열어 두기 — 기록마다 짝을 검사하는 backend 규칙(GX9)과 검증 계층 경고에 걸린다.
- **시험.** EngineTests(기록 장치): resolve 대상 subresource의 접근·전이 열(그래프 전이 없음, 다음 SRV 읽기의 before가 `ResolveDestination`), resolve 규칙 위반 검증 오류, 구간 중첩·culled 구간 생략·기록 경계의 marker 재push(기록 장치 `PushMarker`·`PopMarker` 열), 짝 없는 `PopScope`·열린 채 `Execute` 검증 오류. **RG3 병렬 기록 설계(개정 31).** RG3의 두 일 가운데 병렬 기록만 먼저 넣는다. render pass 병합(같은 attachment 연속 pass의 load·store 생략)은 RG3 후속으로 남는다(개정 40에서 GX13 의존을 지웠다 — 4.4절 GX13 결정).
- **UE 방식.** RDG는 pass 묶음마다 `FRHICommandList`를 task에서 기록하고(`RenderCore/Private/RenderGraphBuilder.cpp:2093, 2995`), RHI가 그 목록들을 제출 순서대로 번역한다(`RHI/Public/RHICommandList.h:4440–4458`). 기록(pass 람다 실행)과 번역(장치 명령)이 나뉘어 있어 기록만 병렬이어도 결과 순서가 정해진다.
- **Rocks 구조.** 같은 두 단계로 나눈다.
  - 기록 목록 `GraphCommandList`(RenderGraph 내부): `graphics::CommandContext`를 구현해 pass 기록 함수의 호출을 프레임 arena의 명령 열(종류 표지 + 인자, Span 인자는 복사)로 쌓는다. worker마다 `FrameArenaWriter`로 잠금 없이 할당한다.
  - 실행(Deferred, `RenderGraphDesc::scheduler`가 있고 `parallelRecording`이 켜져 있을 때): (1) 소유 스레드가 남은 pass의 자원 할당·장치 view 생성을 선언 순서로 모두 끝낸다(pass 기록 함수가 보는 장치 handle이 정해진다). (2) CP2 `ParallelFor`로 pass마다 기록 함수를 그 pass의 `GraphCommandList`에 기록한다(pass마다 CPU 구간은 기록한 worker에 남는다). `ParallelFor`가 돌아오면 모든 기록이 끝났다(명시 join, 시간에 기대지 않는다). (3) 소유 스레드가 선언 순서로 지금과 같은 일을 한다: 장치 기록 열기·구간·prologue 전이·pass GPU 구간을 내고 그 사이에 기록 목록을 장치 `CommandContext`로 재생한다. 그래서 장치 호출 열은 직렬 실행과 같다(재생 위치가 직렬 실행의 기록 함수 위치다).
  - 장치는 그대로 소유 스레드 하나만 쓴다(GX11의 "기록 객체는 스레드마다" 규칙의 장치 쪽 병렬 기록 객체는 만들지 않는다). 그래서 OpenGL ES도 같은 경로로 병렬 기록이 된다.
- **기록 목록의 한계(계약).** 기록 중에는 장치 결과를 알 수 없으므로 값을 돌려주는 호출은 기록 때 성공으로 돌려주고 재생 때 실패하면 그 pass의 실행 오류로 남긴다(`SetDrawConstants`의 크기 불일치, 복사·clear 실패). `WriteTimestamp`·`BeginTransitions`·`EndTransitions`는 기록 목록에서 쓸 수 없다(`Unsupported`·무효 짝, 그래프가 GPU 구간과 분리 전이를 소유 스레드에서 낸다). pass 기록 함수는 장치 호출 결과에 따라 다른 명령을 고르지 않는다(직렬·병렬 결과가 같아야 한다).
- **기록 경계 결함 수정(함께 넣는다).** 지금 Compute·Copy pass는 열린 장치 기록에 이어 쓰므로, 바로 앞 Raster pass의 attachment를 복사 원본·UAV로 쓰면 장치가 거부한다(`CopyTexture`·쓰기 묶기는 패스 attachment를 받지 않는다). 직렬 실행에서는 `CopyTexture`의 실패 결과를 pass 기록 함수가 버려 조용히 복사가 빠졌고, 병렬 기록의 재생이 그 실패를 드러냈다. 규칙: Compute·Copy pass가 지금 기록을 연 Raster pass의 attachment subresource를 복사 원본·대상(`CopySource`·`CopyDestination`)으로 쓰면 그 기록을 닫고 attachment 없는 기록을 연다(SRV·UAV 접근은 backend가 render pass를 나눠 처리하므로 기록을 유지한다. RG2 분리 전이의 "Raster → Compute 읽기" 경로가 그대로다). Deferred 컴파일이 같은 규칙으로 pass마다 "새 기록을 엶" 표시를 정하고, 분리 전이(begin·end가 같은 기록 안)와 재사용 자리(앞 기록의 attachment였던 자리는 새 기록부터)가 그 경계를 쓴다(지금까지는 Raster pass만 경계였다).
- **설정.** `RenderGraphDesc::scheduler`(CP2 `WorkerScheduler`, null이면 직렬)·`scratch`(`ParallelFor` helper용 스레드 안전 Allocator)·`parallelRecording`(기본 참). 즉시 실행 모드는 직렬이다(AddPass가 바로 실행한다). `GraphStats::parallelPasses`가 병렬로 기록한 pass 수다.
- **버린 대안.** (가) 장치에 스레드별 기록 객체(D3D12 명령 목록·Vulkan secondary 명령 버퍼·D3D11 deferred context)를 두고 그래프가 그것을 나눠 주기 — backend 넷 모두에 새 계약(기록 객체 수명·제출 순서·render pass 상속)이 들고, OpenGL ES는 여전히 소유 스레드 재생이 필요해 두 경로가 생긴다. 번역 비용이 문제가 될 때 장치 쪽 병렬 번역(목록 묶음별 명령 목록)을 그 위에 더한다. (나) pass 기록 함수를 worker에서 장치에 직접 부르기 — 장치 기록은 소유 스레드 전용이다(5.4절).
- **완료 기준.** 기록 장치에서 병렬·직렬 그래프의 장치 호출 열이 같음(전이·그리기·marker·timestamp 순서), pass가 많은 그래프의 병렬 기록 pass 수, 기록 목록에서 값 돌려주는 호출의 실패 전달, scheduler 없는 그래프는 직렬. Sandbox `--self-test` 모든 backend: 같은 그래프를 병렬·직렬로 실행한 출력 픽셀·버퍼 바이트가 같다. worker 순서는 `ParallelFor` join과 재생 순서로만 정해지고 sleep·경쟁 운에 기대지 않는다.
- **구현(2026-11-20, RG3 병렬 기록).** 위 설계 그대로다. RenderGraph: 내부 `GraphCommandList`(CommandContext의 호출 24종을 명령 열로 쌓고 Span 인자는 arena에 복사, `Replay`가 값 돌려주는 호출의 첫 실패를 돌려줌), `PreparePass`(자원 할당·장치 view 생성 분리), `RecordPassesInParallel`(남은 pass 2개 이상일 때 선언 순서로 준비한 뒤 `ParallelFor`, pass마다 `GraphCommandList`를 프레임 arena에 만들고 기록 오류는 그래프 실행 오류), `ExecutePass`는 기록 목록이 있으면 기록 함수 대신 pass GPU 구간 안에서 재생. `RenderGraphDesc::scheduler`·`scratch`·`parallelRecording`, `GraphStats::parallelPasses`. RenderGraph 모듈이 Task에 의존한다. 기록 경계: 실행의 `UsesAttachmentsOf`(복사 접근만)와 Deferred 컴파일의 `PassRecord::opensRecording`(분리 전이 `SplitBeginPass`·재사용 자리 `waitsForRecording`)이 같은 규칙이다.
- 스펙과 다르게 정한 것: 기록 경계는 attachment의 복사 접근(`CopySource`·`CopyDestination`)만 본다. 처음에는 attachment의 모든 접근으로 넣었으나, Raster pass 결과를 바로 읽는 Compute pass(RG2 분리 전이 시험의 "Raster → Compute 읽기")까지 기록을 나눠 분리 전이를 없앴다. SRV·UAV 접근은 backend가 render pass를 나눠 처리하므로 기록을 유지한다.
- 시험 결과: EngineTests `RenderGraphParallelTests`(`RenderGraph_ParallelRecordingMatchesSerialCalls`: Raster 4·Compute·Copy와 culled pass·구간이 있는 그래프를 직렬·병렬(worker 3)로 실행해 자원 생성을 뺀 장치 호출 열과 전이 기록이 같고 병렬 기록 pass 6, `ParallelRecordingReportsRecordAndReplayFailures`: `WriteTimestamp`는 Unsupported 기록 오류, 파이프라인 없는 `SetDrawConstants`는 재생 실패, `ParallelRecordingNeedsASchedulerAndTheSwitch`). Sandbox `--self-test`의 `RunParallelGraph`(Programs/Sandbox/Private/RenderGraphSelfTest.cpp): Raster 6(그리기별 상수 색 파이프라인)과 Copy 1 그래프를 직렬·병렬로 실행한 출력 픽셀이 같고 마지막 pass 색, 병렬 기록 pass 7, 검증 오류 0 — D3D12·D3D12 WARP·D3D11·D3D11 WARP·GLES·GLES on GL core·Vulkan(GTX 1060·lavapipe). 기록 경계 결함은 이 Sandbox 시험의 병렬 재생이 `CopyTexture` 실패(`InvalidArgument`)를 드러내 찾았다.

**RG4 async compute 설계(개정 32).** compute pass를 graphics queue와 따로 도는 compute queue에 내어 graphics 작업과 GPU에서 겹치게 한다. 계획 API06("graph serial/async lowering의 결과 일치·실제 queue 표시")의 그래프 쪽이다.
- **UE 방식.**
  - pass 표시 `AsyncCompute`가 pipe를 고른다. 장치·설정이 허락하지 않으면 그 pass를 graphics pipe의 compute pass로 바꾼다(`RC/Private/RenderGraphBuilder.cpp:473–498`). 허락 조건은 설정 `r.RDG.AsyncCompute`, 즉시 실행 모드 아님, render pass 병합 꺼짐, 장치 값 "효율적인 async compute"다(`RC/Private/RenderGraphPrivate.h:229–234`). render pass 병합과 배타인 이유는 병합하면 fence의 전이가 병합 구간 끝으로 옮겨지기 때문이다(같은 곳 주석).
  - 간선: 다른 pipe 사이 의존마다 소비 pass에 "다른 pipe의 가장 늦은 생산자"를, 생산 pass에 "다른 pipe 소비자 목록"(정렬)을 둔다(`RenderGraphBuilder.cpp:1160–1196`). 다른 pipe가 읽은 자원을 쓰는 pass도 그 읽기 pass에 기댄다(`:1231–1235`).
  - fork·join(`:1562–1667`): async pass마다 fork = max(다른 pipe 생산자, 앞 async pass의 fork, prologue), join = min(culling되지 않은 첫 다른 pipe 소비자, 뒤 async pass의 join, epilogue)다. 그래서 fork는 선언 순서로 늘기만 하고 join도 그렇다. fence는 fork·join이 바뀔 때만 새로 둔다(graphics fork pass의 epilogue begin → async pass prologue end, async pass epilogue begin → graphics join pass prologue end).
  - 수명 연장: async pass가 쓰는 자원의 할당은 fork pass 앞, 해제는 join pass 뒤로 옮긴다(두 pipe가 나란히 돌므로 그 구간 안에서는 놓을 수 없다, 같은 곳 주석).
  - 실행: 선언 순서 그대로이고 pass마다 명령 목록의 pipe를 바꾼다(`:3519`). 첫 실행에는 앞 실행의 "모든 pipe" 외부 자원을 맞추는 async → graphics fence를 둔다(`:2098–2102`).
  - D3D12 장치(`Runtime/D3D12RHI/Private/D3D12LegacyBarriers.cpp:380–420, 1110–1150, 1580–1635`): 다른 pipe 전이는 원본 pipe가 begin 때 sync point를 신호하고 대상 pipe가 end 때 기다린다. barrier 자체는 graphics 상태를 다룰 수 있는 graphics queue에서 낸다(graphics → async는 begin 때 graphics에서, async → graphics는 end 때 graphics에서). compute queue는 graphics 상태 barrier를 받지 않기 때문이다.
  - D3D12 "효율적인 async compute"는 제조사 판단이다: AMD는 참, NVIDIA는 `D3D12_OPTIONS6.PerPrimitiveShadingRateSupportedWithViewportIndexing`(Ampere 이후)일 때만 참, 그 밖은 거짓이고 명령줄로 강제할 수 있다(`Runtime/D3D12RHI/Private/D3D12Adapter.cpp:1447–1484`).
  - Vulkan 장치: graphics와 다른 queue family의 compute queue를 쓰고(`Runtime/VulkanRHI/Private/VulkanDevice.cpp:355–372`, 조건에 `VK_KHR_maintenance9`), 있으면 "효율적"이다(`VulkanRHI.cpp:994`). image는 기본 exclusive와 queue family 소유권 이전, 설정으로 concurrent를 고를 수 있고(`VulkanTexture.cpp:33–40, 615–624`), 버퍼는 maintenance9 덕에 소유권 이전이 없다(`VulkanBarriers.cpp:1438, 1522–1530`).
- **Rocks 구조.**
  - **장치(GX1·GX5 확장).**
    - `QueueKind::AsyncCompute`. `GpuFencePoint`·`IsFenceComplete`·`WaitFence`·`NotifyFence`가 두 queue의 지점을 받는다. `LastSubmittedFence(QueueKind)`(기본 graphics).
    - `DeviceFeatures::asyncCompute`(graphics와 따로 도는 compute queue가 있다)와 `efficientAsyncCompute`(겹쳐서 이득이 난다고 보는 장치, UE "효율적인 async compute"와 같은 판단). D3D12는 compute queue를 늘 만들고 효율 판단은 UE와 같다. Vulkan은 UE 5.8과 같은 조건(graphics와 다른 family의 compute queue, synchronization2, `VK_KHR_maintenance9`, `Runtime/VulkanRHI/Private/VulkanDevice.cpp:355–372·472`)을 갖출 때 둘 다 참이다(2026-11-20 사용자 결정). 하나라도 없으면 둘 다 거짓이고 그래프는 graphics pipe로 낮춘다. 개발 기계 GTX 1060(드라이버 560.94)은 maintenance9가 없고 lavapipe는 family가 하나라 둘 다 거짓이다. D3D11·OpenGL ES는 둘 다 거짓이다.
    - `PassDesc::queue`. `AsyncCompute` 기록은 attachment가 없어야 하고(`InvalidArgument`), 장치에 `asyncCompute`가 없으면 `Unsupported`다. compute 기록이 받는 명령은 compute 파이프라인·묶기·그리기별 상수·dispatch(간접 포함)·쓰기 view clear·버퍼 복사·전이(compute 상태만: `SrvCompute`·`UavCompute`·`Constant`·`IndirectArgs`·`CopySource`·`CopyDestination`과 before의 `Unknown`·`Discard`)·분리 전이·timestamp·marker다. 그 밖(그리기·viewport·graphics 파이프라인·graphics 상태 전이·텍스처 복사·패스 대상 복사)은 무시하고 `IgnoredDraws`를 올린다(값을 돌려주는 것은 `InvalidArgument`). 장치가 메우는 암묵 전이도 compute 상태 사이만 낸다.
    - `EndFrame`은 기록의 queue에 제출하고 그 queue의 지점을 돌려준다. 쌓인 업로드가 있으면 먼저 graphics queue에 제출하고 compute 제출이 그것을 기다린다(업로드는 다음 제출 전에 실행된다는 GX8 계약을 두 queue에 지킨다).
    - `Device::QueueWait(queue, point)`: 이 호출 뒤 queue에 내는 모든 제출은 point(다른 queue의 제출한 지점)가 끝난 뒤에 실행된다. 같은 queue의 지점은 할 일이 없다(제출 순서). D3D12는 `ID3D12CommandQueue::Wait`다. Vulkan compute queue 경로(아래 "남은 것")는 queue마다 기다릴 상대 timeline 값의 최댓값을 두고 그 뒤 모든 제출에 timeline semaphore 대기(대기 stage는 모든 명령)로 붙인다(semaphore 대기는 그 제출 안의 명령만 묶으므로 다음 제출마다 다시 붙인다. 이미 지난 값의 대기는 비용이 없다). 실패: 다른 장치 지점 `WrongContext`, 제출하지 않은 값 `InvalidArgument`, compute queue가 없는 장치에서 `AsyncCompute` 쪽 `Unsupported`.
    - 상태 추적은 장치 전체에 하나이고 기록 순서를 따른다. 두 queue가 같은 자원을 겹쳐 쓰지 않게 하는 것은 호출자의 `QueueWait`다(장치는 경쟁을 찾지 않는다).
    - `Retire`·회수: 자원·view·파이프라인의 마지막 사용은 queue마다 따로 정하고(기록 중이면 그 기록의 지점, 아니면 그 queue의 마지막 제출) 둘 다 끝난 뒤에 해제한다. 기록 저장소(D3D12 명령 allocator, Vulkan 명령 버퍼·descriptor pool·event)는 queue마다 따로이고 그 queue의 fence로 다시 쓴다.
    - timestamp: compute 기록의 `WriteTimestamp`도 된다. `TimestampSample::queue`가 queue를 알리고 번호는 queue마다 따로다. `CalibrateClocks(QueueKind)`가 queue마다 GPU tick과 CPU 시각 쌍을 준다(D3D12는 queue마다 clock calibration, Vulkan은 device 시간축 하나라 같은 값).
    - Vulkan 공유 방식(UE 5.8과 같다, 2026-11-20 사용자 결정): image는 `VK_SHARING_MODE_EXCLUSIVE`이고 다른 queue family 사이 전이에 소유권 이전(원본 queue release, 대상 queue acquire)을 둔다. 다만 두 family가 서로 `VkQueueFamilyOwnershipTransferPropertiesKHR::optimalImageTransferToQueueFamilies`에 들면 이전을 생략한다(`VulkanDevice.cpp:472–510`). 버퍼는 maintenance9 덕에 이전이 없다(`VulkanBarriers.cpp:1438, 1522–1530`). 이전이 필요 없을 때 다른 queue 사이 barrier는 graphics queue에서 한 번만 낸다(`VulkanBarriers.cpp:1500–1508`).
  - **그래프.**
    - 설정 `RenderGraphDesc::asyncCompute`(`GraphAsyncCompute`): `Auto`(기본, 장치 `efficientAsyncCompute`일 때 compute queue), `Always`(장치에 `asyncCompute`가 있으면 늘, 시험·측정용. UE의 명령줄 강제와 같은 자리), `Disabled`. 즉시 실행 모드와 render pass 병합(RG3 후속)은 늘 끈다. 끄면 AsyncCompute pass는 graphics pipe의 Compute pass와 똑같이 실행한다(UE와 같은 낮추기).
    - pipe 간선: subresource마다 마지막으로 접근한 pass를 따라, 다른 pipe의 앞 접근이 있으면 의존이다(읽기 → 읽기도 넣는다. UE보다 보수적이지만 다른 pipe의 읽기 상태를 합치지 않으므로 그 사이 전이 자리가 필요하다). 다른 pipe 사이에는 읽기 상태를 합치지 않는다.
    - fork·join은 UE와 같은 식이다. prologue는 "그래프 시작", epilogue는 "그래프 끝"이다.
    - 수명 연장: async pass가 쓰는 자원의 첫 사용을 fork pass(prologue면 첫 실행 pass)로, 마지막 사용을 join pass(epilogue면 그래프 끝)로 넓힌다. 같은 그래프 안 재사용(RG2)과 `GraphLifetime`이 이 넓힌 값을 쓴다.
    - 기록과 제출: 장치는 한 번에 기록 하나이므로, 선언 순서로 실행하다가 async pass를 만나면 열린 graphics 기록을 닫고 compute 기록을 연다. 이어진 async pass는 같은 compute 기록이다. compute 기록을 열기 전에 `QueueWait(AsyncCompute, fork 지점)`을 부른다. fork pass는 그 pass 뒤에서 graphics 기록을 닫아 제출 지점을 남기고(다음 pass가 새 기록을 연다), prologue fork는 그래프 시작의 graphics 지점(그래프 업로드를 먼저 제출한 뒤의 마지막 제출)이다. join pass는 새 graphics 기록을 열고 그 앞에서 `QueueWait(Graphics, 그 join이 기다릴 마지막 compute 지점)`을 부른다. 기다리지 않은 compute 제출이 남으면 그래프 끝에서 graphics 기록 하나를 열어(마지막 전이·export 상태도 여기서 낸다) 기다린다(epilogue join). 그래서 그래프의 마지막 제출은 늘 graphics이고, 풀 반납의 마지막 사용 지점(graphics `LastSubmittedFence`)이 compute 작업까지 덮는다.
    - 다른 pipe 전이의 자리(UE D3D12와 같다): graphics → async 전이는 fork pass의 epilogue(graphics 기록, 닫기 직전)에서 내고, prologue fork면 그래프 시작에 그 전이만 담은 graphics 기록 하나(UE prologue pass)를 열어 낸다. async → graphics 전이는 소비 pass의 prologue(join 뒤 graphics 기록)에서 낸다. async → async 전이만 compute 기록에서 낸다. 다른 pipe 전이는 나누지 않는다(begin·end가 다른 기록·queue다).
    - GPU 계측: compute 기록에는 debug marker(그래프 구간·pass 이름)만 남기고 `GpuTrace` GPU 구간은 두지 않는다(GPU 구간은 graphics queue 하나의 장부다. compute queue 구간은 후속). CPU 구간은 그대로다.
    - 진단: `GraphStats::asyncComputePasses`(compute queue에서 실행한 pass)·`computeRecordings`·`queueWaits`(fork·join 대기 수). `RenderGraph::PassPipe(pass)`가 실행 pipe를 알린다.
  - **render pass 병합과 배타(계약).** 병합(RG3 후속)을 켠 그래프는 async compute를 끈다. 병합 구간 안에 fork·join 전이가 들어갈 수 없기 때문이다(UE와 같다). 병합이 아직 없으므로 지금은 계약만 둔다.
- **결정 R6 확정(권장안, 개정 32).** copy queue는 그래프 밖, 업로드·스트리밍 계층에 둔다. 그래프 pipe는 graphics·async compute 둘뿐이고 Copy pass는 graphics pipe다(UE와 같다).
- **버린 대안.**
  - (가) Vulkan concurrent 공유로 maintenance9 없는 장치에서도 compute queue 쓰기(개정 32 초안): 버퍼·텍스처를 `VK_SHARING_MODE_CONCURRENT`로 만들면 소유권 이전이 없어 개발 기계(GTX 1060)에서도 compute queue를 시험할 수 있었다. 2026-11-20 사용자 결정으로 버렸다: UE 5.8과 같게 한다(maintenance9가 없으면 끄고, image는 exclusive와 이전). 근거는 UE 동작과 맞추는 것(UE는 concurrent를 설정 예외로만 두고 기본은 exclusive), concurrent가 image 압축을 막을 수 있는 장치의 비용, maintenance9가 버퍼 이전을 없애 exclusive의 부담이 image에 한정된다는 점이다. 대가로 이 기계에서는 Vulkan compute queue 실행 시험을 할 수 없다(실기 경로 시험은 D3D12).
  - (나) Vulkan binary semaphore(compute queue 경로를 넣을 때의 선택): 기다릴 쪽이 정해지기 전에 신호해야 하고 신호 하나를 정확히 한 번 기다려야 해서, 제출마다 쓰이지 않을 수도 있는 semaphore를 두거나 기다릴 쪽을 미리 알려야 한다. timeline semaphore는 queue마다 하나로 값만 비교한다.
  - (다) compute 기록이 graphics 기록과 동시에 열리는 장치(기록 객체 둘): 장치 계약 "한 번에 기록 하나"를 바꾸고 backend 넷의 기록 상태를 둘로 나눠야 한다. 선언 순서 실행에서는 기록을 닫고 여는 것으로 같은 queue 순서가 나온다(제출이 늘 뿐이다).
  - (라) 다른 pipe 전이를 compute queue에서 내기: D3D12 compute queue는 graphics 상태(`PIXEL_SHADER_RESOURCE`·`RENDER_TARGET` 등) barrier를 받지 않는다. UE D3D12처럼 graphics queue에서 낸다.
  - (마) fork를 늘 "async pass 바로 앞까지 낸 graphics 전부"로 두기: 구현은 단순하지만 fork pass와 async pass 사이 graphics pass와 겹치지 못한다. UE처럼 fork pass에서 기록을 나눈다.
- **한계.**
  - 다른 pipe의 읽기 → 읽기도 동기화한다(위). 겹침이 줄 수 있다.
  - async pass는 Copy를 쓰지 않는다(UE처럼 Copy pass는 graphics pipe).
  - compute queue의 GPU 구간이 `GpuTrace`에 없다. 겹침은 시험의 timestamp로 잰다(아래).
  - D3D12는 효율 판단이 UE와 같아 개발 기계(GTX 1060, Pascal)·WARP는 `Auto`에서 graphics pipe다. compute queue 경로는 `Always`로 시험한다.
  - Vulkan compute queue 경로(queue·timeline semaphore·image 소유권 이전·queue별 기록 저장소)는 maintenance9 장치에서 실행 검증과 함께 넣는다(남은 것). 그때까지 Vulkan은 켜는 조건만 보고 로그로 남기며 늘 graphics pipe다.

**GX12·RG5 transient aliasing 설계(개정 33).** 수명이 겹치지 않는 그래프 자원이 같은 장치 메모리를 나눠 쓰게 한다(transient heap 위의 placed 자원과 aliasing barrier). RG2의 "같은 desc 객체 이어 쓰기"와 달리 desc가 달라도 메모리를 나눈다. 함께 RG4에서 남은 compute queue GPU 구간을 `GpuTrace`에 넣는다.
- **UE 방식.**
  - RHI 계약 `IRHITransientResourceAllocator`(`RHI/Public/RHITransientResourceAllocator.h:535–558`): 그래프가 자원마다 할당·해제 fence(pass 번호)와 함께 `CreateTexture`·`CreateBuffer`·`DeallocateMemory`를 부르고 그래프 끝에 `Flush`한다. D3D12·Vulkan만 구현하고 나머지는 null이라 풀을 쓴다(`RHI/Public/DynamicRHI.h:312`).
  - fence(`RHITransientResourceAllocator.h:14–118`): 할당은 한 pipe, 해제는 두 pipe일 수 있다. async compute는 compute pass 번호와 graphics fork·join 구간으로 나타내고, 해제 fence와 획득 fence가 두 pipe에서 동시에 살아 있으면(`Contains`) 그 메모리를 나누지 않는다. 획득 위치는 `GetAcquireFence`다.
  - 할당기(`RHICore/Private/RHICoreTransientResourceAllocator.cpp:132–259`): heap 안 빈 구간 목록(offset 순)을 처음부터 훑어 붙어 있는 빈 구간들을 이어 붙이되, 각 구간을 놓은 자원의 fence가 새 할당과 동시에 살지 않을 때만 쓴다(first fit). 쓴 구간을 놓았던 자원들이 "aliasing 겹침" 목록이 되고 새 자원의 획득 전이에 실린다. 해제(`:261–296`)는 구간을 fence와 함께 목록에 끼우고, `Flush`(`:298`)가 프레임 끝에 이웃 구간을 합치고 fence를 지운다.
  - heap 캐시: heap은 최소 128 MiB(`:20, 524`), 정렬 64 KiB(`:525`), 쓰지 않은 heap은 16번의 GC 주기 뒤 놓는다(`:41, 528, 597`). heap마다 만든 placed 자원을 (offset, desc hash)로 캐시한다(`RHICore/Public/RHICoreTransientResourceAllocator.h:154–291`).
  - D3D12(`D3D12RHI/Private/D3D12TransientResourceAllocator.cpp:15–53, 188`): resource heap tier 2면 `ALLOW_ALL_BUFFERS_AND_TEXTURES` heap 하나, tier 1이면 버퍼·RT/DS 아닌 텍스처·RT/DS 텍스처 heap을 나눈다. `CreatePlacedResource`로 만든다. 획득은 aliasing barrier(before null)다(`D3D12LegacyBarriers.cpp:1346–1388`). RT/DS는 획득 뒤 clear·discard로 초기화한다.
  - Vulkan: 획득 전이의 before가 Discard면 image `oldLayout`이 UNDEFINED인 aliasing barrier다(`VulkanRHI/Private/VulkanBarriers.cpp:973, 1112`).
  - 그래프(`RC/Private/RenderGraphBuilder.cpp:501–560`): transient 대상은 공유가 아닌 텍스처와 UAV 버퍼이고, 업로드 대상·추출(export) 자원은 기본으로 빠진다. 설정 `r.RDG.TransientAllocator`(기본 1)로 끄고, async compute 자원 aliasing은 `r.RDG.AsyncComputeTransientAliasing`과 RHI 지원 표시를 함께 본다(`RenderGraphPrivate.h:240–243`). 획득 전이는 첫 사용 pass에 겹침 목록과 함께 낸다(`:4076, 4215`).
- **Rocks 구조.**
  - **장치(GX12).**
    - `DeviceFeatures::transientHeaps`(D3D12·Vulkan 참, D3D11·OpenGL ES 거짓).
    - `TransientHeapKind`: `Buffers`·`Textures`(렌더 타깃·깊이 아닌 텍스처)·`Targets`(렌더 타깃·깊이 텍스처). 늘 셋으로 나눈다(D3D12 tier 1 규칙과 같고, Vulkan은 선형·최적 자원을 나눠 `bufferImageGranularity`를 따로 맞추지 않는다).

    - 설정: `RenderGraphDesc::transientAliasing`(기본 참, UE `r.RDG.TransientAllocator` 1과 같다)과 `asyncComputeAliasing`(기본 거짓, 1차는 async compute 자원을 aliasing에서 뺀다. UE는 1이지만 RHI 지원 표시가 함께 필요하다). 장치에 `transientHeaps`가 없거나 즉시 실행 모드면 풀(RG2)이다.
    - 대상: 그래프가 만든 텍스처(`RenderTarget`·`DepthStencil`·`Storage` 용도)와 쓰기 용도 버퍼. import·export·업로드 대상·`Sampled` 텍스처는 빼고, `asyncComputeAliasing`이 꺼져 있으면 async pass가 쓰는 자원도 뺀다. 나머지는 RG2 풀로 간다.
    - 할당(컴파일): 남은 pass를 선언 순서로 훑으며 자원을 첫 사용 pass에 할당하고 마지막 사용 pass 뒤에 놓는다(RG4로 넓힌 수명 그대로). 할당기는 UE와 같은 first fit이다: heap 종류마다 빈 구간 목록, 구간마다 놓은 자원과 fence, 동시에 살지 않는 구간만 이어 붙임, 쓴 구간의 앞 자원들이 겹침 목록. 할당은 앞 pass들이 놓은 구간만 받으므로 fence 비교가 따로 필요 없다: async compute 자원은 RG4로 넓힌 수명(fork·join, graphics 순서)으로 할당하고 획득은 fork의 graphics 기록에서 하므로, UE의 세 fence(graphics·async compute·fork·join) 대신 pass 구간 하나로 같은 안전을 얻는다(UE보다 보수적이다: async 자원이 fork·join 구간 전체를 차지한다). heap 크기를 넘으면 그 종류의 heap을 하나 더 둔다.
    - heap 캐시(`GraphResourcePool`이 가진다, 그래프 사이 유지): heap마다 종류·크기·마지막 사용 지점(graphics·compute)·마지막 사용 프레임과 placed 자원 캐시((offset, desc 키) → handle). 그래프는 마지막 사용 지점이 **두 queue 모두 끝난** heap만 받는다(아니면 새로 만든다). 쓰지 않은 heap은 설정한 프레임 수(기본 16, UE와 같다) 뒤 `Retire`한다. heap 크기 기본은 128 MiB이고 자원 하나가 더 크면 그 크기로 만든다(UE와 같다).
    - 실행: 자원의 첫 전이 before는 `Discard`이고 `acquire`다(attachment면 `PassDesc`의 attachment `acquire`). 그래프 끝에 heap마다 마지막 사용 지점을 적고 캐시에 돌려준다.
    - 진단: `GraphStats::transientResources`·`aliasedResources`(겹침 목록이 있는 획득)·`transientBytes`(transient 자원 크기 합, aliasing 없을 때의 사용량)·`transientPeakBytes`(heap에서 실제로 쓴 최대 끝 offset 합, aliasing한 사용량)·`transientHeaps`.
  - **compute queue GPU 구간(RG4 남은 것).** `GpuTraceSettings::queue`(기본 graphics)를 두어 장부 하나가 queue 하나를 맡는다. calibration은 `CalibrateClocks(queue)`, queue 정의의 종류 칸은 queue 번호다. 렌더 lane의 timestamp 통지(`RenderNotice`)에 queue를 싣고 `Consume`은 자기 queue의 통지만 쓴다. 그래프는 `RenderGraphDesc::computeTrace`가 있으면 compute 기록의 pass GPU 구간을 그 장부에 쓰고, 첫 compute 기록에서 GPU 프레임을 열어 마지막 async pass의 compute 기록을 닫기 전에 닫는다. 그래프 구간(`GraphScope`) GPU 구간은 graphics 장부 그대로다.

- **버린 대안.**
  - (가) heap 하나에 모든 종류(D3D12 tier 2·UE 기본): 메모리를 더 나누지만 tier 1 장치와 Vulkan granularity 처리가 갈라진다. 종류별 heap으로 시작하고 tier 2 통합은 계측 뒤에 본다.
  - (나) 다음 그래프가 GPU 완료 없이 같은 heap을 다시 쓰기(UE: 같은 queue 순서와 aliasing barrier에 맡긴다): 두 queue 마지막 사용이 끝난 heap만 받기로 했다(사용자 지시). 프레임 수만큼 heap이 늘 수 있다(계측).
  - (다) aliasing 없이 RG2 풀만: desc가 다른 자원끼리 메모리를 나누지 못한다(완료 기준의 최대 사용량 감소가 없다).
- **한계.** 종류별 heap이라 렌더 타깃과 버퍼·Storage 텍스처는 메모리를 나누지 않는다. 1차는 async compute 자원을 aliasing에서 뺀다(설정으로 켤 수 있다). Vulkan은 async compute queue가 없으므로 graphics queue만이다.

**구현(2026-11-18, RG2 A부).** 프레임 안 풀 재사용, export 자원의 풀 반납(결정 R15), 그래프 안 업로드다. begin·end 분리 전이(B부)는 Graphics `ResourceAccess`·`Transition`과 D3D12·Vulkan backend를 고쳐야 하므로 다른 세션의 D3D11·D3D12 공용 코드 정리 병합 뒤에 한다. 계약은 [렌더 기반 구현](../../Implementation/RenderBase.ko.md) 9절이다.
- **프레임 안 재사용.** Deferred 컴파일이 culling·수명 뒤 남은 pass를 실행 순서로 훑어 장치 객체 자리(`PhysicalResource`)를 정한다: pass p에서 처음 쓰는 자원은 p 앞에서 놓인 같은 풀 키의 자리를 받고(없으면 새 자리), p에서 마지막으로 쓰는 자원은 p 뒤에 자리를 놓는다. 같은 pass에서 쓰는 두 자원은 자리를 나누지 않는다. export 자원은 그래프 끝까지 놓지 않고, 업로드 대상은 그래프 시작에 자리를 받는다(업로드가 첫 pass 앞에서 실행되므로 앞 자원의 객체를 덮지 않기 위해서다). 자리는 첫 자원의 첫 pass 직전에 풀에서 받고 그래프 끝에 한 번 돌려준다. UE도 마지막 사용 pass에서 풀 자원을 놓고 뒤 pass의 할당이 같은 desc를 다시 받는다(`RC/Private/RenderGraphBuilder.cpp:3128–3175, 3632–3646`).
  - 이어 받은 자원의 첫 전이 before는 `Discard`다(이전 내용 무효). backend는 `Discard` before를 `Unknown`처럼 장치 추적 상태에서 바꾼다(D3D12 `D3D12Frame.cpp`, Vulkan `VulkanAccess.cpp`의 검증 생략·추적 상태 사용, Vulkan 버퍼는 모든 쓰기를 기다리는 barrier). UE 풀 재사용은 앞 자원의 마지막 상태를 이어받고 `Discard`는 transient aliasing에만 쓴다(`RenderGraphBuilder.cpp:4060–4080`). Rocks는 이전 내용이 필요 없음을 전이 열에 드러내려고 `Discard`로 했다(결과는 같다).
  - Immediate 모드는 앞을 내다볼 수 없어 같은 그래프 안 재사용을 하지 않는다(자원마다 자리 하나). 그래서 완료 기준 (d)의 즉시·지연 동치 시험은 재사용이 없는 그래프로 대조한다.
  - 진단: `GraphLifetime::reusedWithinGraph`, `GraphStats::reusedWithinGraph`(풀 생성·재사용 계수와 따로).
  - 7.5절 view 단위 선언에서 뒤 view의 장면 텍스처가 앞 view의 객체를 이어 쓴다(시험 `RenderGraph_ViewsReuseSceneTexturesWithinAGraph`: view 둘 × 텍스처 둘 → 장치 생성 2). `SceneTextureTable`(키 (ViewSet, view))·`GraphSharedData`는 RG1 남은 것과 Renderer RS0 범위이고 이번에 넣지 않았다.
- **export 풀 반납(결정 R15).** RenderBase에 Retire 대행자 `RenderRetireSink`를 두었다. `RenderHandleTable::BindTexture`·`BindBuffer`가 sink를 받고, `BeginRetire`·`TakeReleasedRetire` 결과(`RetiredResource::sink`)가 그것을 실어 나르며, 새 공용 함수 `ReleaseRetiredResource(device, handle, retired)`가 sink가 있으면 sink로, 없으면 장치 Retire로 넘긴다(렌더 lane `RetireOnDevice`도 이 함수를 쓴다). `GraphResourcePool`은 sink다: `Export`가 풀 자원을 handle에 잇고 export 상태로 두며(풀 byte 합에 든다), handle의 Retire(lease가 남았으면 마지막 lease가 풀린 뒤)가 오면 반납 대기로 두었다가 마지막 사용 fence가 끝난 뒤(`CollectReturned`, Acquire·Evict가 부른다) 쓰지 않음으로 돌린다. 풀이 먼저 파괴되면 export 자원의 소유를 handle에 넘긴다(`DetachRetireSink`, 그 뒤 Retire는 장치 Retire). 풀 계수: `exported`·`returning`(지금 수), `exports`·`returned`(누적). RG1의 `Detach`·`detached`는 없앴다.
  - 시험: 완료를 미룬 동안 반납된 history를 다시 주지 않음(장치 생성 3), 완료 뒤에는 다시 줌, 정상 상태 8프레임 동안 장치 생성 3·장치 Retire 0. import lease가 남은 동안의 Retire는 lease가 풀린 뒤 반납. 렌더 lane `Retire`로 6프레임 history를 돌려 장치 생성 2·장치 Retire 0·handle 표 0. 풀 파괴 뒤 handle Retire는 장치 Retire.
- **그래프 안 업로드.** `RenderGraph::UploadBuffer(buffer, data, offset)`·`UploadTexture(texture, mip, pixels)`(UE `QueueBufferUpload`, `RC/Public/RenderGraphBuilder.h:309–333`). 데이터는 선언 때 프레임 arena에 복사한다. 업로드는 그 자원의 생산자이고(생산 전 읽기 검사를 통과한다) 자원을 쓰는 어느 pass보다 먼저 선언해야 한다(아니면 검증 오류). Deferred는 컴파일 뒤 첫 기록을 열기 전에(UE `SubmitBufferUploads`와 같은 자리, `RenderGraphBuilder.cpp:2691–2837`), Immediate는 그 자원의 첫 pass 직전에 장치 업로드 경로(`Device::UpdateBuffer`·`UpdateTexture`, GX8 업로드 ring)로 올린다. 남은 pass가 쓰지 않고 export도 아닌 자원은 올리지도 할당하지도 않는다.
  - 전이: 장치 업로드는 상태 중립이다(D3D12·Vulkan 업로드 기록은 제출 끝 상태에서 복사 대상으로 갔다 돌아온다, GLES·D3D11은 드라이버). UE도 업로드를 그래프 상태 추적 밖에서 `Unknown → CopyDest → Unknown`으로 감싼다(`RenderGraphBuilder.cpp:2750–2796`). 그래서 그래프는 업로드에 복사 대상 상태를 따로 두지 않고, 뒤 pass의 읽기 전이를 장치 추적 상태(before `Unknown`)에서 낸다. 요청의 "복사 대상 접근 선언"을 그래프 상태로 두면 장치 상태와 어긋나 D3D12·Vulkan 검증 오류가 되므로 이렇게 정했다.
  - 텍스처: D3D12·D3D11 `UpdateTexture`는 렌더 타깃 텍스처를 받지 않고, 버퍼 → 텍스처 복사 명령이 아직 없다(GX4 범위 밖). 그래서 업로드는 새 그래프 텍스처 용도 `Sampled`에만 받는다: 모든 mip을 한 번씩 올려야 하고(빠지면 Execute 검증 오류), pass는 읽기만 한다(쓰기·렌더 타깃은 검증 오류). 풀은 새로 만들면 mip 사슬을 생성 초기 데이터로, 다시 주면 mip마다 `UpdateTexture`로 채운다(`GraphResourcePool::AcquireTexture(desc, pixels)`). `Sampled` 그래프 텍스처는 압축 형식도 된다. 렌더 타깃 텍스처 업로드는 `Unsupported`다.
  - import 자원에는 올리지 않는다(렌더 lane `UpdateBuffer`·`UpdateTexture` 경로). UE는 한 그래프에서 버퍼마다 업로드 하나지만 Rocks는 같은 버퍼의 여러 구간 업로드를 선언 순서대로 올린다.
  - 진단: `GraphStats::uploads`(버퍼 업로드 하나, 텍스처 mip 하나가 1).
- 풀 키에 버퍼 `stride`를 더했다(GX2의 구조화 버퍼).
- 시험(EngineTests `RenderGraphReuseTests`, 기록 backend): view 둘의 프레임 안 재사용과 장치 handle 동일성·`Discard` attachment 전이, Immediate 재사용 없음, export·겹침·다른 desc 비공유, 버퍼 재사용의 `Discard` → UAV 장치 전이(검증 0), 위 R15 시험 넷, 업로드가 첫 기록 앞·두 구간 순서·읽기 전이, 제거된 자원의 업로드 생략, 업로드 대상이 앞 객체를 받지 않고 뒤 자원에 넘김, Immediate 업로드 위치, `Sampled` mip 업로드(생성 → 다시 쓰면 mip 갱신 둘), 업로드 음성 대조(렌더 타깃 `Unsupported`·범위 밖·빈 데이터·mip 크기·두 번·`Sampled` 쓰기·렌더 타깃·올리지 않은 mip 읽기·pass 뒤 업로드·import·빠진 mip).

**스왑체인 공유 설계(개정 64, [UI 도구](../UiToolkit/README.ko.md) 18.6절 요청 1).** 한 그래프에서 같은 스왑체인을 대상으로 하는 Raster pass 여럿이 백버퍼 하나를 함께 쓰고, 그 스왑체인의 마지막 pass에서만 present한다(뒤 pass는 load). 장면 tone map 뒤 UI를 같은 창에 그리려는 것이다.
- **지금(개정 63까지).** 스왑체인 타깃 pass마다 장치 `BeginFrame`(늘 clear)으로 기록을 열고 그 기록의 `EndFrame`이 present한다. 장면 pass와 UI pass가 같은 스왑체인을 대상으로 하면 present가 두 번이고 UI pass가 장면을 지운다.
- **UE 방식.**
  - 창 백버퍼는 그래프의 외부 텍스처다(`SlateRHIRenderer/Private/SlateRHIRenderer.cpp:984`). 외부 자원에 쓰는 pass는 culling 뿌리이고(7.1절 culling 행) transient 대상이 아니다(`RC/Private/RenderGraphBuilder.cpp:501–560`).
  - UI pass의 시작 동작은 호출자가 정한다: 창이 clear를 요구하면(픽셀 투명 창·와이어프레임 등) clear, 아니면 load다(`SlateRHIRenderer.cpp:992–1072`). 같은 백버퍼에 장면을 먼저 그렸으면 load로 잇는다.
  - present는 그래프 밖이다: 모든 창의 그래프를 `Execute`한 뒤(`:1489–1493`) 창마다 present 상태 전이와 `EndDrawingViewport`(present)를 낸다(`:1295–1320`, `:1503`). 그래서 한 프레임에 창마다 present 하나다.
- **Rocks 구조.**
  - **장치(GX).**
    - `SwapChainPassDesc`(스왑체인, `load`, `clear`, `present`)와 `Device::BeginFrame(const SwapChainPassDesc&)`. `BeginFrame(swapChain, clear)`는 clear + present인 간단한 형태로 남는다(`BeginOffscreen`과 같은 자리).
    - `present`가 거짓이면 `EndFrame`은 제출만 하고 present하지 않으며 백버퍼(D3D12 지금 백버퍼 번호, D3D11 백버퍼, Vulkan·OpenGL ES 스왑체인 중간 이미지)를 그대로 둔다. 다음 `BeginFrame`이 같은 백버퍼에 이어 그린다. D3D12 백버퍼 번호는 present 때만 바뀌고, Vulkan의 실제 acquire는 present하는 `EndFrame`의 blit 앞이므로(4.4절 GX5 Vulkan) 잡아 둔 swapchain image가 없다.
    - 스왑체인마다 "그리는 중인 프레임" 표시를 둔다: `BeginFrame`이 켜고, present하는 `EndFrame`(present 성공·실패와 무관)과 `ResizeSwapChain`이 끈다. `load` `Load`는 이 표시가 켜져 있을 때만 받는다(아니면 `InvalidArgument`). present 뒤·처음 백버퍼 내용은 정의되지 않기 때문이다(DXGI flip discard, Vulkan 중간 이미지의 첫 layout UNDEFINED). `Clear`·`DontCare`는 늘 받는다.
    - backend: D3D12는 기록마다 present → 렌더 타깃 → present 전이(지금과 같다). Vulkan은 present하지 않는 기록 끝에 중간 이미지를 attachment layout으로 두고 다음 기록이 attachment 쓰기 뒤에서 잇는다. load는 render pass `LOAD_OP_LOAD`·`DONT_CARE`로 낮춘다. D3D11·OpenGL ES는 clear를 생략한다.
    - 진단 `Device::PresentCount()`(낸 present 누적 수, 실패한 present는 세지 않는다). 시험이 "프레임당 present 하나"를 장치에서 센다.
  - **그래프.**
    - `GraphPassAccesses::SwapChainTarget(swapChain, load = Clear, clear)`와 `GraphRenderTarget::load`. 시작 동작은 호출자가 정한다(UE와 같다). 그래프가 뒤 pass를 load로 바꾸지 않는다: 뒤 pass가 의도적으로 지울 수 있어야 하고, 앞 pass가 없을 때 load는 오류여야 하기 때문이다.
    - 검증(`AddPass`): 그래프에서 그 스왑체인의 첫 pass가 `Load`면 검증 오류다(생산 전 읽기와 같은 성격 — 이 그래프의 앞 pass가 그리지 않은 백버퍼). 스왑체인은 그래프 자원이 아니므로 SRV·복사·UAV로 선언할 수 없다(handle이 없다). pass 안의 `CopyPassTarget`만 백버퍼를 읽는다(지금과 같다).
    - 그래프는 스왑체인마다 (handle, 첫 pass, 마지막 pass)를 `AddPass` 때 적는다. 스왑체인 pass는 culling 뿌리라 제거되지 않으므로 적은 마지막 pass가 실행에서도 마지막이다.
    - 실행(Deferred): 스왑체인 pass는 `BeginFrame({swapChain, load, clear, present = 그 스왑체인의 마지막 pass인가})`로 기록을 연다. 그래서 present는 그 스왑체인을 쓰는 마지막 pass의 기록이 닫힐 때 한 번이다. 그 사이 Compute·Copy pass·다른 타깃 pass가 있어도 된다(기록은 지금 규칙대로 나뉜다). 스왑체인이 둘이면 각자 마지막 pass에서 따로 present한다.
    - 실행(Immediate): `AddPass`가 바로 실행하므로 뒤 pass를 알 수 없다. 스왑체인 pass는 모두 present 없이 열고, `Execute`가 성공하면 그래프 끝에서 스왑체인마다(처음 쓴 순서) 그리기 없는 present 기록 `BeginFrame({swapChain, Load, present})` 하나를 열고 닫는다. 그래서 즉시·지연 모드의 장치 호출 열은 이 present 기록만큼 다르다(완료 기준 (d)의 동치는 스왑체인이 없는 그래프로 대조한다).
    - 실패: pass·기록 오류로 `Execute`가 멈추면 이미 닫은 present 없는 기록은 present되지 않고, 이 그래프의 그 스왑체인 present도 없다(그래프 진단 `LastError`에 실패한 pass). 첫 `BeginFrame` 실패(스왑체인 크기 변경 실패로 버퍼 없음·장치 손실)도 같다. 다음 그래프가 clear로 새 프레임을 그린다.
    - 병렬 기록(RG3): present 여부는 소유 스레드가 기록을 열 때 정하므로 직렬·병렬 장치 호출 열이 같다. async compute(RG4): 스왑체인 pass는 Raster라 늘 graphics다. fork·join이 기록을 나눠도 present는 마지막 스왑체인 pass의 기록이다. transient aliasing(RG5): 스왑체인은 그래프 자원이 아니라 대상이 아니다.
    - 크기 변경·표면 소실은 렌더 lane의 표면 작업이고 프레임 packet 처리(그래프 실행) 사이에 실행된다(5.3절). 그래서 한 그래프 안에서 스왑체인 크기·버퍼가 바뀌지 않는다. Vulkan OUT_OF_DATE는 present하는 `EndFrame`의 acquire가 다시 만들고 잇는다(지금과 같다).
    - 진단: `GraphStats::presents`(present를 낸 기록 수 — 그래프가 닫은 present 기록 가운데 `EndFrame`이 성공한 수).
- **버린 대안.**
  - (가) 그래프는 present하지 않고 호출자(렌더 lane 처리기)가 `Execute` 뒤 `Device::Present(swapChain)`를 부른다(UE 구조에 가장 가깝다). 장치에 기록 밖 present가 새로 들고, Vulkan은 그 present를 위해 acquire·blit 기록을 하나 더 열어 제출해야 한다. 처리기마다 present를 잊지 않아야 하고 그래프 실패 때 present 여부도 처리기가 따로 정해야 한다. 그래프가 마지막 pass를 정확히 알므로 그 기록에서 낸다(present 횟수·위치는 UE와 같다).
  - (나) 백버퍼를 그래프 텍스처로 import. 장치에 백버퍼 `TextureHandle`이 없고(D3D12 백버퍼 번호는 present마다 바뀌고 Vulkan·OpenGL ES는 중간 이미지다) SRV·복사·aliasing 배제 규칙을 새로 둬야 한다. 요청은 같은 백버퍼에 이어 그리기뿐이다.
  - (다) 뒤 pass의 시작 동작을 그래프가 늘 load로 바꾸기. 뒤 pass가 의도적으로 clear할 수 없고, 앞 pass가 culling·조건으로 빠졌을 때 오류를 숨긴다.
  - (라) 같은 스왑체인의 연속 pass를 기록 하나로 합치기. 사이에 다른 타깃 pass나 attachment 복사 pass가 끼면 안 되고 RG3 후속 render pass 병합과 겹친다. 기록 수 최적화는 병합 단계에서 본다.
- **한계.**
  - 마지막 스왑체인 기록 안(그 기록에 이어 쓴 Compute·Copy pass 포함)에서 실패하면 그 기록은 닫힐 때 제출되며 present된다(장치에 present 취소가 없다). 지금 동작(모든 스왑체인 pass가 present)과 같다.
  - Immediate 모드는 present 기록 하나가 더 든다(디버그 모드).
  - Sandbox `ScreenPacket`의 UI packet 자리와 `UiLaneRenderer::AddPasses` 호출(18.6절 요청 2)은 UI 타입이 engine-runtime에 없어 이번에 넣지 않는다. UI 브랜치 병합 뒤 게임 UI 단계(UT5)에서 Sandbox에 연결한다.
- **완료 기준.**
