# Rocks Core 기능 감사표 — Unreal 공개 기능 기준

## 범위와 판정 기준

사용자 요구는 Unreal Core 기능별로 **Rocks에서 해당 기능이 가능한지 물었을 때 모두 Yes라고 답할 수 있는 것**이다. 각 기능을 지원하는 형태는 달라도 되며 Unreal의 클래스명·접두사·내부 알고리즘·ABI를 복제하라는 뜻은 아니다. Unreal 모듈인 Core는 기초 자료형·컨테이너·수학·플랫폼 추상화 등을 담당하고, CoreUObject는 객체·반영·GC·패키지 관련 기능을 담당한다. Rocks에서는 Base/PlatformBase/Core/MetaSchema/ObjectRuntime/Serialization 등 적절한 모듈에 기능을 배치한다. 상위 Engine·Editor·에셋 시스템에 속하는 항목은 Core 선행 계약과 통합 과제로 연결한다.

이 감사표는 Epic의 공개 문서와 현재 저장소를 대조한 **1차 범주별 목록**이다. 공개 API 목록은 버전·플랫폼·문서 생성 상태에 따라 완전하지 않고, 비공개·내부 항목이나 엔진 전체 피처까지 이 문서만으로 전수 완료를 증명할 수 없다. 따라서 아래에 없는 기능도 제외하지 않는다. 기준 Unreal 버전의 실제 공개 헤더·모듈 API 목록과 문서의 기계적 대조, 중복·deprecated·플랫폼 전용 분류, 차이점 심사 및 누락 보강을 완료 게이트로 둔다. 모든 기능을 즉시 구현한다는 뜻은 아니다.

**현재 비교 기준은 사용자가 지정한 Unreal Engine 5.6이다.** 가능한 항목은 UE 5.6의 공개 문서와 접근 권한이 있는 공식 소스의 고정 커밋을 기준으로 확인한다. UE-C26~UE-C33의 UE 5.8 검색 결과는 기능 후보를 식별한 보조 자료이며 해당 기능의 UE 5.6 존재나 의미를 검증한 증거가 아니다. 일반 API 문서 링크는 표시 버전이 바뀔 수 있으므로 원문에서 5.6 표기나 고정 소스를 확인하지 못한 항목은 기준 버전 미확인으로 둔다. 공개 API·헤더의 전체 목록과 세부 심볼, 플랫폼별 구현의 전수 대조는 후속이다.

`부분`: 관련 코드의 일부만 확인. `후속`: 아래 근거 범위에서 구현을 확인하지 못했거나 설계 단계. `미확인`: 현재 상태 또는 대응 의미를 추가 검토해야 한다. `예외`: 사용자가 명시적으로 제외한 Blueprint 시각 스크립트는 제외하고, 게임 로직은 자체 언어로 구현한다. 현행 코드의 `noexcept`·STL 비사용·명시적 allocator·경고 오류 처리·Windows/macOS·안정성 우선·직관적 사용법·한국어 사용/주의 주석을 공통 요구로 유지한다.

플랫폼 계층은 Unreal의 Generic 기반과 플랫폼별 구현·확장 구조를 우선 기준으로 한다. 공통 경로 유틸과 파일 I/O 인터페이스·물리 구현·래퍼 체인의 차이, 실제 현황 및 검증 계획은 [플랫폼 계층 설계](PlatformLayer.ko.md)에 기록한다.

## 확인 가능한 주요 출처

- Epic [Core 모듈 API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core)와 [CoreUObject 모듈 API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/CoreUObject): 공개 심볼과 모듈 경계. 각 세부 항목의 버전·플랫폼 지원은 원문과 소스 확인이 필요하다.
- Epic [FMallocBinned2](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/FMallocBinned2), [FMallocBinned3](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/FMallocBinned3), [가상 메모리 풀](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/FPooledVirtualMemoryAllocator): allocator·pool·page·통계와 관측 기능의 사례. Rocks에서 특정 구현 방식 또는 성능을 동일하게 할 필요는 없다.
- Epic [Task System](https://dev.epicgames.com/documentation/unreal-engine/tasks-systems-in-unreal-engine), [TArray](https://dev.epicgames.com/documentation/unreal-engine/array-containers-in-unreal-engine), [TMap](https://dev.epicgames.com/documentation/unreal-engine/map-containers-in-unreal-engine), [TSet](https://dev.epicgames.com/documentation/en-us/unreal-engine/set-containers-in-unreal-engine): 작업 의존·중첩·동기화와 자료구조 사용성 사례.
- Epic [Reflection](https://dev.epicgames.com/documentation/en-us/unreal-engine/reflection-system-in-unreal-engine), [UClass](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/CoreUObject/UClass), [객체 생성](https://dev.epicgames.com/documentation/unreal-engine/creating-objects-in-unreal-engine), [Object Handling](https://dev.epicgames.com/documentation/unreal-engine/unreal-object-handling-in-unreal-engine): 타입·기본값·객체 생성·반영·GC·저장 범위의 사례.

기반 수학·기본 충돌·플랫폼 비동기 I/O를 포함한 기능별 작업 계약과 완료 기준은 [Core 상세 기능·구현 명세](CoreDetailedSpec.ko.md)를 따른다.

## UE5 Core 공용 유틸리티 후속 작업 — 공개 API 대조

다음은 Epic 공개 문서와 Rocks 공개 헤더를 대조해 식별한 우선 과제다. 공개 문서 전체나 UE 소스 전체의 전수 대조는 아니며, Rocks에 구현이 있는 경우에도 의미·플랫폼·시험 범위가 같다는 뜻은 아니다. 보안 정책이나 수명 안전성에서 의도적으로 다르게 처리할 부분은 그 이유를 기록하고 별도 사용 경로와 회귀 테스트를 마련한다.

### 경로와 플랫폼 계층

- [FPaths](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/FPaths)·[FPathViews](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/FPathViews) 대비 Rocks `Path`는 루트 판별·정규화·결합·절대/상대 변환·포함 확인·파일명·`Directory`·`Parent`·확장자 및 `BaseFileName`·`Split`의 초기 구현을 제공한다. `String`의 `/`·`/=`는 원문 경로 결합을 지원하며 별도의 `NormalizeFilename`·`CollapseRelativeDirectories`도 있다. 반환 view는 입력을 빌리며 문자열 처리만 수행한다. Windows·POSIX 문법은 명시적으로 선택하고 호스트의 기본 문법과 native 구분자는 플랫폼 계층에서 선택한다. 이 변경의 통합 빌드와 각 OS의 실제 실행 결과는 별도 증거로 확인한다.
- UE의 `ChangeExtension`은 확장자 구분점이 없으면 원문을 유지하고 `SetExtension`은 없는 경우 추가한다. Rocks에도 별도 API를 두며 표기·구분자를 보존한다. Epic의 [GetExtension 예제](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Core/FPathViews/GetExtension)와 [Split 예제](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/FPathViews/Split)에 맞춰 `.name`의 확장자는 `name`, basename은 빈 값이다. Rocks는 `Split(".")`에서 빈 이름, `Split("..")`에서 `..`을 반환하고 `BaseFileName("..")`은 `.`이다. 끝 점은 빈 확장자 구분점으로 처리한다. 숨김 파일과 끝 점의 교체·제거, 오류와 할당 실패를 별도로 검증한다.
- Epic [FPathViews::Equals](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/FPathViews/Equals)는 대소문자와 구분자 표기를 무시하고 끝 구분자도 무시하며, 현재 `.`·`..`는 그대로 비교한다고 설명한다. Rocks `IsUnder`는 지정 문법을 정규화한 뒤 Windows 드라이브 문자를 제외한 경로 구성요소를 byte 대소문자 구분해 비교하므로 동일 API로 간주하지 않는다. UE 사용 사례에 필요한 동일성·정렬·부모 경로 비교와 정책별 의미를 추가하고, OS 실제 파일 동일성 및 symlink/junction을 통한 보안 경계 확인은 별도 API로 다룬다.
- 복합 확장자·점 포함 옵션, `GetPathLeaf`·volume 분해·components/ancestors 순회, builder append, child-relative view, 엔진·프로젝트·사용자·임시·저장·설정 디렉터리 조회는 공개 Path API에서 확인되지 않아 후속이다. 플랫폼 문법 경계를 확장할 때 한 호스트에서 Windows/POSIX 양쪽 문법을 검사하는 기능과 새 타깃의 미지원 오류를 유지한다.

### 파일과 I/O

Epic [IPlatformFile](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/IPlatformFile)은 파일/디렉터리 존재·열기·이동·삭제·속성·순회와 async/mapped 접근 등을 제공하고, [FPlatformFileManager](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Core/FPlatformFileManager)는 물리 파일 구현과 wrapper chain을 관리한다. Rocks `Serialization/Archive`·`Record`는 데이터 직렬화 기반이다. 별도의 `Platform/File.h`에 파일 시스템·핸들 인터페이스와 물리 Windows/macOS backend, 소유형 `File`의 동기 open/read/write/seek/size/close 및 Exists/Delete 초기 구현이 있다. 부분 전송 반복과 오류·수명 계약을 포함하지만 wrapper chain 관리자나 비동기/매핑 파일을 의미하지 않는다.

1. 구현된 동기 핸들의 열기·닫기·부분 읽기/쓰기·seek·크기와 Windows UTF-8→UTF-16 경계의 플랫폼 검증을 마무리하고, 일반 stat과 directory 생성·열거를 추가한다. 실제 파일 테스트에는 유니코드, 권한 오류, 부분 전송, 취소·동시 닫기, 누수와 임시 디렉터리 정리가 포함돼야 한다.
2. 물리 파일 위에 로깅·캐시·패키지 등의 교체 가능한 wrapper와 수명·동시 호출 계약을 추가한다. 프로젝트/엔진 기본 경로는 초기화 및 headless 실행 조건을 명시한다.
3. 비동기 I/O, mapping, watch 및 package dispatcher는 완료 취소·늦은 완료·대기와 종료 규약을 별도로 확립한다. 성능이나 OS 지원 범위를 테스트 없이 가정하지 않는다.

현재 공용 Core 확장의 Windows 검증은 Foundation Debug native 407건·harness 66건·meta 41건, Foundation ASan native 407건·harness 67건·meta 41건, Core Release native 320건·harness 59건이 PASS다. 각 build evidence는 `sourceStableDuringRun=true`, `runnerReportCurrent=true`이며 전체 `clang-format` 검사도 PASS다. 당시 파일 및 메타컴파일러 symlink fixture는 권한 제약으로 SKIP되었다. 이후 Windows 개발자 모드를 활성화한 별도 재검증에서 파일 fixture 1건과 메타컴파일러 전체 41건이 모두 통과했으며, 두 링크 fixture 모두 건너뛰지 않았다. 현재 변경의 macOS 실기기 빌드·실행, 실제 OS close 오류 강제 주입, 디렉터리·전체 stat·flush·truncate·async/mapping/watch 및 wrapper chain 관리자는 별도 후속 검증·구현 대상이다.

### 문자열·컨테이너·할당기·스레드

아래 세부 항목은 Epic GitHub의 UE `5.6` 브랜치에서 확인한 commit `cdda65cecacd9a1278020925c357bf4cc0b17e8c`의 Core 공개 헤더와 Rocks 현재 공개 헤더를 비교한 결과다. 이는 UE 5.6 전체 Core의 전수 검증을 대체하지 않는다. 아래 GitHub 소스 링크는 Epic UnrealEngine 저장소 접근 권한이 있어야 열린다. 미확인 항목은 구현 완료로 취급하지 않는다.

- **문자열:** UE5.6 [UnrealString.h.inl](https://github.com/EpicGames/UnrealEngine/blob/cdda65cecacd9a1278020925c357bf4cc0b17e8c/Engine/Source/Runtime/Core/Public/Containers/UnrealString.h.inl)을 기준으로 Rocks는 `String`·`StringView`의 앞/뒤 `Find`, `Contains`, 접두·접미 검사, `Split`, byte 부분 문자열, ASCII 대소문자·공백 처리와 비중첩 `TryReplace`를 구현했다. 검색 기본값은 ASCII 대소문자 무시이고 비ASCII는 byte 비교다. UTF-8 byte 인덱스는 UE `TCHAR` 인덱스와 다르며 임의 `StringView`의 유효 UTF-8과 수명은 호출자 책임이다. 빈 검색어·방향·시작 위치 경계는 테스트하며 치환의 자기 별칭과 OOM에서는 원본을 보존한다. Unicode folding·정규화, format, `Join`, `ParseIntoArray` 등은 후속이다.
- **Name:** UE5.6 [NameTypes.h](https://github.com/EpicGames/UnrealEngine/blob/cdda65cecacd9a1278020925c357bf4cc0b17e8c/Engine/Source/Runtime/Core/Public/UObject/NameTypes.h)을 기준으로 기본 None, 빈 문자열·ASCII 대소문자 변형 `None`의 동등성, ASCII 대소문자 무시 비교, 표기 보존과 번호 접미사를 구현했다. 번호 있는 `None_N`은 None이 아니다. Rocks `GetNumber()`는 외부 N을, 번호가 없으면 -1을 반환하여 UE 내부 번호 표현과 다르다. 정상 이름의 비교는 pool domain을 구분하고 None 비교는 domain을 무시한다. `IsValid`는 token 형태만 확인하며 발급 여부·표기 ID·domain 검증은 pool `Acquire`가 담당한다. view는 `NameLease` 수명에 종속되며 이 token을 영속·네트워크 ID로 사용하지 않는다. Unicode folding·정규화 및 영속 identity는 후속이다.
- **Text:** UE5.6 [Text.h](https://github.com/EpicGames/UnrealEngine/blob/cdda65cecacd9a1278020925c357bf4cc0b17e8c/Engine/Source/Runtime/Core/Public/Internationalization/Text.h)은 순서형·이름형 서식과 숫자·백분율·통화·날짜/시간의 문화권별 표현을 제공한다. Rocks `Localization/Text`는 invariant/localized 문구, 정수, 이름형 인자 서식과 catalog 일부를 구현하며 plural/gender·문화권별 숫자·통화·날짜/시간은 후속이다. culture 변경 시 일관된 snapshot, fallback, 번역 누락·오류, 정수 경계, 순서형/이름형 인자, 복수형·성별·환산·시간대 경계와 실패 시 소유권을 검증한다.
- **배열:** UE5.6 [Array.h](https://github.com/EpicGames/UnrealEngine/blob/cdda65cecacd9a1278020925c357bf4cc0b17e8c/Engine/Source/Runtime/Core/Public/Containers/Array.h)을 기준으로 Rocks는 단일 insert/emplace, span·배열 append, resize, 순서 보존/교환 삭제, pop, 앞/뒤 검색, reset·empty·shrink를 구현했다. move-only 원소, 자기 alias, 인덱스·overflow, OOM과 포인터·view 무효화, allocator 수명과 반환 순서를 검증한다. 추가 범위 조작, 검색 조건자·필터, heap·안정 정렬과 inline allocator는 후속이다. `Array::Sort`는 비안정 정렬을 제공하며 UE `TArray::Sort`와 달리 raw pointer를 자동 역참조하지 않는다.
- **Map/Set:** UE5.6 [Map.h](https://github.com/EpicGames/UnrealEngine/blob/cdda65cecacd9a1278020925c357bf4cc0b17e8c/Engine/Source/Runtime/Core/Public/Containers/Map.h)의 `TMap::Add`는 같은 key의 항목을 교체한다. [Set.h](https://github.com/EpicGames/UnrealEngine/blob/cdda65cecacd9a1278020925c357bf4cc0b17e8c/Engine/Source/Runtime/Core/Public/Containers/Set.h)의 `TSet::Add`/`Emplace`도 중복 key 원소를 새 원소로 교체한다. Rocks `HashMap::Insert`·`HashSet::Add`는 중복이면 기존 항목을 보존하고 입력을 소비하지 않으며, `HashMap::InsertOrAssign`은 값만 교체하고 기존 key를 유지한다. 동일 ID·다른 표시명을 비교상 같은 key로 다루는 예제에서 key·value 교체, 입력 이동 여부, 포인터/참조 무효화, OOM rollback을 검증한다. Rocks는 find·erase·reserve·compact·일부 집합 연산이 있으나 UE의 추가 iterator/정렬/다중 key 등 전체 표면을 제공한다고 볼 수 없다.
- **기타 컨테이너·알고리즘:** UE5.6 [BitArray.h](https://github.com/EpicGames/UnrealEngine/blob/cdda65cecacd9a1278020925c357bf4cc0b17e8c/Engine/Source/Runtime/Core/Public/Containers/BitArray.h)을 기준으로 Rocks는 bit 크기·삽입·삭제·설정·검색·개수와 AND/OR/XOR 조합을 부분 구현했다. 자동 기하 성장, 명시적 reserve, word 경계, 자기 조합, OOM 보존을 검증한다. 겹치는 구간의 `RemoveAtSwap`은 UE의 BitArray와 Array에서 채우는 원본 구간이 달라 Rocks도 각각의 규약을 따른다. sparse array, queue·deque, heap·tree, 스마트 포인터, tuple과 나머지 범용 Algo 등은 후속이다. queue의 생산/소비자 수·순서·종료·OOM 및 안정 정렬의 comparator 정책은 별도로 검증한다.
- [FMalloc](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Core/FMalloc)의 `Realloc`·`TryRealloc`, 할당 크기, TLS cache와 heap 검증은 Rocks의 공통 `Allocator`가 아직 제공하지 않는다. [FMemMark](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/FMemMark)의 표시 이후 일괄 해제와 현재 Rocks Stack의 개별 LIFO 반환은 다르므로 임시 scratch 용도의 안전한 일괄 수명 계약이 별도로 필요하다. 외부 allocator 함수 바인딩은 실제 라이브러리의 제품 배포 통합이나 성능 동등성을 의미하지 않는다.
- Rocks의 thread start/wait/join, 비재귀 mutex, condition variable, manual-reset event, semaphore는 기반이다. Epic [FRunnableThread](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Core/FRunnableThread?lang=en-US)의 이름·우선순위·affinity·stack 옵션 및 thread 관리 기능은 현재 Rocks 공개 API에서 확인되지 않는다. UE Core의 `FCriticalSection`이 재귀 mutex라는 점과 Rocks Mutex의 비재귀 계약도 명시적으로 구분한다. 플랫폼별 가용성·실패·join·경합과 OS 실 실행을 검사한다.

범용 알고리즘의 사용 및 수명 규약은 [정렬·이진 탐색](../Implementation/Algorithms.ko.md)을 따른다. UE 5.6 `TArray` 공개 헤더에서 정렬과 안정 정렬 제공을 확인했으며, 별도 `Algo` 구현의 UE 5.6 원본은 아직 대조하지 않았다.

### 우선순위와 완료 기준

현재 단계에서는 ① 플랫폼 파일·디렉터리와 경로 보정·플랫폼 실검증, ② 문자열 Unicode·format과 추가 범위 기능, Name 영속 identity 및 Map/Set 중복 정책, ③ 범용 알고리즘·나머지 컨테이너와 스레드 옵션, ④ 재할당·일괄 scratch·공급자 통합과 계측을 이어간다. 수학·기본 충돌은 검증된 상용 엔진 공개 구현의 라이선스를 확인하고 SIMD·경계 테스트와 함께 계획한다. 비동기 파일·config도 의존 관계에 따라 진행한다. 각 기능은 사용 예제, 실패 주입 및 수명·경계·동시성 테스트, Windows/macOS 실행 증거, 독립 교차 검증을 갖추기 전까지 전체 완료로 표시하지 않는다.

## 실행 순서와 완료 게이트

1. **Core 조사 게이트:** 기준 UE 버전·플랫폼·공개 헤더와 문서의 인벤토리를 기계적으로 수집한다. 기능별 Rocks 담당 모듈, 검증 목표, 우선순위, 현재 상태, 근거와 미확인 사유를 붙이고 신규/변경 심볼을 재감사한다. 사용자 명시 예외인 Blueprint를 빼고 기능 단위 누락을 삭제하지 않는다. 법적·라이선스 조건을 확인해 코드·알고리즘 참고 범위를 정한다.
2. **현재 Foundation 우선:** 객체 타입 조회·수명/GC/Reflection/Serialization 안정성을 검증하면서 Core 기능 간 의존성을 확정한다. 일반 내부 콜백의 재진입 진단 한계, 다중 World에서 자동 문맥 미전파, 미구현 타입 제한 및 기본값은 실제 상태로 유지한다.
3. **메모리 기반 우선:** 구현된 Arena·Stack·Pool·Binned·Budget·Debug와 가상 메모리·외부 연결 경계의 사용·수명 계약은 [할당기 설계와 사용 규약](../Implementation/Allocators.ko.md)을 따른다. frame 수명 관리, 자동 일괄 해제 stack, thread cache, page guard 및 실제 jemalloc·TCMalloc 등 공급자 제품 통합은 후속이다. Windows scratch의 mimalloc v3.6.1 함수 연결 probe는 통과하였으나 제품 통합이나 macOS 검증은 아니다. Windows Core Debug·Release 및 Foundation Debug·ASan 검증은 통과하였다. macOS 빌드·실행과 OS fault injection·성능은 미검증이다. 각 사용 시나리오와 수명을 먼저 검증하고 성능은 측정한다. 특정 Unreal allocator 계열을 같은 방식으로 복제한다고 가정하지 않는다.
4. **범용 Core 확장:** 문자열/컨테이너 및 정렬·알고리즘, math/기본 geometry, 플랫폼 동기화·시간, config/file/async I/O를 의존 관계에 맞춰 확장한다. 각 feature는 필요한 대표 게임 코드가 불필요한 수동 scope/registry/복잡한 단계 없이 읽히는지 검증한다.
5. **상위 연결 및 완료:** 클래스·기본값·에셋/패키지·네트워크·프로파일링/에디터/헤드리스를 개별 milestone으로 연결한다. 기능별 정상/경계/실패/수명 테스트, 재현 가능한 stress, 메모리/락 및 진단, 사용자 코드 예시, Windows/macOS 실 실행, 서브에이전트 독립 교차 검증을 통과해야 완료로 표시한다. 특정 OS를 실행하지 못한 경우 그 범위를 명시한다.

**기능 동등성 최종 게이트:** 확정한 기준 버전의 공개 Core 기능 목록에 대해 각 기능에 Rocks의 구현·사용 경로, 적용 플랫폼, 의미 차이, 테스트 및 실행 증거를 연결한다. 기능별 Yes는 실제 구현과 검증 증거가 있을 때만 표기한다. `부분`, `후속`, `미확인`, 실행하지 않은 플랫폼, 단순 계획 또는 테스트 실패를 Yes로 간주하지 않는다. 명시 예외는 사용자가 제외한 Blueprint이며 관련 게임 로직은 자체 언어로 연결한다. 기준 버전·범위 밖의 신규 기능은 재감사한다.

이 표는 전체 Core를 이미 완료했다는 주장이 아니다. 성능·기능 동등성과 공개 문서 밖의 누락 없음은 별도 조사·측정 전까지 미검증으로 둔다.
