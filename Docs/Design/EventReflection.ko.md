# 이벤트 리플렉션(CU3)

이 문서는 리플렉션된 이벤트(UiToolkit CU3, UE dynamic multicast delegate 대응)와 그 위의 함수 바인딩(함수 리플렉션 FR4)을 정한다: 재사용 함수 바인딩 값, 이벤트 필드 타입, 서명·frame 배치 검사, 발행, 대상 파괴 시 자동 해제, 발행자 수명, 저장, 리플렉션 schema, 단계. 사용처는 Sparks 이벤트(EI1c·EI3 — SL 5.2·5.5절, 연동 요구 SE-R2), UI 이벤트 연결(WidgetAsset — UiToolkit 5절), 입력 action 함수 바인딩(InputActions IA7), 에디터 이벤트 목록. 구조는 UE 5.8을 따르고 이름은 Rocks식이다(UE 이름은 대응표에만).

- 개정 8(2026-11-27): ED18 — 손자 클래스가 물려받은 이벤트의 생성 소스가 선언 조상의 생성 헤더를 include(UiWidget TileViewWidget 빌드 오류에서 발견).

## 3. 결정

- **ED1 이벤트 타입과 인자:** 이벤트 필드는 ObjectRuntime `Event<Args...>`(`Object/Event.h`)다. 안쪽 저장은 Core `MulticastDelegate`(등록 순서·발행 중 추가·제거·지연 정리 — Core 계약 그대로, 중복 구현 금지). `Args`는 FD4의 매개변수 형식이고 각 인자는 (a) nothrow 복사 가능한 값(정수·`bool`·실수·enum·`ObjectHandle`·`WeakObjectRef<T>`·`ClassRef<T>`·`Guid` 등 — Core가 대상마다 복사해 넘긴다) 또는 (b) `const T&`(`String`·컨테이너·struct·`SoftObjectRef<T>` — 복사할 수 없거나 큰 형식, IA7 `const ActionEventData&`)다. 이 모양 규칙(`detail::IsEventArgument`)은 `Event` 클래스 수준 static_assert이고, frame 칸 복사 가능(`ValueCopy` — 리플렉션 struct는 생성 헤더가 필요하다)은 바인딩·발행이 인스턴스화하는 `BindingFrame`이 본다(개정 6 — 이벤트 필드 선언은 같은 헤더 struct의 생성 헤더보다 먼저 오므로 클래스 수준에 두면 리플렉션 struct 인자를 쓸 수 없다). `StringView`는 받지 않는다(발행자 저장소를 가리켜 큐에 넣을 수 없다 — `const String&`). 반환은 없다(UE와 같다). 이벤트 필드는 리플렉션 클래스의 필드에만 둔다: struct 멤버·컨테이너(Array·Optional·Map·정적 배열) 원소는 불가(바인딩이 발행자 객체에 묶이고 값 복사로 바인딩이 둘이 되면 안 된다 — UE는 struct 안 delegate를 허용하지만 Rocks는 막는다). `Event`는 복사·이동을 지운다(adapter가 상태 주소를 쥔다 — ED2).
- **ED2 항목과 상태:** `Event`는 `Allocator*`와 지연 할당 상태 포인터(16 byte — ED13)다. 상태는 안쪽 `MulticastDelegate<void(Args...)>`, 리플렉션 바인딩 레코드 배열(바인딩 id 순 — `{id, FunctionBinding, DelegateHandle, dead}`), 발행 문맥 사슬(ED6)을 쥔다. native 구독(`TryAdd(Delegate)`·`TryAddLambda` — C++ 엔진 코드, 저장하지 않는다)과 리플렉션 바인딩(`TryBind` — 저장한다)은 모두 안쪽 delegate의 항목이라 호출 순서는 섞인 등록 순서다. 리플렉션 바인딩의 항목은 `{상태*, 바인딩 id}`만 쥔 adapter다(inline 48 byte 안 — 레코드 배열이 발행 중 커지거나 당겨져도 adapter는 id로 찾는다). adapter의 소멸이 레코드를 지운다(Core `Retire`는 실행 중이 아닌 항목을 그 자리에서 소멸하고, 실행 중인 항목은 그 실행이 끝난 뒤 정리에서 소멸한다 — 정리 중 소멸자 재진입을 허용한다). 지운 표시는 레코드의 `dead` 하나다(Core 항목 쪽의 따로 된 "제거 중" 표시는 없다).
- **ED3 `FunctionBinding`(EV1a — FR4의 재사용 값):** `(ObjectHandle target, Guid functionId)`와 바인딩 때 찾은 함수 서술·연산표 포인터. `Result<FunctionBinding> FunctionBinding::Create<Args...>(registry, access, target, functionId)`(배치를 넘기는 `CreateWithLayout`도 있다) — 대상 타입 lease(`AcquireType` — Registry 오류 그대로), 함수 찾기(`FindFunction` — 기반 체인, 없으면 `NotFound`), static 함수 거부(`InvalidArgument` — 대상 없는 바인딩은 뜻이 없다), 서명·배치 검사(ED5 — `TypeMismatch`). `Result<void> Invoke(registry, access, BindingFrame<Args...>&)` — frame 배치 digest를 대조하고(다르면 `InvalidArgument`) 대상 slot이 살아 있는지 `InspectLifecycle`로 본 뒤(`WrongThread`·`WrongContext`·`ShuttingDown`·`Busy`·회수됐으면 `StaleHandle` — thunk의 Resolve와 같은 순서) 캐시한 연산표의 생성 `invoke`를 바로 부른다(`Destroyed`·`Unreachable` 대상의 해석 실패는 thunk가 낸다). 호출마다 lease·TypeRegistry 잠금·함수 찾기가 없다: **살아 있는 객체 slot은 자기 타입 lease를 쥐므로**(ObjectRegistry — 기반 레코드는 파생의 의존으로 묶인다) 대상이 살아 있는 동안 그 타입 레코드와 함수 서술·연산표가 풀리거나 바뀌지 않는다(같은 handle generation이면 같은 객체, 타입 revision(SE-O2)이 생기면 이 불변식을 다시 본다). 대상이 사라진 뒤 같은 타입이 다시 등록돼도 handle generation이 달라 `StaleHandle`이다. Event와 InputActions의 `InputActionBindings`(이벤트 마스크·`consumes`·전달 중 지운 바인딩 규칙이 따로 있다)가 함께 쓴다. 대상은 handle만 쥔다(강한 참조가 아니므로 대상 수명을 늘리지 않고 GC trace 대상도 아니다). FunctionId로 잇는다(이름을 바꿔도 ids rename으로 이어진다 — UE는 `FName`). 바인딩을 기다리게 하는 frame은 `BindingFrame<Args...>`(기대 배치의 칸에 값 ops로 인자를 복사해 담는 스택 저장소 — Event·IA7·시험이 쓴다)다.
- **ED4 바인딩 API:** `Event::TryBind(registry, access, target, functionId)` → `Result<DelegateHandle>`. 같은 (대상, 함수) 쌍이 이미 있으면 `AlreadyExists`(UE `AddUnique`는 handle을 공유해 한쪽 `Remove`가 다른 바인딩자의 것까지 지운다 — Rocks는 거부한다). `EditorOnly` 함수는 에디터 빌드에서 받는다(에디터 도구 바인딩). 게임 빌드에는 그 함수가 없어 `NotFound`이고, 저장된 바인딩이 EditorOnly 함수를 가리키면 쿠킹(asset-cook — TypeRegistry 함수 flag를 본다)이 오류로 거부한다(EV3a). `Remove(DelegateHandle)`(native 구독·리플렉션 바인딩 공통 — 리플렉션 바인딩은 레코드를 먼저 죽음 표시해 실행 중인 자기 항목을 지워도 같은 쌍을 바로 다시 바인딩할 수 있다), `UnbindAll(target)`(UE `RemoveAll(Object)`), `Clear()`(전부 — 논리 파괴). 바인딩·발행은 발행자 소유 스레드·접근 문맥에서만(ED12).
- **ED5 서명·배치 검사(FD11 개정):** `FunctionSignatureMatches(const FunctionSchema&, const RuntimeFunctionOps&, const FrameLayout& expected)` — 반환이 없고 Result 함수가 아니며, 매개변수 수가 같고 칸마다 **칸 서술**(생성 `ParameterSchema`와 같은 값 형식 `value`·`element`·`key` — 종류와 대상 TypeId, `rocks::Object` 대상은 `Guid{}`, 형식을 가르는 flag `ParameterFlags::ObjectHandle`, 칸 C++ 형식의 크기·정렬)과 offset이 같고 frame 크기·정렬이 같다. 이름은 무시하고 값·`const&` 차이는 frame 칸이 같아 저절로 무시된다. `ValueType`만으로는 `Array<int32>`/`Array<float>`는 원소로, `ObjectHandle`/`WeakObjectRef<Object>`는 flag로 가른다. **`NativeTypeKey`를 쓰지 않는다**(개정 3 — 리뷰): 기본 형식·템플릿 형식(`int32`·`String`·`Array<T>`·`WeakObjectRef<T>`)의 키는 실행 이미지마다 따로 생겨(`Core/TypeKey.h` — export 키는 리플렉션 타입·Binds 대상뿐) Modular 빌드(에디터 기본)의 모듈 사이 바인딩이 모두 실패한다. 칸 서술은 이미지와 무관하다(enum·struct 대상은 TypeId — 바인딩하는 번역 단위가 그 생성 헤더를 봐야 한다, 없으면 컴파일 오류). 기대 배치 `FrameLayout`(칸 서술·offset·크기·정렬·digest)은 `detail::FrameLayoutOf<Args...>()`가 생성 frame과 같은 규칙(칸 `FrameSlot<T>` — `const T&`는 `T`, 선언 순서, 뒤에 `ErrorCode error`, 표준 배치 struct의 offset 규칙)으로 계산하고, 바인딩이 digest를 쥐어 `Invoke`가 넘겨받은 frame의 배치와 대조한다(다른 `BindingFrame`을 넘기면 `InvalidArgument` — 바이트를 다른 형식으로 읽지 않는다). 생성 frame 배치 규칙은 FunctionReflection 7절이 정본이고 시험이 생성 frame과 템플릿 계산을 대조한다.
- **ED6 발행:** `Broadcast(const EventContext&, Args... args)` — `EventContext`는 `{ObjectRegistry&, const ObjectAccessContext&, ObjectHandle publisher}`다. (1)·(2) 발행자를 root로 붙잡는다(`TryPin` — 접근 문맥·스레드 검사를 함께 하고, 발행 중 호출된 함수가 `Collect`·`DrainRetired`를 불러도 발행자가 회수되지 않는다. Borrow가 아니라 root인 까닭: 살아 있는 Borrow는 전체 GC를 막아 구독자가 발행 중 부른 `Collect`가 `Busy`가 된다. root는 `Collect`를 막지 않고 발행자만 살려 둔다(시험 `Event_PublisherDestroyedDuringBroadcast`) — 개정 4. 발행자 자신의 함수 바인딩도 된다(`Event_SelfBindingAndNoArguments`). 붙잡기마다 Registry gate 잠금이 한 번 있다(ED13). 파괴 요청된 발행자는 붙잡지 못하므로 발행하지 않고 그 오류를 돌려준다: 논리 파괴가 먼저 `Clear`(연산표 `clear`)로 연결을 비운다 — ED8), (3) 리플렉션 바인딩이 하나라도 있으면 스택에 frame 하나를 만들어 인자를 한 번 복사한다(`const T&` 칸은 값 ops `copy` — 할당은 Registry 객체 allocator, 실패하면 리플렉션 바인딩만 건너뛰고 오류로 센다), (4) 상태의 문맥 사슬에 `{context, frame*, firstError}`를 RAII로 쌓고 안쪽 `MulticastDelegate::Broadcast(args...)`를 부른다 — native 구독은 Core대로, adapter는 사슬 꼭대기의 frame으로 `FunctionBinding::Invoke`(같은 frame을 바인딩마다 다시 쓴다: FD4가 "thunk는 인자를 옮기지 않는다"를 보장한다). 지금 실행 중인 adapter는 언제나 가장 안쪽 발행의 것이므로 사슬 꼭대기가 맞다(thread_local이 아니라 상태 안에 둔다 — 공개 헤더에 thread_local을 두지 않는다). 대상 실패: `StaleHandle`(대상 회수 — 생존 조회)·`Destroyed`(파괴 요청 — thunk)는 죽음 표시(ED7), 그 밖(`Busy`·`Unreachable` 대상의 해석 실패·할당 실패)은 그 호출만 실패. 살아 있는 대상의 함수는 바뀌지 않으므로(ED3 lease 불변식) 호출 때 `TypeMismatch`·`NotFound`는 생기지 않는다. 다른 대상은 계속 부른다. `Broadcast`는 결과를 돌려주지 않고(엔진 호출 지점마다 결과 처리를 강요하지 않는다), 결과가 필요한 호출자는 `TryBroadcast`(첫 실패 코드)를 쓴다. 바인딩별 경고 로그는 ObjectRuntime에 로그 경로가 생길 때(실행 host EI2가 실패를 보고하는 단계) 더한다(개정 4).
- **ED7 자동 해제:** adapter의 생존 질의는 레코드의 죽음 표시만 본다(Core 정리는 registry 없이 돈다 — C1: lambda 호출 대상의 `IsAlive()`가 Core의 생존 판정이다, 개정 4에서 EI3로부터 당김). 표시는 (a) 호출 실패(ED6), (b) `Event::Compact(registry, access)`가 레코드 대상을 Registry 생존 조회로 훑어 단다. `TryBind`는 Registry가 있으므로 Core C2와 같은 상한(죽은·의심 항목이 직전 정리 뒤 살아 있던 수 + 8을 넘지 않음)으로 분할 상환 `Compact`를 한다 — 한 번도 발행되지 않는 이벤트(UI)에도 죽은 바인딩이 끝없이 쌓이지 않는다. 대상 쪽 역방향 목록은 두지 않는다(1M 객체 — 구독하지 않는 객체에 비용이 없게, UE도 없다). `UnbindAll`·`Compact`는 레코드를 표시한 뒤 Core `CompactDead`를 한 번 부른다(죽은 항목 k개를 한 pass로 해제 — 항목마다 `Remove`로 훑지 않는다, 발행 중이면 가장 바깥 발행 뒤로 미뤄지고 그동안 죽은 항목은 불리지 않는다). 직전 정리 수는 살아 있는 레코드 수로 갱신한다. C1은 Sparks 연결 항목(slot·generation key — SL 5.5)도 쓴다.
- **ED8 발행자 수명:** 발행 중 발행자는 root로 산다(ED6 — 발행 중 회수되지 않는다). 파괴 요청된 발행자와 생성 중(Reserved) 발행자는 붙잡지 못해 발행하지 않으므로, 파괴를 알리는 이벤트(`died` 등)는 `RequestDestroy` 전에 발행하고 생성 중에는 발행하지 않는다(생성 뒤 `BeginPlay`류에서). 발행자의 논리 파괴(World `DestroyActor`·`DestroyComponent`의 정리, SE-O1 회수 전 cleanup hook)는 이벤트 연산 `Clear`를 불러 연결을 비운다(SL 5.5 "발행자 Detach가 delegate를 비운다" — `RequestDestroy` 전, C++는 `Event::Clear`·도구는 연산표 `clear`). 파괴 요청 뒤에는 연산표로 지우지 않는다(연산표는 Alive 발행자만 해석한다 — 그 뒤에는 발행할 수 없고 남은 항목은 회수 때 소멸자가 정리하므로 지울 까닭이 없다). 저장소 회수 때는 `Event` 소멸자가 남은 항목을 정리한다(Core — 발행 중 파괴는 Fatal이지만 root가 그 경로를 막는다). 리플렉션 바인딩의 adapter 코드는 `TryBind`를 부른 image에 있다(템플릿) — 바인딩하는 모듈은 그 바인딩보다 오래 살아야 하고, 모듈 사이 바인딩(Sparks·에디터·reload 되는 모듈)은 발행자 모듈 코드인 `RuntimeEventOps`(EV2 — ED9)로 한다.
- **ED9 schema 모양:** `FieldKind::Event` 하나를 더한다(SE-R2). `ValueKind`는 늘리지 않는다(값 종류 성질 표·descriptor·FieldValue wire·text·Sparks 형식 대응이 모두 손을 타게 된다 — 이벤트 필드의 `value`는 `Opaque`). `FieldSchema`에 `Span<const ParameterSchema> eventParameters`(FunctionSchema와 같은 `ParameterSchema` — offset은 발행 frame 기준). 런타임 연산은 `RuntimeTypeOps::events`(`RuntimeEventOps` — FieldId, `bind`·`unbind`·`unbindFunction`·`unbindAll`·`clear`·`compact`·`broadcastFromFrame`(도구·Sparks host가 frame으로 발행 — struct 인자는 FieldValue로 담지 못하므로 frame 경로)과 발행 frame의 `construct`·`destroy`·매개변수 연산, 바인딩 나열 `bindings`는 EV3a — ED20)이고, 그 필드의 값 연산(read·write·diff·copy)은 null이다. 값 필드를 다루는 모든 경로(그래프 저장·diff·클래스 기본값·Inspector·속성 경로·ValueCopy·ReferenceLayout·descriptor·Sparks schema)가 `FieldKind::Event`를 건너뛰거나 이벤트 경로로 돌려야 한다 — 지금 `FieldKind::` 쓰임 97곳(42파일)은 대부분 `==` 비교라 컴파일러가 잡지 않는다: EV2가 점검표를 문서에 남기고, 이벤트 필드 fixture로 그 경로 전부를 지나는 시험을 둔다.
- **ED10 저장:** (a) **클래스 기본값:** 이벤트 필드는 기본값 레코드에서 늘 비어 있다(생성자에는 Registry·handle이 없어 리플렉션 바인딩을 만들 수 없다 — ClassDefaults는 객체가 아니다). (b) **에셋 바인딩(EV3b):** WidgetAsset·Prefab 같은 템플릿은 인스턴스별 바인딩 목록이 아니라 템플릿 바인딩 표(원천 subobject 경로, 이벤트 FieldId, 대상 경로, FunctionId)를 두고 인스턴싱 때 적용한다(UE `UComponentDelegateBinding`·`BindDynamicDelegates`) — remap이 필요 없고 인스턴스마다 저장 비용이 없다. (c) **그래프 저장(EV3a — 세이브 게임 등 실행 중에 만든 바인딩):** 레코드의 (대상 참조, FunctionId) 배열을 저장한다(`Transient` 이벤트 필드는 저장하지 않는다). 대상 참조는 약한 참조 그래프 정책(ReflectionExtensions 5.1)을 그대로 쓰되, 집합 밖 대상(정책이 null + `ExternalReference` 진단)·Include 지연 덮어쓰기에서 0이 된 항목은 버린다(null 대상 바인딩은 뜻이 없다). 로드: decode는 (그래프 handle, FunctionId)를 보류 레코드로 두고(공개 전 객체는 해석되지 않는다 — ConstructionContext), Commit 뒤 fixup이 `TryBind`한다. 서명이 바뀐 바인딩: 에디터는 레코드를 보존(다시 저장할 때 사라지지 않게)하고 표시하며, 게임은 경고 후 버리고, 쿠킹은 오류로 거부한다(UE는 함수가 사라지면 실행 때 `FindFunctionChecked`가 Fatal이다).
- **ED11 Sparks:** 이벤트 schema(EV4 — EI1c)는 `Params` 이름·형식, 발행 측(`publisher` — 네트워크 단계 전에는 기본 `all`), 노출 지정자 `ScriptAssignable`(UE `BlueprintAssignable` — Sparks `on X.Event` 연결 가능)·`ScriptBroadcast`(Sparks가 엔진 이벤트를 `emit` — 기본 불가, 멤버 이벤트는 선언한 클래스만 `emit` — SL 5.2). Sparks 연결 항목(SL 5.5 — 연결 slot·generation key·handler ID, 큐 기록 thunk)은 native 구독(C1 생존 판정 대상)으로 들어가며 리플렉션 바인딩이 아니다. 인자는 큐에 넣을 때 깊게 복사한다(`const T&` 인자가 발행자 저장소를 가리킬 수 있다). **열린 결정(EV4):** SL 5.4는 스크립트 단계 안의 native 발행도 큐 항목으로 기록하고 전달 때 C++·Sparks handler를 연결 순서대로 실행한다고 하는데, ED6은 C++ 구독자를 즉시 부른다 — 스크립트 단계 안 발행의 큐 경로(host hook)를 EV4에서 SL과 함께 정한다.
- **ED12 스레드·문맥:** 이벤트는 발행자와 같은 소유 스레드·접근 문맥에서만 바인딩·발행한다(FD8과 같은 Registry 문맥 — `Broadcast`가 받은 access로 대상 함수를 부른다). 다른 스레드의 발행은 그 스레드의 큐로 넘긴다(엔진은 Game lane 전달 — Sparks 큐 SL 5.4).
- **ED13 비용:** `Event`는 16 byte(`Allocator*` + 상태 포인터)이고 구독이 생길 때 상태를 할당한다 — 이벤트가 4–6개인 Actor 1M에서 상태를 늘 두면 수백 MB다(SL 5.5가 1M 때문에 지연 slot 표를 고른 것과 같은 이유, UE Sparse delegate의 몫). 리플렉션 바인딩 호출은 발행당 frame 생성 1회(스택, `const T&` 칸만 복사 할당) + 바인딩마다 대상 해석과 생성 thunk 호출이다(할당 없음, TypeRegistry 잠금 없음 — Registry gate는 발행자 pin·unpin 한 번씩과 바인딩마다 생존 조회·해석에서 잠근다). bench(native·리플렉션 바인딩 1·16·256개 발행 비용)는 bench 프로그램으로 후속이다(시험은 시간에 기대지 않는다).
- **ED14 검사(메타 컴파일러 RMC28xx, 메시지 영어 — RMC2801 NATIVE 이벤트, RMC2802 자리(struct 멤버·컨테이너·Optional·정적 배열·함수 칸), RMC2803 `Params`, RMC2804 인자 형식, RMC2805 지정자. StringView·비const 참조·값 `String`·값 컨테이너는 `Event`의 static_assert가 Clang 단계(RMC3000)에서 먼저 막고, 컨테이너 안 이벤트는 컨테이너의 C++ 요구가 먼저 막는다):** 리플렉션 클래스의 `Event<…>` 필드에 `ROCKS_PROPERTY` 없음(저장·Sparks가 보지 못하는 이벤트를 막는다), struct 멤버·컨테이너·정적 배열 안 `Event`, `Params` 수·lowerCamel ASCII·겹침(Sparks 키워드와의 겹침은 노출 단계 EV4), `Args` 형식(FD4 거부 형식, 값 인자의 nothrow 복사, `StringView`), flag(받는 것: `Transient`(바인딩 저장 안 함 — UE에서 흔하다)·`SaveGame`·`DuplicateTransient`·`NonTryoutDuplicateTransient`(바인딩 저장·복제 규칙 — 효과는 EV3a, ED10 (c))·`EditorOnly`(EditorOnly 리플렉션 규칙)·`Category`·`Name`. 거부: `ReadOnly`·`Required`·`ScriptReadOnly`·`ScriptWritable`·`TextExportTransient`·값 필드 전용 flag), `Event` 필드를 가진 클래스의 `T(Allocator&)` 생성자(이벤트가 allocator를 받는다).
- **ED15 등록 규칙(EV2a — `TypeRegistry::Register`, 실패는 `InvalidArgument`):** `FieldKind::Event` 필드는 클래스에만 둔다(struct 멤버는 거부 — struct는 값이고 `Event`는 복사할 수 없다). `value`·`element`·`key`는 `{Opaque, 0}`, `maxElements` 0, `assetBundles` 비어 있음, flag는 `Transient`·`SaveGame`·`DuplicateTransient`·`NonTryoutDuplicateTransient`·`EditorOnly`만(`EditorOnly`면 `editorOnlyFieldIds`에 있다 — 값 필드와 같은 규칙), 이름은 비어 있지 않은 ASCII 식별자, 이름·도구 이름은 값 필드와 같은 이름 공간·규칙(대소문자 무시 유일). `eventParameters`는 함수 매개변수와 같은 칸 규칙(`ValidSlot` — 이름 있음·겹침 없음, 강한 참조·InstancedStruct·정적 배열 거부, 수 ≤ `MaxFunctionParameters`, offset이 발행 frame 범위·칸 정렬 안)이고 값 연산 칸은 연산표의 `parameters`다. 이벤트 필드가 아닌 필드(struct 멤버 포함)는 `eventParameters`가 비어 있어야 한다(struct 등록도 거부 — 레코드에 호출자 메모리를 가리키는 span이 남지 않게). 연산표: `RuntimeTypeOps::events`가 schema의 이벤트 필드와 같은 수·**순서**(상속 필드 포함 — 값 필드 연산표는 ID로 맞추지만 이벤트는 순서까지 같아야 한다)이고 항목마다 fieldId가 같고 모든 thunk·`construct`·`destroy`·`frameLayout`이 있고 `parameters` 수가 같고 `frameSize` ≥ 1·`frameAlignment`는 2의 거듭제곱이며 `frameLayout`의 크기·정렬·칸 수·칸 offset이 연산표·schema와 같다. 이벤트 필드에는 `RuntimeFieldOps`가 없다(있으면 거부 — 지금도 Opaque 필드의 연산표는 거부된다). `completeFieldLayout`은 typed 필드 + 이벤트 필드 = 전체 필드이고, codec 요구는 이벤트 필드를 건너뛴다. 상속 필드 대조(`ContainsInheritedFields`)는 `eventParameters`(이름·형식·flag·원소 상한·offset)도 대조한다(다르면 `TypeMismatch`). 등록이 `eventParameters`와 그 이름, `events` 배열과 항목마다의 `parameters` 배열을 레코드 블록에 깊게 복사한다. `TypeLease::EventOps(schemaIndex)`는 이벤트 연산 배열을 fieldId로 찾는다(클래스당 이벤트는 몇 개다 — 색인을 두지 않는다).
- **ED16 연산표(`Object/EventOps.h` — 헤더 전용 템플릿):** `RuntimeEventOps{fieldId, bind(registry, access, publisher, target, functionId) → Result<DelegateHandle>, unbind(…, publisher, DelegateHandle) → Result<void>, unbindFunction(…, publisher, target, functionId) → Result<void>, unbindAll(…, publisher, target) → Result<usize>, clear(…, publisher) → Result<void>, compact(…, publisher) → Result<usize>, broadcastFromFrame(…, publisher, void* frame) → Result<void>, construct(frame, Allocator&) → Result<void>, destroy(frame), parameters, frameSize, frameAlignment, frameLayout}`. 이름은 `Event`와 짝이다: `Event::Unbind(handle)`(리플렉션 바인딩만 — native 구독 handle은 `false`, 연산표는 `NotFound`: 다른 이벤트의 handle로 C++ 구독을 지우지 않는다)·`Event::Unbind(target, functionId)`(UE `Remove(Object, FunctionName)` — handle은 저장해도 유지되지 않으므로 저장·도구 경로는 이 쌍으로 지운다)·`UnbindAll(target)`·`Clear`(native까지)·`Compact`. 발행자 해석: 바꾸는 연산은 `ResolveForWrite<클래스>`(encode 고정 중이면 `Busy`), `broadcastFromFrame`은 읽기 `Resolve<클래스>`이고 발행 동안 Borrow를 쥔다 — 리플렉션 함수 thunk(FD8)와 같아 발행 중 구독자가 부른 `Collect`는 `Busy`다(Borrow를 놓은 뒤 포인터를 쓰는 것은 Borrow 계약 위반이고, Borrow끼리는 부딪히지 않으므로 자기 함수 바인딩도 된다). C++ native `Broadcast`(EventContext)는 그대로 root다. `frameLayout`은 발행 frame의 기대 배치(`FrameLayoutOf<Args...>` — 정적 저장소)로 에디터가 `FunctionSignatureMatches`로 바인딩 후보 함수를 거른다. 후속: 바인딩 나열(EV3a encode·EV5 목록)·frame 배치를 대조하는 host 래퍼(lease·인자 쓰기·발행 — `FunctionCall` 대응, EV4). 생성 코드와 손으로 만든 함수표 모두 `detail::MakeEventOps<&Class::member>(fieldId)` 한 줄로 만든다(멤버 포인터 템플릿 — 생성 코드는 `GeneratedType<T>` friend 문맥이라 private 멤버도 된다). thunk는 이 템플릿을 부른 곳, 곧 발행자 클래스 모듈 image에 생기므로 그 모듈 lease(`RuntimeTypeOps::module`)가 코드 수명을 지킨다(ED8의 모듈 사이 바인딩 경로). 조회는 `TypeLease::EventOps(schemaIndex)`(필드 index로 — `FieldOps`와 같은 모양, 이벤트 필드가 아니면 nullptr).
- **ED17 발행 frame:** 배치는 `BindingFrame<Args...>`의 저장소와 같다(`detail::BindingFrameShape<Args...>` — 칸 `FrameSlot<T>`(`const T&`는 `T`)를 선언 순서로, 뒤에 쓰지 않는 `ErrorCode` 칸). 생성 schema의 `eventParameters[i].offset`·연산표 `frameSize`·`frameAlignment`는 이 shape의 constexpr 값이다(메타 컴파일러가 C++ 배치를 계산하지 않는다). `construct`는 칸마다 값 ops `construct`(실패하지 않는다 — `RuntimeValueOps::construct`는 void)와 뒤 `ErrorCode` 칸, `destroy`는 소멸이다. `broadcastFromFrame`은 `const T&` 인자를 `TryBroadcast`의 바인딩 frame에 한 번 더 복사한다(성능 메모 — 필요하면 frame을 그대로 쓰는 발행 경로를 더한다). 그래서 `FunctionBinding`의 서명 검사(ED5)·`FrameLayoutOf`와 같은 규칙이 schema 쪽에도 그대로다.
- **ED18 메타 컴파일러(EV2b):** 필드 형식이 `rocks::Event<Args...>`(정규 철자)이면 이벤트 필드다(`FieldModel.IsEvent` + 매개변수 칸 — 값 종류 문자열 `Opaque`만으로는 갈래가 모호하다). `Params = "a,b"`는 이벤트 필드에만 쓰는 지정자이고(다른 필드는 RMC2803) 수가 `Args`와 같아야 한다(인자 없는 이벤트는 생략 가능). 칸 규칙은 함수 매개변수(`ResolveFunctionSlot` — FD4·FD5)를 다시 쓰고 `StringView`(값·참조 모두)는 거부한다. 생성: schema 필드 `{id, FieldKind::Event, flags, name, …, value {Opaque}}` + `eventParameters`(이름·형식·flag는 C#, offset은 `detail::EventFrameShape<decltype(소유 클래스::멤버)>::Value.offsets[i]` — import한 상속 이벤트도 C++ 철자 없이 낸다, 파생 모듈 생성 소스는 상속 이벤트 인자의 enum·struct 생성 헤더를 include한다 — ED5; 상속 이벤트의 연산표는 선언 클래스의 NativeTypeKey를 쓰므로 생성 소스는 직접 base뿐 아니라 이벤트를 선언한 조상 클래스의 생성 헤더도 include한다 — 손자 클래스 시험 `Meta.InheritedEventFromAGrandparentHeaderCompiles`), 연산표 `events`는 `detail::MakeEventOps<&T::member>(id)`, 필드 연산표·`VisitFields`(로그 `{@Obj}`)·Trace·참조 위치 표에서 뺀다(대상 handle은 GC 간선이 아니다). descriptor schema 7: 이벤트 필드는 자기 키 집합(`owner`·`name`·`id`·`fieldKind: "Event"`·`flags`·`toolName`·`category`·`displayName`·`params` — 값 형식 칸·`maxElements`·`bitfield`·`assetBundles`·`scriptName`이 없다, reader는 키 집합을 정확히 대조한다), `params: [{name, value, element?, key?, flags, maxElements}]`(함수 매개변수의 칸 서술 + `flags`(`ObjectHandle` — 상속 이벤트를 다시 싣는 파생 모듈이 `ObjectHandle`·`WeakObjectRef<Object>`를 가른다) — reader가 같은 규칙으로 다시 검사), 그 밖의 필드는 `params`가 없다. Sparks binding schema는 EV4 전까지 이벤트 필드를 내지 않는다(`ScriptVisible` 류 지정자는 ED14대로 거부). 이벤트 필드는 도구 이름 겹침 검사(RMC2203 — 값 필드와 같은 이름 공간)에 들어가고, Sparks 이름 겹침(RMC2605)은 노출 단계 EV4에서 넣는다.

- **ED19 바인딩 기록 wire(EV3a1):** 이벤트 필드 TLV는 살아 있는 리플렉션 바인딩이 하나 이상일 때만 쓴다(없으면 필드가 없다 — 바인딩 없는 객체의 저장 byte가 그대로이고, 클래스 기본값(늘 비어 있다)과의 차이 저장도 바인딩이 있을 때만 쓴다). wire는 `RecordList`이고 항목마다 고정 schema(`EventBindingRecordType` — 이름 있는 상수 Guid, 판 1)의 record 하나: 멤버 `target`(약한 참조 wire — 그래프 약한 참조 정책 그대로: 집합 밖은 Reject·Admit·Include 규칙대로 0 + `ExternalReference`, Include는 지연 덮어쓰기)과 `function`(Guid — FunctionId). 항목 순서는 바인딩 등록 순서(레코드 id 순). 저장 때 대상이 죽었거나 집합 밖이면 null 항목으로 남고(Include 지연 덮어쓰기 때문에 저장 때 걸러 낼 수 없다) 로드가 버린다 — 그래서 그런 바인딩이 있던 객체를 "로드 → 다시 저장"하면 byte가 원본과 다를 수 있다. 진단 경로는 이벤트 필드까지이고 항목 index는 싣지 않는다(원소 index 경로는 배열·Map 종류 필드만 받는다). native 구독은 저장하지 않는다(코드가 다시 만든다 — UE도 dynamic delegate만 저장한다). 그래프 형식판은 올리지 않는다(새 wire 종류가 없고 B9 선례와 같다 — 이 기록을 모르는 옛 판은 `CorruptData`로 거부하지만 하위호환은 두지 않는다).
- **ED20 저장(EV3a1):** `RuntimeEventOps::bindings(registry, access, publisher, visitor, user)`가 살아 있는 리플렉션 바인딩을 등록 순서로 `(target, functionId)` 방문한다(읽기 Borrow — 저장은 owner를 `PinForEncode`로 쥐므로 쓰기 Borrow는 `Busy`다, `Event::ForEachBinding`). 직렬화기(`EncodeObjectFields`)가 이벤트 필드마다 `ExcludesCurrent`(Transient·제외 flag·포함 filter)를 거친 뒤 나열해 ED19 기록을 쓴다 — 기록 형식이 이벤트 형식과 무관하므로 생성 thunk가 아니라 ObjectSerialization 한 곳에 둔다(ED9의 `encode`·`decode` 칸 대신 — 개정 7). 클래스 기본값 레코드(`RawSource`)는 이벤트를 쓰지 않는다(ED10 (a)). 같은 나열 thunk를 EV5 에디터 목록·디버거가 쓴다.
- **ED21 로드(EV3a1):** 1단계는 기록을 검사만 한다(schema·판·멤버 wire·약한 참조 token). 2단계는 대상 token을 그래프 handle로 바꾸고 null 대상(죽은·집합 밖·Include 미해결) 항목은 버린 뒤 `(발행자 handle, 이벤트 필드 index, 대상 handle, FunctionId)`를 load 단계의 보류 목록에 쌓는다 — 공개 전 객체는 `Resolve`할 수 없어 `TryBind`를 못 한다. Commit이 객체를 게시한 뒤 바인딩 단계가 보류 목록을 순서대로 `RuntimeEventOps::bind`한다: `LoadObjectGraph`는 Commit 직후 스스로, `ObjectGraphStage`(호출자가 Commit한다)는 새 `BindEvents()`(진단은 Stage의 `options.hooks`)를 Commit 뒤 호출자가 부른다(에셋 로더 — 게시 뒤·job 파괴 전, 에디터 패키지 집합 — 패키지는 `PackageLoadState::BindEvents`). 바인딩 단계는 되돌릴 수 없으므로 실패해도 로드 결과를 바꾸지 않고 진단만 낸다(ED22). 발행자가 게시와 바인딩 사이에 파괴 요청되면 그 바인딩은 진단 없이 건너뛴다.
- **ED22 실패와 진단(EV3a1):** 바인딩 단계의 실패(함수 없음 `NotFound`·서명 다름 `TypeMismatch`·대상이 그 사이 사라짐·할당 실패)는 바인딩을 버리고 새 진단 `FieldDiagnosticKind::EventBindingDropped`(value = 이유: 1 함수 없음, 2 서명 다름, 3 대상 없음, 4 그 밖)를 hooks로 낸다(필드 = 이벤트 필드, 객체 = 발행자 노드). 이유 값은 이름 있는 상수(`EventBindingDropped*` — `Object/FieldCodecHooks.h`)이고 진단의 객체 타입·경로(이벤트 필드 한 단계)를 채운다. 에디터 열기는 패키지마다 `EditorWarningKind::DroppedEventBindings`(detail = 버린 수)로 알리고, 런타임 에셋 로드는 패키지 hooks가 수만 센다(로그 경로가 생기면 경고 — EV3a2 전에는 에디터에서 다시 저장하면 그 바인딩이 사라진다). UE는 함수가 사라지면 실행 때 `FindFunctionChecked`가 Fatal이다 — Rocks는 로드에서 걸러 실행 중 Fatal이 없다. 같은 (대상, 함수) 겹침(`AlreadyExists`)은 기록 손상이 아니라 정상 병합(이미 같은 바인딩)이라 진단 없이 넘긴다.
- **ED23 정책·복제·판정(EV3a1):** 저장 flag 규칙은 값 필드와 같다: `Transient` 이벤트는 쓰지 않고, 세이브 게임(`includeFlags = SaveGame`)은 `SaveGame` 이벤트만, 에셋 복제(`DuplicateTransient`·`NonTryoutDuplicateTransient` 제외)는 그 flag 이벤트를 빼고 복제본에 같은 바인딩을 만든다(대상이 복제 집합 안이면 복제본을 가리키고, 밖이면 패키지 writer 정책대로 null — 버린다). 바뀐 필드 판정(`FindChangedFields` — 계약 설정)과 클래스 기본값 되돌리기는 이벤트 필드를 보지 않는다(값이 아니다). Required 검사 대상이 아니다.
- **ED24 에디터 보존·쿠킹(EV3a2):** 에디터 로드에서 풀리지 않은 바인딩(함수 없음·서명 다름)은 버리지 않고 이벤트 상태의 미해결 레코드로 보존해 다시 저장할 때 그대로 쓴다(호출되지 않는다 — 함수를 고치거나 바인딩을 지우는 것은 편집자 몫, EV5 목록에 표시). 쿠킹(`excludedFlags`에 EditorOnly)은 EditorOnly 함수를 가리키는 바인딩과 미해결 레코드를 오류로 거부한다(`FindFunction` flag — 쿠킹 데이터에는 함수가 없다).

### 3.1 값 필드 경로 점검표(EV2)

`FieldKind::`·Opaque 갈래는 거의 `==` 비교라 새 종류를 컴파일러가 잡지 않는다(2026-11-27 조사 — `switch` 없음, C++ 42파일·C# 7파일). 판정은 `IsEventField(const FieldSchema&)`(`Meta/TypeSchema.h` — `kind == FieldKind::Event`) 하나로 한다. EV2a가 C++ 경로를 고치고, EV2b 시험이 typed 필드와 이벤트 필드가 섞인 생성 fixture로 이 표의 경로를 모두 지난다(손 등록 클래스는 typed 필드 연산표를 손으로 만들어야 해 의미가 적다).

## 5. 버린 대안

- **Core `MulticastDelegate`를 그대로 리플렉션:** 저장할 항목을 구별하지 못하고, Core가 ObjectRuntime(Registry·생성 thunk)을 볼 수 없다.
- **UE처럼 native·dynamic 두 타입:** 엔진 이벤트마다 C++ 구독용과 리플렉션용을 둘 두게 된다.
- **함수 이름으로 바인딩(UE):** 이름 변경에 약하고, 도구 이름과 C++ 이름이 갈라진다(SparksBinding B19).
- **바인딩마다 `FunctionCall`(개정 1):** 바인딩·발행마다 frame 힙 할당과 TypeRegistry 전역 잠금·기반 체인 선형 탐색이 든다. UE `Parms`처럼 발행 frame 하나를 바인딩이 함께 쓴다.
- **바인딩이 FunctionHandle(lease)을 쥠:** 바인딩이 남아 있는 동안 모듈 reload·Unregister가 막힌다. 대상 객체 slot이 이미 타입 lease를 쥐므로 그 수명 안에서 캐시한 연산표를 쓴다.
- **`ValueType` 목록으로 서명 비교(개정 1):** 컨테이너 원소·`ObjectHandle`/`WeakObjectRef`를 가르지 못하고, 실행 경로(`SetArgumentValue`의 C++ 형식 검사)와 기준이 달라진다.
- **이벤트를 fields 밖 별도 목록(`TypeSchema::events`만):** FieldId·경로·저장 경로를 따로 만들어야 하고 SE-R2·SL이 이미 필드로 정했다. 필드로 두되 연산은 `RuntimeEventOps`로 나눈다(ED9).
- **`ValueKind::Event`(개정 1):** `FieldKind::Event`와 중복이고 값 종류 표 전체가 손을 탄다.
- **클래스 기본값·인스턴스 그래프에 에셋 바인딩 저장 + remap(개정 1):** ClassDefaults는 객체가 아니어서 생성자에서 바인딩을 만들 수 없고, 인스턴스마다 저장 비용이 든다. 템플릿 바인딩 표(UE).
- **이벤트 상태를 늘 할당(개정 1, 96 byte):** 1M 규모에서 수백 MB.
- **대상 쪽 역방향 목록:** 모든 객체에 비용이 들고 UE도 두지 않는다.
