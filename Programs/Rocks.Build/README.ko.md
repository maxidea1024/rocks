# Rocks.Build native 실행기

`NativeBuildEngine.BuildAsync`는 명시한 모듈 그래프에서 C++23 compile → static archive → executable link action을 만들고 실행한다. CMake와 Python을 호출하지 않는다. 호스트 도구·C# 규칙 컴파일, Clang metadata 생성과 SDK/game 조립은 상위 CLI가 담당한다. `NativeCompileProfile.Arguments`가 native compile과 AST 생성의 공통 target 옵션이다.

## 현재 지원 범위

- Windows clang-cl/x64와 macOS clang++의 Debug/Development/Release/ASan(구성별 옵션은 [빌드 구성](../../Build/README.md#빌드-구성)). Release는 ThinLTO이며 Windows에서 llvm-lib·lld-link를 요구한다. ThinLTO는 코드 생성 옵션이라 `NativeCompileProfile`(AST 프로필)이 아니라 compile action에만 붙는다. 모듈별 `NativeModuleInput.Optimization`은 최적화 여부만 바꾸고 compile action identity에 포함된다. Windows ASan은 선택한 x64 compiler runtime DLL 및 같은 디렉터리의 import/thunk를 함께 사용한다. Mac deployment target은 `MACOSX_DEPLOYMENT_TARGET` 또는 명시 기본 13.0이며 compile/link/ABI 신원에 동일하게 적용한다.
- 모듈 dependency는 public include/define을 전파한다. private include/define은 owner에서만 사용한다. 현재 dependency 자체의 public/private 구분은 없다. 정적 의존의 PrebuiltLibraries/AdditionalLinkArguments는 최종 link로 전달한다.
- 소스(손으로 쓴 `Sources`·규칙 생성 `GeneratedSources`·리플렉션 생성 `ReflectionSources`)가 하나도 없는 static module은 header-only다. 가짜 archive를 만들지 않고 ModuleOutputs에도 기록하지 않는다. DLL/shared library, PCH, Unity, remote executor, artifact cache 서버는 아직 구현하지 않았다.
- 리플렉션 생성 소스(`NativeModuleInput.ReflectionSources` — [리플렉션 생성 소스](../../Docs/Design/ReflectionGeneratedSources.ko.md) 6.3절): `Metadata`가 있는 모듈에 `MetadataLayout`(Rocks.Build.Cli)이 리플렉션 헤더마다 타입별 생성 소스 `<out>/Generated/<모듈>/Source/Public|Private/<철자>.generated.cpp`(타입 본문)와 `<out>/Generated/<모듈>/Source/<모듈>.module.generated.cpp`(타입 등록 함수 정의)를 넣는다. 이 소스의 compile action이 실패하면 컴파일러 출력 뒤에 `NativeModuleInput.ReflectionSourceFailureNote`(RMC3000 안내 — 표시 전용이라 action key에 들지 않는다)를 붙인다. 액션 그래프는 `Sources`와 같은 include·정의·프로필로 컴파일해 그 모듈의 archive(실행 파일 모듈이면 그 실행 파일)에 넣고 `compile_commands.json`에도 싣는다. 그래서 손으로 쓴 소스가 없던 리플렉션 모듈(ReflectionTestFixtures·CoreTypeBindings·ConfigTestFixtures·CurvesTestFixtures·WorldTestFixtures·AssetTestFixtures)도 정적 라이브러리가 되어 ModuleOutputs에 실린다. `Sources`와 목록을 따로 두는 이유는 모듈 진입점 판정이다(아래 "모듈 표"). 생성 소스 디렉터리는 include 루트도 header 디렉터리도 아니며, 생성 소스의 key는 cpp 내용과 그 모듈의 include 디렉터리다. 생성 소스만 가진 실행 파일은 거부한다(`Executable requires a source`).
- `Identity`는 전체 compiler 진단용이며 설치 경로가 들어갈 수 있다. `AbiIdentity`는 Installed SDK용 compiler version·effective triple(MSVC 환경 버전 접미 제거)·architecture·SDK version/build·deployment의 경로 독립 digest다(`--version`의 `Target:` 줄은 Apple clang에서 호스트 커널 버전이라 쓰지 않는다). 실제 증분 key에는 별도로 compiler/archiver/linker 및 선언 SDK 경로의 내용과 실행 환경을 포함한다.
- discovery는 툴체인 신원도 채운다: `CompilerVersion`(`--version` 첫 줄, 경로·URL을 담은 괄호는 commit hash만 남김), `TargetTriple`(`-print-effective-triple`), `CompilerDigest`·`LinkerDigest`(Windows 컴파일러·`LinkerPath`, Android NDK clang·`ld.lld`, macOS `xcrun --find clang++`·`ld`+`libLTO.dylib`), `OwnedRoots`(`resource`·`runtime`·`sysroot`·`ndk`), 정렬된 `AbiFields`, `RemovedEnvironment`. 수동으로 만든 툴체인은 이 필드가 비어 있으며, Core에 닿는 실행 파일을 빌드하면 ArgumentException이다.

## 빌드 환경 위생

`Rocks.Tooling.Common/NativeEnvironment`(와 Android discovery)는 프로세스 환경을 물려주지 않고 **허용 목록**의 변수만 정규 철자로 담은 새 환경을 만든다. Keyed 변수(Windows `INCLUDE`·`LIB`·`VCToolsInstallDir`·`WindowsSdkDir` 등 VS·SDK 환경, macOS `DEVELOPER_DIR`·`SDKROOT`·`MACOSX_DEPLOYMENT_TARGET`·`ZERO_AR_DATE` 등, 모두 `SOURCE_DATE_EPOCH`)만 증분 key(`Fingerprints.Toolchain`)에 들고, Runtime 변수(`PATH`·`TEMP`·시스템 폴더·`ROCKS_CLANG_FORMAT` 등)는 넘기되 key에서 뺀다 — 도구는 절대 경로와 바이너리 digest로 key에 있다. 그래서 실행마다 바뀌는 `DOTNET_CLI_TELEMETRY_SESSIONID`(dotnet msbuild) 같은 변수가 빌드를 무효화하지 않는다. 컴파일러·링커 동작을 바꾸는 것으로 알려진 변수(`CL`·`_CL_`·`LINK`·`_LINK_`·`CCC_OVERRIDE_OPTIONS`·`COMPILER_PATH`·`CPATH`·`C_INCLUDE_PATH`·`CPLUS_INCLUDE_PATH`·`OBJC_INCLUDE_PATH`·`LIBRARY_PATH`)는 목록 밖이라 빠지며(실측: `CL=/fp:fast`가 clang-cl에 fast-math를 켠다), 있었으면 `NativeToolchain.RemovedEnvironment`에 남고 빌드 CLI가 `Build environment: removed …` 한 줄로 알린다. 기본 config 파일(Homebrew LLVM의 `etc/clang/*.cfg`)은 discovery가 받는다고 확인한 컴파일러면 모든 드라이버의 CompileArguments·LinkArguments·probe 맨 앞의 `--no-default-config`(접두 없음 — clang-cl도 직접 받는다)로 끈다. 받지 않는 컴파일러가 config 파일을 읽으면(`--version`의 `Configuration file:` 줄) discovery 오류다. MetaCompiler는 이 인자를 허용 목록에만 두고 네이티브 프로필이 실어 올 때 쓴다.

모듈의 `AdditionalCompileArguments`·`AdditionalLinkArguments`는 FP 모델 인자(`FloatingPointArguments.IsModelArgument` — `-ffast-math`·`/fp:*`·`-ffp-*`·ISA 선택 `-m*` 등), `-mllvm`·`/mllvm:`·`-Wl,-mllvm,`·`-Xlinker`·`-Ofast`, CL 옵션(`/`·`-` 두 접두를 대소문자 구분으로 대조 — `-Fo`·`-EHsc`도 잡고 `-fdiagnostics-color`는 오인하지 않는다), 절대 경로(`/LIBPATH:`·`-L`·`-Wl,-rpath,`·`-fmacro-prefix-map=`·`-iquote`, 경로를 담은 define 값)를 거부한다. 외부 파일은 include 디렉터리·`AdditionalInputs`·`PrebuiltLibraries`로 선언한다.

## 빌드 주입 상수(BuildInfo)

`NativeModuleInput.ProvidesBuildInfo` 표지 모듈(엔진 Core — `Core/Build/BuildInfo.h`)에 닿는 `Executable` 모듈마다 빌드가 출력 잠금 아래에서 `<out>/BuildInfo/<Module>.BuildInfo.cpp`(`rocks::build::ToolchainFingerprint()`·`ToolBuildId()`·`CurrentEngineVersion()` 정의, 머리말 `BuildInfo 2`)를 만들어 그 모듈 소스에 더한다(계획 두 단계 — 1단계 계획으로 manifest를 만든 뒤 액션 그래프를 세운다). 같은 폴더에 `<Module>.BuildInfo.txt`(manifest 원문, SHA-256 = ID)와 `ToolchainFingerprint.txt`(지문 정규 텍스트, SHA-256 = 지문)가 있다. 이름 "Core"로 판정하지 않는다.

- 툴체인 지문(`ToolchainFingerprint.CanonicalText`·`Compute`): 컴파일러 식별·버전, 컴파일러·링커 바이너리 SHA-256, 대상(MSVC 접미 제거), 빌드 프로필의 FP 모델 인자. 구성·호스트 경로·환경은 넣지 않으며 모든 구성 × 최적화 × 언어 조합의 FP 모델 인자가 같아야 한다. 에셋 너겟 키에만 쓴다.
- 도구 빌드 ID: 그 실행 파일 도달 집합의 Compile·Archive·Link 액션(정규화한 인자 — 툴체인 인자 부분열 제외, object는 `obj:<소스 키>`, 경로는 키)과 입력(소스, 선언 입력, include 디렉터리 inventory, prebuilt — 액션 출력·`<out>/BuildInfo`·`OwnedRoots` 제외, MetaCompiler 생성 헤더 포함)의 내용 SHA-256. 경로 키는 `Path.GetRelativePath`로 가장 긴 루트부터 `out:`·`sdk:`(설치 SDK 게임 빌드의 `SdkDirectory`)·`src:`이고, 루트 밖 include는 `ext<i>:`, 그 밖 파일은 `ext:<이름>`이며 그때 `host-dependent: yes`다. 텍스트 확장자(header·`.cpp .cc .cxx .c++ .m .mm`)만 CRLF를 LF로 정규화해 해시한다. 진단·캐시 무효화용이며 패키지에 쓰지 않는다.
- 엔진 버전(`EngineVersion`, [ReflectionFoundations](../../Docs/Design/ReflectionFoundations.ko.md) 8.2절): 단일 출처는 저장소 `Build/Build.version`이고 `EngineVersion.Read`가 엄격하게 읽는다(세 키 정확히 한 번, 0–65535 정수, 주·부 모두 0 거부, 모르는 키·중복·주석·후행 쉼표·1 KiB 초과 거부 — 경로를 담은 InvalidDataException). 빌드 CLI가 실행마다 한 번 읽어(`game`은 SDK manifest 값) `NativeBuildRequest.EngineVersion`으로 넘기고, `BuildInfoGenerator`는 파일을 읽지 않는다. 값은 생성 TU의 `CurrentEngineVersion()`(`return {주, 부, 패치};`)과 manifest(형식 `rocks-tool-build-id 2`)의 `executable:` 다음 줄 `engine-version: 주.부.패치`에만 들어가며 action key·`ContextFingerprint`·compile 정의에는 들어가지 않는다 — 바꾸면 생성 TU와 link만 다시 돈다. BuildInfo 대상이 있는데 값이 없거나 빈 값(0.0.x)이면 ArgumentException이다. 프로젝트 연결 판정은 `EngineVersion.CanLinkProject`(주·부 같음)이다.
- 증분: 생성 TU의 key는 cpp 내용이고 `<out>/BuildInfo`는 header 디렉터리가 아니다. ID가 같으면 생성 파일을 다시 쓰지 않아 no-op이 0 액션이고, Core에 닿는 실행 파일은 입력 byte가 하나만 바뀌어도(주석 포함) 생성 TU와 link가 다시 돈다. 첫 InputSnapshot은 Prepare가 읽은 digest·열거의 메모로 만들어 마지막 비교가 Prepare 읽기부터 빌드 끝까지를 덮는다.
- `NativeBuildResult.ToolchainFingerprint`(대상이 없으면 null)·`ToolBuildIds`(link가 성공한 실행 파일만)는 action-report.json에 실린다.

## 모듈 표(ModuleTables)

`NativeModuleInput.ProvidesModuleTable` 표지 모듈(엔진 Core — `Core/Module/ModuleEntry.h`)에 닿는 `Executable` 모듈마다 `ModuleTables.Add`가 `<실행 파일>.ModuleTable.cpp`를 그 모듈의 생성 소스로 더한다(`<out>/GeneratedSources/<실행 파일>/`, 규칙 생성 TU와 같은 경로·증분 — [모듈 로더](../../Docs/Design/ModuleLoader.ko.md) 3.2절). 이름 "Core"로 판정하지 않는다.

- 진입점 모듈(`ModuleTables.EntryModules`): `ThirdParty`가 아니고, 소스·생성 소스·prebuilt 라이브러리가 있으며, 도달 집합에 표지 모듈이 있는 모듈이다. header-only 모듈과 표지 모듈 아래 모듈은 빠진다. 리플렉션 생성 소스(`ReflectionSources`)도 코드로 센다 — 리플렉션 헤더만 가진 모듈도 진입점 모듈이고, 손으로 쓴 소스와 규칙 생성 소스가 없으면 `MetadataLayout`(Rocks.Build.Cli)이 진입점 TU `<모듈>.ModuleEntry.cpp`를 생성 소스로 더한다([모듈 로더](../../Docs/Design/ModuleLoader.ko.md) 3.10절). 액션 그래프는 이 모듈들의 compile에만 `ROCKS_MODULE_NAME=<이름>`과 `ROCKS_MODULE_TYPES=0|1`(리플렉션 생성 소스가 있으면 1 — 진입 기술이 모듈 생성 소스의 `RegisterModuleOwnTypes`를 싣는다)을 더한다(규칙은 둘 다 정의할 수 없다 — `InputValidation`).
- 표: 실행 파일에서 의존 우선 깊이 탐색의 후위 순서로 진입점 모듈만 나열하고(실행 파일이 마지막), 행마다 직접 의존 가운데 진입점 모듈(면제 모듈을 거치면 그 너머의 진입점 모듈)과 `LoadingPhase`(기술자 모듈은 `DescriptorModuleSet.Apply`가 채운다)를 싣는다. 모든 `RocksModuleEntry_<이름>()`을 참조하므로 매크로가 빠진 모듈은 링크 오류다. 진입점 모듈 이름은 C 식별자여야 한다(ArgumentException).
- `InputValidation`은 대소문자만 다른 두 모듈 이름과 모듈 이름과 대소문자가 다른 의존 철자를 거부한다(MD17).

## 입력과 증분 계약

action의 hit는 두 단으로 판정한다([유니티 빌드·PCH](../../Docs/Design/UnityBuildPch.ko.md) 4절, UB0).

1. **선언 입력 key**(`NativeAction.Key`): 이전 실행 결과에 의존하지 않는다. toolchain key, action 인자, 번역 단위 구성(compile identity — 그 action의 소스이고 모듈의 전체 소스 목록이 아니다), 입력 파일 내용(소스, archive·link의 object·라이브러리), 명시 AdditionalInputs 내용, ContextFingerprint, 그리고 include 디렉터리와 소스 디렉터리의 **헤더 이름 목록**(존재 집합 — 내용이 아니다)을 담는다. 이름 목록의 확장자는 `.h/.hh/.hpp/.hxx/.inl/.inc/.ipp/.tpp/.c`다.
2. **의존 기록 검증**: compile action은 컴파일러에 depfile을 쓰게 하고(clang-cl `/clang:-MD /clang:-MF<파일>`, clang++ `-MD -MF <파일>`) 실행기가 그것을 읽어 의존 기록 `<object>.deps`(컴파일러가 실제로 연 파일과 각 내용의 SHA-256)를 object와 함께 게시한다. 선언 입력 key가 같으면 기록의 모든 파일을 현재 내용과 대조하고, 하나라도 다르거나 없거나 기록이 깨졌으면 다시 실행한다. 실패·취소한 실행은 기록을 남기지 않는다.

그래서 헤더 하나를 고치면 그 헤더를 실제로 연 번역 단위만 다시 컴파일되고, 모듈에 소스를 더하거나 지워도 다른 번역 단위는 그대로다. 툴체인 소유 헤더(`OwnedRoots`, `FingerprintPaths`, keyed 환경 `INCLUDE` 아래)는 의존 기록에 넣지 않는다 — toolchain key가 대신한다. depfile 파서(`Depfile`)는 Make 문법을 따른다(공백 `\ `, 공백 앞 역슬래시 두 배, `\#`, `$$`, 줄 이음, 상대·절대 경로). include로 열지 않는 추가 생성 입력은 지금처럼 AdditionalInputs로 선언한다. 한 빌드 안에서 파일 내용과 디렉터리 이름 목록은 한 번만 읽고(`BuildInputs`), 빌드 중 입력이 바뀌었는지는 빌드 전후 입력 비교(header 디렉터리 내용 포함)와 header 디렉터리 밖 의존 파일의 재확인이 본다.

repository root를 include해도 `out`과 현재 output의 임시 산출물은 탐색하지 않는다. `out/Generated`처럼 출력 tree 내부를 직접 include root로 선언한 경우 그 root는 별도 입력으로 검사한다. include 디렉터리 inventory(headersOnly 열거)는 점으로 시작하는 하위 디렉터리(`.claude`·`.vs`·`.native-tmp` 등), `.git`(파일 또는 디렉터리)을 가진 중첩 작업 사본, `.native-build.lock`을 가진 Rocks 출력 디렉터리를 깊이와 무관하게 뺀다(열거 루트 자신은 빼지 않는다). 새 optional/shadow header의 생성·삭제(`__has_include` 결과 변화 포함)는 헤더 이름 목록을 바꾸므로 의존 기록의 positive include만 믿지 않는다.

cache hit은 key와 모든 출력 파일이 기록과 일치할 때만 인정한다. 출력은 (크기, 수정 시각, 파일 ID)가 모두 기록과 같으면 기록된 SHA-256을 믿고, 하나라도 다르면 내용을 다시 해시해 대조한다(수정 시각만으로 hit를 판정하지 않는다. 파일 ID는 Windows에서 볼륨 일련번호와 파일 색인, 그 밖에서는 장치와 inode이고, 얻지 못하면 언제나 다시 해시한다). 같은 plan의 산출물을 입력으로 받는 action(archive·link)은 그 산출물의 기록 해시를 쓰고 파일을 다시 읽지 않는다. 입력이나 출력이 없거나 변조되면 재실행한다. 기록 파일 `native-cache.json`은 형식 번호를 갖고, 형식이 다르면 전부 miss다. compiler 실패 시 기존 출력은 유지하고 임시 산출물을 제거한다. dependency는 모든 출력 게시 이후에만 실행되며, crash 중 부분 교체가 남아도 다음 cache 검증은 그 상태를 성공으로 재사용하지 않는다. 게시 중 일반 파일 오류는 이전 출력을 복구한다.

`NativeActionResult.DurationMilliseconds`(`action-report.json`의 action마다)는 그 action을 실행한 벽시계 시간(ms)이다. cache 검사 뒤부터 출력 게시·임시 디렉터리 정리까지를 재며 실행 슬롯을 기다린 시간은 넣지 않는다(병렬 action끼리는 겹친다). cache hit이나 선행 action 실패로 실행하지 않은 action은 0이다. 측정값이라 action key·`compile_commands.json`·도구 빌드 ID에는 들어가지 않는다([리플렉션 생성 소스](../../Docs/Design/ReflectionGeneratedSources.ko.md) GSD12 — 모듈별 compile 시간 합과 느린 번역 단위를 여기서 읽는다).

한 output directory의 writer는 프로세스 간 파일 잠금으로 직렬화한다. 다른 directory는 독립 실행한다. 실행 슬롯을 얻기 전에 dependency를 기다리므로 작은 worker 예산에서도 DAG가 진척한다. 취소는 공통 ProcessRunner로 compiler/linker 자식 트리를 종료하고 join한 뒤 임시 출력과 잠금을 반환한다. source/toolchain 변경을 실행 전후에 검출한 결과는 성공이 아니며 이번 action cache를 폐기한다.

## 유니티 빌드

[유니티 빌드·PCH](../../Docs/Design/UnityBuildPch.ko.md) 6절(UB1). 모듈 규칙 `Unity = UnityMode.On`이면 그 모듈의 손으로 쓴 C++ 소스를 묶음 번역 단위로 컴파일한다(`Default`는 빌드 기본값 — 지금은 끔, 외부 라이브러리 모듈은 언제나 끔). 리플렉션 생성 소스는 모듈 설정과 무관하게 자기들끼리 묶는다(`ReflectionUnity = false`로 끈다).

- 구성(`UnityBuild.Plan`): 루트 기준 경로 순으로 정렬하고, 경로 해시를 `UnityAnchorFiles`(기본 16)로 나눈 나머지가 0인 파일 앞에서 구간을 나눈다. 구간의 바이트 합이 `UnityBatchBytes`(기본 384 KiB)를 넘으면 파일 수로 균등 분할한다. 구성원 하나는 단독 번역 단위다. 파일 하나의 추가·삭제·편집은 그 구간만 바꾼다.
- 묶지 않는 것: C 소스, BuildInfo·규칙 생성 TU·모듈 표 TU, `UnityExclude`, 상한보다 큰 파일, 첫 `#include` 앞에서 `#define`하는 파일(빌드 결과 `UnityDefineExcluded`와 CLI 출력으로 알린다).
- 묶음 파일: `<out>/Unity/<모듈>/<모듈>.Unity.<첫 구성원 경로 해시 12자리>.cpp`, 내용은 구성원마다 루트 기준 `#include "…"`다. 묶음 TU에만 `/I<root>`(출력 아래 구성원이면 `/I<out>`)를 include 목록 맨 뒤에 붙인다. `__FILE__`은 단독 TU와 같다.
- object: `obj/<모듈>/<변형>/<해시>.obj`(+ 의존 기록 `.deps`). 변형은 `u<유니티>p<PCH>`(예: `u1p1`, 검증 빌드 `--unity off --pch off`는 `u0p0`)이고 compile action의 Id에도 들어간다 — 일반 빌드와 검증 빌드를 번갈아 돌려도 서로의 object와 기록을 덮어쓰지 않는다. 빌드가 성공하면 이번 변형 디렉터리와 묶음 디렉터리에서 이번 계획이 만들지 않은 파일을 지운다.
- `compile_commands.json`은 원본 소스마다 논리 명령 하나이고(`output`은 그 소스가 단독 TU일 때의 object 경로다 — 묶인 소스의 그 파일은 없다), 도구 빌드 ID는 유니티 켬·끔과 묶음 구성에 따라 바뀌지 않는다(archive·link의 object는 원본 소스 키 목록으로 적는다).
- 명령 옵션: `--unity on|off`, `--pch on|off`, `--adaptive on|off`(기본 on). 켠 모듈은 묶음 충돌 정책 검사(`Rocks.ToolTests policy` — 파일 지역 이름, 파일 범위 using, `.cpp` 매크로, pragma 균형)의 대상이다. `Rocks.ToolTests unity-audit`는 설정과 무관하게 모든 엔진 모듈의 충돌을 센다.

## 정의 헤더·PCH·작업 파일 분리

[유니티 빌드·PCH](../../Docs/Design/UnityBuildPch.ko.md) 7·8절(UB4).

- 정의 헤더: 모듈 정의(전파된 public define, 모듈 public/private define, 진입점 모듈의 `ROCKS_MODULE_NAME`)는 명령줄 `/D`가 아니라 `<out>/Definitions/<모듈>.Definitions.h`로 가고 번역 단위마다 강제 include된다(`/FI`·`-include`). 구성·플랫폼·타깃 매크로는 명령줄에 남는다. 리플렉션 AST 생성도 같은 파일을 쓴다(MetaCompiler `--definitions-header`).
- 모듈 PCH: 규칙 `PrivatePchHeader`가 있으면 그 헤더를 미리 컴파일해(`Pch` action — `<out>/Pch/<모듈>/<변형>/`) 모듈의 C++ 번역 단위가 쓴다. 소스는 PCH 헤더를 include하지 않는다(빌드가 강제 include한다). 강제 include 순서는 [정의 헤더] → [PCH 헤더]다. C 소스, 생성 TU, 첫 `#include` 앞에서 `#define`하는 파일은 PCH를 쓰지 않는다. PCH를 쓸 번역 단위가 `PrivatePchMinTus`(기본 3)보다 적으면 만들지 않는다. 낡은 PCH는 action key(2단 key + 소비자가 PCH의 기록 해시를 입력으로 가짐)가 막는다 — clang의 입력 검증에 기대지 않는다(`-Xclang -fno-pch-timestamp`).
- 작업 파일 분리(`--adaptive on`, 기본): 빌드마다 `git status --porcelain`으로 작업 파일을 구해, 그 소스(와 짝 헤더가 작업 파일인 소스)를 유니티 묶음에서 빼 단독 번역 단위로 돌린다. 편집 중인 파일을 고치면 그 파일만 다시 컴파일된다. git이 실패하면 빌드 오류이고 작업 사본이 아니면 분리하지 않는다. CI는 `--adaptive off`다.
- `compile_commands.json`의 논리 명령은 PCH 바이너리 대신 정의 헤더와 PCH 헤더를 같은 순서로 강제 include하고, 도구 빌드 ID는 PCH·작업 파일 집합과 무관하다(정의 헤더와 PCH 헤더는 내용 해시로 입력에 든다).
- 공유 PCH(UB5): 규칙 `SharedPchHeader`(public include 기준 철자)가 있는 모듈이 공유 PCH를 제공한다. 모듈 PCH가 없는 모듈은 도달 집합의 제공 모듈 중 다른 제공 모듈을 가장 많이 포함하는 것의 헤더를 자기 인자로 미리 컴파일해 쓴다(변형 key가 같은 모듈끼리 action 하나를 함께 쓴다 — `<out>/Pch/<제공 모듈>/<변형>/`). 강제 include 순서는 [공유 정의 헤더] → [PCH 헤더] → [소비 모듈 추가 정의 헤더]다. 사용 검사(빌드 오류): 제공 모듈 include closure의 포함, PCH closure 헤더를 가리는 앞선 헤더(shadow), 추가 정의가 PCH closure 헤더의 전처리 조건에 쓰임(매크로 본문을 거친 간접 참조 포함). 설치 SDK manifest가 `SharedPchHeader`를 나른다.
- 엔진의 제공 모듈은 Core(`Core/CoreSharedPch.h`)와 ObjectRuntime(`Object/ObjectSharedPch.h`)이다. 목록에 넣는 기준(소비 번역 단위의 30% 이상이 include, 최근 4주 12회 이하 변경, 소비 모듈 정의를 전처리 조건에 쓰지 않음)과 근거는 [스펙](../../Docs/Design/UnityBuildPch.ko.md) 8.4절에 있다. 소스와 헤더는 PCH 헤더를 include하지 않는다(정책 검사 `pch-header-include`). 공개 헤더 단독 컴파일 검사(`PublicHeaderChecks`)는 유니티와 PCH 없이 돈다.
- `--timing on`: compile·PCH action에 clang `-ftime-trace`를 붙이고 `<out>/Timing/<타깃>.timing.json`(번역 단위별 시간, 헤더별 누적 파싱 시간·템플릿 인스턴스화 상위 목록)으로 집계한다. 공유 PCH 헤더 구성을 정하는 자료다. 인자가 달라지므로 켜고 끌 때 다시 컴파일된다.
- `--plan-only on`(build 전용): 메타 생성과 계획까지만 하고 `compile_commands.json`·묶음 파일·정의 헤더를 쓴 뒤 끝낸다(아무것도 컴파일하지 않는다).

## 긴 명령줄(response file)

Windows는 프로세스 명령줄을 CreateProcessW 한계(끝 NUL 포함 UTF-16 32,767자) 안에 넣어야 한다. 깊은 경로의 작업 사본에서는 object가 많은 link·archive(실측: 루트 127자에서 FoundationTests link 약 39,000자, PublicHeaderChecks archive 약 35,000자 — 루트 13자에서도 약 18,000자)와 include가 많은 compile이 이를 넘어 `파일 이름이나 확장명이 너무 깁니다`로 시작조차 못 했다. Executor는 펼친 인자로 만든 명령이 호스트 한계를 넘으면(`NativeCommandLine.ExceedsHostLimit` — Windows는 .NET이 실제로 만드는 명령줄 길이 + NUL이 32,767 초과, `.cmd`·`.bat` wrapper 도구는 cmd.exe 한계 8,191자에서 cmd.exe 몫 512자를 남긴 7,679 초과, POSIX는 인자 영역이 128 KiB 초과) 인자 전체를 action 임시 디렉터리의 `arguments+.rsp`에 쓰고 도구를 `@<파일>` 인자 하나로 실행한다. 한계 안의 명령은 지금처럼 그대로 넘긴다(macOS는 CI에서만 확인하므로 실제로 필요할 때만 경로가 바뀐다).

- 도구별 문법(`NativeCommandLine.QuotingOf`, 인용·인코딩은 `Rocks.Tooling.Common/ResponseFile`): clang-cl·llvm-lib·lib.exe는 Windows 규칙(CommandLineToArgvW — 역슬래시는 큰따옴표 앞에서만 특별)이고 전체를 한 줄로 쓴다. clang-cl은 response file의 줄 끝에서 `/link` 뒤 인자 묶음을 끊기 때문이다(실측: 여러 줄이면 `/link` 다음 줄의 링커 옵션이 컴파일러 입력이 된다). clang 드라이버(macOS clang++, NDK clang++)는 Windows 호스트에서도 GNU 규칙(역슬래시 escape, 작은따옴표도 인용, 인자마다 한 줄)이고, llvm-ar는 호스트 기본 규칙(Windows 호스트는 Windows 규칙, macOS는 GNU — 실측)이다. 인코딩은 Windows 규칙이 BOM 있는 UTF-16LE(LLVM 도구와 MSVC 도구가 모두 읽는다), GNU 규칙이 BOM 없는 UTF-8이다. 공백·큰따옴표·역슬래시·한글 경로와 define 값이 그대로 전달된다. GNU 규칙은 빈 인자를 나타낼 수 없어(LLVM이 빈 토큰을 버린다) 거부한다.
- Apple `/usr/bin/ar`처럼 response file 문법을 모르는 도구(toolchain의 컴파일러·archiver가 아닌 도구 포함)는 쓰지 않는다. 그런 명령이 한계를 넘어 시작하지 못하면 진단에 명령 길이와 이유를 붙인다(종료 코드 실패에는 붙이지 않는다). toolchain의 `CompileArguments`·`LinkArguments`에 빈 인자·NUL이 있으면 빌드 전에 거부한다.
- 결정성: action key는 물리 action의 인자로, `compile_commands.json`과 BuildInfo manifest의 compile 부분은 원본 소스마다의 논리 명령(`NativePlan.LogicalCompiles` — 유니티 묶음·depfile 인자가 없다)으로 만든다. 둘 다 `NativeAction.Arguments`와 같은 꼴(펼친 인자, 출력은 `{OUTPUTn}` 자리 표시)로 만든다. response file 경로·임시 디렉터리 이름은 어디에도 들어가지 않으므로 response file 사용 여부가 증분 key·툴체인 지문·도구 빌드 ID를 바꾸지 않고, 같은 인자면 response file byte도 같다. `compile_commands.json`은 언제나 펼친 인자라 clangd와 정책 감사(`@` 인자를 펼치지 않은 response file로 거부)가 실제 인자를 본다.
- 수명: 파일은 invocation마다 고유한 `<out>/.native-tmp/<guid>/`에 있어 병렬 action끼리 겹치지 않고, 이름의 `+`로 같은 디렉터리의 staged 출력(16진 object, 모듈 이름 기반 lib·exe·pdb)과도 겹치지 않는다. 임시 디렉터리 정리가 성공·실패·취소 모두에서 함께 지운다. 자식 정리가 끝나지 않으면(ProcessCleanupException) 자식이 아직 읽을 수 있으므로 디렉터리째 보존하고 경로를 알린다.
- 진단: response file로 실행한 action이 실패하면 도구 출력 뒤에 `Command (arguments passed in arguments+.rsp; shown expanded with final output paths): …`로 펼친 명령을 붙인다(출력은 `compile_commands.json`처럼 최종 경로).
- clang-cl이 lld-link를, clang++가 ld.lld·ld64를 부를 때의 긴 명령은 clang 드라이버가 스스로 response file로 넘긴다.

## 경로 포함 판정과 드라이브 루트

작업 사본·설치 SDK·게임 프로젝트가 드라이브 루트(`subst X: <경로>` 뒤 `X:\`)여도 된다. build·test·sdk의 출력은 증거 위치 때문에 `<작업 사본>/out` 아래여야 하고(밖이면 출력을 만들기 전에 거부한다), 엔진 입력 검사는 소스 루트를 담는 출력(드라이브 루트 포함)을 거부한다. 저장소 도구의 "이 경로가 그 루트 안인가" 판정은 `Rocks.Tooling.Common/DirectoryPath`(`IsAtOrUnder`·`IsStrictlyUnder`·`WithTrailingSeparator`)로 한다. 예전처럼 `TrimEndingDirectorySeparator(root) + 구분자`로 접두를 만들면 드라이브 루트·POSIX `/`·장치 경로 루트(`\\?\X:\`)에서 `X:\\`가 되어 그 아래 어떤 경로와도 맞지 않았다(실측: 드라이브 루트의 설치 SDK로 게임을 빌드하면 `SDK path escapes its root`, 소스 루트를 담는 드라이브 루트 출력을 거부하지 못함). 판정은 철자 비교다(symlink·junction·8.3 이름은 풀지 않고, macOS에서도 대소문자를 구분한다). 루트 기준 상대 경로 키는 `Path.GetRelativePath`로 계산한다(BuildInfo `PortablePaths`). 끝 구분자가 붙은 디렉터리 인자도 받는다: CLI `--output`·`sdk --destination`과 MetaCompiler `--output-root`는 끝 구분자를 떼고(그대로 두면 증거 preset이 빈 조각을 갖거나 stage·검증 디렉터리가 대상 안에 생겼다), 파일시스템 루트인 SDK 대상·MetaCompiler 출력 루트는 거부한다. `Rocks.proj`는 따옴표로 감싸 넘기는 디렉터리 속성(`NativeOutput`·`AndroidNdk`·`SdkDestination`·`SdkDirectory`·`GameDirectory`)의 끝 역슬래시를 두 개로 맞춘다 — `-p:GameDirectory=X:\`가 `"X:\"`로 넘어가 `\"`가 따옴표 escape로 읽히고 뒤 인자가 모두 한 인자로 붙던 문제다. 작업 사본 루트는 전처럼 `"<루트>."`로 넘긴다. 확인한 드라이브 루트는 subst·매핑 디렉터리다 — 실제 볼륨 루트(`System Volume Information`·`$RECYCLE.BIN`이 있는 VHD·USB 등)의 재귀 열거는 확인하지 않았다.

caller는 요청 collection과 소스 tree를 진행 중 임의 변경하지 않아야 한다. 별도 프로세스가 같은 output을 직접 덮어쓰는 동작은 지원하지 않는다. SDK 이식성 검사는 상위 manifest 검증의 책임이며, 이 실행기의 절대 경로를 포함한 보수적 local key를 portable SDK 신원으로 사용하지 않는다.

Windows 실제 회귀 40그룹(엔진 버전 1묶음, BuildInfo 9묶음 — 허용 목록 환경·우회 인자·경로 경계 포함, response file 6묶음 — NDK Android 포함, 경로 포함 판정 2묶음 포함)은 통과했다. macOS 실행은 별도 native CI 결과를 확인하기 전에는 통과로 기록하지 않는다. 기존 Foundation 179개와 새 CLI 전체 경로의 통합 검증은 상위 빌드 담당자가 수행한다.
